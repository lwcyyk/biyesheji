# 正确已有方法对真实切片的处理

版本AW-EVIDENCE-1，2026-11-05。证据为作者提供的模拟benchmark运行及固定源码。下述基线处理是纸面分析；未执行工具、模型或新增控制器。来源与事件定位见WORKLOAD_EVIDENCE.md、CONTRACT_AND_TRACE.json。

## 1. 固定所解决的合同

令u为已经按benchmark政策识别的用户，o为目标订单，P为已获确认的旧item/新variant配对多重集，p为付款方法，S为相同mock环境的状态。取本次明确可核对的前置条件：

\[
Identified(u)\land Owner(o)=u\land Status(o)=delivered
\land Confirmed(o,P,p)\land PairValid(S,o,P)\land PayValid(S,u,p).
\]

PairValid保留旧item多重数、长度相等、同产品variant和available条件；PayValid保留订单主人付款方法及适用时的gift-card检查。目标为一次调用后`status=exchange requested`，exchange_items/new_items包含P的全部目标，付款引用和价格差正确。[SOURCE/DERIVED：工具20–73行；对话22/28/29；返回31]

Confirmed是对**本条已有对话**的规范化人工提取，依据真实可见的提案和明确同意。没有把隐藏task.actions或私有instruction给方法。可靠地从任意自然语言生成TaskSpec/批准绑定的通用算法尚无本轮结论；该困难不能通过把人工标注当作免费oracle消除。

## 2. G-batch：保留现有中心调用与原生批量操作

当前actor已经以同样可见信息完成此流程。正确基线继续使用同一agent/环境组织形式：

|阶段|动作|接口/信息|成本与结果|
|---|---|---|---|
|形成上下文|使用实际已经返回的用户、订单和两份产品数据，收齐需求/回退选项|原轨迹消息0–27；只读工具|前缀9次工具调用全部计费；先前对话成本保留|
|提出完整操作|将两个替代选项结合既有订单/付款上下文供用户确认|消息22及28|已有对话消息；没有新增授权服务|
|取得确认|接收消息29的明确同意|模拟用户可见答复|1个最终选项确认事件；其他澄清轮次未省略计费|
|检查和执行|把完整两个配对交给现成exchange工具；工具逐项检查状态、item、variant和付款|实际消息30；invoke源码|1次逻辑工具请求|
|记录结果|读取消息31的exchange requested与完整metadata|同一工具返回|1次返回；不重复计为另一请求，不推定银行/物流效果|

工具源码先完成相关检查，再连续写入订单metadata，成功后返回JSON。当前顺序mock执行没有其他工具插入调用内部，也没有该次调用的失败/丢响应。这里可在工具边界将成功调用表示为一次离散状态转移；源码并未提供真实数据库的崩溃原子性、事务隔离或远端Exactly-once保证。

若将原系统升级为强制授权PEP，确认/用户绑定检查、解析和持久状态都需按普通安全工程加入，并向双方同等提供。本轮无需通过这个新增工程来声称原有API已拥有独立的确认凭证验证。

## 3. 有范围的决定性证明

### 命题W：已确认单订单批量换货族的更新请求最优值为1

输入族W_k（k>=1）固定：一个顺序mock执行器；同一已识别用户和delivered订单；k个符合工具多重数及variant条件的替换目标；合法付款；完整范围已确认；无并发/失败/版本漂移；只允许现有工具目录，不允许方法直接写评分器数据库。所有目标都必须进入同一订单的换货申请。[MODEL，来自实际切片的限定推广]

度量C_mut为完成目标的exchange状态更新工具调用次数。已取得观察、确认及输入规范化的费用另计。正确G-batch对全部k项发一次现成批量工具调用。

**上界。** 配对/付款条件使工具的所有前置检查通过。代码将完整item/new-item列表和付款/价格差写入同一订单，并置exchange requested。因此C_mut<=1。

**下界。** 初态为delivered且尚无目标换货记录。零次更新时，已有只读工具无法改变这些目标字段；其他操作或拒绝/转人工也不满足本族目标。故必须至少一次相关更新，C_mut>=1。

上下界闭合，最优值为1，实际消息30–31已达到。这个结果是原生批量接口及顺序状态转移的直接性质，未构成新的算法贡献。[DERIVED]

该结论不是完整episode总调用数最优性证明。起点若只有用户自然语言、订单ID未知，搜索次序和澄清方式会改变只读/对话费用；本轮采用实际已支付前缀，既没有免费获取目标订单，也没有用reference actions充当在线提示。

### 切片为何保留关键约束

投影保留目标订单前态、配对多重集、付款上下文、完整确认和成功返回。边界之前所有工具在该记录中均为只读，原调用费用仍保留。前缀的其他订单返回对目标订单状态无写入；因此在这个固定历史的后缀上，相关前置条件与结果没有因删去显示细节而改变。[SOURCE/DERIVED]

这里是“固定历史后缀的约束保持”，没有提升为任意策略、预算或故障模型下的双向模拟。

## 4. 为什么把两个item分开并不构成强基线

同一批准要求两个目标。先提交仅键盘的子列表时，若工具前置检查通过，状态已变exchange requested；再提交温控器会遇到`status != delivered`守卫。第一步本身也没有履行收齐全部项目的一次性政策。[SOURCE/PAPER_COUNTERFACTUAL]

这条反事实未执行，单独保存于paper/SPLIT_CALL_COUNTERFACTUAL.json。它只说明拆分策略改变完成合同。正确通用方法能读取数组接口及一次性规则，直接批量处理；用“逐item修改”的弱对照产生差距无法支持新机制。

### I-confluence相关命题分别审查

1. **定性判据。** 继承Bailis等Definition6/Theorem1，适用特定事务、merge及可用性合同。本切片没有复制merge输入，无法据此声称必须采用新协调协议。
2. **判定复杂度。** 原定理未给任意自然语言政策/程序的高效判定算法；本轮只手工检查有限局部前后条件，不作一般复杂度主张。
3. **协调点选择。** 本族目标要求至少一次状态更新，原生batch已达到；这不等于证明一般工作流的最少协调点问题已解决。
4. **权利分配。** 唯一执行者只有一份订单更新资格；不存在本记录支持的多副本分配优化输入。Balegas原有本地权利及转移能力继续保留，无需再次发明。

## 6. 完整费用和信息公平性

已读轨迹给出：10次逻辑工具调用、34条message、7条user message、最终1个明确选项确认事件。没有实际业务HTTP接口、工具延迟、消息字节账单或底层LLM重试数。它们均留为NOT_REPORTED，不用零填补。该轨迹的作者user_cost也无法代替完整成本。[sources/COST_LEDGER.json]

当前工具代码对k个替换及m个订单item的检查包含重复count和列表扫描，量级可达O(k²+km+k logk)加目录/JSON处理；所有方法调用同一provider函数，都承担该费用。客户端可复用已经返回的目录及普通索引/计数结构，其建立、读取和O(k)批准参数缓冲同等计费，不能用免费预处理建立差距。

隐藏user instruction、task.actions、完整fixtures和评分hash只用于源核对/评估。强基线的计划来自已经公开给agent的对话及工具返回。自动解析自然语言批准的正确性尚无本轮保证；在规范化输入上的C_mut=1保持该限定。

## 7. 技术困难的分类结论

本记录确有一次性接口、条件授权、需求收齐和联合完成约束；它们已由现成批量接口、顺序状态检查及明确确认处理。记录没有展示多执行器共享批准的分布式状态问题，也没有展示该情况下不可避免协调的实际代价。

对已提取合同和W_k族，裁决为`COVERED_BY_EXISTING_METHODS`。对断连自治或跨服务原子授权的新理论目标，仍缺实际拓扑/接口/轨迹证据。没有取得“已有方法尚未覆盖的具体结构”，机制实现门保持关闭。
