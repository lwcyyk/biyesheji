Abstract
A recent line of work has explored injection attacks against
end-to-end encrypted (E2EE) applications. These break con-
ﬁdentiality by sending adversarial content to a target victim
E2EE client—thereby “injecting” this content into otherwise
honest client state—followed by monitoring some encrypted
backup or other server-side state. Known injection attacks
exploit features such as compression before encryption of
backups, and practitioners so far lack a way to prevent these
attacks while retaining practicality.
We address this gap by introducing a framework for pre-
venting injection attacks that can be used with a variety of
E2EE applications. Underlying the framework is a new ap-
proach that we call view-based partitioning, which allows
application features to be designed to ensure that injection
attacks cannot be exploited to leak conﬁdential information.
Intuitively, application state can be partitioned according to
potentially adversarial views, and within individual views
(e.g., all the messages visible to a particular sender in an
E2EE messaging app) compression and other performance
features can be used without risk of injection attacks.
We provide a formal security model for injection attacks,
and prove that application developers can use our framework
to prevent injection attacks. We evaluate various implementa-
tions of our framework as applied to backing up E2EE appli-
cation state via SQLite and XML databases. Our experiments
show that security comes with manageable performance over-
heads for these applications.
1 Introduction
Popular applications utilize end-to-end encryption (E2EE) to
help protect the data of billions of users worldwide (e.g., [47]).
While extensive research (c.f., [5, 7, 11, 14]) has studied the
security of the E2EE protocols used, such as the Signal proto-
col [28,29], the increasing complexity of modern, feature-rich
E2EE applications raises new security challenges.
Our focus is on injection attacks against E2EE applica-
tions [12, 15, 16, 48, 53]. These involve an adversary that
sends payloads to a victim using some standard interface pro-
vided by the application (e.g., sending text messages), thus
“injecting” content into the victim’s plaintext application state.
In turn, per the standard E2EE threat model, the adversary
can additionally observe snapshots of the victim’s encrypted
data that are sent to back-end servers. From these adaptive
injections and observations, the adversary extracts sensitive
information from the victim. Recent proof-of-concept injec-
tion attacks have shown how to recover sensitive message data
from WhatsApp [16], metadata about conversations in Sig-
nal [16], and passwords from E2EE password managers [15].
These attacks exploit intricacies of application-level logic—
which process data before encryption—in order to bypass the
strong guarantees of E2EE.
There has been little progress in our understanding of how
to defend against injection attacks efﬁciently. One potential
solution is to disable all mechanisms that introduce interac-
tions between different sending clients’ data, such as turn-
ing off database compression, deduplication, and shared data
structures. But this approach is not practical, since it pro-
hibitively impacts the performance and user-experience of
applications [15, 16, 23]. For example, turning off attachment
deduplication and compression in WhatsApp results in back-
ups requiring orders of magnitude more space. With billions
of users, this is prohibitive, and we thus need better solutions.
We introduce a general framework for efﬁciently mitigating
injection attacks. Our framework serves as a design template
for introducing features into an application (e.g., compressed,
encrypted backups), in a way that is robust to injection attacks,
without sacriﬁcing the efﬁciency beneﬁts of these features.
The core idea underlying our approach is what we call
view-based partitioning: instead of performing some sensi-
tive feature-related computation (e.g., compression) over the
entire application state, we can partition a client’s application
state based on the views of different actors—for example,
partitioning database rows for messages based on the external
user that sent the message—and then process each partition in-
dependently. This approach allows feature developers to strike
a balance between security and performance: we leverage the

beneﬁts of features in a per-view context, while disabling the
cross-user interactions of data that lead to injection attacks.
We provide an abstract, formal speciﬁcation of our view-based
partitioning framework.
To exercise it and demonstrate practicality, we implement
view-based partitioning for encrypted backups based on two
E2EE applications: WhatsApp and KeePassXC. Both use
encrypted backups that have been shown to be vulnerable
to injection attacks 1 that exploit deduplication or compres-
sion [15, 16]. We discuss in the body how we mapped our
abstract framework onto these applications, with relatively
modest engineering effort. The most complex part of our im-
plementation involves refactoring backup format processing—
SQLite for WhatsApp and XML for KeePassXC—to provide
isolation between partitioned views. Here we experimented
with various approaches to achieve modularity and efﬁciency.
As SQLite and XML are widely used for client-side appli-
cations [41], future developers will be able to build off our
engineering efforts.
We provide a formal model to analyze the security of our
framework in light of injection attacks. Doing so is subtle,
because standard notions, such as left-or-right security, would
not allow any non-trivial client-side processing, even those
that cannot be exploited by injection attacks. Instead, our deﬁ-
nition captures the following guarantee: an application feature
is considered resistant to injection attacks if any injection-
using adversary that succeeds in learning one bit of infor-
mation about client state can be simulated by an efﬁcient
adversary that does not perform injections. Using this model,
we formally show that injections do not assist attackers when
using our view-based partitioning approach. Of course, this
guarantee comes with important caveats, such as implementa-
tions correctly partitioning views; see Section 4 for a discus-
sion of such limitations.
Despite enjoying much stronger security, our new en-
crypted backup features are efﬁcient. To showcase this, we
perform an extensive performance evaluation. Given the lack
of existing benchmark datasets for the relevant applications,
we devise a comprehensive evaluation pipeline that utilizes
synthetic, but realistic, testing data, using off-the-shelf gener-
ative AI models. Our experiments with these datasets show
that our framework mitigates injection attacks while main-
taining backup sizes that are comparable to existing, insecure
backup approaches. For example, our framework increases
the size of a KeePassXC backup with 200 passwords from
29.7 KB to 36.5 KB. A naive approach that disables compres-
sion would result in a 530 KB backup, which is 14× worse
than our approach. For WhatsApp, our experiments show that
we can modestly decrease backup size: for a chat history
of 200 K messages, we show a reduction from 21.9 MB to
21.4 MB. We discuss why computational overhead during
backups is small. Our framework introduces no overhead to

Summary of contributions. Our work begins the princi-
pled study of injection attacks, an emerging threat model for
E2EE applications. We make several contributions:
• View-based partitioning: We introduce a new mitigation
framework for injection attacks (Section 4), which re-
lies on partitioning application state based on possible
adversarial views.
• Case studies: Our framework is developer-friendly, con-
ﬁgurable, generalizes to a wide array of features, and
is compatible with both new and existing applications.
To showcase this, we apply it to implement injection
security for E2EE deduplication and compression based
on WhatsApp and KeePassXC (Section 5).
• Security formalization : We provide the ﬁrst formal,
general-purpose security model for injection attacks, and
prove within it the security guarantees of our framework
(Section 6).
• Evaluation: We perform an extensive evaluation of our
framework implementations, showing that our system
is practical (Section 7). We develop a comprehensive
methodology and evaluation pipeline for test-data gener-
ation in the application domains we consider.
We have released our implementations and testing pipeline as
public, open-source projects [2].
2 Background on Injection Attacks
We start by providing an overview of injection attacks, and
describing the components of E2EE applications that are most
relevant to this threat model.
E2EE applications. We denote byU an application client
that some user uses to exchange content with other users of
the service. Content is relayed as encrypted messages through
platform-operated servers. The client encodes and stores all
relevant user information (such as exchanged messages) in the
device’s internal storage; we refer to this stored information
as U’s application state, which we denote by st. This stored
data is underpinned by the application’s data model, which is
an abstract speciﬁcation of the structure of the data. While the
data model varies by application, a common structure consists
of a primary database for most content, with an auxiliary
blob store for larger ﬁles [41]. The data model deﬁnes the
fundamental data units for the application, which are the
smallest items that are relevant to the model (e.g., rows in a
database, and ﬁles in a blob store), and how these relate to
one another.
The user’s application statest consists of the “logical” view
of this stored data, i.e., the data units and their relationships.

To support various features, the client may periodically
export all or part of st outside U’s device. For example, the
application may support backups, which requires storing pe-

support multi-device synchronization, which requires propa-

logical subroutines. First, st is serialized into a binary string,
which we denote by ˆst ← encode(st). Note that ˆst may corre-

may be re-serialized using a different structure. For example,
a relational database may be encoded using a simpler struc-

(For our purposes, we treat this as a separate step within the
export process, even in the case where the format is the same.)
Following this, ˆst may be processed in additional ways, us-
ing some “ﬁlter” function F : {0,1}∗ → {0,1}∗, such as a
compression algorithm. Lastly, F( ˆst) is encrypted—using an
application-speciﬁc encryption schemeE := (Kg,Enc,Dec)
and a per-user key k2 from the key space of E—and uploaded
to some location outside the device.
Injection attacks. We consider the following injection at-
tack threat model, which we summarize in Figure 1. An adver-
sary A seeks to learn sensitive information about U’s internal
2The encryption key is sometimes derived from a user password.
state, e.g., messages or attachments sent by another honest
client U ′ to U. To do so, the adversary can adaptively and
iteratively utilize two capabilities: (1) an injection channel,
and (2) passive observations of encrypted application state.
An injection channel is any way by which A can inter-
act with U in order to add adversarially-chosen content to
st. We restrict our attention to injection channels enacted via
an unmodiﬁed but adversarially-controlled application client.
Therefore, A can interact with U in any way allowed by the
E2EE application. For example, the adversary may be able
to send text messages to U, which get added as new rows in
the relational database on U’s device. In other cases, injec-
tion channels are more subtle. For example, a feature present
in many modern password managers is credential sharing,
which allows users to jointly own credentials (e.g., for shared
accounts). In this case, the shared credential is present in the
vaults of all users with access to it, and updates are automati-
cally propagated. So, A can share credentials with the victim,
which get stored in the victim’s vault alongside all their per-
sonal credentials, thereby injecting content into the victim’s
application state.
The adversary can interleave injections with passive obser-
vations of encrypted application state exported to backend
servers. This can arise from, for example, compromise of the
cloud account within which backups are stored, a compro-
mised service provider, or insider attacks at the provider. We
note that such passive observation is a standard adversarial
capability assumed in E2EE threat models; we do not assume
the ability to decrypt encrypted exports
This process then repeats iteratively: A injects informa-
tion into U’s state st, observes a resulting encrypted export—
which now depends on both adversarial data and U’s private
data—adaptively chooses the next payload to inject, and so on.
The adversary’s goal is to somehow back out conﬁdential in-
formation. Since exports are encrypted, a priori, the adversary
should not be able to learn any information. However, injec-
tion attacks arise from client logic thatcombines data received
from different senders in subtle ways, resulting in cross-user
data interactions in st, which lead to perceivable differences
in the behavior of encrypted exports (e.g., lengths or number
of ciphertexts) that allow for the recovery of information.
Prior work. There is a long line of work exploiting content-
dependent mechanisms (e.g., compression, deduplication,
etc.) used in encrypted applications [22, 25]. Even without
injections, passive observation of encrypted payloads can lead
to vulnerabilities, since adversaries can “ﬁngerprint” cipher-
texts and correlate them to known plaintexts.
Injection capabilities greatly increase the attack surface
with respect to passive attacks [25]. Injection-style attacks
against encrypted applications were ﬁrst explored in the con-
text of compression mechanisms applied before encryption:
ﬂuctuations in the sizes or number of ciphertexts can reveal
to an adversary whether their injected data compresses more

number of works have uncovered vulnerabilities in various

crypted messaging protocol [17], client-side encrypted ﬁle
storage [9, 21–23], and more [19, 43, 44, 46].
A second, related line of work has studied injection attacks
against searchable encryption [8, 12, 36, 48, 52, 53], showing
that, under certain leakage patterns, an adversary that can in-
ject ﬁles into an encrypted index is able to recover signiﬁcant
information about its content.
More recently, a series of works [15, 16, 34, 40] have ex-
plored injection attacks against modern E2EE applications,
leading to discovery of vulnerabilities in widely used ap-
plications such as WhatsApp, Signal, and popular password
managers. These attacks target application-level logic, which
processes data before encryption. A summary of a few rep-
resentative injection attacks appears in Figure 2. Several of
these vulnerabilities exploit attack vectors from the afore-
mentioned lines of work, such as compression of plaintext
client side state and/or deduplication of ﬁles such as images.
These allow injection attackers to infer, from the lengths of
encrypted backups, conﬁdential information about messages,
ﬁles, or passwords sent to the target by other (honest) users.
Besides storage-saving mechanisms, other injection attacks
against E2EE applications exploit more subtle features, such
as search indexes, vault-health reports in password managers,
UI icons, and more [12, 15, 16, 48, 53]. While the speciﬁcs
of the attacks from prior work vary, they all follow the com-
mon pattern of exploiting some feature or mechanism that
leads to “interactions” between data in st, which the adversary
can trigger via injections. In terms of our basic abstraction
of E2EE clients from earlier in the section, we can model
these cross-user data interactions as arising when the “ﬁl-
ter” function F used during Export is such that F( ˆst) varies
in some predictable way depending on whether the items
stored in st satisfy some relationship; we call such functions
similarity-sensitive functions, examples of which include ﬁle
deduplication and database compression. If this is the case,
the adversary can leverage variations in |F( ˆst)|—which prop-
agate to the sizes of the encrypted exports—to tell whether
their injections are somehow “similar” to other content in st.
Towards mitigations. Mitigating all attacks that arise from
content-dependent mechanisms requires addressing both pas-
sive and active attacks. This work primarily studies the latter,
since active attacks lead to signiﬁcantly more leakage than
passive attacks [25]. That is, we focus on the problem of dis-
abling injection channels, reducing security to that of passive
attacks. Mitigating passive leakage is an orthogonal problem,
deserving of focused study, which we leave out of scope
The ﬁndings from prior work highlight a key lesson: in-
jection attacks are a potentially ubiquitous problem—arising
from common design patterns and features—and will increase
in relevance as E2EE applications become more complex and
feature-rich. In the presence of adversarial senders, any client-
side data interactions may provide a channel for injection
attacks. Thus, the formal study of injection attacks, and the
search for principled mitigations, is of critical importance.
As explained in the introduction, disabling all cross-user
interactions is not practical for most applications. For some
attack vectors, such as compression, we have no practical
solutions that scale to the demands of large workloads, and
thus many attacks remain either completely unpatched [16]
or only partially mitigated [15] (e.g., by introducing noise).
While some works have explored mitigations for these vectors
in other contexts, these mitigations are not applicable to E2EE
applications, either because they are speciﬁcally tailored to
other settings (e.g., web applications [4, 24, 35]), or do not
meet the demands of modern applications [4, 24, 35].
While other injection attacks have indeed been fully miti-
gated (for example, some of the attacks in [15]), these ﬁxes
are bespoke patches to the speciﬁc bugs that were found, and
do not point to more general approaches to address injec-
tion attacks. Moreover, there have been no formal security
models suggested for injection attacks, and so we lack strong
assurance about the security of mitigations.
In summary, there is a lack of general approaches for ad-
dressing injection attacks and frameworks for reasoning about
security-performance trade-offs. This has resulted in promi-
nent attack vectors remaining unresolved in practice. We now
turn to ﬁlling these gaps.
3 Mitigation Framework Overview
We ﬁrst provide an overview of the main ideas behind our
mitigation framework, deferring details to Section 4.
We use two application settings to illustrate the core ideas
of our framework. First, we considerDedupMsg, a messaging
application that supports attachment deduplication. During
backups, application clients store unique copies (veriﬁed by
comparing checksums) of received attachments as standalone
ﬁles in the cloud. Additionally, we consider a separate messag-
ing application, CompMsg, that employs database compres-

[PDF_PAGE 6]
sion. Messages are stored in a relational database on the user’s
device, which is serialized and compressed during backups.
Both deduplication and compression are common vectors for
injection attacks (Section 2). Our framework mitigates such
attacks in both application settings.
Main insight: exports as user views. The starting point
for our framework is the insight that, conceptually, st acts as
a form of shared storage for the other application users that
interact withU. That is, users can “read” or “write” to st as de-
termined by their communications withU: a message fromU ′
to U can be thought of as a write fromU ′ to st, and a message
from U to U ′ can be thought of as granting read-permissions
to U ′ for a particular database row. Thus, st consists of the
union of storage views from multiple (potentially adversar-
ial) users. Through this lens, we can cast injection attacks
as an interference problem [20]: they arise from performing
some sensitive computation (e.g., compression, deduplication)
over parts of a shared storage that “belong” to different users.
In the language of Section 2, injection attacks result from
computing a similarity-sensitive function F over the entire
(shared) application state. In CompMsg (resp. DedupMsg), F
corresponds to compression (resp. deduplication).
This directly leads to the main idea behind our framework,
which we call view-based partitioning: instead of applying F
to all of ˆst, we can partition ˆst based on the views of different
users, and then apply F independently to each partition. In
other words, st can be divided into separate subsets that are
readable by a common set of (one or more) users—for exam-
ple, in a messaging application, each partition corresponds to
a separate (group or individual) chat; and in a password man-
ager, each partition corresponds to a separate shared folder.
Each partition constitutes a separate “trust context”, and thus
all data therein can be processed together, separate from the
rest of the application state.
For example, in CompMsg, instead of monolithic database
compression, we can compress in individual streams the
database rows that are accessible to a common set of users,
i.e., the sent and received messages within a conversation.
Each compression stream may contain messages in the view
of a single user (for individual chats), or multiple users (for
group chats). Similarly, in DedupMsg, instead of deduplicat-
ing all received attachments, we can separately deduplicate
the ﬁles sent within each chat.
With this approach, we isolate F according to user views.
Therefore, A’s injections only interact with data that A knew
a priori, and thus A cannot learn any information about U’s
sensitive data. This approach strikes a balance between us-
ability and security: instead of completely disabling F, we
still leverage its beneﬁts in a per-view basis, while achieving
the strict isolation necessary to prevent injection attacks.

design goals. In particular, we want a framework that has the
following properties:
• Generality: The framework should be applicable to a
variety of E2EE application types and features, and not
tailored to speciﬁc similarity-sensitive functions (e.g.,
only useful for compression or deduplication).
• Low developer overhead: The framework should be fea-
sible to integrate into existing applications, avoiding
extensive and disruptive changes to existing codebases.
• Low performance overhead: The framework should sup-
port improving security in the face of injection attacks
without signiﬁcant performance degradation.
• Conﬁgurability: Developers should have the option to
ﬁne-tune the balance between security and performance
imposed by the framework. Some applications may pre-
fer more granular security guarantees at the cost of de-
creased performance, while others may prefer more ﬂex-
ible guarantees in order to increase performance.
Overview of framework construction. Equipped with this
list of goals, we now provide a brief overview of the construc-
tion of our framework. We show a summary of our system in
Figure 3. The ﬁrst design decision of our construction is to
dynamically partition st during exports. That is, we leave st
as-is during the standard runtime of the application, and in-
corporate the framework logic exclusively into the export
process. Alternative approaches could have partitioned st dur-
ing runtime, such as maintaining separate database copies
for each user. However, such approaches would require more
developer effort and may incur prohibitive runtime overheads
(e.g., changes to group structures would require reorganizing
multiple database instances).
In more detail, at the heart of our framework lies a par-
titioner, a software module that intercepts st at the start of
Export, and splits all data units (database cells, individual

[PDF_PAGE 7]
ﬁles, etc.) according to user views. That is, a partitioner pro-
cesses st, and assigns each of its data units to a “bucket”,
depending on the users with access to it: for example, all
database rows for the messages between U ′ and U are as-
signed to a bucket for U ′, and all rows for messages sent in
a group chat G get assigned to a bucket for G. (We explain
shortly how the mapping between data units and user views
is established.) The output of the partitioner is thus a series
of bitstrings (“buckets”) bk1, ...,bkn, which collectively en-
code all data units in st, but partitioned based on user views.
Then, to complete the export, F is computed individually on
each bki, and each resulting string is encrypted.
Partitioners must be tailored to the application’s data model,
and be able to carefully reason about its ﬁle formats and
data structures: what are the relevant data units for each ﬁle
type, how to parse the serialized ﬁles, etc. Towards our goal
of minimizing developer effort, however, partitioners should
be independent of the application’s schema, depending only
on the application’s data model. This allows application de-
velopers to leverage existing implementations for their data
models, e.g., all Android applications can beneﬁt from the
implementation of a generic SQLite partitioner. As mentioned
earlier, however, (schema-agnostic) partitioners also need to
be able to dynamically map data units to buckets during
their processing of st, which naturally depends on the ap-
plication’s schema.
We resolve this tension by making this mapping a pa-
rameter to the framework, which partitioners can use in a
black-box way. That is, we introduce the concept of a view
policy, a speciﬁcation of how data units map to user views.
Abstractly, a view policy implements an “oracle” Π which can
be queried with some s ∈ st, and returns an identiﬁer for its
respective bucket. For example, view policies forCompMsg
and DedupMsg would map database rows and individual ﬁles,
respectively, to bucket identiﬁers. The goal of a view policy
(and view-based partitioning more broadly) is to ensure that
data units which are assigned to the same bucket are read-
able by the same set of users, enforcing our desired per-view
isolation. In other words, view policies lift the application’s
implicit notion of “trust contexts” (e.g., chats) to the level of
our framework, so that partitioners can split st in a way that
respects user views.
Developers thus specify a view policy as an input to the
framework, and partitioners “query” Π(s) as they iterate over
data units, and assign them to buckets. So, a partitioner’s
speciﬁcation is general for a data model, but its function-
ing is guided by a (schema-dependent) policy. (We explain
the details of partitioner implementations in Section 4.) An
added beneﬁt of this approach is that it is conﬁgurable by de-
fault: developers can specify an arbitrary granularity to their
view policies.
Going back to our examples, CompMsg can use a generic
partitioner for its particular data model, which intercepts the
relational database during backups, and computes an input
view policy Π on each row s (corresponding to messages) to
allocate it to the bucket corresponding to a subset of users with
a shared view (i.e., a particular chat.) Similarly, DedupMsg
can use a partitioner that intercepts attachment ﬁles during
exports, and allocates each ﬁle f to a bucket by evaluating Π′
on f ; the ﬁles within the same bucket are then deduplicated
between (only) themselves.
In principle, any language can be used to specify view
policies, as long as they abide by the input-output behavior
described above. However—leveraging our insight of client
state as a form of shared storage—we will implement view
policies in a simple way usingaccess control policies: a user’s
view in st is equivalent to their “access” in this shared storage,
and thus we can leverage the rich literature on access control
to specify view policies in a user-friendly way. (In Section 4,
we describe in detail the speciﬁc format of access control
policies that we adopt.)
While the central goal of view-based partitioning is to
split st according to user views, we further relax this require-
ment to make the partitioning strategy more conﬁgurable.
That is, we additionally introduce ﬁlter policies, which reﬁne
the output of access control policies in order to specify more
granular bucketization schemes. For example, a ﬁlter policy
could say that all data units that map to saved contacts of
U can be merged into a single bucket, and can thus be com-
pressed together. So, instead of being limited to just per-group
and user buckets, ﬁlter policies provide a way to ﬁnetune the
trade-off between performance and security, according to trust
models of the application. In summary, our implementation
of view policies will consist of a two-step process, whereby
data units are ﬁrst mapped to users using standard access
control policies, and these users are (optionally) narrowed fur-
ther using a ﬁlter policy, which ultimately returns the bucket
identiﬁer for this data unit.
4 Mitigation Framework Design
We describe our mitigation framework in detail in this section.
View policies. As described in Section 3, our framework
consists of an atomic module that developers integrate (exclu-
sively) into their exports, in order to implement view-based
partitioning and mitigate injection attacks. The core com-
ponent of our framework is a partitioner, the program that
intercepts st at the start of Export and performs the partition-
ing. The behavior of a partitioner is guided by a view policy,
which is a mapping Π from data units to bucket identiﬁers.
View policies are thus the speciﬁcation that determines how
view-based partitioning should be performed.
View policies can be implemented in any language, as
our framework uses them in a black-box way. Partitioners
just require that a view policy Π satisﬁes two requirements.
First, we assume that Π is underpinned by the interface de-
scribed above, mapping data units from st to bucket labels.
2970    34th USENIX Security Symposium USENIX Association

[PDF_PAGE 8]
A policy must thus be compatible with the data model of st.
The second requirement is that Π must be complete: it must
output some value for every data unit in st. For example, a
view policy for CompMsg must output some value for every
database row; and a view policy for DedupMsg must output
some value for every attachment ﬁle. In many cases, a policy
can just output some generic label to denote that this data
unit is not sensitive, and can thus go in some catch-all bucket
(e.g., for metadata). By supporting custom view policies, our
framework lets developers ﬁne-tune the granularity of how
partitioning is performed, which is a goal of our system.
View-based partitioning. As described in Section 3, the
goal of a partitioner is to implement a view-based partitioning
of st, as speciﬁed by view policyΠ. We now specify this goal
in more detail. Let B = (bk1, ...,bkn) be the buckets output
by the partitioner. To achieve view-based partitioning, these
buckets must satisfy two properties. The ﬁrst iscompleteness,
which means that the strings in B can be combined in some
deterministic way to reconstruct ˆst. The second (and main)
property is that the buckets should be consistent with Π. That
is, the partitioner should assigns ∈ st to bki, where i = Π(s). If
this holds, view-based partitioning leads to non-interference
between buckets: any changes to any s should only result
in changes to bucket Π(s). We call this property view non-
interference, which we deﬁne formally in Section 6.
Main framework component: partitioner. We now ex-
plain the speciﬁcation of partitioners. Their high-level behav-
ior is simple: the partitioner iterates over every data units ∈ st,
veriﬁes the bucket fors by computing Π(s), and appends s
to this bucket. At the end, the output is a list of bitstrings
bk1, ...,bkn, corresponding to the ﬁnal bucket contents. The
speciﬁc implementation of each step in this process depends
on the format of st. For any given ﬁle type, we distinguish
between two partitioner implementations, which operate at
different levels of abstraction and present different tradeoffs.
The ﬁrst type is anapplication-layer partitioner, which op-
erates at the logical level, splitting st before seralization (e.g.,
in CompMsg, partitioning the logical relational database). To
do so, the partitioner iterates directly over s ∈ st, using the
same application-level API through which the client interacts
with storage. If Π(s) corresponds to a new bucket label, the
partitioner creates an empty copy of st (e.g., a new relational
database), and inserts s to it; otherwise, it inserts s to the
existing copy. These operations are also performed with the
application-level API. At the end, there will be multiple copies
of the logical storage. The partitioner serializes each using
encode, which yields bk1, ...,bkn. The copies of the storage
are then deleted.
The second type is a data-layer partitioner, which operates
on the encoded data, splitting ˆst instead after st has been seri-
alized (e.g., in CompMsg, partitioning the encoded database).
These partitioners are more complex: instead of iterating over
the data units in s, they iterate directly over the bytes of ˆst,

An implementation of view policies. While our framework
can be used with any suitable implementation of view policies,
we now describe an example format, which is easy to use,
update, and conﬁgure. As described in Section 3, we can
implement view policies by composing an access control
policy with what we call a “ﬁlter” policy. The former maps
data units to users with access to them, and the latter speciﬁes
the bucket for these senders, which allows conﬁgurability. We
describe each of these policies below.
An access control policy is a functionΠacc that maps a data
unit s to a set of user IDs {uid1, ...,uidn} that have access
to it. There are many standard approaches for specifying
access control, such as schema annotations [31, 37], runtime
labels [51], and more [39, 50]. Following various works [18,
27,33,49], our approach is to specify Πacc using a centralized
controller, i.e., a singular location in client-side code that
encodes this information. This could be handled in many
ways; for example, one could dynamically maintain at runtime
a separate list mapping identiﬁers for data units (e.g., primary
keys of database rows) to user IDs. Such a dynamic approach,
however, would incur some runtime overhead and might be
harder to update in response to policy changes.
USENIX Association 34th USENIX Security Symposium    2971

[PDF_PAGE 9]
Instead, we rely on the observation that most applications’
data models already implicitly or explicitly encode access
information for other reasons. For example, in a messaging
application, a database table storing messages will inevitably
contain columns for the sender and recipients of the message,
which are also users with “access” to this row. So, Πacc can be
speciﬁed in terms of the data modelitself, via a list of static
functions that evaluate to user identiﬁers. In the prior exam-
ple, Πacc could have a single clause encoding the statement
“if s is a row in the messages table, return s.sender”. This
single line would capture the policy for the entire table.
An access control policy on its own enforces strict isola-
tion between individual senders and groups. As mentioned
earlier, however, view policies should be conﬁgurable, and
support more ﬂexible isolation conditions. We handle this via
ﬁlter policies. These policies are functions Πﬁlt that map a
set of user IDs {uid1, ...,uidn} to a bucket label. Intuitively,
ﬁlter policies specify whether certain user groups can be “col-
lapsed” together, meaning that their data should be processed
together. Concretely, Πﬁlt outputs a “proxy” value, which ex-
tracts a particular feature from a group of users. 3 The sim-
plest ﬁlter policy is just Πﬁlt(uid1, ...,uidm) = uid1, ...,uidm,
which speciﬁes standard group-based partitioning. A more
advance policy could, for example, return 1 if (uid1, ...,uidm)
are all contacts of U, and 0 otherwise. Access control policies
and ﬁlter policies compose to implement a full view policy
Π(s) = Πﬁlt(Πacc(s)). The access policy speciﬁes the access
boundaries of st, and ﬁlter policies provide a simple lever to
conﬁgurable the balance of security and performance.
Summary. We now summarize the use of our framework.
First, in the setup phase, the developer speciﬁes a view pol-
icy for their application. In our example format, they specify
a single conﬁguration ﬁle, which denotes (as a function of
their data model) how to map data units to users IDs. For
instance, this ﬁle could consist of a list of sensitive database
tables, and, for each, the column(s) encoding the users with
“access” to each row. The developer additionally speciﬁes, if
desired, a ﬁlter policy ﬁle; the framework defaults to the stan-
dard group-based ﬁlter. Both of these policy ﬁles are placed
in some arbitrary location in the client code. In this same
setup phase, the developer incorporates a partitioner into their
Export code, initialized with pointers to the conﬁguration
ﬁles. The developer can rely on existing implementations for
the ﬁle types used by their application. The modiﬁed appli-
cation can then be shipped to end-user devices. Regular-use
operations, such as sending or receiving messages, are un-
modiﬁed, and thus incur no overhead. During exports, the
framework kicks into gear: the partitioner silently intercepts
the input to F, reads from both policies to determine how to
split the application state, computes F independently on each
partition, and encrypts the resulting outputs.
3This is similar to the notion of keys in sorting algorithms, which deﬁne
the criteria to compare the elements by.
Framework extensions. View-based partitioning can be
adapted to a variety of different types of cross-user computa-
tions. We describe two examples here. First, in some cases,
st contains data structures that are themselves a function of
cross-user data. A notable example is (inverted) search in-
dices, which map keywords to the documents in which they
appear (e.g., an index for text messages would map individual
words to identiﬁers for the chats that contain them). As shown
by prior work [16, 48], an adversary can use injection attacks
to exploit ﬂuctuations in the size of such data structures to
learn information about their contents.
To deal with search indices, our framework can be used to
create a “partitioned index”, where every keyword-document
mapping is split according to user views. Consider an inverted
index that maps every keyword w to a set of document identi-
ﬁers{d1, ...,dn}. In this context, the relevant data units—that
is, what we want to partition—are the document identiﬁers.
So, we can use a view policy Π to map document identiﬁers
to buckets. A partitioner can then iterate over each index key-
word, and use Π to split {d1, ...,dn} into equivalence classes
D1, ...,Dt, where Π(d′) = Π(d′′) for every d′,d′′ in the same
class. The partitioner then creates a new index entry sepa-
rately mapping w to each set Di. Note that our framework can
be applied dynamically during exports, leaving the index un-
changed during regular application usage. During imports, we
can then efﬁciently re-merge the index, simply by combining
all entries for the same keyword.
As a second example, view-based partitioning can also be
applied to network-based features. For instance, password
managers often display a small identifying icon (e.g., a com-
pany logo) next to a user’s saved credentials. Such icons,
however, are fetched only once per domain: new credentials
for an existing domain reuse the icon stored in the client. As
shown in prior work [15], an adversary can inject credentials
for particular domains and observe whether network requests
are triggered or not, which reveals whether these domains are
already present in the victim’s vault. To mitigate this, we can
use view-based partitioning to perform a “partitioned fetch”
of URL icons: icons are only reused across credentials in
the same bucket. We can use a view policy that maps creden-
tials to bucket identiﬁers, and a partitioner can then intercept
the request that determines whether a new icon needs to be
fetched, verify if the domain is present in credentials within
the same bucket as this new credential (as opposed to across
all credentials), and fetch the icon if and only if it is not.
Additional security considerations. Our framework en-
forces view-non interference as a function of the speciﬁed
view policy. Therefore, similar to other policy-based sys-
tems [10, 27, 31, 49] our resulting guarantees rely on policy
correctness. We opt for this approach, since data models can
vary signiﬁcantly across applications; it is not feasible to
have a single partitioning strategy for all applications. Using
custom policies means our framework is highly conﬁgurable
2972    34th USENIX Security Symposium USENIX Association

[PDF_PAGE 10]
across applications, and allows developers to ﬁne-tune the
granularity of how partitioning is performed. Further, as our
case-studies in Section 5 show, specifying policies is feasi-
ble, and can generally be bootstrapped from the application’s
existing access control logic.
Since similarity-sensitive functions are still applied within
each bucket, an adversary could possibly learn information
via passive attacks. As discussed in Section 2, however, this is
outside the guarantees of our framework; its goal is to disable
injection channels. Mitigating passive leakage requires differ-
ent techniques (e.g., size-locked constructions [48]), which
can compose with our framework (i.e., using them within
individual buckets) for even stronger security guarantees.
5 Case-Study Implementations
We exercise our framework in this section, and use it to con-
struct injection-robust encrypted backups based on two case-
study applications: WhatsApp and KeePassXC. As mentioned
in Section 2, prior work [15,16] found both applications to be
vulnerable to injection attacks, and so we apply view-based
partitioning to address these attack vectors. We make our
framework implementations available as an open-source ar-
tifact [2]. As described later, these implementations should
be useful to a broader set of applications, since they work for
widely-used ﬁle formats, and thus may serve as the starting
point for injection attack mitigations for other applications.
5.1 Example # 1: WhatsApp
Two unmitigated attack vectors in WhatsApp are ﬁle dedupli-
cation and compression. We describe each of these in turn.
Mitigating deduplication attacks. As described in Sec-
tion 2, WhatsApp clients perform client-side deduplication of
sent and received attachments during backups, which leads to
injection attacks. At a high-level, applying our framework to
ﬁle deduplication translates to deduplicating ﬁles separately
for each bucket, instead of globally across all ﬁles. Thus, there
will be at most one copy of each ﬁleper bucket, and so we mit-
igate injection attacks while still leveraging the performance
beneﬁts of deduplication. In the context of deduplication, the
client state st corresponds to attachments (binary ﬁles) stored
in the device’s ﬁlesystem, and the similarity-sensitive function
F(st) returns the same ﬁles as st, but with duplicate copies
removed. Therefore, a partitioner implementation for this data
model takes as input a path to the location in the ﬁlesystem
where attachments are stored, and (as usual) an access control
policy and a partition policy.
As described in Section 4, view policies must be compatible
with st. In this case, the data units in st are individual ﬁles,
so a view policy Π takes as input the path for an individual
ﬁle, and returns a bucket identiﬁer. As described in Section 4,
we implement Π as the composition of an access control
policy and a ﬁlter policy. The access control policy receives
as input the path for an individual ﬁle, and returns a set of
user IDs who have access to this ﬁle, i.e., the members of
the chat—group or individual—in which the ﬁle was sent.
Our partitioner implementation (described below) makes no
assumptions about how this policy is written, but an example
implementation could consist of a (single) SELECT statement
to a database table where ﬁle metadata is stored. Then, a ﬁlter
policy takes as input the set of user identiﬁers, and returns
the bucket that these are assigned to. For example, a policy
could read the database table where user metadata is stored,
and return 1 if all users are stored contacts.
The partitioner itself must also be compatible withst, i.e., it
must be aﬁlesystem partitioner. Its implementation is straight-
forward: it iterates through all ﬁle paths inst, veriﬁes which
users can read this ﬁle (using the access control policy), and
appends this ﬁle path to a list (based on the ﬁlter policy). The
output is then a list of lists, where each inner list speciﬁes the
ﬁles that belong to each bucket. Lastly, deduplication is com-
puted on each inner list. Note that, in the case of ﬁlesystems,
the application-layer and data-layer partitioner are the same,
since ﬁles are exported in the same way in which they are
stored on the device.
As mentioned in Section 2, client-side ﬁle deduplication
is a common vector for injection attacks. Therefore, other
applications can leverage our ﬁlesystem partitioner to mitigate
deduplication-based attacks.
Mitigating compression attacks. We now switch gears
to compression attacks. As described in Section 2, What-
sApp clients compress application databases before encrypt-
ing them during backups, which leads to injection attacks.
Applying our framework to compression translates to com-
pressing in individual streams the database rows that belong
to each bucket. In this setting,st corresponds to the client-side
database, ˆst to the serialized database during backups, and
F to a compression algorithm. For WhatsApp, application
databases are relational databases, which are serialized using
SQLite’s database ﬁle format [42], and then compressed with
zlib. Our framework implementation must thus be tailored to
this data model and serialization format. The data units for a
relational database correspond to the database rows, which
are thus the inputs to view policies for this data model. An
access control policy encodes the database tables that contain
sensitive information, and the column in each table that stores
the set of users with “access” to this row. This can be imple-
mented, for example, via a function that veriﬁes whether the
input row belongs to one of the sensitive tables, and then has,
for every sensitive table, a SELECT statement to extract the
set of relevant user labels (e.g., the sender of a text message).
The application-layer partitioner iterates over all tables
and all rows in the input database, using standard SQLite
APIs, and veriﬁes the view policy for every row. Buckets are
initialized as empty copies of the relational database, with the
USENIX Association 34th USENIX Security Symposium    2973

[PDF_PAGE 11]
same schema as st. We then add rows to the corresponding
bucket (database copy) using SQL INSERT statements. Once
all data units have been assigned to a bucket, we serialize
each database copy individually using SQLite’s database ﬁle
format, which are the bitstrings returned by the partitioner.
The data-layer SQLite partitioner is more complex, since
SQLite’s database ﬁle format is intricate. We describe it at a
high-level here, and refer interested readers to our code [2]
for more details. In this format, each database table and index
is stored as a B-tree, with the rows of the table stored in the
leaf nodes of the corresponding tree. A serialized database
consists of the nodes for each table and index organized in
sequential pages of a ﬁxed size. Our data-layer partitioner
iterates over the bytes of a ﬁle in page-sized jumps, checking
whether each page corresponds to an intermediate or leaf
node and whether it is an index page or a table page. If it
corresponds to an intermediate node or is an index page, no
users have permission for it, so it is sent to a default bucket
designated for metadata. If it is a leaf node, the partitioner
carefully reconstructs the database rows, which as data units
can be fed to the view policy to determine the correct bucket
for the corresponding bytes.
Unlike ﬁle deduplication, compressing data in multiple
streams raises additional engineering challenges, due to the
fact that we must be able to reconstruct the database after
decompression. This is not an issue for application-layer
partitioners, as they compress each database copy individu-
ally. Later, these can be decompressed individually again, and
database rows can be arranged in their original order based on
primary keys. However, data-layer partitioners have no con-
cept of the application-level structure of st: the byte streams
in each bucket correspond to potentially non-contiguous por-
tions of ˆst, so there is no natural way to reorganize the decom-
pressed byte streams to recover st.
We thus had to implement a custom multi-stream com-
pression functionality as a wrapper around existing com-
pression algorithms, that allows for seamless reintegration
of the decompressed byte steams. At a high-level, our wrap-
per maintains an internal data structure called a stream key,
which keeps track of the way in which compression streams
were used: every time data is fed to one of the compressions
streams, the stream key records which stream was used, and
how many bytes were fed to it. Once all streams are closed,
our wrapper returns the concatenated output of all streams,
with the stream key prepended as a header; the stream key
itself is not compressed. Later, the stream key can be used to
interleave the decompressed streams to recoverst, by progres-
sively appending bytes from streams in the order and quantity
speciﬁed by the stream key.
5.2 Example # 2: KeePassXC
KeePassXC addressed compression-based attacks by insert-
ing random noise of some random length (between 64 and
512 bytes) every time databases are saved [15]. While this
signiﬁcantly degrades the feasibility of attacks, it is not a full,
provable mitigation, since noise can potentially be bypassed
by, for example, using statistical techniques. Our framework
thus provides a more robust mitigation.
In KeePassXC, application databases (corresponding to st)
are object-oriented databases, which are serialized using an
XML-based format [15] during exports (corresponding to ˆst),
and then compressed with gzip. Therefore, in this context,
data units correspond to XML elements and their associated
paths in the tree representation of the XML ﬁle. While we
make no assumptions about how access control policies are
speciﬁed, we provide a high level syntax for deﬁning policies.
Simply, a user deﬁnes rules each consisting of two expres-
sions using XPath syntax. One expression speciﬁes a set of
XML elements, and the second speciﬁes a corresponding
set of elements whose values encode the user permissions
for the ﬁrst set. For instance, if the database contains shared
folders, each accessible by a different set of users, the two
expressions might be root/folder and root/folder/sharedwith
to represent the rule “The elements under root/folder are acce-
sible to the users speciﬁed by the value of the corresponding
root/folder/sharedwith element”.
Our application-layer XML partitioner creates multiple
copies of the original database S1,S2, ...,Sn, each of which
only contains elements from one bucket such that F can be
safely applied to each individually. The original st is recov-
ered by merging S1,S2, ...,Sn. The data-layer XML partitioner
parses ˆst byte by byte, allocating bytes to buckets as it tra-
verses the tree of elements. These byte streams (one per
bucket) are fed into the multi-stream compression algorithm
(Section 5.1), which combines these into a single compressed
ﬁle and reassembles the original ˆst at decompression time.
As described in Section 2, compression is a common attack
vector for injection attacks. Since partitioners are schema-
agnostic, other applications that use SQLite or XML can
beneﬁt from our implementations. Further, our multi-stream
compression approach may be of general interest, even for
applications with ﬁle formats that differ from the ones of our
case studies.
6 Security Analysis
We analyze the security of our framework in this section. We
begin by introducing a formal model and security deﬁnition
for injection attacks, and then prove that our framework meets
this deﬁnition. Of independent interest, as part of this proof,
we derive a simple, general property of E2EE clients that
we show is sufﬁcient for robustness against injection attacks
(and, indeed, is met by our framework); this may be useful
for guiding other mitigation approaches in the future.

6.1 Security Deﬁnition for Injection Attacks

then introduce our security deﬁnition, which formally models

Primitive: encrypted exports client. Recall from Section 2
that injection attacks primarily leverage application clients
in end-user devices (how they store data locally, how they
export the application state, etc.), and that application servers
are assumed to be honest-but-curious. Thus, our primitive
will be client-centric, ignoring application servers and other
external elements. We then narrow our focus exclusively to
the components of clients that play a role in injection attacks:
(1) interactions with other clients, and (2) observations of
clients exports. Therefore, we only need to model these two
main operations. Putting these ideas together, our primitive

Security deﬁnition. Having introduced the concept of en-
crypted exports clients, we are now ready to formally deﬁne
injection attacks. Following standard approaches, we employ
a left-or-right (LOR) security deﬁnition: the adversary sub-
mits pairs of challenge messages to an oracle, and one of the
messages gets added to the application state (via the Send
operation) based on the value of a randomly-chosen challenge
bit b. The adversary then has access to the standard Send
and Export algorithms—which model adaptive injections and
exports—which they use to try and identify the value of b.
This approach models the fact that an adversary that can in-
ject content and observe exports should not be able to learn a
single bit of information about honest messages.
While simple, there is a key challenge that limits the util-
ity of just directly using this deﬁnition: schemes may have
some “baseline” leakage of information, orthogonal to injec-
tion attacks, which could lead to trivial wins; by submitting
challenge messages that differ with respect to this leakage,
the adversary could immediately identify b. For example, in
the case of ﬁle deduplication, the adversary could submit as
challenge messages ﬁles(F0,F1) followed by (F0,F2). If the
next export includes one (resp. two) encrypted ﬁle(s), the ad-
versary knows that b = 0 (resp. b = 1). This is a vacuous win,
since it does not require injections, but rather relies just on
challenge messages. Preventing such attacks is outside the
scope of our framework.
To deal with this issue, we devise a new approach, which
we call a “relative” security deﬁnition. We will deﬁnetwo sep-
arate security games. In the ﬁrst game, the adversary cannot
perform injections; they can only submit challenge messages,
and a simulator is able to trigger exports. In the second game,
the adversary additionally has an injection oracle. Then, intu-
itively, a scheme is secure if the advantage of an adversary in
the second game is not much greater than the advantage of
the simulator in the ﬁrst game, i.e., performing injections does
not “help” to break security. We call this security guarantee
injection simulatability. This approach bypasses the problem
of trivial wins, as these simply amount to wins in both games;
we only care about whether there are cases where there is
a difference in success probability. We stress that injection
simulatability reﬂects the speciﬁc security goal of disabling

6.2 General Security Result
Our goal is to show that our framework meets our security
deﬁnition. However, proving this directly is challenging, due
to the complexities of our framework. Our strategy will thus
be to ﬁrst distill a simpler, higher-level property of E2EE
clients, which we show is sufﬁcient for security, and then
separately show that our framework meets this property.
Length independence property. Our goal is to identify
a particular property of encrypted exports schemes that can
be used to build a generic simulator, which can emulate any
adversary with injection capabilities. The main challenge for
such a generic simulator is that it only has access to exports of
honest operations, but needs to simulate exports of additional
operations (i.e., injections). This directly leads to the main
insight of our generic result: for such a simulator to exist, C
needs to be such that injections alter exports in a predictable
way, which only depends on these injections, and can thus be
simulated. In fact, as we show later on, being able to simulate
lengths of exports is sufﬁcient. We call this propertylength
independence. Just like our security games, length indepen-
dence is parametrized by a corruption predicate P.

framework (by design) reveals information in a per-bucket
context, which could lead to passive attacks; mitigating these
is outside the scope of injection simulatability, and of this

implementations of our framework (speciﬁcally, partitioners)

7 Evaluation
In this section, we explore the performance of our implemen-
tations from Section 5. We show that our framework is a
practical approach for mitigating injection attacks.
For deduplication, we did not have to experimentally deter-
mine the overhead introduced by our framework, since this
can be directly characterized deterministically: deduplication
overhead is agnostic to the speciﬁc content of ﬁles, as it is
(only) a direct function of the size and number of duplicate
ﬁles. Intuitively, overhead is a function of the number of buck-
ets spanned by each set of duplicate ﬁles: every additional
bucket adds a copy of the respective ﬁle. We show a precise,
closed-form formula for the resulting overhead in Appendix D.
While this lead to a noticeable performance overhead for some
workloads, others may see better performance. Further, note
that there is no overhead added in terms of runtime, since
deduplication can be performed in parallel across all buckets.
Unlike deduplication, the performance of view-based parti-
tioning needs to be assessed experimentally. We thus perform
an extensive evaluation of it, which is the focus of the rest of
this section. All of the code and data used in our experiments
can be found alongside our open-source library [2].
7.1 Methodology
We measure the overhead of our framework in terms of export
size, latency, and CPU utilization. All experiments are run
on a laptop with an Apple M3 processor and 16GB of RAM.
Since the performance of compression depends heavily on the
structure of data, it is critical to perform our experiments on
representative workloads: inputs to our framework implemen-
tation should be real WhatsApp and KeePassXC databases,
populated with representative application data.
The ﬁrst step in our methodology was to identify the rele-
vant parameters to vary across our experiments. We identiﬁed
three main variables: the amount of data in the database, de-
noted by m; the number of buckets that result after partitioning
the database, which we denote by n; and how the m bytes of
data are distributed across alln buckets. For the latter, we used
two distribution models in our experiments: an “even” model
(all buckets have the same amount of data), and a “long-tail”
model (data is allocated across buckets according to a power-
law). We describe shortly how values ofm and n were chosen.
Next, we acquired representative testing data for each ap-
plication. For KeePassXC, we used open-source lists of user-
names and passwords from real-world data breaches [32], and
the Tranco list [26] for URLs. For WhatsApp, we had to gen-
erate our own synthetic data; to our knowledge, there are no
high-quality datasets of personal messages publicly available.
Note that the performance of compression depends heavily on
the relationships between parts of the input data, and thus sim-
ply generating random words would have not been sufﬁcient.
Therefore, our approach was to use a large language model
(LLM) to generate internally-consistent multi-message con-
versations, speciﬁcally tailored to imitate the style and content
of instant messaging conversations.
Using this testing data, we set up a comprehensive eval-
uation pipeline. This included scripts for generating empty
copies of real WhastApp and KeePassXC databases, sampling
from the relevant testing datasets, populating the databases
in accordance with each applications’ client logic, and then
running our framework implementations on the resulting
databases. Our entire evaluation pipeline, including LLM
prompts, are included in our open-source artifact [2].
Equipped with this experimental setup, we were ready to
run our experiments. We took care to estimate representative
values of m and n for our experiment runs. Users of password
managers generally store approximately 200 passwords [45].
We were unable to ﬁnd statistics on typical number of folders
used, so we chose 10 folders as a baseline, which we deem
reasonable. WhatsApp handles around 100 billion messages
a day as of 2020 [13], and currently has around 2 billion daily
users [1]. Using these ﬁgures, we estimate an average user
sends 50 messages a day. So, if we pick 10 years of usage as a
baseline, we estimate that a typical WhatsApp database could
easily store 200,000 messages. We do not have statistics for
typical number of groups, and thus chose 100 as a baseline
(this includes one-on-one conversations).

8 Conclusion
In this work, we present an efﬁcient and provably secure
framework for preventing injection attacks against E2EE ap-
plications. To formally analyze our approach, we introduce a
novel security model for injection attacks, and show security
of our constructions within this model. We perform experi-
ments to assess the overhead of our framework based on two
example applications, and ﬁnd that our approach is amenable
to practical adoption. As E2EE applications grow in number
and complexity, we hope our work can help ensure that this
will not lead also to a growth in attack vectors.
Ethical Considerations
In our work, we propose principled mitigations for injection
attacks on E2EE applications, and evaluate their performance
using workloads that reﬂect real-world use scenarios. Below,
we describe the ethical considerations raised by our work.
Privacy of experimental workloads. The usernames and
passwords for the input data come from SecLists and the
URLs come from Tranco, as we discuss in Section 7. SecLists
is a testing tool for security applications that includes public
datasets. Tranco maintains a list of top-ranked websites. Given
that these data sources are public and widely available, our
usage of them to generate workloads does not put users at risk
of security or privacy breaches. In addition, we used a large
language model to generate synthetic message data for our
WhatsApp workloads. By doing so, we avoid compromising
the privacy of real user messages.
Addressing unresolved vulnerabilities. Many existing
E2EE applications have either partial or, in some cases, no mit-
igations for the injection attacks that we address in this paper.
However, these attacks have been established in prior work,
and are public knowledge. Although mentioning them can in-
crease awareness of their existence, we do so in a constructive
way and provide a concrete solution to protect against them.
We are also reaching out to affected platforms to make them
aware of the mitigations we propose.
Open Science
We have made our implementation and datasets public and
open source [2]. This repository contains all artifacts involved
in our work, including evaluation pipelines and datasets to
reproduce our results. Concretely, the contained artifacts are:
ﬁlesystem partitioner (Section 5.1); multi-stream dedupli-
cation library (Section 5.1); SQLite application-layer and
data-layer partitioners (Section 5.1); XML application-layer
and data-layer partitioners (Section 5.2); multi-stream com-
pression library (Section 5.1); evaluation pipeline, including
scripts to generate fresh synthetic data and evaluate frame-
work implementations (Section 7.1); and the synthetic data
speciﬁcally used by our experimental evaluation (Section 7.2).

B Proof of Theorem 2
We show the proof of Theorem 2 in this section.
Proof. To prove perfect length independence, we need to
deﬁne a functionSimLen that satisﬁes the equation in Deﬁ-
nition 1 for ε = 0. First, note that the lengths of ciphertexts
returned by ˆC.Export are deterministic, and based exclusively
on its inputs: our framework uses E in a standard way (with-
out, for example, randomized padding), for which ciphertext
lengths are exclusively a function of the plaintexts. Con-
cretely, for a transcript τ, it follows that | ˆC.Export(Run(τ))|
will be determined by |F(bk1)|, ...,|F(bkn)| for bki ∈
Partencode(Run(τ), Π). So, SimLen needs to be such that, for
any U ⊆ I, SimLen can extend an export of this form for sub-
transcript τ − τPΠ(·,U) to an export of this form for all of τ. If
so, our framework will achieve perfect length independence,
since, as explained above, the length of this longer export
uniquely determines the length of any encryption of it.
To show this, the key insight is that, due to view non-
interference, any particular bki in the export of τ will only
be a function of Send calls that are either all in τPΠ(·,U) or
all in τ − τPΠ(·,U): by Deﬁnition 2, allbki that do not depend
on elements of τPΠ(·,U) will be the same in both exports; on
the other hand, by construction, PΠ(·,U) will ﬁlter allSend
calls that impact any data unit s that affects any modiﬁedbki.
It thus follows that SimLen only needs to construct the new
bki that are in the export of τ but not of τ − τPΠ(·,U), since all
other bki are unchanged. Further, these new bki depend only
on the content of τPΠ(·,U), and can thus be simulated. Con-
cretely, SimLen can simply run an empty instance of ˆC with
these additional sends, and trigger an export; the resulting bk
will be the same as the expected ones in the full export of τ.
This follows from the fact that, by view non-interference, the
value of these bk is the same irrespective of any changes to
the entries in τ − τPΠ(·,U); in particular, all bki are the same
even when these entries are deleted completely.
C Details on Security of Implementations
By design, the speciﬁcation of both application-layer and
data-layer partitioners leads to view non-interference. For the
former, each sti corresponds to a completely fresh encoding
of the data units that are assigned to this bucket by Πacc and
Πﬁlt, which is equivalent to running an instance of the appli-
cation with just those data units, and thus changes to other
data units do not affect sti. Similarly, for the latter, each sti
contains the bits of encode(st) that depend on the data units
that are assigned to this bucket. Therefore, thespeciﬁcation of
partitioners is secure against injection attacks. Showing that
an implementation meets its speciﬁcation requires arguing
that it (1) iterates over all data units at the appropriate granu-
larity, (2) evaluates Π over all data units, and (3) isolates data
units that have been partitioned into different buckets.
For our XML partitioners, XML elements are the natural
choice for data units, as these are the smallest logical compo-
nent of the database. The XML partitioners parse a database

[PDF_PAGE 21]
element by element (although the data-layer partitioner op-
erates at the byte level, it reads bytes until an element can
be parsed to evaluate Πacc). So, as the content of an XML
database consists entirely of elements, the partitioners will
evaluate Πacc on all elements. Once XML elements have been
allocated to buckets, both the application-layer and data-layer
partitioner enforce isolation. The application-layer partitioner
guarantees this by creating database copies each consisting
of only elements from a single bucket, whereas the data-layer
partitioner instead maintains separate byte streams for bytes
corresponding to elements from separate buckets
Our SQLite partitioners use table rows as data units, since
this is the granularity at which injections are possible for most
applications. The application-layer partitioner uses the SQLite
API to iterate over all rows of a database, and evaluates Π
on each to allocate it to a bucket. To maintain isolation, the
application-layer partitioner creates a new database with the
same structure as the original (by copying the schema) for
each bucket. The data-layer partitioner iterates over the pages
of the SQLite ﬁle (Section 5), and parses table leaf pages into
rows that are fed into Π. Because table leaf pages are the only
pages that contain rows, this guarantees that all rows will be
processed by the partitioner. To enforce isolation, the data-
layer partitioner maintains separate byte streams for bytes
corresponding to row data from separate buckets.
We now describe a simple heuristic test, which can be
performed multiple times to increase conﬁdence in the non-
interference of a partitioner implementation. First, one initial-
izes an application state st1 (e.g., an SQLite database) with
some initial data, and triggers an export to obtain a snapshot
C1 of it. Then, one changes a single, arbitrary data units in st1
to some other value (e.g., changing a single database row), to
obtain a new state st2. This is followed by an export of st2 to
obtain C2. Lastly, C1 and C2 are compared. If the partitioner
satisﬁes non-interference, then the only difference between
C1 and C2 should be the content of bucket Πﬁlt(Πacc(s)), and
all other buckets should remain unchanged.

Intuition behind compression storage overhead. Our
evaluation showed the surprising result that the data-layer
partitioning decreases WhatsApp backup size for baseline
databases (see Table 8). We suspect that this could be be-
cause, when using insecure compression with a single stream,
the ﬁxed-size sliding window (which defaults to 32 KB for
zlib and gzip) may be ﬁlled with database rows corresponding
to messages from a mix of groups. On the other hand, when
using partitioned compression of large databases, the sliding
window of many streams will be ﬁlled with database rows
corresponding to messages from a single group, which may
be more compressible as they share metadata and content.
To test this, we performed an experiment where we parti-
tioned the database using the data-layer partitioner, but com-
pressed each bucket sequentially using a single stream. We
would expect this approach to result in an even smaller backup
size than when the data-layer partitioner is used, as it beneﬁts
from database rows corresponding to messages from the same
group being coalesced without the overhead associated with
multiple streams. Indeed, this approach produced WhatsApp
backups that were about 0.5 MB smaller than those from the
regular data-layer partitioner, supporting our hypothesis. For
KeePassXC, this approach resulted in a backup size 1-2 KB
larger than regular insecure compression, suggesting that the
effect is weaker for smaller databases.
Another interesting result is that a long-tail distribution
adds overhead for KeePassXC but not for WhatsApp (see Ta-
ble 8). There are a few possible reasons for this. First, in the
baseline experiments with a long-tail distribution, the smallest
folders in the password manager contain <5 entries. Since
the serialization of each entry is only a few KB in size, the
compression stream for these small folders never ﬁlls the 32
KB sliding window, resulting in suboptimal compression. Ad-
ditionally, KeePassXC maintains a single Root folder, where
serializations of entries are slightly smaller than in shared
folders. Because our long-tail distribution always chooses the
Root folder as the folder with the most entries, this distribu-
tion produces a smaller database than an even distribution for
the same parameters; for KeePassXC our framework intro-
duces more overhead for smaller databases. We suspect the
choice of distribution does not affect overhead for WhatsApp
because the database is much larger, so with a long-tail distri-
bution even the smallest groups will always have enough data
to ﬁll the 32 KB window of their compression stream.
