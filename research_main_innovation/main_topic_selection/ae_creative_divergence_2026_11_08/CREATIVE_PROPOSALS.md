# 四个创造性研究构想

2026-11-08。当前对话内模型辅助发散与定点查新。四项构想的查新前记录见 [IDEAS_BEFORE_SEARCH.md](IDEAS_BEFORE_SEARCH.md)。该记录固定本轮生成顺序，原创性仍由外部先例与具体结果判断。

## 1. 向代理隐藏账户与权限清单

### 用户将看到的系统

用户要求汇总本月获准账户的发票。远端代理获得一个任务接口，可以请求总额、类别和用户批准的字段。账户发现、登录、凭证选择和站点访问由用户控制的执行边界完成。最终详细报告可以只在用户端展示。

研究对象包括账户是否存在、账户之间的关系、可用操作和隐藏的业务后端。哪些信息属于任务结果，哪些仍应隐藏，由用户认可的合同明确给出。

### 一个具体的候选流程

1. 钱包把用户批准的任务转为有限的可调用操作和披露规则。
2. 代理提出抽象操作，私密执行器选择实际账户与接口。
3. 执行器完成受控调用，返回符合任务合同的结果或有限失败状态。
4. 任务结束后，输出一份绑定实际任务与授权版本的回执。

这是一份研究架构。具体调用接口、完整性与时序泄漏仍待设计。

### 潜在核心命题

固定任务 T 及独立定义的允许泄漏函数 \(L_T\)。对两个账户状态 \(V_0,V_1\)，若

\[
L_T(V_0)=L_T(V_1),
\]

希望在声明的对手能力和交互范围内，代理看到的完整会话计算不可区分，同时保持约定的任务完成能力。

泄漏函数应覆盖允许的结果、失败、请求次数、时间与费用。它不能在看到协议全部输出后再被任意扩大。

### 创造性增量的责任

需要建立任务足够的交互抽象、主动探测下的隐私和任务完成性，并完整计入本地推理、网络、填充与验证成本。底层账户选择若必须依赖秘密，应由合适的受控计算位置完成。

MINIM 已研究任务相关的观察最小化。Skill-as-API 已有隐藏技能与统一错误的机制。私密多代理规划也已有形式化工作。进一步的命题级映射必须把这些全部纳入强基线。[MINIM](https://arxiv.org/abs/2606.13949) [Skill-as-API](https://arxiv.org/abs/2609.01677) [私密规划](https://arxiv.org/abs/1810.13354)

### 重要的手工检查

若两个账户库只在一个与任务无关的账户上不同，完整清单接口会直接区分它们。任务白名单已经可以处理这个简单例子。

更有研究价值的情形是实际使用的后端也希望保密，而不同后端会带来不同失败模式、时延或交互需求。这里必须先证明所选任务仍有足够的私密交互接口。

### 两年研究包

任务与泄漏语义、交互抽象或规划算法、完整隐私和可用性证明、通过严格分离门后的密码管理器与执行器验证。区块链可以固定授权版本或回执，核心隐私还依赖实际信息流和执行边界。

## 2. 模型能力变化后的授权重新认证

### 用户将看到的系统

用户曾允许某一处理流程读取照片或工作记录。后续模型升级，引入更强的人脸识别、关联分析或跨模态推断能力。系统能够说明原授权依赖的哪项保证仍成立，哪项需要重新验证，以及当前有哪些可核查证据。

### 一个具体的候选流程

1. 授权同时记录允许的数据、输出、使用目的以及实际依赖的处理器假设。
2. 处理器或相关数据处理流程发生变化时，定位受影响的证明义务。
3. 对适用范围输出保证保留证据、具体违规见证或尚待补证的前提。
4. 在用户已批准的规则下选择复用、重新认证、数据变换或交由用户处理。

这项构想只适用于确实依赖处理器能力的保证。模型无关的非干涉保证，以及对既有输出进行后处理时仍成立的隐私定理，应按其原前提复用。

### 潜在核心命题

给定处理器类 \(\mathcal A\)、数据状态 D 和隐私合同 \(\Phi\)，已有证据说明 \(\Phi(D,\mathcal A)\) 成立。处理器类变为 \(\mathcal A'\) 后，研究如何生成可靠的保留或失效证据，并减少同条件下必要的重新验证费用。

版本哈希可以固定工件，能力与隐私性质需要对应的证明或明确的统计范围。少量攻击失败样本只承担相应测试证据。

### 创造性增量的责任

潜在贡献是处理能力变化的可检查抽象、授权保证的依赖分析、正确的证据复用，以及完整成本界。一般增量验证、依赖追踪、模型评估和重新批准都属于基线。

已有工作研究了获准数据的推断风险、模型迁移与政策改变后的学习工件治理。本轮尚未完成它们到上述精确合同的全文映射。[Priva-See](https://arxiv.org/abs/2609.28537) [Change-Provenant Supervision](https://arxiv.org/abs/2609.28574)

### 重要的手工检查

设公开给处理器的数据直接包含一个秘密位 S。旧处理器总是随机猜测 S，新处理器能够读取该位。旧处理器的低成功率无法单独支持关于新处理器的同一风险界。

这个例子属于标准的威胁模型检查。若数据已经通过具有适用后处理保证的机制转换，后续模型变化可以继续落在已有保证内。新的重新认证机制需要识别这两种情况。

### 两年研究包

能力相关授权语义、可核验的处理器变化分析、保证复用或失效算法、通过门槛后的模型与任务变更评估。研究范围先采用受控数据处理流程，已经脱离控制的明文副本另有责任。

## 3. 私人任务产生的经验，如何取得跨用户复用资格

### 用户将看到的系统

代理帮助用户完成财务、采购或开发任务，形成可复用的流程或技能。用户可以批准其中某种抽象经验用于其他任务，同时保留个人标识、商业事实和未经批准的方法细节。

每个导出的技能都有来源、允许的使用方式、必要参数、执行权限和可检查的释放依据。

### 一个具体的候选流程

1. 执行器记录技能生成所依赖的来源和用户批准的释放规则。
2. 导出过程识别固定事实、可重新绑定的参数、控制结构和所需能力。
3. 生成候选技能及证明义务，检查秘密是否通过常量、分支、工具选择或失败行为被带出。
4. 接收者按新的任务授权绑定自己的账户与能力。

首期可以采用受限工作流语言，使证明对象和执行行为可核查。任意自然语言技能与任意隐藏模型状态的完整保证需要额外方法。

### 潜在核心命题

设任务历史为 \(\tau\)，用户认可的可释放抽象为 \(D(\tau)\)，技能导出器为 E。一个可检验的目标为

\[
D(\tau_0)=D(\tau_1)
\Longrightarrow E(\tau_0)\approx E(\tau_1),
\]

其中等价关系覆盖技能包和约定的观察行为。与此同时，导出技能在声明的新任务类上需要保持可用性。

释放抽象 D 必须独立获准。让导出器自行把全部历史定义为“可释放经验”，会改变这个合同。

### 创造性增量的责任

研究应建立安全的经验抽象或导出方法，完整处理多来源、派生分支和能力重新绑定，并给出隐私、任务效用和验证成本。

FederatedSkill 已研究跨用户的语义技能差分，AntiSkillBench 已研究 persona skill 的隐私与冒用风险，Skill-as-API 已有技能封装调用，OBLIVION 已研究撤销技能被重建。它们均为直接近邻。[FederatedSkill](https://arxiv.org/abs/2606.03143) [AntiSkillBench](https://arxiv.org/abs/2608.03700) [Skill-as-API](https://arxiv.org/abs/2609.01677) [OBLIVION](https://arxiv.org/abs/2608.08264)

### 重要的手工检查

一个技能完全删去姓名和密钥，却根据原用户的秘密位选择两种不同模板。接收者读取模板就能区分该秘密位。常量脱敏不足以覆盖这种控制依赖。

标准信息流分析和程序切片可以处理受限语言中的这类问题。候选需与其联合能力比较。已向不受控接收者交付的明文技能，其后续复制与撤回需要独立合同。

### 两年研究包

经验与许可语义、受限技能导出或证明生成、效用与泄漏界、多来源更新，以及通过门槛后的技能复用验证。去中心化登记可记录来源和许可版本，行为保证仍需由证书及执行边界承担。

## 4. 跨服务认证故障的最小私密诊断

### 用户将看到的系统

代理登录失败后，获得与该任务有关的下一步依据，例如需要用户完成 MFA、需要重新批准某个范围，或当前证据不足以判定。账户存在性、其他权限和内部安全状态则按各自的披露规则处理。

### 一个具体的候选流程

1. 故障回执绑定实际失败请求、账户范围和时间。
2. 请求者证明自己有权获得某一级别的诊断。
3. 各服务提供可核查的局部事实或有限说明。
4. 诊断器形成任务所需的最少修复信息，并保留未知状态与证据边界。

该协议要处理取得诊断资格与当前登录已经失败之间的关系。可用依据可能是独立用户确认、仍有效的设备密钥或明确获准的诊断凭证，具体信任与恢复成本需要计入。

### 潜在核心命题

在服务各自保留私有认证与策略状态的条件下，能否得到对实际故障有依据、对非授权观察者有明确隐私界、对任务修复有用的联合诊断，并给出交互费用和最小披露条件？

### 已确认的直接覆盖

AWS 的 DecodeAuthorizationMessage 已明确把授权失败详情作为需要专门 IAM 权限才能解码的信息。Google Cloud Policy Troubleshooter 依据调用者有权查看的策略工作，并在缺少策略可见性时返回 Unknown。因此，“诊断信息本身需要授权”的基础机制已经存在。[AWS 文档](https://docs.aws.amazon.com/STS/latest/APIReference/API_DecodeAuthorizationMessage.html) [Google Cloud 文档](https://cloud.google.com/policy-intelligence/docs/troubleshoot-access)

RFC 6749 §5.2 中的 invalid_grant 涵盖过期、撤销和客户端不匹配等多种原因。RFC 9807 §10.9 讨论如何避免客户端枚举。这些都是候选合同必须满足的现成边界。[RFC 6749](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2) [RFC 9807](https://www.rfc-editor.org/rfc/rfc9807.html#section-10.9)

### 创造性增量的责任

候选需要推进到跨服务的联合故障依据、最小修复信息、不同诊断资格之间的泄漏控制，以及完整的交互与状态费用。把现有云平台的诊断接口包装成代理工具，有明确的工程路径。

### 两年研究包

故障与资格模型、多方证据协议、诊断正确性与隐私、修复信息最小性及代价界、通过门槛后的异构服务验证。该方向与原课题的认证语义不确定性相接，技术新颖性仍需逐命题核验。

## 5. 四项构想的共同边界

四项均采用可限定的任务、观察与执行接口。每项提出一个新的项目研究目标，现阶段没有取得全球首次或同能力严格优势的证明。

后续比较必须允许基线使用相同本地执行器、源代码、账户知识、数据变换、缓存、密码学工具和服务端接口。所有隐私和性能结论都需要包含失败、时延、证明生成、配置与恢复费用。

本轮为每项形成独立的研究包，保留创造性探索空间。机制实现继续以严格分离声明和实例为前提。
