Verifiable Provenance for Multi-Agent LLM Systems

Abstract
Multi-agent large language model (LLM) systems built on LangGraph-style frameworks
share an unencrypted state store with no field-level read access control, so one agent can
read another’s private fields. The 2026 OWASP Agentic Top 10 and CVE-2025-67644 show
that this layer is already being exploited. We propose CapChain, a replacement for the
step that merges each agent’s output into shared state, with three primitives: capability
tokens that cryptographically bind which agent may read which field, a tamper-evident
provenance log with logarithmic-cost audit, and a capability-aware reducer that decides
whether each field may be forwarded, redacting and logging unauthorized merges. We eval-
uate the reducer’s attribute–purpose gate on the MAGPIE contextual-privacy benchmark,
with scoring based on two deterministic tiers: verbatim matching and keyword-and-entity
salience. Across 150 conditions (25 scenarios× 3 open-source models × 2 instruction modes),
the Salient tier triggers the redactor for 4.67% of inter-agent messages. This rate counts
the reducer’s gate activations (redaction decisions), not leakage prevented. By relocating
enforcement from the language model to the state-transition layer that graph-structured
orchestrators expose, CapChain brings cryptographic, capability-based access control and
audit-by-construction provenance to a structural locus that prompt-level defenses can-
not reach.
Keywords: cryptography; distributed trust architectures; multi-agent LLM security; object-
capability discipline; capability tokens; Merkle provenance; contextual integrity; privacy-
preserving computation; inter-agent communication; LangGraph
1. Introduction
Large language models have moved from single-turn chatbots to multi-agent systems
in which several language-model-driven agents collaborate, exchange intermediate state,
and call external tools to complete complex tasks [ 1–3]. LangGraph is a widely used
framework for such systems in 2025–2026 production deployments [4].
The privacy gap is both structural and operational. On the empirical side, indirect
prompt injection (IPI), introduced by Greshake et al. in 2023 [5] and shown to be effectively
universal by Liu et al. [6], has matured into systematic benchmarks. The MAGPIE bench-
mark of contextual privacy reports that 2025-class frontier models leak up to 35.1% (GPT-5,
implicit-instruction regime) and 50.7% (Gemini 2.5 Pro, explicit-instruction regime) of
sensitive information [7]. AgentLeak’s seven-channel leakage taxonomy across five LLMs

∼2.5× amplification that output-only analyses miss [ 8]. The MIT 2025 AI Agent Index

On the implementation side, March 2026 saw the disclosure of CVE-2025-67644, a

framework-level software defects now share the same attack surface.
Policy and standards now demand answers. The OWASP GenAI Security Project
released the OWASP Top 10 for Agentic Applications on 9 December 2025, with two risks
explicitly framed at the inter-agent layer: ASI06 (Memory and Context Poisoning) and
ASI07 (Insecure Inter-Agent Communication) [11]. On 8 January 2026, the U.S. Department
of Commerce published the NIST CAISI Request for Information on securing AI agent
systems [12]. The CAISI process explicitly invited empirical evidence of multi-agent failure
modes: the kind of evidence the present paper contributes.
Existing defenses are predominantly policy-based. A 2025–2026 wave of agent-security
work has targeted most layers of the stack; Table 1 enumerates more than a dozen such
defenses classified by enforcement layer and threat model. A recent survey converges
on the same diagnosis: insecure inter-LLM communication remains the central unsolved
layer [13]. No broadly established framework establishes distributed trust by binding
cryptographic capability primitives at the state-transition layer that LangGraph and its
peers expose. Every inter-agent disclosure ultimately passes through the reducer that
merges one agent’s output into shared state. This makes the state-transition layer the single
chokepoint at which a structural, non-prompt defense can mediate the trust transition. The
natural control, LangGraph’s default reducer, applies no read-access check at all.

Under the default reducer, a private field written by the seller-CEO’s agent (an undisclosed

2. Background and Related Work
2.1. LLM-Based Multi-Agent Frameworks
Agentic LLM systems build on a short lineage: ReAct’s interleaved reasoning and
tool use [1], Toolformer’s learned API invocation [2], and AutoGen’s scalable multi-agent
conversations [3].
AutoGen [3] consolidated this trajectory into a multi-agent conversation framework
with explicit roles and message passing, while LangGraph [4] introduced a graph abstrac-
https://doi.org/10.3390/app16157776

[PDF PAGE 4]
Appl. Sci. 2026, 16, 7776 4 of 31
tion over agent state in which each node is an agent step and each edge is a transition
guarded by a developer-specified reducer that merges incoming state updates into a global
StateGraph. A persistent checkpointer (SQLite, Postgres, Redis, or a custom store) writes
serialized state across nodes, enabling resumability and time travel. Across surveys of
the field [13], the dominant architectural pattern coalesces around a four-module abstrac-
tion (profile, memory, planning, action), coupled by a shared, persistent, mutable state
dictionary that every agent in the system can, in principle, read and write.
This shared state dictionary is the locus of our work. As LangGraph deployments have
entered production, the persistent checkpointer has emerged as both a critical operational
surface (state survives crashes, can be replayed, can be inspected) and a critical attack
surface (any agent able to write state can poison every downstream consumer).
2.2. Threats to Multi-Agent Privacy
Indirect prompt injection (IPI) [5,6] extends from a single tool boundary to the multi-
agent setting, multiplying the attack surface; systematic benchmarks now quantify the
inter-agent component, with MAGPIE [7] measuring substantial inter-agent contextual-
privacy leakage and AgentLeak [8] further finding that inter-agent leakage substantially
exceeds the model-output channel (the leak-rate figures are given in Section 1). The Kong
et al. survey [17] documents that single-agent defenses often fail to transfer to multi-agent
settings (and sometimes worsen attack-success rates) because the inter-agent message
boundary introduces a new trust transition they were never designed to mediate.
Two further observations shape our methodology. First, because several agent bench-
marks can be saturated without genuinely solving the underlying task [ 18], we adopt
a leakage-based metric rather than a task-completion one: our principal benchmark is
MAGPIE’s contextual-privacy probe [7], scored by deterministic leakage detectors, with
AgentLeak’s verbatim inter-agent metric [ 8] retained as a cross-anchor. Second, Con-
fAIde [19] shows that LLMs fail to apply context-appropriate privacy norms even when
they can name those norms, motivating approaches that move privacy enforcement off the
LLM and onto a structural mechanism.

A 2025–2026 survey (TRiSM [13]) identifies insecure inter-LLM communication as the
central unsolved threat: no end-to-end framework yet binds trust primitives at the agent
layer. Across these defenses, the state-merge layer under an adversarial peer-agent threat
model is not gated by any cryptographic capability mechanism.
Each occupied locus leaves the state-merge cell empty for a mechanistic rather than
incidental reason. Model-training defenses such as StruQ [ 20] harden a model against
adversarial input, but an adversarial peer is a legitimately authorized writer rather than
malformed input, so input hardening cannot bind read access to a persisted field. Prompt-
and context-layer defenses (AirGapAgent [ 21], Spotlighting [ 22], PrivacyChecker [ 23],
PromptArmor [24]) act on what one agent is told or shown and rely on the model honoring
that instruction, which ConfAIde [ 19] shows it does not do reliably; they never inspect
the merge write itself. Tool- and action-layer defenses (Progent [25], agent firewalls [26])
constrain external tool calls, but an inter-agent disclosure travels through the shared state,
not a tool boundary. Planner- and orchestrator-layer defenses govern plan steps or iso-
late whole applications above the shared store: ACE [ 27] and IsolateGPT [ 29] operate
at a granularity coarser than the per-field merge, while CaMeL [ 28] assigns per-value
capabilities with allowed-reader sets inside a custom Python interpreter during plan execu-
tion, fine-grained but bound to in-process planner values rather than cryptographically
to persisted state fields at the reducer. Channel- and session-layer defenses (SAGA [ 30],
and the offline-verifiable agent-to-agent messaging of Alshammari et al. [ 33]) authenti-
cate who communicates with whom and that a message is intact, but an authenticated
channel still delivers the private field to an authorized peer. Payload-encryption defenses
(PrivacyAsst [31], AgentCrypt [32]) protect a payload against an outside observer, yet the
peer recipient holds the key and reads the plaintext, so encryption carries no per-field
read-access rule. Each upper-layer defense therefore either delegates the disclosure de-
cision to the LLM or secures a different property (input robustness, channel authenticity,
payload confidentiality); none binds an unforgeable, cryptographically-verifiable per-field
read-access capability with tamper-evident provenance at the reducer where the merge
executes; under an adversarial peer-agent threat model, this is the gap CapChain fills.
2.4. Capability-Based Security Foundations
CapChain imports a half-century-old operating-system tradition. Lampson’s 1971
protection matrix [34] formalized access rights as (subject, object, operation) triples; the
capability-list dual (a per-subject list of unforgeable tokens authorizing operations on ob-
jects) proved foundational for secure operating-system design. KeyKOS [35] demonstrated
a capability-only kernel in production at Tymshare. The seL4 microkernel’s comprehen-
sive functional-correctness proof [36] established that capability-based access control is
amenable to formal verification at the kernel scale. Miller’s object-capability discipline [37]
https://doi.org/10.3390/app16157776

[PDF PAGE 6]
Appl. Sci. 2026, 16, 7776 6 of 31
consolidated the operational rule that delegations can only attenuate authority: the invari-
ant “only connectivity begets connectivity”.
CapChain transports this discipline to the LLM-state layer through HMAC capability
tokens: the narrow function produces a child token whose attribute set is a subset of the
parent’s, never a superset. We do not inherit Miller’s full E-language guarantees (e.g., vat
memory safety and eventual-send semantics); instead, we approximate unforgeability via
HMAC under the EUF-CMA assumption below, and acknowledge the residual gaps in
Section 7.
The cryptographic primitives are equally classical. The HMAC construction of Bel-
lare, Canetti, and Krawczyk [ 14], standardized as RFC 2104 [ 15], provides existential
unforgeability under chosen-message attack (EUF-CMA): the original analysis assumed
collision-resistance of the underlying hash, and Bellare’s later proof [38] weakens this to a
pseudorandom-function property on the compression function, accommodating the post-
2005 SHA-1 attack landscape. Merkle’s binary tree construction [16] permits authentication
of arbitrarily many leaves with a logarithmic-size proof per leaf; the IETF’s Certificate
Transparency log [39] standardizes an append-only Merkle log with the same O(log N)
inclusion-proof bound that ProvChain inherits. ProvChain composes the two: every state
transition appends a Merkle leaf signed under the issuing agent’s private key, yielding
O(log N) auditability while preserving classical EUF-CMA-equivalent unforgeability for
the chain root.
Recent work approaches the state-transition layer from adjacent directions: Maris [40]
enforces field-level privacy in LangGraph via a formally verified logical reference monitor,
but does not bind an unforgeable cryptographic capability at the reducer where inter-
agent reads are merged. The closest system-level peer is IsolateGPT [29], which enforces
process-level execution isolation between third-party LLM apps using a hub-and-spoke
architecture with an isolated memory plane under an honest-but-untrusted-apps threat
model. CapChain operates at a finer granularity (field-level capability gating within a single
shared StateGraph) and under an adversarial peer-agent threat model, with cryptographic
binding (HMAC) and audit-by-construction provenance (ProvChain) that IsolateGPT does
not provide. The contemporaneous CaMeL [28] is the closest peer in capability vocabulary;
Section 7.2 compares their layers, mechanisms, and threat models against CapChain row-
by-row.
3. Threat Model
We make the threat model concrete before describing the defense in Section 4, so that
subsequent claims can be evaluated against a fixed adversary.
3.1. System and Trust Model
We consider a multi-agent LLM system instantiated on a graph-structured orchestrator
(LangGraph [4] is our reference implementation; AutoGen [ 3] and similar frameworks
share the same abstraction). The system comprises:
• N agents {A1, . . ., AN}, each a stateless LLM call parameterized by a system prompt,
an allowed-tool set, and a view over the shared state;
• a shared, persistent StateGraph S whose schema declares per-field reducers that
merge incoming updates;
• a persistent checkpointer (SQLite, Postgres, or Redis) that serializes S across node
executions for resumability and replay;
• zero or more external tools T invoked by agents during their turns.
A subset of the fields in S is labeled private: the agent that originally wrote them
(the issuer) intends them to flow only to a declared set of authorized readers. “Private”
https://doi.org/10.3390/app16157776

[PDF PAGE 7]
Appl. Sci. 2026, 16, 7776 7 of 31
covers both regulatory categories (e.g., PHI, PCI) and contextual-integrity (CI) [19] norms
(e.g., a diagnosis disclosed to a triage agent should not flow to a research-coordination
agent). The threat model does not constrain vendor diversity across the N agents. Our
evaluation (Section 5.1) samples one MoE per major open-source vendor (Google, Zhipu,
Alibaba) to test the defense effect against diversity in the underlying LLM substrate. Vendor-
homogeneous and cross-vendor-collusion cohorts are left as sensitivity checks outside the
main evaluation.
The trusted computing base is small and explicit:
Trusted (i) the LangGraph runtime that schedules nodes and invokes the reducer; (ii) the
reducer implementation that merges incoming updates and that we modify to
become capability-aware (CAR, Section 4.3); (iii) the HMAC key used to issue
and verify capability tokens, held by an issuer process outside the agents’ exe-
cution context; (iv) the checkpointer’s underlying storage, modulo the integrity
attack surface witnessed by CVE-2025-67644 [10].
Untrusted (i) any token emitted by an agent’s LLM call, since indirect prompt injection [5,6]
and memory-poisoning [41,42] can flip an otherwise-honest agent into emit-
ting attacker-controlled output; (ii) all tool inputs and outputs, since fetched
documents and third-party APIs may be adversary-controlled; (iii) the con-
tents of the shared state S at read time, since previous nodes may have written
attacker-influenced values.
This locates trust in the smallest set of components an operator can actually audit,
and treats every byte produced by an LLM or fetched by a tool as adversarial input to
the reducer.
The persistence layer deserves a precise boundary, since the motivating CVE-2025-
67644 [10] targets exactly this layer. The checkpointer’s storage is trusted for integrity
only modulo that attack surface; we state what CapChain does and does not provide if the
assumption fails. First, integrity violations are detected rather than prevented: an attacker
who tampers with stored state cannot produce a ProvChain entry that verifies, since entries
are signed and Merkle-anchored (Section 4.2), so a modified or injected field surfaces at the
next CAR verification as a provenance mismatch; CapChain does not block the write; it
makes it non-repudiably visible. Second, confidentiality at rest is out of scope: CapChain
gates inter-agent reads at merge time and does not encrypt fields at rest, so an attacker
with direct read access to a compromised store sees plaintext private fields, for which
payload-level encryption such as AgentCrypt [32] is complementary. Third, availability is
out of scope: an attacker able to delete or corrupt the store can deny service or truncate the
provenance log, and CapChain provides detection of the resulting gap, not prevention.
3.2. Adversary Capabilities and Goals
We evaluate CapChain against three capability levels, in increasing strength.
The weakest and default level covers honest-but-curious agents. Every agent follows
the orchestration protocol (it reads only the state slice the framework provides, calls only its
allowed tools, and emits well-formed updates) but may attempt to infer private information
from the state slices it does see. This is the regime measured by MAGPIE [ 7] under the
implicit-instruction setting, where GPT-5 leaks 35.1% of private fields with no explicit
prompt injection or do-not-share annotation. The honest-but-curious level is the focus of
our principal empirical result.
The next level covers a compromised single agent. Exactly one agent Ac is under
adversarial control. Ac can emit arbitrary state-update payloads, attempt to forge or replay
provenance entries, and craft prompts that nudge downstream agents into disclosure.
This regime covers the inter-agent channel attacks cataloged by AgentLeak [8] (at 68.8%
https://doi.org/10.3390/app16157776

[PDF PAGE 8]
Appl. Sci. 2026, 16, 7776 8 of 31
inter-agent leakage). We require CapChain to prevent Ac from causing any downstream
agent to receive a field outside the receiving node’s declared accepted-purpose set; this is a
design-level target argued in Sections 4.1 and 4.2, not an empirically measured outcome.
The strongest level covers a collusive minority. A strict minority of agents
{Ac1, . . ., Ack } with k < N/2 are jointly compromised and may coordinate their writes to
defeat the defense. This regime models a worst-case multi-vendor deployment in which a
minority of the agent fleet is simultaneously subverted. The authentication and provenance
gates hold under colluding-minority adversaries by the EUF-CMA argument of Section 4.1
(argued, not empirically measured). The attribute–purpose gate enforces contextual ap-
propriateness up to and including the compromised-single-agent level, but not under a
colluding minority.
These levels map onto Table 1: the compromised-single-agent and colluding-minority
levels are its compromised-single-agent and adversarial-peer columns, where prior state-
merge defenses are absent. The honest-but-curious level is milder than either and is the
realistic privacy-leak baseline the state-merge layer must handle first; it is the regime our
empirical study (Section 6) exercises, while CapChain’s cryptographic primitives extend
the guarantee to the harder columns at the design level.
For every capability level above, we consider three concrete attacker goals against
which we measure CapChain:
1. Privacy leakage: cause an unauthorized agent Au to observe a private field issued for
some A ̸= Au. Measured by the inter-agent leak rate (LR) (Section 6).
2. State poisoning: write a field that appears to originate from a trusted issuer when it
does not, causing downstream agents to act on attacker-controlled values. Would be
measured by provenance-verification failure rate on synthetic forge-attempt traces
(compromised-agent and colluding-minority adversaries are treated at the design
level only; see the security arguments in Sections 4.1 and 4.2).
3. Audit evasion: cause a leakage or poisoning event that is not recorded in the prove-
nance log, defeating post hoc forensics. Would be measured by reconciliation between
observed inter-agent traffic and audit log entries (addressed analytically in Section 4.2).
Empirical evaluation in this paper targets the honest-but-curious regime via MAG-
PIE’s contextual-integrity probes [7] (each scenario is a multi-agent negotiation in which
an agent’s private_preferences block is an inferable secret the LLM is incentivized to
disclose); because no published benchmark yet exercises an adversarial peer-agent state-
merge regime, compromised-agent and colluding-minority adversaries are addressed at
the design level only for empirical evaluation.
3.3. Out of Scope
Five attack classes are out of scope: model-level jailbreaks (orthogonal to the orchestra-
tor), side channels (constant-time crypto is an orthogonal direction), denial of service on the
runtime, supply-chain compromise of the LLM weights or Python runtime, and majority
collusion (k ≥ N/2, the standard Byzantine boundary, future work). Three further bound-
ary cases are noted explicitly to head off common questions. (a) Tool-argument hijacking
by injected content is in scope for the state-poisoning goal at the write-back boundary, but
out of scope at tool-invocation time. The tool-invocation layer is what Progent [25] targets.
(b) CapTok TTL clock-skew and cross-reboot replay are handled by an issuer-maintained
monotonic counter checked at every verify call. (c) Prompt collision and role-confusion at
the user input boundary are prompt-layer concerns, addressed by AirGapAgent [21] and
PromptArmor [24] rather than at the state-merge layer.

4.1. CapTok: HMAC Capability Token
Intuitively, a capability token (the CapTok stage of Figure 2) is an unforgeable permis-
sion slip: it names the one field an agent may touch, states what the agent may do with it
(read, forward, or aggregate), and carries a cryptographic seal so that no agent can alter the
slip or mint its own.
A capability token τ is a 7-tuple
τ = (rid, attrs, ttl, ops, hholder, τparent, µ) (1)
where rid is the resource identifier (the field path being authorized in the StateGraph,
e.g., patient.ssn); attrs is the attribute set tagging the field’s sensitivity class (e.g.,
{PHI, diagnosis, covered_entity}); ttl is the expiry epoch; ops is the permitted opera-
tion set ( ⊆ { read, forward, aggregate}); hholder is the hash of the public identity of the
bearing agent, binding the token to one specific agent so another cannot replay it; τparent is
https://doi.org/10.3390/app16157776

[PDF PAGE 10]
Appl. Sci. 2026, 16, 7776 10 of 31
the parent-token id (⊥ for issuer-direct tokens), linking a delegated token to the one it was
derived from and enabling attenuation: a child token may only drop permissions, never
add them; and
µ = HMAC-SHA256(kissuer, rid ∥ attrs ∥ ttl ∥ ops ∥ hholder ∥ τparent) (2)
is the message-authentication tag [15] (a keyed hash that only the holder of the secret key
kissuer can produce or verify), computed over the other six fields under that key, which is
held outside the agents’ execution context. Because µ covers all six fields, changing any
one of them invalidates the seal.
The token of Equation (1) supports three operations:
ISSUE (rid, attrs, ttl, ops, A) creates a fresh root token bound to agent A; this requires
possession of kissuer, so only the issuer process (a trusted runtime component, Section 3.1)
can mint tokens.
NARROW (τ, attrs ′, ttl′, ops′, A′) produces a child token τ′ with attrs ′ ⊆ attrs, ttl′ ≤ ttl,
ops′ ⊆ ops, bearer A′, and parent pointer τ. Narrow cannot widen; this is the attenuation
property of [37], transplanted to a LangGraph setting. The MAC is re-computed by the
issuer (callers submit a narrowing request; the issuer is the only entity that can mint µ′).
VERIFY (τ, rid⋆, op⋆, A⋆) returns ⊤ iff rid⋆ = rid, op⋆ ∈ ops, h(A⋆) = hholder, ttl > now(),
and the MAC reconstructs under kissuer. It is used by CAR to authorize the requested
operation op⋆ on the resource named by rid: both the sender’s forward right and each
recipient’sread right at the merge (Algorithm 1, Gate a and Gate c).
The MAC input in Equation (2) uses canonical serialization of the six fields, so no
two distinct assignments share a byte representation, defeating the “MAC over naive
concatenation” attack; the bearer’s long-lived Ed25519 key anchorshholder (see Section 4.2).
The MAC binds the token’s authority to the issuer’s secretkissuer; the formal security
argument follows.
Under EUF-CMA of HMAC-SHA256 [14,38], no probabilistic polynomial-time adver-
sary, including compromised-agent and colluding-minority adversaries, can produce a
forged token τ† ̸= τ that carries a valid MAC for the same (rid, ops) without possession of
kissuer. Two additional properties prevent the standard circumvention attacks:
Canonical encoding. The MAC input uses canonical serialization (JSON sort-keys
in the reference implementation, migrating to length-prefixed CBOR/dag-cbor in the
production design) of the six MAC-covered fields (all of τ except µ itself), so no two
distinct field assignments share a byte representation. This defeats the “MAC over naive
concatenation” boundary-reinterpretation attack, in which an adversary moves a delimiter
to re-parse the same byte string as a different field assignment with the same MAC.
No widening at the issuer. The issuer process accepts narrowing requests only after
verifying attrs ′ ⊆ attrs, ttl′ ≤ ttl, and ops′ ⊆ ops. An adversary that controls request
parameters cannot widen authority; the most they can do is request a strictly narrower
child token, which is the intended capability-attenuation semantics of [37].
Together, these obligations imply that the CapTok construction addresses the privacy-
leakage goal (Section 3.2).

4.2. ProvChain: Merkle-Anchored Provenance
Every state write is accompanied by a provenance entry πi =
(opi, h(datai), τid,i, prev_rooti, σi), where σi = Signskai
(opi ∥ h(datai) ∥ τid,i ∥ prev_rooti)
under the writing agent’s Ed25519 signing keyskai (the same long-lived key that anchors
hholder in CapTok (Section 4.1)). The chain is structured as a Merkle tree [16]: leaf ℓi = h(πi);
internal nodes are pairwise hashes; prev_rooti is the Merkle root of all entries written before
πi. The root after entry N thus binds every prior write.
For any field read in the StateGraph, CAR can produce an audit proof in O(log N)
hash evaluations consisting of the Merkle path from the relevant leaf ℓi to the current root.
This construction addresses the state-poisoning and audit-evasion goals; the formal
statements (forgery resistance, tamper detection, and replay prevention) follow.
Under EUF-CMA of Ed25519 (for the per-write signatures σi) and collision-resistance
of SHA-256 (for the Merkle hashes), the Merkle root rN after entry N is computationally
binding over the entry sequence (π1, . . . ,πN) (no distinct sequence yields the same root).
Forgery resistance. An adversary that cannot break Ed25519 EUF-CMA cannot present
a forged sequence (π′
1, . . ., π′
N) with π′
i ̸= πi for some i that hashes to the same root rN; the
only way to produce a valid path to rN is the one written by the legitimate signing agent.
Tamper detection. An adversary cannot mutate any historical πi (i < N) in place
without changing some ancestor hash, which an auditor walking the Merkle path from rN
to πi detects in O(log N) hash evaluations [16,39]. Together with forgery resistance, this
addresses the state-poisoning and audit-evasion goals.
Replay prevention. The provenance integrity gate of the Capability-Aware Reducer
requires prev_rooti to equal exactly the current root at commit time. Any replay submitted
after a subsequent write fails this predecessor check. CAR’s per-agent commit serialization
additionally eliminates the interleave window (a race condition) in which two writes could
attempt to claim the same predecessor root.

4.3. CAR: Capability-Aware Reducer
The reducer is the LangGraph state-transition primitive: every node’s output update
flows through a developer-defined reducer that merges incoming values into the persistent
StateGraph. CAR replaces that function with a three-gate decision procedure (Algorithm 1).
The HMAC authentication gate enforces authority on the writer: the sender holds a
token permitting the forward operation on the field. The provenance integrity gate enforces
integrity: the write is correctly chained, so any historical tampering surfaces immediately.
The attribute–purpose gate enforces read access subject to contextual appropriateness [19]: a
field reaches a receiving node only if its attribute set matches that node’s declared purpose,
so even an authorized write whose attributes do not match (e.g., a diagnosis-tagged
value bound for a payment-processing node) is withheld from that reader. Concretely,
each node declares accepted_purposes ⊆ Attrs at schema definition (for instance, a triage
node may declare {triage, coverage_eligibility, public}); the gate authorizes a read iff
attrs (τ) ∩ accepted_purposes ̸= ∅. This read decision is enforced cryptographically rather
than by a mutable list: the issuer mints a read-scoped CapTok (ops = {read}, bound to the
recipient’s identityhholder) to each node the policy authorizes, and CAR admits the field
to a recipient only if that recipient presents a read capability that VERIFY s (Section 4.1).
A recipient outside the policy holds no such token and cannot read the field even if an
attacker tampers with the stored reader list, since the unforgeable read capability, not the
list, gates the merge; this is the per-field read-access binding the abstract claims. Shareable
fields carry purpose tags (e.g., public, negotiation) drawn from the same alphabet, so a
node whose accepted set includes one of them holds a read capability and is admitted; a
sensitivity-only field such as {PHI, safety_event} matches no permissive node’s accepted
set, so no read capability is minted for those nodes and the field is redacted for them.
Failure paths never silently drop: every rejection produces an audit-log entry naming the
failed gate, so downstream forensics can reconstruct the attack trace.
A concrete walk-through anchors these three gates against the MAGPIE
clinical_trials_2 scenario. Clinical-operations agent A1 (“David Chen”) holds
a CapTok τ over the private field undisclosed_adverse_events (the raw primate-
toxicology safety data he is NDA-bound to withhold), bearing the attribute set {PHI,
safety_event, covered_entity} ; the receiving Research-Coordination agent A2 declares
its accepted purposes {study_design, public} at schema-definition time. Figure 3 shows
the three artifacts that flow through CAR on a single write attempt: the CapTok token
A1 presents, the ProvChain entry CAR writes, and the audit-event emitted when the
attribute–purpose gate rejects.

4.5. Composition and the OWASP Agentic Top 10 Mapping
By construction, a CAR-registered LangGraph deployment makes CAR the only
code path through which a state update reaches persistent storage, so the three-gate
guarantees hold for the deployment as a whole (the attribute–purpose gate’s contextual-
appropriateness guarantee holding up to the compromised-single-agent level, subject to
the colluding-minority caveat of Section 3.2). This complete-mediation property (every
state write is checked) holds because LangGraph routes every state update through the
registered reducer (CAR is registered on every state channel), and the checkpointer (trusted
per Section 3) accepts writes only from that reducer, leaving no bypass channel. The present
https://doi.org/10.3390/app16157776

[PDF PAGE 14]
Appl. Sci. 2026, 16, 7776 14 of 31
prototype (Section 4.4) exercises the attribute–purpose gate at the message boundary; this
LangGraph-native no-bypass property is argued, not empirically measured. CapTok with
the authentication gate addresses privacy leakage, mapped to OWASP Agentic Top 10 (2026)
risk ASI07 (Insecure Inter-Agent Communication) [8,11]; ProvChain with the provenance
integrity gate addresses state poisoning and audit evasion, mapped to ASI06 (Memory and
Context Poisoning) [11,41,42]; the attribute–purpose gate adds defense-in-depth for con-
textual appropriateness. The remaining eight OWASP categories (ASI01–05, ASI08–10) are
orthogonal to the inter-agent channel (e.g., ASI01 prompt injection at the user boundary) or
covered by complementary defenses CapChain does not subsume (e.g., ASI09 unbounded
tool use, overlapping with Progent [25]).

5.2. Benchmark Selection and Justification
The evaluation uses two complementary benchmarks rather than a single saturated
source, in deliberate response to the Berkeley RDI finding [18] that several popular agent
benchmarks can be saturated without genuinely solving the underlying task.
MAGPIE (204 scenarios) [ 7] is the principal contextual privacy benchmark. MAG-
PIE does not itself rank scenarios by severity; we therefore apply a structural composite
ranking that operationalizes the intuition that observable inter-agent leak rate scales with
(disclosure pressure) × (information richness) × (inter-agent channel count). Each scenario
receives a composite score S1 · S2 · N, where S1 is the sum of |penalty| values across all
private_preferences items in MAGPIE’s own scenario schema (the per-field disclosure
https://doi.org/10.3390/app16157776

[PDF PAGE 16]
Appl. Sci. 2026, 16, 7776 16 of 31
cost the agent must weigh), S2 is the count of distinct private-field identifiers across all
agents (the surface area for leak events), and N is the agent count (a proxy for the N(N − 1)
directed inter-agent channels). MAGPIE annotates disclosure penalties on only a minority
of its scenarios, so S1, and hence the multiplicative composite, is strictly positive for the
seven penalty-bearing scenarios and zero for the remainder.
We accordingly evaluate a stratified pool of 25 scenarios. Seven are the penalty-
annotated high-severity scenarios and the composite ranks. The remaining eighteen are
drawn from the un-penalized majority, selected by the S2 information-richness tie-break, to
broaden coverage beyond the few penalty-bearing scenarios. The high-severity stratum
concentrates the disclosure-cost signal CapChain targets, while the coverage stratum guards
external validity against over-fitting to a few high-stakes scenarios.
The scoring is deterministic and uses only MAGPIE-native metadata; no LLM-based
judgment enters scenario selection. MAGPIE’s leakage signal (GPT-5 leaks 35.1% under
the implicit-instruction regime; Gemini 2.5 Pro leaks 50.7% under the explicit-instruction
regime) is the principal motivation for CapChain’s structural enforcement.
Baseline MAGPIE traces are produced by MAGPIE’s published source (upstream
commit e1e01b7) via a thin wrapper that does not modify the upstream agent state ma-
chine, prompt construction, dispatcher, or termination logic. The wrapper adds two things.
First, it adds an Ollama branch at the upstream agent’s LLM-call site, so our open-source
MoE suite can drive the same simulation MAGPIE drove with Gemini-2.5-Pro and GPT-5.
Second, it adds CLI flags forcing the paper-reported settings:temperature=0.0 (overriding
upstream’s source-code default of0.7, which contradicts the temperature 0 stated in the
MAGPIE paper), max_rounds=10 (matching the MAGPIE paper), and seed=42. Every re-
ported number traces back to a fully-pinned configuration via the wrapper’s per-condition
manifest. Using the MAGPIE source rather than a LangGraph re-implementation avoids
a framework-choice confound on top of the open-source-MoE vs frontier-API substrate
confound; cross-framework validation on AutoGen and CrewAI is planned (Section 7).
MAGPIE’s contextual-integrity scenarios do not compromise agents; agents follow
the orchestration protocol and may only infer private fields from the state slices they
legitimately see. The empirical results in Section 6 therefore evaluate CapChain against
the honest-but-curious adversary capability level. Empirical claims about compromised-
agent and colluding-minority adversaries are addressed at the design level only (via
the EUF-CMA-secure CapTok issuance and the chained ProvChain signature path of
Sections 4.1 and 4.2).
Following MAGPIE [7], we evaluate two instruction modes. Explicit Instruction is
upstream’s default behavior. Each agent’s system prompt namesprivate_preferences as
“DO NOT SHARE THESE” and dumps the JSON, including per-item penalty and reason
fields. This matches MAGPIE’s “direct system prompt specifying which private items
must not be disclosed, along with penalties for disclosure”. Implicit Instruction recon-
structs the “without any indication of which information was sensitive” condition from
the MAGPIE paper. The public/private dict-label split, the “DO NOT SHARE” annotation,
and the penalty/reason fields are all stripped; the agent is left with one undifferentiated
preferences block from which sensitivity must be inferred by role, persona, and context.
Since upstream’s public source ships only the Explicit template, the Implicit recon-
struction is a single-site prompt rewrite at the upstream LLM-call site. Each scenario is run
under both instruction modes when the experimental budget permits; Section 6 reports
per-model results for both with the per-paper Implicit-vs-Explicit differential as a secondary
finding.

5.3. Scoring Protocol: Deterministic Detectors (Verbatim and Salient)
A single regex matcher has known recall limits on paraphrased disclosures; an offline
keyword detector trades some of that recall for full reproducibility and zero per-message
cost. We therefore apply two deterministic tiers per trace, a Verbatim Detector (V , defined
below) and a Salient keyword Detector (S, defined below), and report per-tier leak rates
separately. The headline statistic is the Salient-tier firing rate (Section 6.2).
The Verbatim Detector applies three composed sub-detectors per call: a canary-
substring matcher (AgentLeak Tier 1, vendored from [ 8], commit 6729179d); a regex
matcher for SSN, credit-card, and CANARY_* tokens (AgentLeak Tier 2) gated by the sce-
nario’s private-value set; and a sliding-window matcher that fires when≥ 6 consecutive
content words of any private field appear verbatim. The canary and regex matchers fire
densely on AgentLeak’s canary-embedded benchmark (where the published 68.8% inter-
agent baseline is measured). On MAGPIE’s free-form narrative private fields, the canary
matcher is by construction silent, and the sliding-window matcher is the principal detector.
A zero LRverb on a paraphrase-prone dataset does not imply that there is no leak, only
that the leak was not a verbatim copy; the paraphrase channel is the Salient Detector’s job
(defined below).
We report per-tier leak rates LRV and LRS separately for every condition; the headline
is the Salient-tier firing rate LRS. The two tiers are complementary and non-redundant: the
Verbatim tier is the deterministic floor (a reproducibility anchor and the cross-benchmark
tie to AgentLeak’s published rate) and the Salient tier is the deterministic paraphrase-aware
mid-tier whose auto-keyword extraction is one of this paper’s methodological contributions.
Downstream-efficacy measurement requires live-runtime paired runs; the scope discussion
in Section 7.4 covers this.
The Verbatim Detector and the auto-extracted Salient keyword tier (S, defined imme-
diately below) are both applied to the full trace of every condition, independently; neither
prefilters the other. Both run on every inter-agent message, so the Salient firing count is a
property of the whole trace rather than of a Verbatim-fired condition.
Salient keywords are extracted offline from each MAGPIE scenario’s
private_preferences block. For each private field of each agent, a Stanza named-
entity-recognition (NER) pass extracts up to three candidates from a curated entity-type set:
PERSON entities matching agent names are dropped, while ORG, GPE, DATE, MONEY, PRODUCT,
EVENT, and similar types are retained. Per-scenario TF-IDF (term frequency–inverse
document frequency) over the same corpus then fills any remaining top-k slots (k = 5) with
the highest-weighted n-grams (n ∈ {1, 2, 3}). The combined per-field keyword set is frozen
as a keyword artifact together with the Stanza version and the accepted entity-type set, so
the keyword set can be reproduced bit-for-bit. The Salient Detector then fires whenever
an inter-agent message matches at least one proper-noun-NER keyword ( ORG, GPE, LOC,
PERSON, and similar types) from another agent’s set, or at least two keywords overall
from that set. This decouples the Salient tier from the byte-substring blindness of the
Verbatim Detector (Section 4.4) at the cost of an offline keyword artifact rather than an
LLM round-trip per message.
The reported redaction effect is measured by post hoc derivation: the would-have-been
CapChain trace is obtained by replaying CAR’s attribute–purpose gate against the recorded
vanilla conversation log, so the two variants share a byte-identical underlying conversation
https://doi.org/10.3390/app16157776

[PDF PAGE 18]
Appl. Sci. 2026, 16, 7776 18 of 31
and differ only in the attribute–purpose gate decisions. This makes the pairing structural
rather than empirical and sidesteps the GPU multi-head-attention nondeterminism that
would otherwise break a live-paired comparison at production N. The recorded conver-
sation is replayed unchanged, so the redacted field never re-enters a downstream agent’s
context window. The measurement therefore counts attribute–purpose gate decisions on a
fixed transcript. It does not model how a recipient would behave had it seen the redacted
message. The scope of what this measurement does and does not capture is discussed in
Section 7.4.
The Verbatim tier is a reproducibility floor: anyone re-running the Verbatim scorer
on a saved trace gets the same integer, with no LLM-induced drift across model snapshot
versions. The Verbatim tier also serves as the Section 3 motivational anchor (a zero LR V
across the suite × MAGPIE confirms that string-match defenses cannot register the para-
phrase channel) and, citing AgentLeak’s own paper, as the cross-benchmark anchor (the
same canary-and-regex matcher reports AgentLeak’s published inter-agent leak rate on
its canary-embedded scenarios [ 8]). The Salient tier is the deterministic mid-tier: the
auto-keyword extraction is one of this paper’s methodological contributions and serves
operational deployments that cannot afford a per-message LLM call.
5.4. Benchmark Sanitization Audit
In response to the 2026-04 Berkeley RDI BenchJack findings [18] that several popular
agent benchmarks can be saturated without solving, we performed an explicit four-step
sanitization audit on both benchmarks used above:
1. Scoring-code review. Each benchmark’s scoring script was read end-to-end. No
unsanitized eval(), exec(), or shell-out paths were found in MAGPIE or AgentLeak
(verified by static grep over both scoring scripts).
2. Reference-answer leak check. For each scenario, the agent-visible context was diffed
against the gold answer. No scenario in the two subsets we use has the gold answer
embedded in any agent’s system prompt or initial state (verified by content diff).
3. Seed determinism. Each run’s manifest records the seed for scenario sub-sampling
and for every LLM call; re-running a manifest from scratch reproduces identical
trace hashes.
4. Explicit Berkeley RDI acknowledgment. We cite the BenchJack work [18] to situate
the audit as a deliberate methodological response to it rather than an afterthought.

condition quantity rather than a paired difference, we characterize its uncertainty and
structure with cluster-bootstrap 95% confidence intervals (resampling the 150 conditions

Kruskal–Wallis test across models, a Wilcoxon signed-rank test across instruction modes
(paired within scenario–model), and Cohen’sh effect sizes, rather than a paired sign test
or a multiple-comparison correction on a vanilla-versus-CapChain delta that the post hoc
design makes degenerate.

6.1. Verbatim Detector Floor and Cross-Bench Anchor
Across the suite on all evaluated scenarios, the Verbatim Detector (V) returnsLRV = 0
in every evaluation condition. A zero here does not mean that nothing sensitive was
exchanged; it means that when private information surfaced, it was paraphrased rather than
copied word-for-word, so a literal-string detector cannot see it. This is consistent with two
prior observations: (i) MAGPIE-style scenarios deliberately frame private fields as narrative-
style descriptions whose values are unlikely to appear as literal byte substrings in agent
dialogue (cf. AgentLeak’s per-channel decomposition reporting that inter-agent leakage
rises with paraphrase richness, ref. [ 8]); (ii) the vendored canary-and-regex matcher [ 8]
(commit 6729179d) was tuned for canary-bearing scenarios where the private value is a
fixed-format token (account number, social security ID, canary string), not a narrative
private preference. We retain V as the deterministic floor for two reasons: (a) it cross-
anchors our pipeline to AgentLeak’s published 68.8% inter-agent baseline on canary-
bearing scenarios; (b) it is fully deterministic, so re-scoring any saved trace yields an
identical result.
6.2. Salient Detector Deterministic Mid-Tier (Paraphrase-Aware)
Across the 150 recorded baseline traces in the analysis pool, the Salient-augmented
attribute–purpose gate configuration records 330 redact events out of 7070 total message-
processing events (one per inter-agent message the reducer processes) ( LRS = 4.67%;
cluster-bootstrap 95% confidence interval [3.51, 5.90]%, resampling the 150 conditions),
firing in 74 of 150 conditions (49%). Firing is concentrated rather than uniform across the
pool: the per-condition rate has a median of 0.00% and a standard deviation of7.80%, so the
aggregate is driven by a high-stakes subset rather than a uniform per-condition rate. The
substring-only configuration over the same pool records 150 redact events (LRS = 2.12%),
firing in 43 of 150 conditions; the Salient-augmented configuration thus records more
than double the substring-only redact count (330 vs. 150; Cohen’s h = 0.14, a negligible
difference in proportion terms because both rates are low), quantifying the byte-substring
blindness predicted in Section 4.4. The additional firings correspond to paraphrased
restatements the substring detector cannot represent; absent a measured false-positive rate
(Section 7.3), we read the differential as recall gained rather than precision proven (an
independent LLM-judge proxy estimates precision at 56.19%; Section 7.5), and adopt the
Salient-augmented configuration as the conservative default.
To read these statistics in practical terms, the cluster-bootstrap 95% confidence interval
is a precision statement on the headline rate: the gate’s firing rate on comparable traces is
estimated to lie within [3.51, 5.90]%, so the headline 4.67% carries this sampling uncertainty
rather than being an exact point value. The significance tests reported in Section 6.3 address

6.4. Truncation and Error-Row Handling Transparency
Empty and truncated responses are surfaced rather than silently scored as “no leak”.
The suite-wide think:false and num_predict=-1 settings eliminate the thinking-channel
silent-empty failure mode: across the 150-condition analysis pool, all model calls completed
normally, none were truncated, and none returned empty content.
6.5. Live-Runtime Feasibility Check
As a limited live-runtime feasibility check complementing the post hoc derivation, we
re-ran 18 evaluation conditions (3 scenarios × 3 models × 2 instruction modes) with the

Appl. Sci. 2026, 16, 7776 23 of 31
agents executing live and CAR’s attribute–purpose gate intercepting inter-agent messages
at runtime, so that a redacted field actually enters the downstream agent’s context window
rather than being replayed on a fixed transcript (Section 5.3). All 18 cells completed with
no rejected writes and no truncated turns. The mean wall-clock cost was 19.7 minutes per
cell (range 10.2 to 39.8), dominated by model inference; the three constant-time CAR gate
evaluations per write (HMAC-SHA256 verification, an O(log N) Merkle-path check, and a
set intersection) cost a combined 6.8 microseconds per state write in a CPU microbenchmark,
summing the three gates’ median latencies (HMAC-SHA256 verification 3.5, theO(log N)
Merkle-path check 3.3 at N = 1024, and the set intersection 0.04 microseconds), negligible
against the inference-dominated per-cell wall-clock above.
Run live, the Salient gate fires on 4.27% of inter-agent messages (36 of 844), close to
the post hoc headline of 4.67%, so the gate activates at a comparable aggregate rate when
the redaction genuinely propagates downstream. Per-condition redact counts match the
post hoc derivation exactly in only 8 of 18 conditions (44%); the majority therefore diverge
once redaction actually propagates downstream. The divergences are concentrated after
the first redaction in a conversation and run predominantly in the direction of fewer live
redactions than post hoc. A plausible explanation, which we cannot confirm without the
downstream-efficacy measurement deferred below, is that once the gate removes a private
field upstream, downstream agents no longer restate it, so the live conversation carries
less salient content for the gate to act on later, whereas the fixed post hoc transcript still
contains the original downstream text. The live run thus reproduces the post hoc firing
behavior up to the point where redaction begins to change the conversation.
This validation establishes feasibility, negligible runtime overhead, and a compa-
rable aggregate firing rate; it does not establish a residual-leakage figure. Because live
redaction changes the downstream conversation, and because GPU multi-head-attention
nondeterminism precludes a byte-identical paired run at production scale, a clean paired
downstream-efficacy measurement is not identifiable here. This is the same scope boundary
stated for the post hoc derivation in Section 7.4: the empirical contribution is a redaction-
decision rate, and this live feasibility check shows the aggregate rate is realized at runtime,
but with per-condition divergence in the majority of cells, it does not confirm the post hoc
per-condition pattern, nor quantify the leakage ultimately prevented.
7. Discussion
The empirical results support the design’s primary claim: CAR’s attribute–purpose
gate activates on the predicted lexical surface on every model in the suite, with a Salient-
tier firing rate of 4.67% across the open-source MoE evaluation suite (at vendor-varying
per-model rates; Section 6.3). This per-message firing rate is not directly comparable to
MAGPIE’s headline figures (GPT-5 35.1%, Gemini 2.5 Pro 50.7%) [ 7]: MAGPIE counts
disclosed private items as a fraction of the private items defined per scenario, whereas LRS
counts redaction decisions as a fraction of all inter-agent messages, so the denominators
differ. We cite those figures only to locate CapChain within the same benchmark family, not
as a head-to-head reduction. From a policy standpoint, the measurement fills a specific gap
identified by the OWASP Top 10 for Agentic Applications (ASI07) [11] and the NIST CAISI
Request for Information [12]: empirical evidence that a structural, non-prompt mechanism
can gate inter-agent state writes.
7.1. What Cryptography Buys: Limits, Deployment, and Cross-Domain Reach
CapChain demonstrates that the inter-agent privacy boundary in production Lang-
Graph applications can be enforced at the state-transition layer rather than at the prompt
layer. The three primitives together address the attacker goals of Section 3.2 without modi-
https://doi.org/10.3390/app16157776

[PDF PAGE 24]
Appl. Sci. 2026, 16, 7776 24 of 31
fying agent system prompts or retraining any model. However, structural enforcement is
not a substitute for behavioral defenses. CapChain does not prevent an LLM from being
instructed to disclose information it legitimately holds (model-level jailbreak, explicitly out
of scope per Section 3.3). It restricts what the agent can cause to be observed by other agents,
not what the agent itself can be made to emit. Practitioners deploying CapChain should
pair it with the prompt-layer defenses surveyed in Section 2.3 (StruQ [20], Spotlighting [22]),
treating CapChain as the floor and behavioral defenses as the ceiling.
The CapChain prototype is intentionally interface-compatible with LangGraph’s de-
fault reducer (Section 4.4). Migrating an existing production graph requires (i) declaring
the per-field sensitivity attributes once at schema definition, (ii) replacing the default re-
ducer with CAR, and (iii) running an issuer process holding kissuer. No agent prompts are
touched. The prototype runs against the standard SQLite, Postgres, and Redis LangGraph
checkpointers without modification.
CAR adds three constant-time gate evaluations per state write (HMAC-SHA256 verifi-
cation, Merkle-path verification at O(log N) over the provenance log, and a deterministic
attribute–purpose set intersection), which a CPU microbenchmark (median of 200,000 iter-
ations per gate on a commodity arm64 CPU) measures at a combined median of 6.8 mi-
croseconds (3.5, 3.3 at N = 1024, and 0.04 microseconds, respectively). Implemented as
a LangGraph custom reducer, the attribute–purpose gate adds 0.16 microseconds at the
reducer call, and a single-merge graph superstep completes in 165 microseconds, both
sub-millisecond. The dominant overhead is the database round-trip for the provenance
write, which is co-located with the existing checkpointer write and therefore does not add a
separate transaction. A full LangGraph-native multi-agent deployment and its end-to-end
wall-clock profile are deferred to future work.
The capability schema generalizes across regulatory regimes because attrs in
Section 4.1 is a free attribute set, not a domain-specific enum. The same three-gate CAR
mechanism shown in the walk-through in Figure 3 evaluates the same intersection test
on each regulatory domain; only the attribute alphabet changes. The encoding template
is mechanical: for any private field with a regulated content class (PHI/PCI/SOX/. . . ),
attach the corresponding regulatory tag to attrs; nodes whose static purpose declaration
is incompatible with that tag have the write rejected by the attribute–purpose gate. This
cross-domain property (one schema, multiple regulatory regimes) follows from capabilities
being symbolic rather than domain-specific; a full empirical cross-domain study (worked
HIPAA and PCI-DSS instantiations) is left to future work.

Several 2025–2026 works sharpen this boundary. Fides [43] tracks dynamic information
flow over a planner’s execution values to stop prompt-injection exfiltration; CapChain
instead binds a cryptographic capability to persisted state fields at the merge step, so its
guarantee is about which agent may read a field rather than taint on planner values. The
authenticated, offline-verifiable agent-to-agent messaging scheme of Alshammari et al. [33]
provides Merkle and signed-tree-head receipts for messages exchanged between agents;
this is the closest neighbor to ProvChain, but it attests message exchange rather than
the field-level read access that CAR enforces on shared state. Maris [ 40] is the closest in
setting: it enforces field-level privacy policies in LangGraph through a formally verified
MFOTL reference monitor that the runtime is trusted to execute, whereas CapChain binds
an unforgeable HMAC capability and tamper-evident provenance to each field, adding
non-repudiation and forgery- and replay-resistance under a compromised- or colluding-
peer adversary that a trusted logical monitor does not provide. Conseca [ 44] generates
per-purpose policies just-in-time at the tool boundary rather than binding a cryptographic
capability at the reducer. Several of these neighbors report strong end-to-end mitigation
against prompt injection or single-orchestrator adversaries (Fides completes AgentDojo
tasks with information-flow security guarantees against prompt injection); CapChain
instead measures the honest-but-curious contextual-privacy regime on MAGPIE, where
the disclosing peer is authorized, and attack-success-rate is not the operative metric, so a
like-for-like efficacy comparison is left to the live-runtime work of Sections 6.5 and 7.4.

7.3. Limitations, Scope, and Threats to Validity
We name limitations explicitly so future work can build on a stable baseline.
The evaluation covers 25 scenarios from the MAGPIE stratified high-stakes pool on
three open-source MoE LLMs (Section 5.1); this is a deliberately bounded slice of the
benchmark, so the scope of generalization from these results is correspondingly limited
and external validity is bounded, and the Salient firing is concentrated rather than uniform
across the pool: many conditions never fire and the aggregate is driven by a high-stakes
subset, so the reported rate should not be read as a uniform per-deployment rate. Frontier
closed-source APIs (Opus 4.7, GPT-5.5, Gemini 3.5 Pro) are out of scope to keep the empirical
cost defensible and to extend rather than duplicate MAGPIE’s frontier-API measurement.
All three suite models are Q4_K_M-quantized for VRAM compatibility; safety-tuning
behavior is known to degrade under heavy quantization, so the absolute LRS magnitudes
reported here may be higher than the same models would exhibit in FP16 deployments.
A second limit concerns the issuer key as the root of trust. CapChain’s cryptographic
guarantees assume the HMAC issuer process and its key kissuer are defended at the opera-
tional level (HSM-backed key storage, threshold cryptography for issuance, or equivalent).
Compromise of kissuer (whether by operator coercion, key exfiltration through a side-
channel, or supply-chain attack on the issuer binary) is equivalent to losing the root of trust
and invalidates all derived capabilities issued under that key. Such defenses are orthogonal
to CapChain’s contribution and are out of scope; we assume the operator follows standard
key-management practice (rotation, hardware-backed storage, separation of duties).
Three suite-level caveats apply to the reported per-model numbers:
1. Per-model differential is not attributed. The per-model redact-event counts are re-
ported for transparency only. The suite’s three models differ simultaneously in
vendor, training corpus, parameter scale, and response style; isolating the cause of
the per-model gap would require controlling for response length (verbosity) and the
detector’s lexical-surface overlap with each scenario’s private-field keywords, which
we leave to follow-up work, so the counts should not be read as a substrate-level
vulnerability rating.
2. Task-success rate is heterogeneous across the suite. TSR (consensus within
max_rounds=10) varies across models; per-model rates and the TSR-conditional
robustness check are in Section 6.3; TSR =0 conditions still emit private-field
utterances and enter the leak-rate denominator.
3. Multi-round emergence ceiling. The MAGPIE-reported round-2/3 leak-emergence
pattern was observed on frontier closed-source models. Whether MoE Q4_K_M
models compress leak emergence within the same window is itself a sensitivity we
have not validated. The high proposal:accept_proposal ratio under GLM-4.7-flash
suggests the round-10 cap may be hitting a behavioral rather than a leak ceiling for
that model.
The Salient-augmented attribute–purpose gate detector (Section 5.3) combines Stanza-
NER pre-boost with per-scenario TF-IDF top-k keyword pulls derived programmatically
from each MAGPIE scenario’sprivate_preferences block, not from human annotation.
Its false-positive rate against a human-rated reference remains unmeasured (we report
a session-level LLM-judge proxy estimate of ≤ 43.81% in Section 7.5). Recall against
paraphrased restatements depends on whether the paraphrase reuses a Salient token; re-
statements that share no Salient token are a known recall limit of the deterministic approach,
which we treat as the reproducible headline. The composite ranking S1 · S2 · N used in
Section 5.2 additionally multiplies by agent count N, biasing the selected pool toward
N ≥ 6 scenarios where the per-condition Salient leak rate is structurally lower (scenarios
with fewer agents show a structurally higher per-condition rate; the agent-count break-
https://doi.org/10.3390/app16157776

[PDF PAGE 27]

down is examined in follow-up work). Our reported aggregate LRS = 4.67% is therefore
best read as a lower bound on the rate at which CAR would gate, in deployments with
smaller, specialized agent pools. Five second-order limitations remain: collusive-minority
detection-vs-prevention (the authentication and provenance integrity gates prevent forgery;
the attribute–purpose gate only detects and logs colluding-minority violations); framework
portability beyond LangGraph; the synthetic-scenario and fixed-seed caveat; multi-round
emergence with truncation handling; and CAR cryptographic overhead. Promoting the
authentication and provenance gate reference implementation to a production LangGraph
reducer integration with a compromised-agent and colluding-minority structured-tool-call
adversarial benchmark is the natural next paper.
7.4. Scope: Redaction Decisions vs Downstream Efficacy
The reported leak rates measure detector-firing rate, not downstream defensive effi-
cacy. The post hoc derivation methodology (Section 5.3) means LRS measures how often
CAR decides to redact a message under the attribute–purpose gate rule, not how much
downstream agent-to-agent leakage CapChain prevents in a live deployment. The two are
distinct.
A live-runtime study would substitute the redacted message into the receiving agent’s
context window; this could either eliminate the downstream leak signal (the intended
outcome) or cause the receiving agent to re-derive the private field from surrounding con-
text (a residual signal the post hoc derivation cannot quantify). The reported LRS = 4.67%
should therefore be read as a lower bound on the events CAR would gate, not as an upper
bound on the residual leak rate after CapChain is deployed. Direct measurement requires
such a live-runtime study and is deferred to follow-up work.
7.5. Construct Validity
For construct validity, the leak rate metric (Section 5.3) treats any appearance of a
private field’s content in an unauthorized agent’s visible context as a leak, regardless
of whether the disclosure is actionable; a paraphrased leak that is not directly usable for
follow-on attack still counts. This is conservative; a more usage-aware metric would require
human raters per scenario. Cross-checking the Salient-fired events against two independent
LLM judges (Gemini-3.5-flash and Claude-Haiku-4.5, 331 field-level events; an event counts
as a confirmed leak if either judge marks it leaked, an automated proxy with a human-rated
per-message audit left to future work) estimates precision at no less than 56.19% (186 of
331 confirmed as genuine leaks). The complementary upper-bound false-positive rate of
43.81% is the expected cost of a recall-first deterministic detector: NER- and keyword-based
PII and leak detectors deliberately favor recall over precision, since for leak detection a
missed disclosure is worse than an over-redaction [45,46]; such over-redactions are typically
entity-name mentions that do not themselves disclose private content, as the proper-noun
fire in Figure 5 illustrates. It is the same recall-oriented stance behind reporting LRS as a
lower bound on gated events (Section 7.4) rather than a downstream-efficacy figure.
8. Conclusions
We presented CapChain, a defense-in-depth architecture that addresses the inter-
agent privacy gap in multi-agent LLM systems built on LangGraph and equivalent graph-
structured orchestrators. Three contributions together address a problem now elevated
by multiple independent authorities (OWASP Top 10 for Agentic Applications 2026 [11],
the NIST CAISI Request for Information [12], and the 2025 MIT AI Agent Index [9]) and
grounded in a real exploited vulnerability (CVE-2025-67644 at CVSS 7.8) [10]. Empirically
(Section 6), we report an empirical measurement of inter-agent contextual privacy on three
https://doi.org/10.3390/app16157776

[PDF PAGE 28]
Appl. Sci. 2026, 16, 7776 28 of 31
open-source mixture-of-experts LLMs spanning three vendors (Gemma 4-26B, GLM-4.7-
flash, Qwen 3.6-35B). The evaluation is scored using MAGPIE’s contextual-integrity probe,
with CAR enforcing LangGraph state-merge reducer semantics on the recorded traces.
This measurement is a redaction-decision rate (how often CAR’s attribute–purpose gate
fires on inter-agent messages) and should be read as a lower bound on gated events, not a
direct measure of leakage prevented in a live deployment (Section 7.4). This extends the
frontier-API measurement of MAGPIE [7] into the open-source MoE substrate. We do not
claim CapChain has been validated as an operational security solution; demonstrating
downstream leakage prevention in a live, end-to-end production deployment remains
future work (Sections 6.5 and 7.4). Analytically (Section 2.3), we characterized why policy-
based defenses (SAGA [30], ACE [27], Progent [25], AgentCrypt [32]) cannot fully close the
inter-agent channel: each operates at a layer either above the shared state (prompt, planner)
or below it (channel, payload), leaving the merge boundary unmonitored. Constructively
(Section 4), we contributed (i) the design of an HMAC capability token (CapTok), a Merkle-
anchored provenance log (ProvChain), and a three-gate capability-aware reducer (CAR)
with explicit mapping to OWASP ASI06 (Memory and Context Poisoning) and ASI07
(Insecure Inter-Agent Communication); and (ii) a reference implementation of CAR’s
attribute–purpose gate, exercised inside the experimental harness at the inter-agent message
boundary.
CapChain demonstrates that cryptographic primitives developed for process-level
capability systems (Lampson’s protection matrix [34], KeyKOS [35], and Miller’s object-
capability discipline [ 37]) transfer to a setting where the bearer is an LLM rather than
a process, by relocating enforcement to the state-transition layer that graph-structured
orchestrators expose. As multi-agent deployments move from prototype to regulated
production, we expect this structural layer to become the natural locus for inter-agent
privacy, integrity, and audit guarantees that prompt-level defenses cannot provide.
