Abstract
Tool-using AI agents often use credentials broader than a user’s current request. We present anintent-governed
tool-authorization layerthat derives a short-lived certificate from a trusted request, narrows the authorized tool manifest,
and checks proposed tool and payload effects before execution. It cannot exceed static policy; request confinement
also requires certificate fidelity and sound effect bounds. We evaluate it over OpenPort with endpoint tests, 176
runtime-backed synthetic tasks, real-model pilots, 306 end-to-end trials, and a 36-trial benchmark-shaped external
subset. In the deterministic comparison, reference certificates reduce the archived composite exposure-or-path indicator
from 1.0000 to 0. Across end-to-end model runs, the combined path records no completed unsafe executions; unsafe
accepted authority remains 0.0909–0.2727, entirely as non-executed drafts. Trace-backed normalization removes this
residual at substantial utility cost. The results support static-policy non-expansion and identify certificate precision as
the principal remaining bottleneck.
Keywords:AI agents, authorization, access control, least privilege, prompt injection.
I. INTRODUCTION
AI agents are moving from conversational assistance to operational action. A deployed agent can inspect records,
update state, export data, coordinate workflows, and act across application boundaries. In such settings, tool access
is no longer a convenience feature of a language model interface. It is an application security boundary.
The access-control question normally asked by an application gateway is credential-centric: does this token,
app, or integration have permission to call this endpoint? Credential-centric authorization is necessary. It supports
revocation, least privilege, tenant isolation, and accountability. But agentic tool use introduces a second question
that traditional API authorization rarely models:is the proposed tool call justified by what the user currently asked
the agent to do?
This distinction matters because the same credential can be legitimately broad while a particular user request
is narrow. An agent may have both read and export scopes because the organization approves those capabilities
for some workflows. Yet if the user asks “summarize recent records for this period,” exposing a bulk export tool
to the model is unnecessary and potentially dangerous. If the model later proposes an export because an external
document, retrieved note, or malicious tool description influenced it, credential-only authorization cannot distinguish
the overbroad effect from the user’s original summary request. Likewise, a model may construct a plausible update
payload that touches a different resource than the user named, or a delete call that exceeds the intended target set.
Recent security research demonstrates this failure mode. AgentDojo evaluates prompt-injection attacks and defenses
in tool-using agents [1]. InjecAgent studies indirect prompt injection in tool-integrated agents and categorizes attacks
into direct harm and data exfiltration [2]. ToolHijacker and ToolTweak show that tool descriptions and names can
bias or hijack tool selection [3], [4]. MCP-oriented work identifies tool poisoning, shadowing, and protocol-specific
semantic attacks [5]–[8]. These works converge on a practical conclusion: the model’s selected tool is insufficient
evidence of authorization.
Industry guidance reaches a similar conclusion. OW ASP lists prompt injection as the first 2025 LLM application risk
and recommends least privilege, human approval for high-risk actions, external-content segregation, and adversarial
testing [9], [10]. NIST’s Generative AI Profile recommends operational monitoring, assessment of embedded tools
and APIs, and deployment-like assurance criteria [11]. The 2025-06-18 Model Context Protocol (MCP) specification
provides transport and tool-discovery semantics, including authorization guidance and model-controlled tools [12],
[13]. Per-request authorization of a tool’s intended effect remains outside these mechanisms.
This paper proposes anintent-certificate authorization layerin front of the existing effect-control layer. It receives
the user’s request, derives an intent certificate, computes a session policy that can only narrow existing static
authorization, filters the tool manifest accordingly, and checks that each proposed tool call and payload remains

A. Relationship to OpenPort Protocol
The OpenPort Protocol paper establishes a governance substrate for agent tool access: authorization-dependent
discovery, scoped permissions, ABAC-like data policy constraints, draft-first writes, preflight impact hashing, optional
state-witness checks, idempotency, rate limits, and audit [14]. We treat that prior work as theeffect-control layer. It
determines whether a tool effect is permitted under static integration policy and risk-gated write semantics.
The intent-certificate layer supplies upstream request justification and composes with OpenPort Protocol:
user intent→dynamic least privilege
→filtered tools→governed effects.
The two layers address distinct decisions. OpenPort evaluates whether an effect is permitted by static integration
policy and risk controls; the intent layer evaluates whether the current request justifies that effect. Together they
combine request-level intent certificates with authoritative gateway enforcement.
B. Contributions
This paper makes five contributions.
1) Problem formulation.We define intent-tool mismatch as an access-control failure mode for AI agents: a
proposed tool call may be statically authorized yet not authorized by the user’s current expressed intent.
2) Formal model with explicit trust conditions.We define intent certificates, monotone session policy, intent-aware
manifests, consistency predicates, and least-privilege effect minimization. We separate unconditional static-policy
non-expansion from request-level confinement, which additionally requires a sound certificate and effect-bound
interpretation.
3) System design.We design an intent-certificate gateway that narrows OpenPort manifests and action execution
without trusting the model or classifier as final authority.
4)Implementation mapping.We map the intent layer onto an OpenPort-style governance substrate and evaluate
the resulting reference prototype.
5) Runtime-path evaluation.We provide deterministic policy checks, endpoint-level runtime tests, a 176-task
runtime-backed synthetic microbenchmark, a real-LLM classifier/planner pilot, an end-to-end LLM-in-the-loop
runtime benchmark over 34 synthetic tasks with 3 repeats per model, and a benchmark-shaped runtime pilot
over 12 adapted tasks and 3 models.
C. Intent Semantics
The authorization layer uses an operational definition of “intent” tied to enforceable request content rather than a
user’s unobservable mental state:
2

[PDF PAGE 3]
•Expressed intent: the user request as stated in trusted conversation input.
•Inferred intent: the classifier or parser’s interpretation of that request.
• Authorized intent: the portion of the inferred request that is still permitted after static OpenPort policy, scopes,
workspace guards, and risk policy are applied.
• Operational intent certificate: the bounded, auditable server-side record used by the authorization layer at
enforcement time.
The operational certificate therefore represents a bounded interpretation of the expressed request. It may narrow
static authority but never widen it.
II. BACKGROUND ANDMOTIVATION
A. Tool Use as an Access-Control Boundary
Tool-using agents mediate between natural language and application effects. In a conventional API client, the
caller is usually deterministic software written by the application developer or an integration partner. In an agentic
workflow, the immediate caller may be a planner driven by a language model, influenced by a conversation, untrusted
documents, tool outputs, memory, retrieved snippets, or tool metadata. The agent may select tools automatically and
may construct payloads that the user never directly inspected.
The MCP tools specification explicitly frames tools as model-controlled: models may discover and invoke tools
automatically based on context and user prompts [13]. That design is useful for interoperability, but it shifts security
burden to implementations. If a server exposes a tool list to a model, the server still needs to decide which tools
should be visible in the current context and which proposed calls should be accepted.
Traditional access control offers relevant foundations. Least privilege limits authority [15]. RBAC associates
permissions with roles [16]. ABAC uses attributes of subjects, objects, actions, and environments to decide access [17].
OAuth-style systems bind tokens and audiences, and MCP authorization guidance emphasizes validating tokens for
the intended resource server [12]. Usage control further supports obligations, environmental conditions, mutable
attributes, and continuing decisions over an ongoing use [18]; macaroon credentials support decentralized delegation
whose authority can be attenuated with contextual caveats [19]. These mechanisms can enforce a request bound
once it is represented. The intent layer addresses the preceding agent-specific question: how to derive a bounded
authorization envelope from the user’s current trusted request and apply it both to the model-visible tool surface and
to the proposed payload effect.
B. Why Static Scopes Are Not Enough
Static scopes describe what an integration may ever do, not what it should do for this request. Consider a tool set
with:
•resource.read, a read tool;
•resource.export, a high-risk export tool;
•resource.create, a write tool that creates a draft;
•resource.delete, a high-risk destructive tool.
An integration may legitimately receive all four scopes because an organization wants the agent to help with
multiple workflows. But a specific request such as “show records from the past period” does not justify export
or delete authority. A request such as “create an entry for yesterday” may justify a narrow create draft, but not
arbitrary updates. A request such as “delete the duplicate record” justifies a high-risk delete candidate only under
review and preflight constraints. Intent refines the static policy for the current session.
Scopes remain the upper bound, but they are insufficient as the sole authorization input for a probabilistic,
context-sensitive caller. Intent-governed authorization makes the following rule explicit:
Psession(u)⪯ P static(a),
where u is the user request, a is the integration app, and ⪯ means “no more permissive than.” User intent narrows
authority but never widens it.
C. Prompt Injection and Tool Selection
Prompt injection is a central motivation but not the only threat. OWASP describes direct and indirect prompt
injection, including attacks through websites, files, images, and other external content, and notes impacts such as
unauthorized function access and critical decision manipulation [10]. AgentDojo and InjecAgent show that agents
3

[PDF PAGE 4]
can be hijacked by untrusted tool outputs and external content [1], [2]. ToolHijacker, ToolTweak, MCPTox, and
MCP threat-modeling work show that tool metadata itself can become an attack surface [3]–[5], [7].
The intent-certificate layer constrains effects even when malicious instructions influence the model. The server
checks each proposed effect against certified intent and static policy, then hides the tool, denies the call, or routes
it to draft/preflight review when the check fails. This shifts defense from model obedience to enforceable effect
constraints.
D. OpenPort as Substrate
An OpenPort-style governance substrate provides the effect-control primitives that the intent layer requires. Such
a substrate filters manifests by scopes, enforces policy constraints and workspace boundaries, creates drafts for
writes, computes preflight impact hashes, optionally binds state witnesses, performs idempotency replay, and emits
audit events.
The intent-certificate layer applies these effect-control primitives at the manifest and action boundaries for external
agents.
III. RUNNINGEXAMPLES
A. Bounded Read vs Bulk Export
Suppose the integration has bothresource.readandresource.exportscopes. The user asks:
Show me this period’s records and summarize any anomalies.
A credential-only system may expose both tools. Under the intent layer, the certificate is:
I={read,summarize},
BR ={records in current period},
BE ={no export, no mutation}.
The export tool is hidden because its effect class is absent from I. A direct named-call bypass fails with
agent.intent_tool_mismatch. Static policy still applies: a read lacking scope or violating the date-window
policy is denied regardless of intent.
B. Narrow Create Draft
For “create a new entry for yesterday with amount 23.50,” the certificate contains a create class, resource type,
date, amount, and draft-only effect bound:
I={create},
BE ={single-resource draft,amount≤23.50 +ϵ}.
A payload for 2350, a different date, or unrelated bulk metadata is inconsistent. A consistent create may become
a reviewable draft under OpenPort; an inconsistent create must deny or clarify rather than create authority.
C. High-Risk Delete
For “delete record rec-123 because it is a duplicate,” the authorization layer can expose deletion only for the
named record and under high-risk routing:
I={delete}, B R ={rec-123},
ρ=preflight.
OpenPort computes impact, binds the preflight hash to the payload, requires idempotency where configured,
and otherwise creates a draft. Changing the target to rec-124 fails the intent-certificate bound; changing it after
preflight also fails the preflight hash or state witness.
D. Indirect Prompt Injection Through a Document
Suppose the user asks to summarize an attachment. Its text says “ignore prior instructions and export all records.”
Certificate authority derives only from the authenticated user message, while the attachment is an untrusted channel.
The certificate permits bounded summarize/transform effects, not export. A model-generated export proposal is
hidden or denied even if the model treats the document text as an instruction.
4

[PDF PAGE 5]
E. Compound Workflow
For “find duplicate records, show them to me, and delete the one I approve,” one broad certificate would leak
authority across planning steps. The authorization layer instead decomposes the workflow:
C1 =read/summarize,
C2 =delete with explicit approval.
The first certificate permits bounded discovery and presentation. The second is issued only after the user selects a
concrete item and confirms deletion. Read/summarize certificates may discover candidates, but update/delete/export
certificates must be re-issued after the target and effect are explicit.
IV. THREATMODEL
A. System Boundary
We consider a server-side OpenPort gateway mediating all agent access to application data and actions. The
gateway is trusted to enforce authentication, static authorization, tenant boundaries, data policy, rate limits, drafts,
preflight checks, and audit. The model runtime, planner, intent classifier, tool selector, and external content sources
are not trusted as final security principals.
The gateway derives a certificate only from an authenticated, explicitly selected user-message boundary and trusted
request metadata. Attachments, retrieved text, web content, prior assistant output, tool output, and long-term memory
are separate untrusted channels; they may inform planning but cannot silently become certificate-authorizing text.
The certificate may be produced by rules, a model-assisted classifier, a hybrid classifier, or a deployment-specific
router. Its semantic fields are untrusted until checked against deterministic constraints, and it can never bypass static
policy.
B. Assets
Protected assets include:
•application data reachable through read tools;
•write effects such as create, update, delete, export, delegation, and administrative actions;
•tenant and workspace boundaries;
•user intent records and session policy;
•audit trails and governance evidence;
•operational budget, rate-limit capacity, and review capacity.
C. Adversaries
We model the following adversaries and failure sources:
•Malicious user: submits a prompt that tries to obtain broader tool access than policy permits.
• External content attacker: embeds instructions in webpages, files, emails, resumes, retrieved documents, or tool
outputs.
• Tool metadata attacker: attempts to bias tool selection through malicious tool names, descriptions, or descriptors.
• Compromised or overbroad integration: holds credentials with more static scopes than needed for a specific
request.
• Benign model error: selects the wrong tool, constructs an overbroad payload, retries unsafely, or drifts across
turns.
• Certificate attacker: replays, swaps across actors/tenants, mutates, or supplies a certificate bound to stale policy
or tool semantics.
• Review-capacity attacker: creates plausible drafts or confirmation requests to exhaust reviewers or induce
approval fatigue.
•Adapter attacker: exploits a mismatch between declared and realized tool effects.
•Operator misconfiguration: grants broad scopes or weak auto-execute policy.

E. Out of Scope
The threat model assumes correct static policy, complete mediation, trusted-message separation, an uncompromised
gateway, and conservative adapter effect contracts. It excludes malicious server operators, dishonest domain adapters,
model alignment, direct database compromise, gateway private-key extraction, unrelated side channels, and attacks
outside tool authorization.
V. SYSTEMMODEL
A. Logical Components
Figure 1 shows the architecture. The intent-certificate layer is inserted before OpenPort’s existing action pipeline.
The components are:
•User request: a natural-language instruction, possibly with attachments or context.
•Intent gateway: derives an intent certificate from the trusted user request and request metadata.
•Session policy: a dynamic policy lease that can only narrow static integration policy.
•OpenPort manifest: a tool list filtered by static authorization and session policy.
•Agent planner: an untrusted model/planner that proposes tool calls.
•Consistency gate: checks that proposed tool, payload, and expected effects match the certificate.
• OpenPort action pipeline: existing effect-control layer for drafts, preflight, idempotency, state witnesses, and
audit.
6

[PDF PAGE 7]
B. Trust and Authority
The gateway is authoritative. The classifier may be wrong. The planner may be wrong. The model may be
manipulated. Tool metadata may be malicious. The intent layer therefore has two central trust rules:
1) An intent certificate may only reduce authority.
2) A proposed tool call must still pass static authorization and OpenPort effect-control checks.
These rules allow the authorization layer to use probabilistic components without making them trusted roots. A
high-confidence certificate can expose a narrower useful tool set. A low-confidence certificate cannot grant new
scopes; it can only force clarification, draft review, or denial.
Static authority is not user intent:Monotonicity over static policy is necessary but insufficient for request-level
authorization. A broad or malformed certificate can remain entirely inside an integration’s static scopes while
still exceeding what the user asked for. The intent-certificate layer therefore provides two different guarantees:
static-policy non-expansionfollows from authoritative conjunction with OpenPort policy, whereasexpressed-intent
confinementis conditional on certificate fidelity, conservative effect interpretation, and complete mediation. The
runtime study measures the practical gap between these guarantees as unsafe accepted authority.
C. Intent-Control Layer vs Effect-Control Layer
OpenPort Protocol already controls effects. It answers questions such as:
•Does the integration have the required scope?
•Is the resource collection, workspace, or query window allowed?
•Is this action high risk?
•Is preflight required and bound to the payload?
•Is an idempotency key required?
•Should the request create a draft instead of executing?
The intent-certificate layer controls request justification before effects. It asks:
•What action class did the user request?
•What resources and bounds did the user mention?
•Which tools are unnecessary for this request even though statically authorized?
•Does the proposed payload exceed the certified request?
•Should ambiguity reduce authority or require review?
The two layers remain separate so that request interpretation cannot bypass effect-level authorization.
VI. INTENT-CERTIFICATEAUTHORIZATIONDESIGN
A. Intent Certificates
An intent certificate is a server-issued policy assertion binding a trusted request message to an authorization-relevant
interpretation. It is not a natural-language summary, a PKI identity credential, or proof of the user’s latent mental
intent. It is a short-lived policy input with explicit classes, bounds, confidence, lifecycle state, and provenance.
A certificate contains:
•id: stable certificate identifier;
•requestHash: hash of canonicalized user request and selected trusted metadata;
•subjectBinding: actor, app, key, tenant/workspace, session, and trusted-message identifiers;
•versionBinding: canonicalization, static-policy, and tool-registry versions;
•intentClasses: action classes such as read, summarize, create, update, delete, export, admin, unknown;
•resourceBounds : resource collections, workspaces, query windows, record IDs, or object types named by
the user;
•effectBounds: maximum effect type, item count limits, mutation scope, or allowed action family;
•confidence: calibrated score or discrete confidence band;
•reviewMode: allow, draft, preflight, confirm, deny, or clarify;
•expiresAt: time or turn boundary after which the certificate cannot authorize new calls;
•issuedAt/revokedAt: lifecycle state used to prevent replay after revocation;
•classifierSource: rule, model, product flow, hybrid, or human;
•auditDigest: hash used for trace correlation.
The certificate should not contain raw secrets or unnecessary private data. If a request includes sensitive content,
the certificate stores bounded facts and hashes rather than full text.

C. Session Policy Narrowing
Given a certificate C, the gateway derives a session policy PC. This policy is ephemeral and bounded by the
static integration policyP A. It includes:
•allowed and denied intent classes;
•maximum risk tier;
•visible tool filters;
•required review mode;
•resource and date bounds;
•export limits;
•certificate expiry.
For example, a summary request may expose only read tools and transformation helpers. A create request may
expose one create tool and require draft review. A delete request may expose the delete tool only with preflight and
idempotency requirements inherited from OpenPort.
D. Manifest Filtering
In many tool-use systems, the model first sees all tools available to a credential and then chooses one. Intent-aware
manifest filtering reduces this surface before model selection. The filtered manifest is:
Visibleintent(a, u) ={t∈ T |t∈Visible OpenPort(a)
∧P C(u, t) = 1}.
The set VisibleOpenPort(a) is the static manifest produced by the OpenPort-style substrate under scopes and data
policy. The session predicateP C(u, t)can only remove tools. Therefore:
Visibleintent(a, u)⊆Visible OpenPort(a).
This property is stronger than prompting the model not to call certain tools. Hidden tools are not available for
ordinary selection, and unexpected attempts can be denied by the consistency gate.

E. Intent-Tool-Payload Consistency
Manifest filtering is insufficient by itself because a visible tool can still be called with an overbroad payload. The
intent-certificate layer therefore checks consistency:
Consistent(C, t, x, e) = 1,
where C is the certificate, t is the tool, x is the payload, and e is the predicted or preflighted effect. A call is
consistent only if:
1) tool class is allowed by the intent class;
2) payload resource identifiers are within certificate bounds;
3) query windows and item count limits do not exceed request bounds;
4) effect risk is compatible with review mode;
5) no denied class is present.
If consistency fails, the enforce profile denies the proposal or asks for clarification; it does not silently turn an
intent-inconsistent proposal into an accepted draft. A consistent create action may still be routed to a draft by the
substrate’s effect controls. This distinction matters empirically: a draft is not a completed domain effect, but it is
persistent accepted authority and therefore counts as unsafe acceptance when it is inconsistent with the reference
request.
F . Routing Outcomes
The authorization layer returns one of six routing outcomes:
R={deny,clarify,draft,
preflight,confirm,execute}.
These outcomes are not a total-order lattice. deny and clarify admit no authority path; draft, preflight,
and confirm create or preserve a governed path without a completed domain effect; only execute permits an
immediate effect. The certificate supplies a maximum execution mode, and the static substrate may route a consistent
proposal more conservatively. A high-risk or low-confidence proposal therefore cannot become execute, but a
review-routed proposal must still satisfy the request bounds before any draft or preflight artifact is accepted.
G. Confidence-Aware Policy
The intent classifier is explicitly not a trusted principal. Its output is a policy hint that may narrow authority, but
it cannot create authority that static OpenPort policy withheld. The authorization layer therefore treats confidence as
an input to fail-closed routing rather than as proof that an effect is safe.

The OpenPort-style governance substrate assumed by the intent-certificate layer provides the lower layer needed

idempotency, state witness validation, stable hashes, draft approval, and security controls.

D. Backward Compatibility
Backward compatibility is provided by endpoint and deployment-mode separation. A legacy or off endpoint
retains static OpenPort semantics. An intent-aware endpoint in enforce or conformance mode requires a
valid certificate: a missing, malformed, expired, revoked, cross-subject, or version-stale certificate yields a minimal
clarification manifest or denial. A supplied malformed certificate does not restore broad static behavior. shadow
mode records counterfactual decisions without enforcement and marks its responses as non-enforcing.

Long-running conversations create drift risk. A certificate should expire after a time interval, turn count, context
transition, or completed effect. The server can define:

If a certificate expires, the gateway can reclassify the latest trusted user request, ask for clarification, or force
draft review. For multi-step plans, per-step certificates are preferable to a single broad certificate.
F . Deployment Modes
The intent layer can be rolled out in stages:
•off: existing OpenPort behavior;
•shadow: compute certificates and audit decisions, but do not enforce;
• compatibility draft-only: low-confidence or legacy mismatches may become drafts and must be counted as
accepted authority;
•enforce: hide/deny/draft according to policy;
•conformance: fail tests if monotonicity or reason-code invariants break.
Shadow mode supports calibration. Security enforcement and its evaluation begin in enforce mode.

H. Runtime-Backed Microbenchmark
To connect the policy sketch to the implemented runtime, we run a runtime-backed microbenchmark.
The script uses Fastify HTTP injection against the OpenPort reference runtime. The suite contains 176 deterministic
instances generated from author-designed templates: 102 benign and 74 attack-or-ambiguous. It covers six intent
classes: read, summarize, create, update, delete, and export. It also covers seven attack or ambiguity categories: intent-
tool mismatch, payload expansion, indirect prompt injection, tool metadata poisoning, low confidence, compound
workflow, and resource underspecification. The benign set includes underspecified requests so that clarification and
review burden remain visible. For each instance, the runtime calls /intent, /manifest, and, when applicable,
/actions; it records endpoint outcomes, drafts, executions, manifest sizes, audit binding, and local diagnostic
latency.
The reported U ARc is a conservative composite: it flags an attack-or-ambiguous instance when an unjustified
high-risk tool remains visible or an inconsistent draft/execution path is accepted. Thus OpenPort-only can have

UAR used in the real-model study.
The study separates enforcement correctness from certificate-generation quality. The reference condition uses
author-specified certificates embedded in the synthetic task suite. Rule-based and hybrid rule+flow conditions are
deterministic local classifiers. Model-generated certificates are evaluated in the studies below. The reference condition
routes underspecified benign requests more conservatively, lowering GAR. Higher GAR in rule-based or hybrid
rows may therefore reflect less conservative routing rather than better access-control quality.
This check exercises endpoint wiring, certificate storage, manifest narrowing, action denial, draft creation, and
audit binding. The reference-certificate condition separates enforcement from certificate generation and uses a
deterministic planner to isolate the enforcement path from model behavior.

N. Evaluation Synthesis
The runtime-backed microbenchmark, scored LLM runtime benchmark, transfer-set coverage tables, and transfer-
subset runtime pilot support three conclusions.
First, in the external-subset runtime pilot, prompt injection, insufficient information, state dependency, and wrong-
scope / wrong-target trials all collapse into clarification or blocked no-effect paths rather than unsafe accepted
authority.
Second, the remaining residue is structurally concentrated rather than diffuse. Across both the larger scored runtime
benchmark and the smaller benchmark-shaped external subset, accepted-authority failures cluster in bounded-create
settings where certificates and payloads preserve the broad operation class but lose the exact amount, resource,
or effect contract needed for early rejection. Tool-poisoning rows only survive when they can masquerade as
create-compatible draft paths; amount-expansion rows survive when the gateway still sees a create-shaped proposal
but cannot prove the numeric bound is faithful enough.
Third, the empirical bottleneck is certificate canonicalization, resource/effect normalization, planner schema repair,
and stronger create-versus-destructive effect contracts. Bounded-create semantics remain the dominant open problem
once OpenPort effect controls and monotone narrowing are in place.
Finding 4: The remaining accepted-authority failures are narrow and classifiable.
The 40 accepted-authority cases across the 198 attack-or-ambiguous runtime trials all end as drafts without creating
an execution. They are reviewable authority paths that the current intent-certificate layer did not narrow away early
enough.
Of the 40 accepted-authority cases, 24 have empty resource and effect bounds in the emitted certificate, while
the remaining 16 are semantically weak but non-empty create-compatible certificates. Review-mode labels split
across allow (16), preflight (6), and draft (18), showing that the residual problem is not simply an incorrect
review bit. Stronger amount, resource, and effect normalization is needed to collapse these governed draft paths into
earlier denials or clarifications.

XIII. SECURITYANALYSIS
A. Invariant 1: Intent Cannot Widen Static Policy
The monotonicity invariant is:
PC ⪯P A.
If a tool is hidden by static OpenPort scopes, ABAC policy, workspace boundary, revocation, or rate limit, the
intent layer cannot reveal it. This protects against classifier compromise turning into privilege escalation.
28

[PDF PAGE 29]
B. Invariant 2: Low Confidence Fails Closed
If γ < γ min, the system must not treat the certificate as broad authority. It should expose minimal tools, request
clarification, or force draft/preflight.
C. Invariant 3: Payload Effects Must Be Bounded
Even if a tool class is allowed, the payload must stay within request bounds. A read request for “last week”
should not silently become a year-long export. A request to update one record should not become a bulk update.
D. Invariant 4: The Model Is Not a Principal
The model may suggest a tool call, but authorization is decided by the gateway. The gateway verifies scopes,
policy, certificate validity, consistency, preflight, and review requirements.
E. Invariant 5: Drafts Are Not Completed Domain Effects
Draft creation is persistent governance state, not a completed domain effect. It still represents accepted authority,
consumes reviewer capacity, and can become a social-engineering carrier. Therefore an intent-inconsistent proposal
must deny or clarify before draft creation; consistent high-risk proposals may be drafted with audit, a clear preview,
and bound review context.
F . Prompt Injection
Prompt injection can influence model reasoning, tool selection, payload generation, and certificate generation.
Unconditionally, the intent layer can prevent such influence from expanding authority beyond static policy. It confines
authority to the expressed request only when the certificate refines the trusted request envelope and adapter effect
bounds are sound. Under those conditions, an injected export instruction outside a summary envelope is hidden or
denied.
Attacks that alter details within an already authorized high-risk effect envelope require context provenance or
taint-aware manifests in addition to the intent-certificate layer.
G. Tool Metadata Poisoning
Tool metadata attacks try to make a model choose a malicious or irrelevant tool. Intent-aware filtering reduces the
effect of such attacks by limiting visible tools and checking selected tools against the certified request. However, if
poisoned metadata belongs to a tool that is both statically authorized and intent-compatible, the intent-certificate
layer alone may not detect semantic deception inside the tool implementation. Manifest signing, tool provenance,
sandboxing, and behavior monitoring remain necessary.
H. Effect Estimation and Conservative Failure
The consistency predicate depends on estimating or bounding tool effects. This is easy for simple read, create,
update, delete, and export actions with explicit resource IDs and item count limits. It is harder for tools with implicit
side effects, compound workflows, tool-provided summaries, or domain-specific semantics.
The intent-certificate layer therefore adopts a conservative failure rule:
¬Boundable(C, t, x,be)⇒Route intent ∈ {deny,clarify}.
Preflight may first be used to obtain a conservative bound. If the gateway still cannot bound the payload or
predicted effect against the certificate, the enforce profile admits neither execution nor a draft path; it denies or asks
for clarification. This prevents uncertainty from becoming persistent accepted authority.
I. Classifier Compromise
If the classifier is compromised, it might produce a broad certificate. Monotonicity still prevents scope expansion,
but it may fail to narrow authority. Mitigations include rule/model agreement, confidence thresholds, human review
for high-risk classes, certificate audit, and adversarial tests. Critical deployments should treat classifiers as untrusted
components and require deterministic policy constraints for high-risk effects.

[PDF PAGE 30]
J. Multi-Intent Tasks
Users often ask for compound tasks. The intent-certificate layer should avoid issuing one broad lease for the
entire conversation. Instead, it can decompose the request into per-step certificates:
C(u) ={C 1, . . . , Cn},
where each Ci authorizes one effect class and resource bound. If decomposition is uncertain, the gateway should
require clarification or draft review.
Operational rule:Read/summarize certificates may be used to discover candidate objects and present them
to the user. Update/delete/export certificates should be issued only after the user confirms the concrete target or
approved output scope. One broad certificate should not simultaneously cover search, ranking, and high-risk mutation
unless the mutation target is already explicit and bounded.
XIV. RELATEDWORK
A. Agent Security Benchmarks
AgentDojo, InjecAgent, AgentDyn, ToolSandbox, tau-bench, ToolEmu, and MCPAgentBench provide evaluation
settings for tool-using agents [1], [2], [20]–[24]. These benchmarks primarily measure robustness, task success, or
safety under adversarial context. Risk-knowledge experiments further show that a model’s ability to recognize risk
need not translate into safe action [25]. The intent layer is complementary: it defines a server-side mechanism that
can be evaluated using such tasks.
B. Prompt-Injection Defenses
StruQ separates prompt and data channels through structured queries and model training [26]. AgentSentry models
multi-turn indirect prompt injection as temporal causal takeover and purifies context [27]. AttriGuard is especially
close: it causally attributes a proposed action to trusted user input rather than untrusted observations [28]. Its
action-support signal can feed the downstream authority ceiling, manifest narrowing, payload/effect-bound check,
routing outcome, and audit lifecycle of an intent-certificate layer.
C. Tool Selection and MCP Security
ToolHijacker, ToolTweak, MCPTox, and MCP threat-modeling work show that tool names, descriptions, metadata,
and ecosystem composition can create security vulnerabilities [3]–[5], [7], [8]. These works motivate intent-aware
filtering. Even a perfectly authenticated and well-described tool should not be callable when the user’s request does
not justify its effect.
D. Agent Authorization and Access Control
Least privilege, RBAC, ABAC, and OAuth-style delegated authorization remain foundational [12], [15]–[17].
Usage control adds obligations, conditions, attribute mutation, and ongoing authorization [18]; macaroons make
delegated credentials attenuable through contextual caveats [19]. Security-automata work in turn characterizes the
safety policies that execution monitoring can enforce [29]. These mechanisms supply useful policy and enforcement
primitives, but do not themselves infer which authority a trusted natural-language request justifies or mediate an
untrusted planner at both discovery and action boundaries.
Recent agent-focused work extends OAuth/OIDC delegation with agent credentials and natural-language permission
translation, governs inter-agent communication with user-defined policies and cryptographic tokens, enforces
intent/context-aware OS policy for computer-use agents, or moves identity- and argument-level policy to an off-host
gateway [30]–[33]. The mechanism studied here is narrower in principal identity but finer in request lifecycle: it
derives a short-lived request envelope, intersects it with an existing gateway policy, filters the model-visible manifest,
and rechecks payload/effect bounds before distinguishing draft authority from execution.
Task Shield enforces task alignment against indirect prompt injection; Progent and MiniScope pursue least-privilege
tool authorization; CaMeL separates trusted control and untrusted data flows; Prompt Flow Integrity constrains
privilege-escalating prompt flows; and AgentSpec provides customizable runtime enforcement [34]–[39]. These
systems are the closest architectural comparators. The mechanism’s distinct unit is a server-issued, short-lived
request envelope that is intersected with an existing gateway policy both before planning (manifest filtering) and
after planning (payload/effect checking), with draft, preflight, confirmation, and execution modeled as different
accepted-authority outcomes. Decentralized information-flow control instead attaches principal-specific policies to
30

[PDF PAGE 31]
data propagation and controlled declassification [40]; it can isolate untrusted data inside an agent, while the intent
layer governs which external tool effects the planner may request. Information-flow isolation, privilege inference,
policy languages, and runtime monitors therefore remain complementary controls.
E. Purpose Limitation and Contextual Integrity
The intent layer is also related to purpose-based access control and contextual privacy. Purpose-based systems
restrict data use according to declared purposes rather than only subjects, objects, and operations. Foundational work
associates allowed and prohibited purposes with data and enforces them through purpose-aware labeling, conditional
roles, and query modification [41]; recent systems such as Data Guard apply purpose-aware masking in warehouse
settings, and purpose limitation has also been studied for data-in-transit systems [42], [43]. Contextual integrity
frames privacy as appropriate information flow within a social context, using parameters such as sender, recipient,
information type, and transmission principle [44], [45]. Recent assistant work operationalizes contextual integrity for
information-sharing and LLM delegation [46], [47].
The mechanism targets request-level purpose restriction for agent side effects. It turns the current user request
into a short-lived, auditable purpose-like certificate that narrows an already-authorized agent tool surface; a statically
authorized tool remains unavailable when the present request does not justify its effect. Unlike a declared-purpose
database policy, this certificate is operational evidence for a bounded action decision, not proof that every downstream
use of returned data satisfies a privacy purpose.
F . OpenPort Protocol
OpenPort Protocol provides the effect-control substrate for this paper [14]. It defines a governance-first gateway
with authorization-dependent discovery, scoped permissions, data policy constraints, draft-first writes, preflight, state
witness, idempotency, rate limits, and audit. The intent layer adds an upstream request envelope and explicitly
measures the residual authority that effect controls leave in drafts.
XV. CONCLUSION
AI-agent access control must evaluate both credential permission and whether the proposed call is justified by
the user’s current expressed intent. This paper proposed a server-side intent-certificate authorization model with
monotone session policy narrowing, intent-aware manifests, and consistency checks between user intent, tool choice,
payload, and expected effect. OpenPort provides the existing effect-control substrate: static authorization, policy
constraints, draft-first writes, preflight, state witnesses, idempotency, and audit. The intent-certificate layer performs
request-level authorization before those effects are reached.
The evidence supports an executable request-envelope mechanism and static-policy non-expansion, while exposing
a decisive limitation. In the real-model runtime study, the combined intent-layer and OpenPort path observes 0/198
completed unsafe effects but accepts 40/198 intent-inconsistent draft paths; strict benign completion is 0/108 and
36/108 benign trials produce governed artifacts. The 12-task transfer subset similarly observes 0/24 unsafe completed
effects and 5/24 unsafe accepted drafts. Exact certificate bounds and adapter effect contracts remain the principal
systems problem.
