## 四、第二阶段：设计安全的 Root/Payload 共享文件合同

优先采用职责分离方案。

建议区分：

**A. Payload 可读取的交接意图对象**

用于承载当前批次、交接请求及必要的状态引用。

**B. Root 私有的审查记录**

用于保存 Root 独立验证结果、退出观察和内部管理事实。

**C. 持久交接 ACK**

用于证明满足既定状态机要求的接收方确认及持久化结果。

这三个对象的权限合同必须分别定义。

Root 私有记录可以保持 root:root/0600。

Payload 必须读取的文件，应明确赋予 UID999 对应的读取权限。

可以评估：

- root:989/0640。
- 其他符合实际 UID/GID 与目录权限的最小授权方式。
- 独立的受控 Unix Domain Socket。
- Root 与 Payload 分离的命名空间。

选择以实际源码和原有信任边界为准。

**不能直接使用 0666、0777 或取消身份验证来解决权限错误。**

如果 Root 需要发布 Payload 可读取的对象，必须确保目标所有者、组和 mode 在发布前已经正确设置。

如果 Payload 需要修改意图，则应通过明确的受控请求接口完成，避免双方不受约束地覆盖同一文件。

### 4.1 原子文件发布

若继续使用文件方式，审查：

- 临时文件创建。
- O_CREAT/O_EXCL。
- O_NOFOLLOW。
- 目标目录权限。
- fchown/fchmod。
- 文件内容写入。
- fsync。
- rename。
- 父目录 fsync。
- 发布后的 stat。
- 路径替换及 TOCTOU。
- 错误后的清理。
- 重复发布与幂等。

同时核对实际 Linux 文件系统和 Python 接口的语义。

不能仅凭 rename 原子性宣称全部持久性和权限条件已经成立。

### 4.2 信任边界

Root 具有更高权限，因此必须检查：

1. Payload 是否能够伪造 Root 审查结果。
2. Payload 是否能够修改 Root 私有 ACK。
3. Payload 是否能够诱导 Root 覆盖任意路径。
4. Payload 是否能够通过符号链接进行路径替换。
5. Root 是否接受了未经核验的用户可写内容。
6. batch_id、boot_id、执行锁是否绑定。
7. 交接文件是否可能跨批次复用。
8. 文件权限失败是否仍能安全停止。

权限修复不得削弱原有的交接真实性。

## 五、第三阶段：修复 Root 等待循环

第二个独立问题：

Payload 已在 T0+20.928 秒退出，Root 最终延迟至约 T0+300 秒才完成。

必须定位 Root scheduler 的实际等待逻辑。

重点检查：

- ready 等待循环。
- CLOSED 状态读取。
- STOP_REQUEST 状态读取。
- waitpid/pidfd。
- socket 接收阻塞。
- 等待超时。
- 轮询间隔。
- 文件状态缓存。
- 事件通知。
- 任务取消。
- finally 清理流程。

### 5.1 停止状态优先级

建立明确的状态优先级。

当出现以下情况时：

- STOP_REQUEST 已确认。
- CLOSED 已确认。
- 当前批次进入终止状态。
- 必要交接失败。
- 接收方退出。
- 资源资格失败。

Root 应立即进入相应的停止处理流程。

必须定义停止与 ACK 并发时的顺序规则。

如果成功 ACK 发生在关闭之后，不得重新激活批次。

### 5.2 状态读取

避免在等待循环中长期复用旧状态快照。

根据实际实现选择：

- 每轮 fresh-read。
- 有限阻塞等待配合状态复查。
- 明确的事件通知。
- 可取消的等待操作。

任何等待方式都必须继续遵守当前批次 deadline。

不能引入无限等待。

### 5.3 异常与清理

检查：

- Root 收到 STOP_REQUEST 后停止创建新操作。
- 终止通知是否只发一次。
- 已有进程是否得到正确回收。
- 账和原始日志是否保留。
- 已确认 CLOSED 后无法恢复执行资格。
- Root 异常退出时外部停止机制是否仍生效。

应在合理的工程响应期限内完成停止处理，但具体延迟保证需要实际动态测试。

不得将尚未测量的停止响应时间写成已证明的硬界。

## 六、第四阶段：新增安全性质

本轮修复至少检查以下性质。

**IPC-1：AuthorizedRead**

当前有效 Payload 能够读取其合同要求的交接意图对象。

**IPC-2：RootIntegrity**

Payload 无权伪造或覆盖 Root 私有审查结果。

**IPC-3：AtomicPublication**

交接对象的发布具有明确的原子性和失败语义。

**IPC-4：NoPathSubstitution**

不允许通过符号链接或未授权路径替换改变发布目标。

**IPC-5：IdentityBinding**

所有交接对象绑定当前 batch_id、boot_id、身份和执行锁。

**IPC-6：NoFalseHandoff**

缺少真实 ACK 或 receiver 确认时不得宣告交接成功。

**IPC-7：StopDominance**

已确认的停止或关闭状态能够阻止继续发放执行资格。

**IPC-8：NoReactivation**

CLOSED 后的迟到消息不能重新激活旧批次。

**IPC-9：SingleClassification**

同一交接事件只能得到一个有效终态分类。

**IPC-10：BudgetPreservation**

权限修复和停止流程不得修改原预算及 deadline。

各性质必须对应实际源码中的检查点和未来验证证据。
