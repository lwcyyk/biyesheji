## 三、第一阶段：证明两个数量约束的实际冲突

对全部必需证据逐项分类。

建立以下表格：

| 字段 | 内容 |

| evidence_id | 唯一证据编号 |
| producer | 产生该证据的测试或服务 |
| source_path | 原始文件路径 |
| sha256 | 内容摘要 |
| size | 字节数 |
| required_by | 哪条安全性质要求它 |
| admin_required | 是否必须纳入行政证据 |
| native_required | 是否必须纳入Native ZIP |
| replay_required | 是否必须保留原始字节以供重放 |
| independently_verified | 是否已有独立检查 |
| equivalence_class | 是否存在可证明等价的冗余副本 |

\[
N_{\mathrm{native}}\ge313>257
\]

### 3.1 判断硬约束的语义

确定：

1. 256 限制来自哪份合同。
2. 257 限制来自哪个终态检查器。
3. 是否属于安全边界。
4. 是否属于内存防护。
5. 是否属于归档工作量限制。
6. 是否属于历史行政格式。
7. 是否必须每份原件对应一个独立文件或ZIP成员。
8. 是否允许经批准的无损证据表示。
9. 是否允许建立新的版本化上限。
10. 是否有其他依赖旧上限的检查器。

如果现行合同明确要求全部独立原件逐件保留，并要求每件单独占用成员，则应形成：

6. 不产生未受审的外部依赖。
7. 不影响 native seal 的安全语义。
8. 不突破资源和时间上限。

**禁止通过把312份原件隐藏在一个不受检验的压缩文件内来规避成员限制。**

## 七、第五阶段：检查MR测试与完整链的生命周期冲突

这是新增的必要审查。

如果MR原生异常关闭会使当前批次进入CLOSED，而完整链又要求同一批次继续运行F1/F4，必须确定这两个要求如何同时成立。

逐项检查：

1. MR异常关闭测试是否会关闭主批次。
2. 是否存在已获准的独立测试实例。
3. 该测试实例是否处于同一资源预算监督之下。
4. 是否能够实际执行systemd故障注入。
5. 故障是否影响主批次工作资格。
6. 测试完成后是否需要恢复已经CLOSED的对象。
7. 资格门要求的是当前批次原生证据还是允许独立批次证明。
8. 原有强制验证合同是否允许证据跨实例引用。

禁止：

- 关闭主批次后直接重新激活。
- 重置T0或预算。
- 将合成异常冒充原生异常。
- 将历史MR证据直接复用为当前批次PASS。
- 为了通过资格门跳过异常关闭测试。

如果无法在现有合同下兼容：

`MR_NATIVE_CLOSURE_LIFECYCLE_CONFLICT`

输出最小矛盾条件和必要的合同修订申请。

如需新增隔离实例或修改证据承认规则，必须先完成信任边界、预算计量、身份和停止语义分析，并取得明确授权。
