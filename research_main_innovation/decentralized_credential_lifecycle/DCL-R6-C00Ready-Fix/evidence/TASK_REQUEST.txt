## 四、第一阶段：独立重建 C00 的八项检查

这是本轮最高优先级。

直接阅读触发：

`BC_SERVICE_IDENTITY_OR_LIMITS`

的源码。

必须找出组成该聚合判断的全部八项真实条件。

不得根据错误名称猜测八项的具体内容。

为每一项建立：

| 字段 | 要求 |
|---|---|
| check_id | 唯一检查编号 |
| source | 实际源码函数及行号 |
| expected | 冻结执行合同规定的值 |
| observed | 实际读取值 |
| evidence_source | OS、systemd、cgroup 或原始日志 |
| read_time | 单调时间 |
| process_identity | PID、starttime、boot_id |
| state_phase | 读取时的启动阶段 |
| result | MATCH、MISMATCH、NOT_READY、READ_ERROR |
| error | 原始 errno 或错误说明 |

重点检查是否涉及：

- service 单位身份。
- MainPID。
- ActiveState/SubState。
- 当前进程 cgroup。
- UID/GID。
- RLIMIT_AS。
- 父 slice 的任务数限制。
- 其他实际冻结的资源属性。

上面仅为核查方向，最终采用源码中真实存在的八项条件。

### 4.1 从既有证据中定位失败字段

尽量利用 batch07 保存的：

- unit journal。
- 进程身份记录。
- cgroup 记录。
- Python 运行时记录。
- Root 启动状态。
- systemd 属性。
- 原始错误日志。

判断每项字段：

- 是否已被历史证据直接证明匹配。
- 是否已被历史证据直接证明失配。
- 是否仅存在间接证据。
- 是否完全缺少当时的实际值。

形成八项逐字段裁决。

如果原始证据无法定位真实失配字段，明确登记：

`C00_FAILED_FIELD_UNRESOLVED`

禁止用事后 systemd 默认值代替失败时刻的实际状态。

## 五、第二阶段：重建启动时序和状态依赖

建立实际事件关系：

`systemd 激活 → Launcher → Root → exec → Guard 入口 → C00 读取 → 资格判定`

结合源码确认实际执行顺序。

重点审查：

1. systemd 何时创建目标服务进程。
2. Type=exec 的实际就绪语义。
3. Manager 何时登记 MainPID。
4. Guard 何时读取单位状态。
5. cgroup 何时完成关联。
6. RLIMIT_AS 何时生效。
7. 父 slice 任务数限制何时生效。
8. 受信启动凭据何时认领。
9. C00 第一次资格读取发生在何处。
10. 是否存在启动状态更新与检查并发。

必须从当前 systemd 255 与实际源码建立判断。

### 5.1 重点排查循环等待关系

检查是否出现：

- Guard 等待 systemd READY。
- systemd 等待 Guard 完成某项动作才进入 READY。

如果双方存在互相依赖，应修订就绪定义，避免引入新的死锁。

尤其要区分：

- 目标进程已经成功 exec。
- 服务已经进入 manager 认可的启动状态。
- 资源限制已经生效。
- Guard 已取得业务运行资格。

这些是不同层次的事实。

## 七、第四阶段：设计有界启动就绪屏障

只有在证据和接口语义支持的条件下，才加入就绪等待。

不得把所有失败统一转化为“等待后重试”。

### 7.1 三种状态

定义：

**STARTING**

合法启动过程尚未完成，某些明确允许暂时不可用的字段正在建立。

**READY**

全部需要的身份和资源条件实际满足。

**FAILED**

出现稳定身份错误、资源限制错误、权限错误、执行锁失配或超出允许期限。

### 7.2 不同状态的处理

对于 STARTING：

- 保持业务执行资格关闭。
- 继续保留已建立的 T0 和 deadline。
- 使用明确的有界等待。
- 在每次检查时重新读取必要的动态状态。
- 记录状态变化和时间。

对于 READY：

- 核对全部八项实际条件。
- 确认其来源、身份和启动代次一致。
- 再允许进入后续 C00 校准。

对于 FAILED：

- 立即拒绝执行。
- 保存具体字段和原始错误。
- 进入安全关闭。

### 7.3 哪些情况禁止等待

以下情况应直接进入失败：

- boot_id 不匹配。
- batch_id 不匹配。
- sealed capability 无效。
- 一次性认领失败。
- 实际运行 UID/GID 非法。
- 资源限制已经确认不符合合同。
- 代码或输入摘要失配。
- 当前服务属于错误的 cgroup。
- 不可恢复的系统读取错误。
- 已发布 STOP_REQUEST 或 CLOSED。

只有被源码和平台语义证明为临时状态的条件，才允许进行等待。

### 7.4 时间上界

使用当前批次的 T0 和 deadline。

就绪等待必须具有独立的有限上界，并计入 1,800 秒总墙钟预算。

如果需要新增独立就绪超时参数，应从实际启动时序和申请合同中确定。

不能自行扩大校准 300 秒软窗口。

不能通过无限轮询使服务最终进入 READY。

不能将八个不同时间的正确值无条件拼接成同一时刻的有效资格。

如需要多次读取，必须给出其一致性前提。

## 十、阶段七：新增正反与竞态测试

建立至少以下测试类别。

### A. 正常启动

- 全部字段立即匹配。
- 合法 STARTING 后进入 READY。
- 字段在不同顺序下就绪。
- 同 PID、同 boot、同执行锁稳定通过。

### B. 真实身份或资源错误

- 错误 UID。
- 错误 GID。
- 错误服务单位。
- 错误 cgroup。
- RLIMIT_AS 不符合要求。
- TasksMax 不符合要求。
- boot_id 不匹配。
- PID 或 starttime 不匹配。

实际测试以冻结八项字段和系统接口为准。

### C. 启动竞态

- MainPID 尚未就绪。
- 单位状态处于 STARTING。
- 状态读取与服务状态更新交错。
- 多字段取样跨越状态变化。
- 读取过程中目标进程退出。
- 服务启动失败。
- 状态长期无法就绪。
- 等待期间 STOP_REQUEST。
- 等待期间 CLOSED。
- 等待期间 boot_id 变化。

### D. 检查器变异

- 任一失败字段被忽略。
- 读取失败被视为成功。
- 旧快照被重复使用。
- 只检查部分字段。
- 使用错误的 PID。
- 使用其他 boot 的证据。
- 将稳定失配误判为 STARTING。
- 超时后继续等待。
- 缺少执行锁仍放行。

变异必须由独立断言检测。

当前只实现静态夹具。

动态测试需要后续独立授权。
