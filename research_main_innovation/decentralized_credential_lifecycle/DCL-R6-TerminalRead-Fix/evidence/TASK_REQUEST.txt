## 三、第一阶段：定位终态读取失败

从原始 traceback 和源码定位：

- 哪个函数读取了期限。
- 读取发生在 CLOSED 之前还是之后。
- 实际要求的活动态条件。
- 实际运行阶段。
- 期限数据存储位置。
- 调用者是否属于 finalizer、seal 或健康检查器。
- 该读取是否具有副作用。
- 异常如何向上传播。
- 是否直接影响 native seal。
- 是否直接影响内部状态裁决。

建立完整事件链：

`WORK → STOP_REQUEST → CLOSED → 期限读取 → 守卫拒绝 → 后续seal/收尾`

上述链仅作为分析起点，必须使用实际日志确定准确顺序。

为每个事件保存：

- 真实时间。
- batch_id。
- boot_id。
- PID/starttime。
- 生命周期状态。
- 状态版本。
- 调用函数。
- 原始返回值。
- 错误类型。
- 原始证据位置。

必须回答：

**为什么 CLOSED 后的证据读取进入了只允许活动态使用的接口？**

若原始证据无法确定 native seal 是否直接依赖该失败，保留：

`NATIVE_SEAL_DEPENDENCY_UNRESOLVED`

不得提前认定修复期限读取就能使 native seal 成功。

## 四、第二阶段：区分活动态检查与终态证据读取

建立两个具有明确不同权限的接口。

### 4.1 活动态检查

建议逻辑接口：

`check_active_runtime()`

用于：

- 工作资格判断。
- 当前运行态健康检查。
- 新任务授权。
- 活动预算使用。
- 资源资格保持。

要求：

- 当前批次有效。
- boot_id 有效。
- 工作状态允许。
- T0 和预算账有效。
- 执行锁匹配。
- 当前资源约束满足。
- STOP_REQUEST/CLOSED 时拒绝新工作。

原有安全约束全部保留。

### 4.2 终态只读检查

建议逻辑接口：

`read_terminal_evidence()`

仅用于：

- 读取已持久化的 T0。
- 读取 deadline 和 stop_at。
- 读取最终预算记录。
- 读取 CLOSED/ABORTED 状态。
- 读取退出见证。
- 读取 seal 所需的历史证据。
- 生成终态审查和封存报告。

要求：

1. 只读取已有证据。
2. 不创建运行态对象。
3. 不发放执行资格。
4. 不更新预算。
5. 不改变生命周期状态。
6. 不重新激活服务。
7. 不修改已有 CLOSED。
8. 不生成新的 T0 或 deadline。
9. 保留证据缺失和损坏的错误。
10. 对批次身份、来源和完整性进行核验。

**终态只读接口必须在 CLOSED 后可用，同时保持 CLOSED 的不可恢复性。**

不得通过取消全部活动态守卫实现修复。

## 五、第三阶段：终态证据的一致性合同

重点研究 CLOSED 后需要读取的字段：

- batch_id。
- boot_id。
- T0。
- deadline。
- stop_at。
- 最终 R。
- journal 状态。
- CLOSED 原因。
- 状态版本。
- 退出证据。
- seal 状态。

每个字段应明确：

1. 创建主体。
2. 首次持久化时间。
3. 是否允许后续修改。
4. 最终可信来源。
5. 完整性校验方式。
6. 终态读取规则。
7. 缺失时的裁决。
8. 与当前批次的绑定。

### 5.1 终态快照

评估是否需要在 CLOSED 转换过程中建立不可变的终态证据快照。

若现有 journal 已包含全部必要记录，优先复用。

如必须新增快照，应确保：

- 来源真实。
- 原子发布。
- 与批次及执行锁绑定。
- 完整性可校验。
- 不覆盖原始 journal。
- 不依赖活动态资格才能读取。

### 5.2 禁止虚构缺失证据

例如：

- T0 缺失，保留缺失状态。
- deadline 缺失，记录证据不足。
- journal 不一致，保留 UNKNOWN。
- seal 输入不完整，保留相应失败或未决状态。

禁止通过构造默认值使终态检查 PASS。

### 5.3 防止跨批次证据复用

终态证据必须绑定：

- 当前 batch_id。
- 原运行 boot_id。
- 执行锁。
- 原始源码摘要。
- 状态版本。
- 必要的持久记录。

如果当前审查发生在新的 boot，应保留证据来源对应的历史 boot 身份，不将历史运行证据重新解释为当前运行资格。

## 八、第六阶段：安全性质

建立以下性质并映射到真实源码。

**TR-1：TerminalReadOnly**

终态检查不会修改运行状态或预算。

**TR-2：ActiveGuardPreserved**

活动态接口继续拒绝 CLOSED 后的工作请求。

**TR-3：NoTerminalReactivation**

终态读取不能重新激活批次。

**TR-4：EvidenceAuthenticity**

终态证据与真实批次、执行锁及持久来源绑定。

**TR-5：DeadlineConsistency**

T0、deadline 和 stop_at 使用有效的历史运行记录。

**TR-6：BudgetConservation**

终态审查不会改变已消耗或预留的预算。

**TR-7：SealPreconditionCorrectness**

native seal 使用完整且适用的终态证据。

**TR-8：NoFalseSealSuccess**

证据缺失或损坏时不得报告 seal 成功。

**TR-9：UnknownPreservation**

无法证明的内部状态继续保持 UNKNOWN。

**TR-10：FinalizerCompatibility**

自动行政收尾保持原有的安全性与证据完整性。
