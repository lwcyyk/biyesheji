## 三、第一阶段：评估三类可行资源隔离方案

停止在现有 v3 上进行无边界的修补。

必须同时评估三条路线，并以原始资源合同为判定依据。

### 方案 A：Windows 原生 Job Object

研究能否利用：

- 独立受信 Launcher。
- CREATE_SUSPENDED。
- 预先创建并配置的 Job Object。
- AssignProcessToJobObject。
- ResumeThread。
- 每进程 HardWS。
- Job 活动进程数量上限。
- Job 总提交内存限制。
- KILL_ON_JOB_CLOSE。
- 独立 Watchdog。
- 全部子孙进程归属。

重点解决：

1. 首个 Controller 如何在执行 Python 代码前获得约束。
2. Launcher 本身是否计入进程树。
3. 若 Launcher 在隔离范围外，原合同是否允许这样的受信边界。
4. 子进程如何保证全部属于受控 Job。
5. 是否允许嵌套 Job。
6. 是否存在 breakaway。
7. HardWS 的瞬时和峰值语义。
8. Job 提交内存与 Working Set 的关系。
9. 是否能给出完整进程树的严格上界。
10. Watchdog 崩溃时如何终止全部工作进程。

特别研究：

**仅依赖 Controller 自行配置 Job，能否覆盖 Controller 执行第一条用户态指令之前的资源消耗？**

如果需要外部受信启动者，明确其责任和计量边界。

### 方案 B：Linux cgroup v2

研究在现有 Windows 环境中，是否可以通过经过验证的 WSL2 或 Linux 容器使用 cgroup v2。

先只读检查：

- WSL2 是否实际可用。
- Linux 内核版本。
- cgroup v2 是否启用。
- memory controller 是否可用。
- 当前用户是否有权限建立受限组。
- Docker 后端是否真正可用。
- 是否存在其他宿主进程限制。
- 启动和退出机制。

重点研究：

- memory.max。
- memory.peak。
- memory.current。
- memory.events。
- memory.oom.group。
- pids.max。
- cgroup.procs。
- 父子 cgroup 资源归属。
- 容器启动前的内核级限制。

使用官方 Linux 内核文档建立语义合同。

明确 cgroup 内存使用量与 Windows 进程树 Working Set 之间的区别。

如果使用 cgroup 会改变原始内存指标，必须提出独立的合同修订申请。

不得将 cgroup memory.max 直接登记为原始 Working Set 指标已经通过。

同时审查内核文档规定的暂时超限行为，以及它对“严格峰值不超过 4 GiB”主张的影响。

### 方案 C：完整地址空间约束

研究是否能够利用：

- 内核级虚拟地址空间上限。
- 最多同时运行进程数量。
- 进程树封闭。
- 启动前生效的资源限制。

构造保守关系：

每个进程的物理驻留工作集受其有效虚拟地址空间约束。

如果可以从操作系统保证每个受控进程的完整地址空间上界，并对进程数量建立严格上限，尝试推导进程树 Working Set 的保守上界。

必须检查共享映射、启动环境、辅助进程及平台实现细节。

如果某个平台缺少可靠的地址空间限制接口，记录其不可用原因。

## 四、第二阶段：建立严格资源包络证明

原始目标：

- 累计访问状态 ≤ 1,000,000。
- 总墙钟时间 ≤ 1,800 秒。
- 进程树 Working Set 峰值 ≤ 4 GiB。

定义全部受控进程集合 P(t)。

原始内存目标可表示为：

\[
\forall t,\quad \sum_{p\in P(t)}WS_p(t)\le 2^{32}\text{ bytes}.
\]

这里的 WS 必须使用冻结的精确计量定义。

若采用每进程上界证明，应给出：

\[
WS_p(t)\le U_p
\]

并证明：

\[
\max_{\text{合法进程配置}}\sum_pU_p\le2^{32}.
\]

要求：

1. 全部允许进程角色都计入。
2. 限制从指定边界开始生效。
3. 全部子孙始终受到限制。
4. 进程总数受到独立约束。
5. 监督器失效能够安全终止任务。
6. 所有内核资源限制都有官方语义依据。
7. 计数器峰值和执行限制采用兼容的定义。
8. 对页面粒度、暂态行为及共享内存明确处理。
9. 对无法界定的资源保留未决责任。
10. 静态证明与未来动态验收分别登记。

如果无法证明原始指标，则给出两个结果：

A. 保持原始指标，说明当前平台缺少的必要能力。

B. 提出新的可执行资源合同，包括新指标、限制方式及与原合同的区别，等待用户明确批准。

禁止自动采用 B。
