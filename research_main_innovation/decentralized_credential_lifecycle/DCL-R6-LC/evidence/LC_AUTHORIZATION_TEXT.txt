## 七、阶段三：准备 inactive systemd 资源单位

依据 AS4-PAYLOAD/1 建立静态单位配置。

核心候选约束：

- 每进程 `RLIMIT_AS` soft=hard=1 GiB。
- 父 slice `TasksMax=4`。
- 全部子 service 共享父层任务数上界。
- 目标用户为专用非特权身份。
- `Restart=no`。
- `Delegate=no`。
- `NoNewPrivileges=yes`。
- `KillMode=control-group`。
- `MemoryAccounting=yes`。
- `TasksAccounting=yes`。
- cgroup memory.max 作为次级保护。

同时核查：

- `Type=exec`
- `LimitAS`
- `MemoryMax`
- `MemorySwapMax`
- `OOMPolicy`
- `LimitCORE`
- `TimeoutStartSec`
- `TimeoutStopSec`
- `RuntimeMaxSec`
- `KillSignal`
- `SendSIGKILL`

最终属性必须与当前 systemd 255 的实际支持范围一致。

### 核心要求

资源限制应在目标 Python exec 之前生效。

普通验证程序及其后代必须受到同一受控环境约束。

独立 Watchdog、监督线程和所有允许的子进程共同占用任务额度。

systemd manager、外部 Launcher 和 pre-exec helper 的 TCB 边界继续单列。

必须对普通用户执行组外工作、调用外部代理、修改 cgroup 和提高资源限制的可能性进行静态审查。

当前只检查配置，不启动单位。

尤其需要注意：

**systemd-analyze verify 通过仅表示指定范围内的配置检查结果，实际限制是否生效仍需后续动态校准确认。**

### 8.1 guard.py

将 Windows Job 相关接口与 Linux 资源接口解耦。

Linux 适配需要支持：

- 受控批次身份。
- 当前 boot_id。
- 运行时摘要。
- 资源单位身份。
- 绝对 deadline。
- 当前预算账。
- 原子持久预留。
- 进程和任务身份。
- cgroup 计量读取。
- 停止状态。
- 运行许可收据。

资源事实应由实际配置和 OS 状态证明。

不能允许用户通过修改 JSON 字段绕过资源资格。

### 8.2 guard_probe.py

完成未来 C00–C12 校准需要的接口适配。

仅实现已冻结的探针类型。

保留：

- 有界资源申请。
- 实际观察与预期分离。
- 失败原件。
- 退出状态。
- 精确内存计量名称。
- 超限后停止。
- 运行时及配置摘要绑定。

本阶段只完成静态准备。

### 8.3 run_batch.py

保持 F1→F4 的原有执行顺序和输入。

实现：

- 统一预算入口。
- 批次身份核验。
- Guard 资格检查。
- 运行权限收据核验。
- 与原业务模块兼容的导入路径。
- 运行前摘要验证。
- 独立的 F1/F4 结果记录。
- 模型异常与资源异常的分类。

如果资源资格缺失，应拒绝正式模型执行。

### 8.4 适配审查

每项改动记录：

`原 Windows 接口 → Linux 接口 → 合同要求 → 代码修改 → 静态检查 → 待动态验证`

不得改变业务状态转换、费用递推、独立参考解释、输入域和正式不变量。
