## 三、第一阶段：独立复核 NC1/NC2 并发反例

本阶段最高优先级是验证 DCL-R2 提出的两条关键并发历史。

固定源码：

https://github.com/casdoor/casdoor/blob/528a0213f01caf70b9f41009cbf7b2f67bdd67ec/object/token_oauth_util.go

同时审查关联 Controller、Token、数据库操作、路由及权限检查代码。

### 3.1 NC1：撤销 ACK 后仍创建派生 Token

现有结论指出：刷新过程先读取和检查父 Token，再插入子 Token，最后删除父 Token。

尝试独立构造以下并发历史：

T1：刷新请求读取有效父 Token。

T2：撤销请求开始执行。

T3：撤销操作提交并返回 ACK。

T4：先前的刷新请求插入新子 Token。

T5：刷新操作完成。

重点验证：

1. 每个步骤在指定源码中是否确实存在。
2. 所需调度顺序是否符合真实调用链。
3. 数据库事务和锁是否阻止这一交错。
4. 是否存在额外的状态重新检查。
5. 插入、删除失败时是否发生回滚。
6. 子 Token 是否可能进入持久有效状态。
7. 撤销 ACK 到底代表什么原生保证。
8. 该反例是否依赖额外的并发假设。

区分源码级可行轨迹、抽象模型允许轨迹和真实运行已观察轨迹。

输出具体调度表、源码位置、依赖条件和结论。

### 3.2 NC2：同父 Token 的双重刷新

构造两个执行域并行使用同一 RT 的历史。

检查：

- 父 Token 读取及检查时刻。
- 是否存在行锁或其他互斥。
- 两个请求是否能够同时通过有效性检查。
- 两次派生 Token 创建的唯一性条件。
- 数据库删除父行的作用。
- 双子 Token 是否可能同时持久存在。
- 哪些失败路径会导致回滚。
- 是否存在可用的去重或 CAS 机制。

必须给出至少一个明确裁决：

`SOURCE_FEASIBLE`

`SOURCE_BLOCKED_BY_CONSTRAINT`

`ASSUMPTION_DEPENDENT`

`UNRESOLVED`

如果源码条件推翻 NC1/NC2 的某项历史结论，直接修订 D1 的相关规格。

如果反例成立，进一步判断强 G 是否也能直接依据标准创建截止、原生幂等和责任保留机制处理。

### 3.3 独立性要求

重新从源码建立推理链，避免直接复述 DCL-R2 的证明。

输出完整事件偏序、必要数据库条件、最短攻击轨迹以及支持或推翻结论的具体证据。

仅进行静态分析，不运行新增原生请求。

## 五、第三阶段：D1 的 BFT 跨域重配置协议闭合

D1 当前已经有完整度较高的抽象协议，但一般 BFT 重配置和全部署精化仍待证明。

本阶段要求构造一个**具体可检查的协议实例**。

### 5.1 明确分布式模型

定义：

- 状态权威节点集合。
- 独立管理域。
- 拜占庭故障数量。
- 网络故障及分区模型。
- 共识协议的安全与活性假设。
- 执行域 E1、E2 与状态权威的关系。
- 用户批准如何进入复制状态机。
- 原生执行门如何识别当前资格。
- 成员变更时旧、新配置的关系。

可以选择已有成熟 BFT 协议作为底座。

如采用经典 `n ≥ 3f+1` 的模型，说明其适用假设及与实际部署的对应。

特别检查新旧委员会之间的安全交接。不同成员配置各自满足静态法定人数条件，并不能自动推出跨配置历史的一致性。

### 5.2 设计完整重配置流程

至少定义：

1. RECONFIG_PROPOSE
2. RECONFIG_PREPARE
3. OLD_STATE_CHECKPOINT
4. RESPONSIBILITY_TRANSFER
5. NEW_MEMBERSHIP_ACTIVATE
6. EXECUTOR_TAKEOVER
7. EVIDENCE_RECONCILE
8. OLD_CONFIGURATION_RETIRE

以上为逻辑步骤，可依据标准协议进行合并。

每步必须给出：

- 消息字段。
- 前置条件。
- 状态转换。
- 提交点。
- 必须持久化的数据。
- 重试行为。
- 拒绝行为。
- 崩溃恢复。
- 需要验证的证明或证书。

### 5.3 完整继承 RHO 责任对象

确保重配置期间至少保留：

- 原授权来源
- 原代次
- 业务意图标识
- 已消耗和预留预算
- DISPATCHED_UNKNOWN 请求
- 迟到结果责任
- 原生材料谱系
- 历史暴露
- 证据状态
- 独立任务 B 的合法支持

研究 RHO 是否存在必须新增的字段。

不能通过迁移 owner 清除原生 UNKNOWN。

### 5.4 必须处理的极端情况

构造并分析：

- E1 在 checkpoint 前崩溃。
- E1 在 checkpoint 后崩溃。
- 新执行域接管后收到旧结果。
- 新旧配置同时接受请求。
- 新旧委员会出现不同的有效状态历史。
- 新旧委员会成员无交集。
- 恶意执行域保留历史 bearer。
- BFT 节点恶意隐瞒部分责任。
- 责任转交期间用户撤销 A。
- 网络分区持续存在。
- 重配置过程中发生第二次重配置。

给出在相应假设下的安全性和活性边界。

活性保证应写明网络恢复与合法法定人数等条件。

### 5.5 安全证明

至少尝试完成：

- 复制状态的唯一有效历史。
- 重配置期间授权资格保持。
- RHO 责任保全。
- 同业务意图预算保持。
- 旧批准不能通过重放重新生效。
- 迟到材料保持原来源。
- 配置更新与接管状态的一致性。
- 原生停止声明受到接口证据约束。

特别指出：

**BFT 一致性保护复制状态；原生 bearer 的继续有效性需要独立的原生截止条件。**

将两种保证拆开证明。

如果所选标准 BFT 机制已直接覆盖重配置状态安全，则明确归属标准机制，继续研究其与原生责任语义的精化问题。

## 八、第六阶段：寻找真正值得保留的架构创新

当前 D1、D2 的主要困难已经明确：

- 有效 bearer 绕过分布式控制。
- 原生创建截止缺乏充分证据。
- 责任接管可由成熟持久协议实现。
- 联合配置可以被通用约束求解器覆盖。
- 原生动作成本已经由强 G 匹配。

因此，本阶段采用**反例驱动的创新探索**。

先寻找现有强 G 存在具体且可验证的合同缺口，再考虑新的架构关系。

优先审查三个研究问题。

### 8.1 跨配置责任证据的完整性

在 BFT 成员重配置、执行域转移和原生结果不确定同时发生时：

- RHO 的完整性如何核验？
- 旧执行域能否隐瞒未决责任？
- 新执行域能否凭已有证据检测遗漏？
- 是否存在不可区分的原生历史？
- 标准 checkpoint、日志复制和证据验证能否覆盖全部要求？

只有出现强 G 无法等价完成的性质，才将其提升为原创机制候选。

### 8.2 配置证书的动态失效与恢复

在执行过程中，以下情况可能改变 D2 配置安全性：

- 历史秘密新近泄露。
- 原生 Token 新近创建。
- 某管理域失陷。
- 证据来源失效。
- 原生撤销范围变化。
- 配置中的合法任务支持变化。

研究配置证书如何失效、如何检测，以及如何重新配置。

重点审查标准持续验证和鲁棒配置技术是否已经完整解决。

### 8.3 原生接口能力不足时的保证边界

给定不同原生能力组合，研究系统能达到：

- C_local
- C_native
- C_effect

中的哪些性质。

尝试形成有意义的可实现条件、必要条件或不可能性边界。

如相关分类、定理和协议已经被 EFFECTBOUND 等先例覆盖，明确记录。

### 严格分离要求

每项新候选都需要：

- 固定输入族。
- 固定故障模型。
- 固定原生能力。
- 固定观察权限。
- 固定成本。
- 最强 G 的具体构造。
- 候选协议的完整保证。
- G 无法匹配的证明，或能够匹配的构造。
- 可独立检查的最小实例。
- 明确判废条件。

同时考虑功能、安全、信任边界和成本差异。

若经过两个完整反证轮次仍被强 G 覆盖，归档该候选，继续研究其他确实不同的问题。避免无限细化相同失败思路。
