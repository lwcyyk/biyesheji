## 三、阶段二：Casdoor 原生接口的纸面精化

这是当前最高优先级任务。

### 3.1 锁定原生版本与真实接口

优先审查项目所用 Casdoor 4.25.0。

参考官方发布版本：

https://github.com/casdoor/casdoor/releases/tag/v4.25.0

公开发布记录对应提交短哈希 `528a021`，必须进一步核对本项目实际源码和运行版本。

重点读取相关源码、API 文档及历史实验记录。

研究以下操作的实际语义：

- Access Token 发行
- Refresh Token 发行
- Refresh Token 使用
- Token Introspection
- OAuth Token Revocation
- UserInfo
- Token 查询与枚举
- 审计记录生成与读取
- Session Logout
- 用户、应用及组织级处置
- 异步响应与持久记录

应核对的接口包括：

- `/api/login/oauth/refresh_token`
- `/api/login/oauth/introspect`
- `/api/login/oauth/revoke`
- `/api/userinfo`
- `/api/get-records`

以上作为检索入口。实际存在性、访问权限、数据模型、错误语义和保证范围必须由指定版本源码确认。

尤其检查 RFC 7009 撤销接口是否已经存在于冻结实验对应的版本中，以及撤销 RT 对相关 AT 的实际影响。

不要直接使用 master 分支或最新在线文档推断旧版本实现。

### 3.2 建立原生能力合同

为每种原生操作建立标准化记录：

1. API 名称与源码位置。
2. 请求参数及必要权限。
3. 操作前置条件。
4. 服务器内部状态变化。
5. 对应的持久化位置。
6. 可能的返回结果。
7. 失败及超时语义。
8. 是否具备幂等性。
9. 是否存在唯一业务意图标识。
10. 是否能追踪派生凭据来源。
11. 是否可以查询已有结果。
12. 是否能证明某次操作没有产生效果。
13. 是否提供创建能力截止。
14. 是否支持完整枚举。
15. 是否具备可用于并发证明的顺序关系。
16. 对旧 AT、RT、会话及异步工作的影响。
17. 可支持的停止保证层次。
18. 是否依赖额外权限或测试配置。

所有保证分别标记：

- `SOURCE_CONFIRMED`
- `CONTRACT_ASSUMPTION`
- `EXPERIMENT_OBSERVED`
- `UNVERIFIED`
- `UNSUPPORTED`

要求引用准确源码位置、版本和文档证据。

### 3.3 重点核查原生事件顺序

针对刷新和撤销操作，尝试重建以下事件的先后关系：

- 请求到达服务器
- 请求认证完成
- 读取当前 Token 状态
- 创建派生 Token
- 数据库提交
- 审计记录生成
- HTTP 响应发送
- 客户端接收响应
- 撤销操作完成
- 接受端实际拒绝旧材料

尤其研究以下轨迹：

**轨迹 A：已创建新 RT，但响应丢失。**

**轨迹 B：旧执行域在撤销提交前发送请求，该请求在撤销 ACK 后才执行到关键步骤。**

**轨迹 C：查询得到空集合，随后出现之前已经发出的延迟刷新请求。**

**轨迹 D：RT 已被标记 inactive，但某个 AT 或会话仍可能有效。**

**轨迹 E：原生记录存在分页、过滤、权限或保留期限限制。**

**轨迹 F：任务 A 被撤销，任务 B 仍依赖同一账户的其他合法支持。**

对每条轨迹给出可能的服务器内部历史、观察结果，以及 D1/D2 当前机制的判断。

分别说明：

- 可证明安全
- 可证明存在风险
- 证据不足，必须 UNKNOWN

### 3.4 重点修复抽象模型与真实接口的差异

检查当前 D1 的 21 类状态转换，逐项判断它们是否有对应的 Casdoor 原生行为。

形成映射：

`抽象状态转换 → 原生调用/内部事件 → 可观察结果 → 证明责任`

检查：

1. 抽象中的原子步骤是否对应多个真实操作。
2. 原生响应是否足以识别抽象后继。
3. 请求崩溃是否产生无法区分的状态。
4. 抽象证据是否需要源代码或额外权限支持。
5. 历史暴露是否允许旧执行方绕过新控制域。
6. 抽象中的截止条件是否能由原生接口实现。
7. 有哪些状态需要扩充、拆分或保留 UNKNOWN。
8. 当前有限知识状态 K 如何覆盖所有真实可能后继。

对每个无法完成的映射，建立最小反例。

若发现抽象安全性质依赖原生接口未提供的能力，必须明确指出，并给出条件性合同或不可能性论证。

### 5.2 明确交接和生效边界

- 旧权威的最后允许放行点
- 原生操作的可能生效点
- 新权威的接管点
- 旧执行域失去受控执行能力的点
- 原生服务停止接受旧材料的点
- 责任关闭证书的生成点

## 六、阶段五：D2 联合配置机制精化

### 6.1 建立可观察的真实配置模型

1. 原生凭据及其撤销效果域。
2. 执行门和可信组件。
3. 独立管理域及故障域。
4. 历史暴露和当前可用的秘密能力。

- 运行时秘密重建
- 已泄露秘密副本
- 原生服务接受
- 任务级授权与原生凭据效果

研究多个配置在相同故障和撤销场景下的实际差异。

### 6.2 精化停止与保留条件

形式化描述：

- 撤销任务 A 需要切断的全部路径。
- 保留任务 B 需要存在的独立合法支持。
- 管理域失陷导致的额外可用路径。
- 历史泄露材料带来的潜在绕过。
- 原生证据的覆盖条件。
- UNKNOWN 情况下允许的恢复动作。

对不同配置分别输出：

- 可行
- 不可行
- 需要附加原生条件
- 证据不足

### 6.3 探索完整机制

研究是否能形成：

- 原生能力感知的配置算法
- 故障域感知的执行门部署
- 历史暴露感知的停止/保留配置
- 配置证书
- 运行时配置失效检测
- 安全重新配置协议
- 配置与 D1 迁移过程的保持关系

优先研究实际安全保证上的差异。

如果通用约束求解器可实现相同模型与成本，则保留求解器作为工程技术，继续寻找其他能够建立独立贡献的机制问题。

### 6.4 联合协议保持

研究是否可以建立：

`D2 配置证书 → D1 执行协议 → 原生状态转换`

之间的形式化保持关系。

重点检查 D1 发生迁移、故障、证据变化和历史秘密暴露后，D2 的配置证书是否仍然有效。

尝试给出：

- 充分条件
- 必要条件
- 保持定理
- 失效反例
- 必须重新配置的触发条件

明确这些结论中哪些已由标准模型细化和持续验证技术覆盖。
