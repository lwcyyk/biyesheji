## 三、第一阶段：确定 WSL 启动代次变化的证据边界

首先从已有原始证据建立事件时间线。

至少列出：

1. 第一次 WSL 调用。
2. 第一次 boot_id 读取。
3. 基础预检。
4. 静态文件及运行时校验。
5. 六条准备操作。
6. systemd 单位状态核验。
7. 最终 boot_id 检查。
8. PREFLIGHT_FAILED。
9. 证据导出。
10. 事后 boot_id 检查。

每个事件记录：

- 时间戳及其时钟来源。
- Windows 命令。
- WSL argv。
- 命令持续时间。
- Linux 进程身份。
- 读取到的 boot_id。
- systemd 状态。
- 命令退出码。
- 原始证据位置。

特别分析：

### H1：WSL 空闲生命周期导致启动代次变化

检查预检是否由多个彼此独立的 `wsl.exe --distribution ... --exec ...` 调用组成。

研究这些调用之间是否缺少保持发行版活动状态的进程或管理服务。

重点评估：

- WSL 在命令结束后是否可能退出当前发行版实例。
- systemd 处于 PID1 是否足以保证发行版持续运行。
- 多次独立 WSL 调用是否可能进入不同启动代次。
- 原始日志是否存在发行版退出或重启的间接证据。

此项只能作为待证假设。

### H2：宿主或外部程序触发 WSL 生命周期变化

检查已有记录是否存在：

- WSL shutdown 或 terminate。
- WSL 服务重启。
- Windows 宿主休眠、重启或更新。
- WSL 内核异常。
- 其他程序管理发行版的事件。

如果现有证据不能确定触发者，明确标记：

`BOOT_CHANGE_CAUSE_UNRESOLVED`

不得根据 boot_id 变化直接认定某一个程序执行了重启。

### H3：预检编排跨越多个 Linux 实例

检查是否存在：

- 静态检查在一个 boot 完成。
- 准备操作在另一个 boot 完成。
- 最终检查在第三个 boot 完成。
- 检查结果被错误地当作同一生命周期证据。

如果成立，定位具体编排路径与证据复用错误。

## 四、第二阶段：设计分层预检机制

目前启动前检查包含大量静态文件和环境核验。

需要将其分为两个层次。

### Layer A：跨 boot 可复用的静态证据

例如：

- 源码 SHA-256。
- 输入摘要。
- 冻结执行锁。
- 已批准的授权文本。
- 静态 Python 版本合同。
- 配置文件内容摘要。
- 历史研究及交付哈希。

只有当实际对象未发生变化、来源可信且验证条件保持时，才允许复用。

### Layer B：当前 boot 必须重新验证的动态证据

至少包括：

- 当前 boot_id。
- 当前进程身份。
- 当前 systemd 管理状态。
- 实际活动单位属性。
- 当前 cgroup 归属。
- 有效资源限制。
- 当前 UID/GID 及进程权限。
- 当前临时目录和 IPC 对象。
- 当前 Root/Launcher/Receiver 状态。
- 当前监督与停止来源。
- 当前资源组成员。

必须明确：

**新的 boot_id 会使所有与旧运行代次绑定的动态资格失效。**

禁止通过修改记录中的 boot_id、时间戳或收据字段使旧证据重新有效。

重新取得的动态证据必须绑定真实的当前启动代次。

### 4.1 静态证据缓存

可以设计静态核验结果缓存，但必须包含：

- 源码或输入摘要。
- 验证规则版本。
- 原始证据引用。
- 当前使用的执行锁。
- 缓存适用条件。

缓存不允许替代动态资源资格。

### 4.2 动态证据失效

明确以下行为：

- boot_id 改变，动态资格立即失效。
- 运行时身份改变，相关资格失效。
- 资源单位属性改变，相关资格失效。
- 当前代码或输入摘要改变，停止。
- 当前授权失效，停止。

失效后不得保留原 RESOURCE_GATE_PASS。

## 五、第三阶段：同一 WSL 会话中的启动编排

优先研究将启动前动态检查与 Launcher 激活放入一次受控的 WSL 生命周期。

候选方案：

**由一个受信编排入口保持 WSL 会话，完成当前 boot 动态核验、准备、最终检查和 Launcher 激活。**

避免多次独立 WSL 命令之间存在无法证明的生命周期空窗。

### 5.1 目标流程

建议设计：

1. Windows 受信入口启动 Ubuntu-24.04。
2. Linux 受信编排进程读取当前 boot_id。
3. 验证静态执行锁。
4. 完成当前 boot 动态资格核验。
5. 完成需要的启动前准备。
6. 再次确认 boot_id、执行锁与动态状态。
7. 原子提交启动资格或取得当前 boot 的一次性启动收据。
8. 在同一受控生命周期内激活 Launcher。
9. Root 协调器重新核验当前启动身份。
10. 确认真实服务启动后才建立对应运行证据。

上述流程为候选设计，具体实施必须以实际 systemd/WSL 接口和源码为准。

### 5.2 启动连续性

必须建立以下安全性质：

**BC-1：SameBoot**

参与一次有效动态预检和启动的关键证据属于同一 boot_id。

**BC-2：FreshRuntime**

Launcher 激活时使用当前系统和资源状态。

**BC-3：NoStaleAuthorization**

旧启动代次的资格不能授权新启动代次执行。

**BC-4：SingleActivation**

一次有效启动收据最多对应一个合法批次激活。

**BC-5：FailClosed**

出现 boot 变化、证据缺失或状态不确定时拒绝启动。

**BC-6：NoBudgetReset**

预检重复或 WSL 重启不能重置已经初始化的预算。

**BC-7：NoFalseStart**

只有确认真实服务进入允许状态后，才能登记 Launcher 已启动。

**BC-8：TCBBoundary**

外部编排器权限、职责和信任边界明确。

### 5.3 不可消除的启动竞态

考虑以下情况：

- 最终 boot 检查后，Launcher 激活前系统重启。
- systemd 接受启动请求后，Launcher 尚未执行。
- Root 取得旧代次启动收据。
- 外部协调器退出。
- 发行版在准备阶段停止。
- 启动请求返回但实际服务未启动。
- 启动过程中 boot_id 变化。

要求通过当前实例身份、执行收据、服务内重新核验和失败停止保持安全。

如果无法证明完整原子性，明确提出附条件保证及未决时间窗口。

不能仅靠缩短时间间隔声称竞态已经消除。
