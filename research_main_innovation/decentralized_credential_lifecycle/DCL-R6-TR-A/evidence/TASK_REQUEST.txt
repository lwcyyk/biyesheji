## 四、核心验收一：真实 CLOSED 后终态只读

`WORK → STOP_REQUEST → CLOSED → TERMINAL_READ`

- batch_id。

- T0。

- stop_at。
- 最终 R。

- CLOSED 原因。

- 原始记录摘要。
- 状态版本。
- 读取时间。
- 当前读取者身份。
- 实际返回码。

### 4.2 只读性质

必须检查终态读取前后的关键对象。

至少比较：

- T0。
- deadline。
- stop_at。
- R。
- journal。
- CLOSED 状态。
- 执行锁。
- 运行态检查点。

要求：

**终态读取不得改变这些对象的业务语义或原始持久记录。**

如接口会写入独立审计记录，必须明确其写入范围、权限和合同依据。

## 九、执行顺序与首次失败规则

按照冻结依赖执行：

`预检 → 单会话启动 → WORK/C00 → 必要兼容回归 → TR40 → 正常CLOSED → 终态只读 → native seal → 自动行政finalizer → 独立校验`

如果真实代码要求终态检查、seal 和 finalizer 使用不同顺序，以已冻结的安全依赖为准。

一旦出现关键失败：

1. 立即停止后续工作发放。
2. 保存首次失败。
3. 自动发布 STOP_REQUEST。
4. 执行冻结关闭路径。
5. 确认受控角色退出。
6. 确认 cgroup 清空。
7. 保留真实预算。
8. 执行适用的 native seal。
9. 执行自动行政封存。
10. 必要时使用已授权的兜底归档。
11. 独立核验原始证据。

禁止：

- 自动重跑失败 case。
- 修改源码后继续。
- 重置 T0 或 R。
- 创建第二执行窗口。
- 跳过失败检查。
- 修改历史证据。
- 将 UNKNOWN 自动改为成功。
- 自动创建下一批次。
