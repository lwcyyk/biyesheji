## 三、阶段一：寻找现有 Linux Python

上一阶段仅检查两个固定路径。本阶段允许扩大至有限的系统运行时发现。

### 3.1 允许的只读检查

使用已安装的 Ubuntu-24.04，直接调用系统现有程序。

允许的命令类型：

- `find`：限定搜索 `/usr/bin`、`/usr/local/bin` 和 `/opt` 中的 Python 可执行文件与符号链接。
- `readlink`：核实发现的 Python 路径。
- `ls`、`stat`：核实文件类型和元数据。
- `python3 --version`：只对实际已发现、路径明确的 Linux 原生解释器进行版本查询。
- `dpkg-query`：读取已安装的 Python 相关软件包信息。
- `apt-cache policy`：读取本机已有的软件包索引，不执行更新。
- `sha256sum`：核实已发现的 Linux 可执行文件摘要。

所有命令必须使用明确的 argv，避免执行任意 shell 组合。

执行前先记录完整命令与参数。

不允许扫描与本任务无关的私人目录或读取凭据。

如果上述工具不存在，记录缺失并停止依赖它的检查。

### 3.2 Python 候选版本

重点发现：

- Python 3.14
- Python 3.13
- Python 3.12
- 其他已经安装的 Python 3

对于实际发现的每个解释器，记录：

1. 绝对路径。
2. 版本。
3. 是否属于 Linux 原生可执行文件。
4. 文件摘要。
5. 系统软件包来源。
6. 是否属于发行版默认环境。
7. 需要的动态链接库。
8. 标准库位置。
9. 是否存在符号链接和版本替换。
10. 是否适合作为隔离验证运行时。

不得使用 Windows Python 作为替代。

不得自动安装、编译、下载或切换系统默认 Python。

### 3.3 核查是否必须使用 Python 3.14

### 4.1 systemd 管理能力

### 4.2 cgroup 控制权限

根据 P 阶段已有的 cgroup v2 证据，补充允许的只读检查。

审查：

- 当前 cgroup 层级。

- 未来父 slice 所需资源接口。
- pids.max 的有效限制条件。
- memory.max 与 AS 限制的关系。
- 可能影响资源隔离的父层约束。

不能通过读取 controller 名称宣称资源限制已经生效。

### 4.3 专用非特权身份

分析未来 batch02 应采用怎样的身份隔离：

- systemd manager 负责配置。
- 专用普通 UID 运行 payload。
- payload 不能修改资源单位。
- payload 无权提高 RLIMIT_AS。
- payload 无权创建组外工作。
- payload 只能访问本批次的输入和输出。
- 预算和日志具备明确写入权限。
- 历史 batch01 保持只读。

评估是否需要：

- 创建专用用户。
- 创建专用用户组。
- 调整目录属主。
- 配置 systemd service 的 User/Group。
- 限制 capabilities。
- 配置 IPC 与 WSL interop。
