## 三、第一阶段：独立定位管理器失败来源

这是本轮最高优先级。

首先确认错误名称中的 `MANAGER` 具体对应哪个实际组件。

可能涉及：

- Root 协调器。
- Launcher 管理逻辑。
- Receiver 所依赖的管理进程。
- systemd 服务管理状态。
- 其他实际源码中定义的 manager。

最终必须依据真实源码裁决，禁止仅根据错误名称推断。

### 3.1 建立事件时间线

从 T0 开始重建：

1. C09 准备。
2. 持久 ACK。
3. Receiver 确认。
4. Launcher 退出。
5. waitpid/pidfd 观察。
6. fresh-read。
7. C09 成功分类。
8. 恢复入口调用。
9. 管理器状态读取。
10. `UNREVIEWED_MANAGER_FAILURE` 产生。
11. STOP_REQUEST 或相应失败状态。
12. 自动关闭流程是否被调用。
13. 人工或外部调用冻结关闭函数。
14. 实际受控进程退出。
15. 最终证据封存。

以上步骤需要逐项确认是否实际发生。

每项记录：

- 事件时间。
- 进程身份。
- boot_id。
- batch_id。
- 调用函数。
- 前置状态。
- 后置状态。
- 原始日志。
- 持久化状态。
- 实际退出码。

### 3.2 分类可能原因

至少检查：

**H1：预期退出未被恢复入口认可。**

例如 C09 已成功交接，但恢复入口仍将已退出的旧管理者视为异常。

**H2：管理器退出事件尚未完成审查。**

例如已经观察到退出，但没有对应的认证记录、状态确认或审查收据。

**H3：状态读取发生竞态。**

例如恢复检查使用了交接前的旧状态，或同时读取了不同阶段的管理信息。

**H4：管理器确实出现新的异常退出。**

例如 C09 成功后，新的监督组件发生未预期故障。

**H5：恢复入口错误地处理管理器生命周期。**

例如正常交接后的旧管理者退出与新管理者异常退出被合并到同一错误分类。

对每项分别登记：

- SOURCE_SUPPORTED
- TRACE_SUPPORTED
- ASSUMPTION_DEPENDENT
- CONTRADICTED
- UNRESOLVED

保留原始错误，避免提前修改分类规则。

## 四、第二阶段：建立管理器事件审查状态机

根据实际源码建立管理器事件的审查模型。

至少区分：

- MANAGER_ACTIVE
- EXIT_OBSERVED
- REVIEW_PENDING
- REVIEWED_EXPECTED
- REVIEWED_UNEXPECTED
- STOP_REQUESTED
- CLOSED

这些是逻辑状态，具体名称可以与现有实现对应。

重点定义：

### 4.1 预期退出

预期退出必须具有可核验的依据，例如：

- 当前 batch_id。
- 当前 boot_id。
- 稳定进程身份。
- 对应的交接意图。
- 真实退出见证。
- 有效 ACK。
- Receiver 确认。
- 当前状态及执行锁。
- 与原预算和 deadline 的一致性。

具体条件按照原交接协议确定。

### 4.2 未审查退出

出现管理器退出事件，但审查条件尚未完成时：

- 保留 REVIEW_PENDING。
- 暂停需要有效管理责任才能进行的新操作。
- 在明确时间界内完成审查。
- 缺少必要证据时安全关闭。

禁止把未审查状态直接升级为成功。

### 4.3 异常退出

如果身份、责任、交接收据或退出行为违反合同：

- 记录精确错误。
- 禁止恢复新工作。
- 发布停止状态。
- 调用自动清理流程。
- 保存原始证据。

### 4.4 幂等与终态

同一退出事件只能形成一个有效终态裁决。

重复恢复调用必须返回已有事实。

CLOSED 后的迟到事件不能重新激活批次。

## 五、第三阶段：修复恢复入口健康检查

定位负责恢复检查的具体函数及其依赖。

重点检查：

1. C09 PASS 是否具有完整持久记录。
2. 恢复入口是否正确读取最新 C09 状态。
3. 是否保留旧管理器身份。
4. 是否识别新管理器的有效责任。
5. 是否混淆预期退出与异常退出。
6. 是否丢失真实 waitpid 退出见证。
7. 是否遗漏 ACK 或 Receiver 确认。
8. 是否发生旧快照读取。
9. 是否缺少恢复前的状态重新核对。
10. 是否在某个状态下要求永远存活的旧管理者。

### 修复要求

只允许基于明确证据认可预期退出。

如果恢复入口判断当前管理责任已经有效移交，应保存对应证据链。

如果交接或管理责任不确定，继续 fail-closed。

禁止：

- 将所有 manager failure 加入允许列表。
- 将所有退出码 23 认作成功。
- 跳过真实 ACK。
- 跳过 Receiver 确认。
- 将 C09H 合成回归作为真实交接证明。
- 删除恢复健康检查。
- 通过固定 PASS 字段放行。

恢复成功需要证明当前监督责任有效，而历史旧管理者退出只能作为已经审查的历史事实处理。

## 六、第四阶段：修复关键失败后的自动关闭缺口

batch09 CalDiag 已经通过显式调用冻结关闭与封存函数完成清理。

本阶段需要检查为什么关键失败未能自动调用相同安全关闭流程。

### 6.1 建立完整失败路径

至少审查：

- 恢复检查返回错误。
- 恢复检查抛出异常。
- Root 协调器异常。
- Launcher 意外退出。
- Watchdog 失败。
- 日志写入失败。
- 预算状态不确定。
- 资源单位异常。
- STOP_REQUEST 已发布。
- CLOSED 已存在。
- 父进程退出。
- 子进程未退出。
- 清理过程中再次发生错误。

每条路径都必须具有明确的停止责任。

### 6.2 统一失败关闭入口

优先复用已经冻结且实际验证可完成清理的关闭函数。

设计统一的失败出口：

`CRITICAL_FAILURE → STOP_REQUEST → ABORTING → CLOSED → CLEANUP → SEALED`

以上为逻辑流程，实际代码按原有状态合同实现。

要求：

1. 关键失败自动触发。
2. 不依赖调用方主动执行第二条清理命令。
3. 停止首先阻断新工作发放。
4. 保留原始错误和失败现场。
5. 保留真实预算账。
6. 对重复停止请求幂等。
7. 清理发生异常时仍尝试已授权的外部停止机制。
8. 受控进程退出得到确认。
9. 清理失败时保留 UNKNOWN。
10. 不自动恢复 CLOSED 批次。

### 6.3 独立停止来源

审查当前的 Root、Controller、Watchdog、systemd 与外部停止事件之间的责任关系。

需要证明：

- Controller 异常退出时仍有停止路径。
- Root 异常退出时仍有停止路径。
- 恢复入口异常时仍有停止路径。
- 原预算记录不会因为清理路径切换而丢失。
- 外部清理权限仅针对当前批次。

如果现有结构无法覆盖某类失效，明确记录未决故障模型。

### 6.4 时间边界

要求自动清理遵守现有 T0/deadline。

不得引入无界等待。

实际停止响应时间尚未验证，必须保留动态验收责任。

## 七、第五阶段：安全性质

至少建立以下性质。

**MR-1：ReviewedExpectedExit**

只有证据完整的预期管理器退出才能被接受。

**MR-2：NoUnreviewedResume**

管理器退出事件尚未审查完成时，禁止继续发放工作。

**MR-3：FreshManagerState**

恢复入口使用当前管理责任状态，并核对对应版本和身份。

**MR-4：NoFalseManagerSuccess**

缺少必要交接证据时不得宣告管理责任有效。

**MR-5：AutomaticFailClosed**

任何必需的关键失败都能触发安全停止流程。

**MR-6：SingleClose**

重复失败与重复关闭请求不会产生冲突终态。

**MR-7：NoReactivation**

CLOSED 后不能通过恢复入口重新获得执行资格。

**MR-8：BudgetConservation**

停止、交接和恢复不会重置预算及已预留信用。

**MR-9：EvidencePreservation**

自动关闭保留原始失败、资源和退出证据。

**MR-10：BoundedCleanup**

在声明的正常调度及系统调用前提下，清理流程具有有限等待与明确失败结果。

每项性质必须对应具体代码、状态字段和测试判据。
