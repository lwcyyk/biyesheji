## 三、第一阶段：明确批量预留语义

当前主选修复：

**对于能够静态确定最大访问额度 N 的子任务，一次持久预留精确 N 个信用。**

首先定义：

`reserve_exact(task_id, N)`

要求 N 必须来自已经冻结且可核验的子任务合同。

N 表示该子任务允许处理的最大计费访问数量，必须覆盖全部合法分支中的对应访问。

对于无法证明最大值的子任务，继续使用现有安全预留机制。

禁止使用未经证明的估计值代替 N。

### 3.1 全局预算

设全批总额度为 B。

定义：

- R：累计持久预留额度。
- A：已经实际处理的计费访问。
- U：已经预留但尚未实际使用的额度。
- Q：仍可发放的额度。

要求保持：

\[
R=A+U
\]

在计数口径一致、预留均成功且无历史模糊记录时成立。

全局必须满足：

\[
0\le R\le B
\]

每个子任务的实际访问：

\[
A_i\le N_i
\]

已预留额度必须覆盖全部已经执行及可能已经执行的计费访问。

若存在崩溃、中断或模糊事务，相关额度采用保守占用规则。

### 3.2 一次预留

子任务获得运行许可之前：

1. 核实批次身份及有效授权。
2. 核实 N 的来源和完整性。
3. 核实剩余全局额度是否足够。
4. 写入预留事务。
5. 完成必要的持久化屏障。
6. 核实预留状态。
7. 发放本子任务的 N 个局部信用。
8. 允许子任务开始处理计费访问。

不得在持久化成功之前授予实际执行权限。

### 3.3 子任务局部消耗

子任务获得 N 个信用之后，可以通过内存中的局部计数器记录使用情况。

每次计费访问之前必须检查局部剩余额度。

局部额度耗尽后，拒绝下一次访问。

禁止：

- 重复申请已经授予的同一批信用。
- 将批次信用迁移到其他子任务。
- 根据实际使用量随意返还未用额度。
- 通过重启恢复完整局部额度。
- 通过多个进程重复使用同一预留。

如果子任务提前结束，未用信用先按保守规则保持占用。

任何额度回收机制都需要独立的零执行证明和安全审核，本轮不引入新的自动退款机制。

## 四、第二阶段：崩溃与重复执行安全

重点检查以下情况。

### S1：预留前崩溃

尚未完成持久预留，不得启动子任务。

### S2：PREPARED 后崩溃

如果已经存在可能生效的持久预留记录，恢复时必须保守计费。

不能因为缺少 COMMITTED 标记就自动退还额度。

### S3：持久化完成但尚未发放局部信用

保留已经预留的信用。

恢复后不得创建第二份独立的 N 信用授权。

### S4：局部信用发放后崩溃

即使只实际使用部分信用，也要保持全部 N 的保守占用，除非存在已验证的安全回收合同。

### S5：重复提交同一 task_id

使用持久化身份与请求内容进行幂等检查。

同一 task_id 和相同请求返回原预留事实。

相同 task_id 与不同请求内容必须拒绝。

### S6：并发申请

两个 Controller 或重复启动不能同时从同一余额中获得重复信用。

核对现有锁、事务和预留日志是否能够保证这一性质。

### S7：日志短写或 fsync 失败

停止发放执行许可。

保留原始残片及模糊预留状态。

禁止自动清空不确定额度。

### S8：批次关闭或期限到达

子任务不得继续使用局部信用。

已关闭批次的额度不能转移到新批次。

### S9：子任务实际访问超过 N

第 N+1 次必须在语义处理前被拒绝。

不能先执行后补账。

## 六、第四阶段：修复时间计量证据

Perf 已经发现：

`COMMITTED` 复用了 `PREPARED` 时间戳。

本轮应修正新版本中的阶段时间记录。

至少记录：

- reserve request。
- journal PREPARED 写入开始。
- PREPARED 写入结束。
- fsync 开始。
- fsync 返回。
- COMMITTED 状态完成。
- 局部信用发放。
- 子任务启动。
- 子任务实际退出。

使用明确的单调时钟记录阶段耗时。

区分：

- 实际系统调用耗时。
- journal 编码和写入耗时。
- fsync 耗时。
- 预留前等待。
- 子任务运行。
- 监督调度。

绝对时间和单调时间分别保存。

不能继续用 PREPARED 时间戳充任 COMMITTED 的实际发生时间。

不要将记录的 fsync 调用耗时解释为完整存储设备的独立物理持久化延迟；持久化保证仍需结合操作系统和文件系统合同。

## 八、第六阶段：性能预测与后续验证标准

建立修复前后的操作成本模型。

设：

- N：子任务最大访问数。
- \(t_r\)：一次持久预留的实际耗时。
- \(t_l\)：局部信用扣减耗时。
- \(t_s\)：其他调度与执行成本。

修复前近似成本：

\[
T_{\mathrm{old}}\approx N t_r+t_s
\]

修复后近似成本：

\[
T_{\mathrm{new}}\approx t_r+N t_l+t_s
\]

上述公式是简化分析模型，需要根据实际实现确认每个成本项。

当前：

- 真实单次 fsync 耗时未知。
- 实际代码路径仍可能存在其他耗时。
- 未来性能收益尚未测量。

因此本轮只提交预测和可证伪条件。
