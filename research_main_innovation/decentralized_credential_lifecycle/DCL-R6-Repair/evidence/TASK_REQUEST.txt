## 三、第一任务：独立复核资源失败的实际原因

必须从 Windows API 调用、程序源码及原始计数器出发，重新建立完整证据链。

当前存在两条关键失败。

### RG-SETUP-1：Job 初始化失败

已知：

- v1 调用 SetInformationJobObject 返回错误 87。
- v2 将 Job 总限制和成员 Working Set 限制分开设置后，初始化成功。

要求：

1. 核对 v1 调用的确切信息类和字段。
2. 检查 `ctypes` 结构定义、字段大小、对齐及长度参数。
3. 检查 32/64 位类型是否正确。
4. 检查 LimitFlags 的组合是否合法。
5. 检查 Job 创建和限制设置的调用顺序。
6. 检查进程是否已经属于其他 Job。
7. 确认 v2 具体修复了哪些条件。
8. 区分真正确定的根因和仅有相关性的修订。

不得只因 v2 能成功初始化，就断言错误 87 的唯一原因已经确定。

### RG-MEMORY-2：内存峰值与限制值不一致

已知：

测试 Job 提交限额：

`100663296 bytes = 96 MiB`

报告提交峰值：

`115167232 bytes = 109.83203125 MiB`

超出报告值：

`14503936 bytes`

单进程 HardWS：

`33554432 bytes = 32 MiB`

报告进程峰值：

`33558528 bytes`

差值：

`4096 bytes`

同时观察到：

- HARDWS_MAX 已启用。
- Python MemoryError 已捕获。
- 测试程序实际保留五个 16 MiB 分配块。
- 进程正常退出。
- 整批精确 Working Set 峰值仍然为 null。

要求独立解释以上现象。

重点核查：

**A. Job 提交内存计数**

- `JobMemoryLimit` 的真实含义。
- `PeakJobMemoryUsed` 的真实计数范围。
- Job hard limit 的错误返回和失败路径。
- 峰值统计是否具有历史状态或暂态影响。
- 是否可能计入失败分配请求。
- 是否使用了错误的 Job 句柄或查询时点。
- 是否存在嵌套 Job 或进程归属问题。
- 是否存在实际提交与记录峰值的时间差。

**B. Working Set 计数**

- `SetProcessWorkingSetSizeEx` 的设置参数。
- `GetProcessWorkingSetSizeEx` 的读取结果。
- HARDWS_MAX 的真实标志。
- 工作集峰值计数器的实际来源。
- 当前工作集与历史峰值的区别。
- Windows 页面粒度。
- 进程退出前后的查询时点。
- 进程创建、初始化和限制应用顺序。
- 是否存在不同结构体计数口径混用。

**C. 进程树归属**

确认：

- Controller
- Watchdog
- Worker
- Probe
- 子进程
- 可能存在的附加辅助进程

是否全部纳入预期资源边界。

核查进程数限制、进程启动顺序、Job 关联以及异常退出路径。

### 必须遵守的判定原则

Windows Job 提交内存与物理 Working Set 属于不同资源指标。

不能使用以下方式直接宣告通过：

- 将 4 KiB 差值作为未经证明的容差。
- 将 Job commit 上限替代树 Working Set 上限。
- 将采样峰值替代严格峰值上界。
- 将 Python 堆限制视作整进程限制。
- 将 MemoryError 视作整批资源限制成立的充分证据。
- 将 `flags=6` 视作所有资源门通过。
- 将配置计算的 3 GiB 视作已校准硬保证。

先建立实际原因与可审查的上界，再修改资格判据。

## 五、第三任务：设计严格的资源上界

保持原始授权指标：

- 总访问状态数 ≤ 1,000,000。
- 总墙钟时间 ≤ 1,800 秒。
- 进程树 Working Set 峰值 ≤ 4 GiB。

资源上界必须覆盖完整批次，包括校准、失败、参考枚举、变异测试和证据重放。

### 5.1 内存上界

如果采用每进程 HardWS 限制与进程数量限制组合，应证明：

`全部可能同时存在进程的严格驻留内存上界之和 ≤ 4294967296 bytes`

必须覆盖：

- 全部允许角色。
- 允许的最大同时进程数。
- 控制器与监督器自身。
- 子孙进程。
- Windows 页面粒度或已证实的额外资源项。
- 限制生效之前的启动阶段。
- 进程被替换、退出和重新创建的阶段。

若存在不能证明的额外峰值，应将其归为未决上界，保留安全余量或采用有正式依据的更强机制。

降低单进程预算可以作为修复候选，但新的上界必须有依据。不能通过修改报告阈值掩盖原有失败。

### 5.2 访问计数

原 batch01 已实际消耗：

`visits = 27`

必须保留。

核对：

- 每次状态展开是否先获得额度。
- DP 缓存命中是否按合同计费。
- 参考枚举是否获得独立额度。
- 变异测试是否计费。
- 反例重放是否计费。
- 失败或崩溃时预留额度是否保留。
- 多进程写入是否可能丢失或重复计数。

禁止清零或重新解释历史访问。

### 5.3 墙钟时间

原 batch01 已登记：

`118.7340827 秒`

必须保留为历史实际消耗。

同时核对原始批次的绝对 deadline。

batch01 已经按资源失败分支停止。禁止延长其原有 deadline、重置计数或把新会话解释为新的免费时间窗口。

若原批次 deadline 已经过期，保持停止状态。

新的独立运行批次应取得明确新授权。

### 5.4 监督器自身失败

还需检查：

- Controller 崩溃。
- Watchdog 崩溃。
- 父进程意外退出。
- 系统终止子进程。
- 子进程拒绝退出。
- Job 句柄提前关闭。
- 异常退出导致日志未完整写入。
- 出现未登记子进程。
- 发生 breakaway。
- 进程计数达到上界。

要求默认执行安全停止，记录已知资源消耗和未完成证据。

## 七、第五任务：重新校准的完整计划

在资源口径和监督器静态修复完成之后，准备完整校准。

必须覆盖：

| 校准项 | 要求 |
|---|---|
| 正常退出 | 正确记录进程结束、资源和日志 |
| 访问计数超限 | 超额状态处理被阻止 |
| Job commit 限制 | 证明设置及计费口径 |
| HardWS 限制 | 证明设置、读取和峰值上界 |
| 整树内存 | 证明完整进程集合的聚合上界 |
| 墙钟超时 | 超限后完整进程树停止 |
| 异常退出 | 保留原始错误和证据 |
| 父进程失败 | 监督器及子孙按合同终止 |
| 子进程逃逸 | 禁止或检测未经许可的 breakaway |
| 重复启动 | 保留原始预算和版本状态 |
| 中断恢复 | 不重新获得已消费额度 |

必须使用低资源、确定行为的合成探针，避免影响冻结主工程。

每个校准需要有：

- 原始输入。
- 执行命令。
- 预期停止条件。
- 实际结果。
- OS 计数器记录。
- 运行资源数据。
- 退出码。
- 日志和版本 SHA-256。
- 明确 PASS/FAIL/INCONCLUSIVE。

只有全部必要资格条件成立，才能获得：

`RESOURCE_GATE_PASS`

如果任一关键硬界仍无法证明，保持：

`RESOURCE_GATE_FAILED`

并停止正式 F1/F4。

## 九、协议和论文裁决要求

本轮资源修复本身属于验证基础设施工作。

它可以提高协议验证的可信度，但不自动形成 D1/D2 的原创安全机制。

本轮不重新提出 I1/I2/I3。

不得将以下事项作为新的协议创新：

- Job Object 组合。
- Working Set 限制。
- 监督器修复。
- 普通有界状态枚举。
- 标准动态规划。
- 标准反例重放。

D1/D2 维持现有协议版本 1.1，除非正式验证发现满足全部假设的协议反例。

保持：

`IMPLEMENTATION_GATE = CLOSED`

F2/F3、Casdoor 构建、原生 T1–T4、外部联系与上传均在本轮范围之外。
