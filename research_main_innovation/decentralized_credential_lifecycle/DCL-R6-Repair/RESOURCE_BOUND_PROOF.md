# 严格资源界：已可证明部分与未闭合前提

2026-11-10。指标保持：访问≤1000000、墙钟≤1800秒、进程树驻留集峰值≤4294967296字节。当前没有完整RESOURCE_GATE_PASS证明；本文给条件引理及反驳原无条件推导的缺项。

## 1. 指标和树界引理

令P(t)为所有计入批次的活进程，含controller、watchdog、worker、probe、子孙及新辅助角色；W_p(t)为该进程驻留工作集。目标为`sup_t Σ[p∈P(t)] W_p(t) ≤ L`。共享页按进程工作集重复计入，不能用“实际物理页只占一次”缩小总数。

若从第一个计入进程的创建/启动阶段起，全部时刻满足：①树归属封闭；②内核保证|P(t)|≤N；③每个角色包含创建/切换/退出阶段的严格上界U_role；④最大并发角色预算和≤L，则逐t求和即得树峰值界。采样不是证明前提，commit限额也不是W_p的替代定义。

v2给N=4、M=768MiB，得到配置乘积3GiB。它只能在“所有四个成员每时刻都已经被有效M约束”成立时推出界。原程序先启动并导入Python，再为自己设置限制；子进程也有CreateProcess至HardWS应用的窗口。该窗口U_start尚无独立有限界，4KiB峰值事件的时间/统计口径也未闭合。因此原前提不足，3GiB不是本项目已获得的硬证明。

形式上，后置条件`∀t≥t_apply: W(t)≤M`不限制t_apply之前的W。给未约束窗口赋一个大值即可构造逻辑反模型；这说明**当前证明不充分**，不说明原Windows机器真的超4GiB，更不证明所有Windows方案都不可能。

## 2. 完整生命周期必须补齐

|区间/角色|当前已知|必须补证|
|---|---|---|
|首个controller解释器/模块启动|旧进程已运行后才进Job/HardWS；-I没有等价于-S|平台前置包络或可信的启动上界；v3加-S只减依赖，不能给内存界|
|watchdog创建/限制应用前|主线程CREATE_SUSPENDED，设置发生在Resume前|创建本身的驻留上界、系统辅助进程归属；主线程暂停不等于零驻留|
|稳态各成员|当前API文档给HardWS约束，旧读回成功|限制时窗、峰值口径、有效继承/不可逃逸、运行校准|
|进程替换/退出|Job配置ActiveLimit4，源路径受控|新旧重叠、存活句柄、PID复用、退出后的字段范围|
|controller/WD失效|KILL_ON_CLOSE与独立watchdog有条件作用|双向失效检测/正常停止握手、句柄所有权与整树终止实际证据|

v3因此保留`require_strict_bound_adapter()`为显式拒绝，未提供通过某个JSON布尔值开放模型的接口。该平台适配器当前未实现；静态修补不登记为硬界闭合。

## 3. 访问额度的条件保持

旧27不变。未来若所有模型语义入口先调用统一reserve、完整计数写入确认后才返回额度、并发受同一锁串行、计数不回滚，且任何模糊预留默认占用/停止，则对成功额度次数归纳可得≤cap。候选缓存命中、参考具体轨迹、变异与重放都需覆盖；v3还对输入状态校验预收费，业务计算不改。

v2缺短写/中断意图保护；v3增加PREPARED→counter fsync→COMMITTED与追加journal。未完成意图使后续拒绝，不能回收模糊额度。文件/磁盘异常、崩溃锁释放和并发事务仍待校准；没有把静态代码当成已执行证明。旧27不是v3重新解释的计数。

## 4. 墙钟及失效假设

绝对deadline保持原值；独立OS等待/监督器须在截止时终止完整树，CPU时间限额不能替代。用户态监控还依赖受信OS调度/计时/终止语义；若管理员能无限挂起全部监督者，普通用户态watchdog无法提供无条件实时保证。该故障边界须明示，不用公平性直接推出固定δ。

v3拒绝到期/关闭/未初始化批次，取消自动建立新时窗；watchdog异常按失败处理。新环境需对controller死亡、WD死亡、两者交互、Job句柄关闭和中断恢复全部取证；当前未获得这组运行证据。

## 5. 更强机制的条件备选

可审的替代方向为**启动前内核强制的全地址空间上限A＋不可提高的进程/任务数上限N**。普通驻留页属于地址空间，若每个计入进程在创建/首个执行入口前就满足AS≤A且N封闭，则`ΣRSS≤N×A`；例N=8、A=512MiB给4GiB。它连共享页重复计数也保守覆盖，前提包含无可绕过的特殊设备/未计入角色和严格启动时序。

[Linux RLIMIT_AS](https://man7.org/linux/man-pages/man2/getrlimit.2.html)和[cgroup pids](https://docs.kernel.org/admin-guide/cgroup-v2.html)提供相应机制语义，但目标平台/启动器必须验证，不能用Python进程启动后自设rlimit填启动窗。迁入过量任务可绕开pids.max的简单推导，必须禁止管理员迁入、调低限额或更换cgroup；计入init和所有辅助角色。

本机仅发现Docker/WSL CLI，未执行它们，也未认证daemon/镜像/内核。Docker普通memory限制不自动等于进程RSS之和，且[官方CLI明确不支持as选项](https://docs.docker.com/reference/cli/docker/container/run/#set-ulimits-in-container---ulimit)。不能提供`docker run --ulimit as=…`作为现成修复命令。

受支持的OCI/服务启动器或受控VM需要独立部署范围、启动前资源证据、代码/镜像/内核哈希与边界批准。Linux RSS与Windows工作集的驻留语义映射、平台TCB开销及所有新监督角色需显式审查；当前未切换平台。条件引理不是本机已建立的新后端。
