L1: Does Matter
L2: Ryo Nishimaki1
L3: NTT Corporation, Tokyo, Japan
L4: ryo.nishimaki.zk@hco.ntt.co.jp
L5: Abstract. We introduce a new deﬁnition for key updates, called backward-
L6: leak uni-directional key updates, in updatable encryption (UE). This
L7: notion is a variant of uni-directional key updates for UE. We show that
L8: existing secure UE schemes in the bi-directional key updates setting
L9: are not secure in the backward-leak uni-directional key updates setting.
L10: Thus, security in the backward-leak uni-directional key updates setting
L11: is strictly stronger than security in the bi-directional key updates setting.
L12: This result is in sharp contrast to the equivalence theorem by Jiang
L13: (Asiacrypt 2020), which says security in the bi-directional key updates
L14: setting is equivalent to security in the existing uni-directional key updates
L15: setting. We call the existing uni-directional key updates “forward-leak
L16: uni-directional” key updates to distinguish two types of uni-directional
L17: key updates in this paper.
L18: We also present two UE schemes with the following features.
L19: – The ﬁrst scheme is post-quantum secure in the backward-leak uni-
L20: directional key updates setting under the learning with errors as-
L21: sumption.
L22: – The second scheme is secure in the no-directional key updates setting
L23: and based on indistinguishability obfuscation and one-way functions.
L24: This result solves the open problem left by Jiang (Asiacrypt 2020).
L25: Keywords. updatable encryption, key update, lattice

L27: Introduction
L28: 1.1
L29: Background
L30: Updatable Encryption. Updatable encryption (UE) is a variant of secret key
L31: encryption (SKE) where we can periodically update a secret key and a ciphertext.
L32: More speciﬁcally, a secret key ke is generated at each period, called epoch. Here,
L33: e denotes an index of an epoch. We can generate a conversion key ∆e+1 that
L34: converts a ciphertext under ke (key at epoch e) to one under ke+1 (key at epoch
L35: e + 1). Such a conversion key is called update token and generated from two
L36: successive secret keys ke, ke+1. Roughly speaking, UE security guarantees that
L37: conﬁdentiality holds even after some old (and even new) keys and tokens are
L38: corrupted as long as trivial winning conditions are not triggered. Adversaries
L39: trivially win if a target secret key is corrupted or a target ciphertext can be
L40: converted into a ciphertext under a corrupted secret key. In this study, we focus
L41: on ciphertext-independent updates UE, where we can generate an update token
L42: only from two secret keys [LT18, KLR19, BDGJ20, Jia20].1
L43: 1The other variant is ciphertext-dependent updates UE, where we need not only two
L44: secret keys but also a part of ciphertext (called header) to generate a token [BLMR13,
L45: EPRS17, BEKS20]. Ciphertext-independent updates UE is more eﬃcient.
L46: A serious threat to encryption is key leakage. In that case, no security is
L47: guaranteed by standard encryption. Key updating is a standard solution to
L48: guarantee security even after key leakage. However, the issue is how to update a
L49: ciphertext generated by an old key. A naive solution is decrypting all ciphertexts
L50: by the old key and re-encrypt them by a new key. However, it incurs signiﬁcant
L51: eﬃciency loss. Moreover, if we save encrypted data in outsourced storage such
L52: as cloud servers, we need to download all ciphertexts from the server, decrypt
L53: and re-encrypt them, and upload them again to keep the new key secret. Update
L54: tokens of UE solve this problem since if we provide the server with an update
L55: token, it can directly convert old ciphertexts into new ones without the new key.
L56: Conﬁdentiality is the primary concern in UE. Conﬁdentiality of UE has been
L57: improved to capture realistic attack models [EPRS17, LT18, KLR19, BDGJ20,
L58: CLT20] since after UE was introduced [BLMR13]. In particular, Lehman and
L59: Tackmann formalized trivially leaked information from corrupted keys and tokens
L60: as the direction of key updates [LT18]. Although previous works proposed UE
L61: schemes with improved conﬁdentiality, most do not focus on preventing infor-
L62: mation leakage from corrupted keys and tokens. We will explain the detail of
L63: the information leakage below. In this work, we focus on the direction of key
L64: updates and try to minimize leaked information from update tokens to improve
L65: UE conﬁdentiality.
L66: Direction of key and ciphertext updates. Directions of key updates describe
L67: information leakage that UE schemes cannot avoid. If an adversary has ∆e+1 and
L68: ke, it might be able to obtain ke+1. Most existing UE schemes cannot prevent this
L69: attack. In particular, in all existing (ciphertext-independent) UE schemes, we
L70: cannot avoid leaking a secret key from both directions [LT18, KLR19, BDGJ20,
L71: Jia20]. That is, we can extract ke+1 (resp. ke) from ∆e+1 and ke (resp. ke+1). This
L72: setting is deﬁned as bi-directional key updates [EPRS17, LT18]. Lehman and
L73: Tackmann also deﬁned uni-directional key updates, where we can extract ke+1
L74: from ke and ∆e+1 (forward direction inference). In other words, this setting means
L75: adversaries might not be able to infer ke from ke+1 and ∆e+1. Uni-directional
L76: key updates are more preferable than bi-directional ones since a token leaks less
L77: information. More information leakage triggers more trivial winning conditions
L78: in conﬁdentiality games for UE.
L79: At ﬁrst glance, secure UE with uni-directional key updates is stronger than
L80: one with bi-directional key updates. However, Jiang proved that secure UE
L81: with bi-directional key updates is equivalent to one with uni-directional key
L82: updates [Jia20] (we call Jiang’s equivalence theorem in this paper). Jiang also pre-
L83: sented the ﬁrst post-quantum UE scheme with bi-directional key updates [Jia20].
L84: A natural question is: Why do we consider only one-way uni-directional
L85: key updates? That is, we can consider a variant of uni-directional key updates
L86: where we can extract ke from ke+1 and ∆e+1 (backward direction inference).
L87: To distinguish two versions of uni-directional key updates, we call the existing
L88: deﬁnition forward-leak uni-directional key updates and our new one backward-
L89: leak uni-directional key updates. The backward-leak uni-directional key updates
L90: setting has never been studied in the UE literature, but it seems to be a valid
L91: 2
L92: setting. It is natural to think the latest key is the most important since the reason
L93: why we update keys is that the current and older keys might be leaked. In the
L94: forward-leak setting, we must protect older keys to protect newer keys even if
L95: older ciphertexts are deleted. This is undesirable. However, in the backward-leak
L96: setting, we need to protect only the latest key if older ciphertexts are properly
L97: deleted. Therefore, the backward-leak key updates are more suitable for UE than
L98: the forward-leak key updates.
L99: A related issue is the direction of ciphertext updates. It describes whether we
L100: can convert ciphertext into one in an older epoch (downgrading ciphertext) by
L101: using an update token or not. If we can both update and downgrade ciphertexts
L102: by using a token, we say a UE scheme provides bi-directional ciphertext updates.
L103: If we can update but cannot downgrade ciphertexts by using a token, we say a
L104: UE scheme provides uni-directional ciphertext updates. UE with uni-directional
L105: ciphertext updates is more desirable since older epoch keys might be leaked, and
L106: downgrading ciphertexts leaks more information. However, all existing (ciphertext-
L107: independent) UE schemes provide bi-directional ciphertext updates.
L108: Thus, the ﬁrst main question of this study is as follows.
L109: Q1. Is UE with backward-leak uni-directional key updates strictly stronger than
L110: UE with bi-directional key updates?
L111: We aﬃrmatively answer the ﬁrst question in this work. Then, the next natural
L112: question is as follows.
L113: Q2. Can we achieve a (post-quantum) UE scheme with backward-leak
L114: uni-directional key updates and uni-directional ciphertext updates?
L115: We also aﬃrmatively answer the second question.
L116: Another natural question is whether we can prevent adversaries from inferring
L117: secret keys from both directions or not. That is, even if adversaries have ke+1
L118: (resp. ke) and ∆e+1, they cannot infer ke (resp. ke+1). Such key updates are called
L119: no-directional key updates [Jia20]. Jiang left this question as an open problem.
L120: Thus, the last question in this work is as follows.
L121: Q3. Can we achieve a UE scheme with no-directional key updates (and
L122: uni-directional ciphertext updates)?
L123: We solve this open question in this work.
L124: 1.2
L125: Our Contribution
L126: The ﬁrst contribution of our work is a deﬁnitional work. We deﬁne a new deﬁnition
L127: of key updates, which we call backward-leak uni-directional key updates. In
L128: addition, we prove that UE with backward-leak uni-directional key updates is
L129: strictly stronger than bi-directional key updates (and forward-leak uni-directional
L130: key updates). More speciﬁcally, we show that there are UE schemes with bi-
L131: directional key updates that are not secure in the backward-leak uni-directional key
L132: 3
L133: updates setting. This is in sharp contrast to Jiang’s equivalence theorem [Jia20]
L134: explained above.
L135: The second contribution is that we present two new constructions of UE. The
L136: features of our UE schemes are as follows.
L137: – The ﬁrst scheme is a UE scheme with backward-leak uni-directional key
L138: updates and secure under the learning with errors (LWE) assumption, which
L139: is known as a post-quantum assumption. This scheme satisﬁes conﬁdentiality
L140: against CPA and ciphertext updates are randomized.
L141: – The second scheme is a UE scheme with no-directional key updates and based
L142: on one-way functions (OWFs) and indistinguishability obfuscation (IO). This
L143: scheme satisﬁes conﬁdentiality against CPA and ciphertext updates are
L144: randomized.
L145: These are the ﬁrst UE schemes with stronger key updates. Note that all our
L146: schemes provide uni-directional ciphertext updates (i.e., cannot downgrade ci-
L147: phertext into older epoch ones). The ﬁrst scheme is implementable since it is
L148: directly constructed from lattices. Although the second scheme is a theoretical
L149: construction,2 it solves the open question left by Jiang [Jia20].
L150: Both schemes satisfy r-IND-UE-CPA security, which was deﬁned by Boyd,
L151: Davies, Gjøsteen, and Jiang [BDGJ20]. However, we consider the backward-leak
L152: uni-directional or no-directional settings. See Sec. 2 for the deﬁnitions.

L207: Technical Overview
L208: In this section, we present a high-level overview of our technique.
L209: Direction of key updates. As we introduce in Sec. 1.1, we can consider two types
L210: of uni-directional tokens, forward-leak and backward-leak uni-directional tokens.
L211: If we can infer in both directions, we call bi-directional token. In the deﬁnitions
L212: 3Their paper [SS21] appeared on Cryptology ePrint archive right after the initial
L213: version of this paper (https://eprint.iacr.org/2021/221/20210311:210911) appeared on
L214: Cryptology ePrint archive. The comparison here is based on the latest versions of their
L215: and our papers.
L216: 5
L217: of conﬁdentiality for UE, trivial winning conditions of adversaries depend on
L218: those token variations.
L219: We show the following adversary against existing bi-directional UE schemes:
L220: (1) s/he triggers the trivial winning condition of the forward-leak uni-directional
L221: key updates setting. (2) s/he does not trigger the trivial winning condition of the
L222: backward-leak uni-directional key updates. (3) s/he trivially breaks conﬁdentiality
L223: of the schemes in the backward-leak uni-directional key updates. Therefore,
L224: existing bi-directional UE schemes are not secure in the backward-leak uni-
L225: directional key updates setting. The best way to understand the separation result
L226: is looking at an example described in Sec. 3.3.
L227: In this section, we explain the source of the diﬀerence between the two
L228: settings. First, we recall that UE needs the power of public key encryption (PKE)
L229: such as the DDH assumption. We can ﬁnd this fact in all existing ciphertext-
L230: independent UE schemes [LT18, KLR19, BDGJ20, Jia20]. Alamati, Montgomery,
L231: and Patranabis [AMP19] prove that ciphertext-independent UE implies PKE.
L232: By this fact, we can assume that an epoch key ke consists of a secret part ske
L233: and a public key part pke. As an example, in RISE scheme [LT18], ske = xe ∈Zp,
L234: pke = gxe ∈G, and ∆e+1 = xe+1/xe where g is a generator of a prime-order
L235: group G. It is easy to see the token is a bi-directional token.
L236: The direction of key updates depends on how to generate a token. A simple
L237: but crucial observation is that we must use ske to generate ∆e+1. Otherwise,
L238: ∆e+1 does not have the power of decrypting and converting a ciphertext at epoch
L239: e. On the other hand, we do not necessarily need ske+1 to generate ∆e+1 since
L240: we can generate a ciphertext at epoch e + 1 by using pke+1.
L241: The relation between the direction types and how to generate a token is
L242: as follows. A forward-leak uni-directional token means ∆e+1 explicitly contains
L243: information about ske+1. By combining the observation above, ∆e+1 should
L244: contain information about ske and ske+1 in the forward-leak uni-directional key
L245: updates setting. In addition, we can update an older epoch ciphertext into a
L246: newer epoch ciphertext and attack the new one if the newer epoch key is revealed.
L247: In other words, we can attack older epoch ciphertext even if older epoch keys are
L248: not revealed (backward-leak inference is not possible in this setting). The key
L249: inference direction could be the same as the ciphertext update direction. By this
L250: observation, it is natural that Jiang’s equivalence theorem holds.
L251: On the other hand, a backward-leak uni-directional token means ∆e+1 explic-
L252: itly contains information about ske. It is possible to generate ∆e+1 from ske and
L253: pke+1 based on the observations so far. Thus, a backward-leak uni-directional
L254: token could hide information about ske+1 and prevent the forward inference. In
L255: addition, this property prevents downgrading a ciphertext into an older epoch
L256: ciphertext. Thus, even if an older epoch key is revealed, we cannot necessarily
L257: attack the newer epoch ciphertexts since downgrading ciphertext and forward-leak
L258: inference are impossible. The key inference direction is opposite to the ciphertext
L259: update direction. This property is in sharp contrast to the forward-leak setting.
L260: Therefore, triggers of trivial winning conditions are diﬀerent in these two set-
L261: tings. An intuition behind our separation result is based on those observations.
L262: 6
L263: See Sec. 3.3 for the detail. Those observations are the starting points of our UE
L264: scheme in the backward-leak uni-directional key updates setting. See the next
L265: paragraph for an overview.
L266: Our backward-leak uni-directional key updates scheme. Roughly speaking, a
L267: token ∆e+1 is a homomorphic encryption of ske under a public key pke+1 in
L268: our backward-leak uni-directional UE scheme. To update a ciphertext cte ←
L269: Enc(pke, µ) at epoch e, we homomorphically decrypt cte by using ∆e+1 =
L270: Enc(pke+1, ske) and obtain Enc(pke+1, µ). It is easy to see that if we have ∆e+1
L271: and ske+1, we can obtain ske by decryption. However, it is diﬃcult to infer ske+1
L272: from ∆e+1 and ske since ske+1 is not used to generate ∆e+1. By the security of
L273: PKE, it is diﬃcult to obtain ske+1 from pke+1. To achieve conﬁdentiality for UE,
L274: we need to re-randomize tokens and updated ciphertext. This is also possible by
L275: using the homomorphic property. Although we use the homomorphic property of
L276: lattice-based encryption in our construction, we do not need fully homomorphic
L277: encryption (FHE). We use the key-switching technique [BV14, BV11] and the
L278: noise smudging technique [AJL+12] to directly achieve secure UE from the LWE
L279: assumption. This idea is inspired by uni-directional proxy re-encryption schemes
L280: based on lattices [Gen09, ABPW13, CCL+14, NX15].
L281: To prove conﬁdentiality, we need to erase information about ske∗where
L282: e∗is the target epoch (otherwise, we cannot use conﬁdentiality under pke∗).
L283: However, secret keys are linked to update tokens. Thus, we need to gradually
L284: erase secret keys in update tokens from new ones to old ones. That is, we change
L285: Enc(pke+1, ske) into Enc(pke+1, 0|ske|). Once this change is done, we can change
L286: Enc(pke, ske−1) into Enc(pke, 0|ske−1|), and so forth. Note that there exists an
L287: epoch er where ∆er+1 is not corrupted such that e∗≤er as long as adversaries
L288: do not trigger the trivial winning conditions. We can start the erasing process
L289: from er since sker is not used anywhere. This proof outline is reminiscent of the
L290: proof technique for multi-hop universal proxy re-encryption [DN21].
L291: Our no-directional key updates scheme. A no-directional token leaks information
L292: about neither ke nor ke+1. To protect ke and ke+1, we obfuscate an update circuit.
L293: We consider a secret key encryption (SKE) scheme SKE.(Gen, Enc, Dec) and the
L294: following circuit R. Two diﬀerent secret keys ske, ske+1 ←SKE.Gen(1λ) are hard-
L295: coded in R. R takes a ciphertext cte ←SKE.Enc(ske, µ) as an input, computes
L296: µ = SKE.Dec(ske, cte), and outputs cte+1 ←SKE.Enc(ske+1, µ). A token is an
L297: obfuscated circuit of R[ske, ske+1] (notation [ske, ske+1] denotes that (ske, ske+1)
L298: are hard-coded). This scheme works as a UE scheme. Intuitively, a token does
L299: not leak information about hard-coded secret keys due to obfuscation security.
L300: However, we do not know how to prove conﬁdentiality of the scheme above.
L301: To prove security, we instantiate the SKE scheme and obfuscation above with
L302: puncturable pseudorandom functions (PRFs) and IO [SW21], respectively. That is,
L303: a secret key is a PRF key K, and a ciphertext is (t, y⊕µ) := (PRG(r), PRF(K, PRG(r))⊕
L304: µ) where PRG is a pseudorandom generator (PRG) and r ←{0, 1}τ. We slightly
L305: modiﬁed the update circuit above so that it takes not only a ciphertext at epoch
L306: e but also randomness re+1 for a ciphertext at the next epoch. That is, we use
L307: 7
L308: a circuit Cre[Ke, Ke+1]((t, c), re+1) that decrypts (t, c) by Ke and encrypts the
L309: result by Ke+1 and re+1. By using this particular scheme and the punctured
L310: programming technique with IO security [SW21], we can prove conﬁdentiality of
L311: our no-directional UE scheme.
L312: The issue is how to simulate update tokens in security proofs. Note that a UE
L313: secret key at epoch e is linked only to UE tokens ∆e and ∆e+1 in the construction
L314: above. In our no-directional scheme, to change target ciphertexts into random
L315: ones, we use pseudorandomness of a PRF key Ke∗, which is a UE key ke∗at
L316: epoch e∗. In the security game of pseudorandomness at punctured points, the
L317: adversary is given y∗and a punctured key Ke∗{t∗} where t∗is chosen by the
L318: adversary and tries to distinguish y∗is PRF(Ke∗, t∗) or random. The punctured
L319: key enables us to evaluate the PRF at all inputs except the punctured point
L320: t∗. By using Ke∗{t∗}, we can simulate tokens ∆e and ∆e+1 for all inputs except
L321: (r, y) such that t∗= PRG(r). The issue is that we cannot evaluate the PRF at
L322: t∗. However, we can overcome this issue by the standard exception handling
L323: technique since t∗can be randomly chosen by the reduction due to PRG security
L324: and y∗= PRF(Ke∗, t∗) is given as a target in the pseudorandomness game. We can
L325: construct functionally equivalent circuits by using Ke∗{t∗}, t∗, y∗, and exceptional
L326: handling. The exceptional handling cannot be detected by IO security. Thus, we
L327: can simulate update tokens and use pseudorandomness to prove conﬁdentiality.
L328: Organization. In Sec. 2, we review the syntax and security deﬁnitions of UE.

L338: In this section, we brieﬂy review the syntax and deﬁnitions of UE.
L339: Syntax.
L340: Deﬁnition 2.1. An updatable encryption scheme UE for message space M con-
L341: sists of a tuple of PPT algorithms (UE.Setup, UE.KeyGen, UE.Enc, UE.Dec, UE.TokGen, UE.Upd).
L342: UE.Setup(1λ) →pp: The setup algorithm takes as input the security parameter
L343: and outputs a public parameter pp. (This algorithm is an option for UE.)
L344: UE.KeyGen(pp) →ke: The key generation algorithm takes as input the public
L345: parameter and outputs an epoch key ke.
L346: UE.Enc(k, µ) →ct: The encryption algorithm takes as input an epoch key and a
L347: plaintext µ and outputs a ciphertext ct.
L348: 8
L349: UE.Dec(k, ct) →µ′: The decryption algorithm takes as input an epoch key and a
L350: ciphertext and outputs a plaintext µ′ or ⊥.
L351: UE.TokGen(ke, ke+1) →∆e+1: The token generation algorithm takes as input two
L352: keys of successive epochs e and e + 1 and outputs a token ∆e+1.
L353: UE.Upd(∆e+1, cte) →cte+1: The update algorithm takes as input a token ∆e+1
L354: and a ciphertext cte and outputs a ciphertext cte+1.
L355: Let T be the maximum number of the epoch.
L356: Security experiments. We review security deﬁnitions for UE in this section.
L357: Deﬁnition 2.2 (Correctness). For any µ ∈M, for 0 ≤e1 ≤e2 ≤T, it holds
L358: that
L359: Pr[UE.Dec(ke2, cte2) ̸= µ] ≤negl(λ),

L658: Observations on Deﬁnitions
L659: On the meaningfulness of backward-leak uni-directional key updates. First of
L660: all, all ciphertext-independent UE schemes rely on public key encryption power
L661: in some sense [LT18, BDGJ20, Jia20].4 This fact is endorsed by the result by
L662: Alamati, Montgomery, and Patranabis [AMP19], which shows any ciphertext-
L663: independent UE scheme that is forward and post-compromise secure implies
L664: PKE. Thus, we can assume that an epoch key consists of a secret key part ske
L665: and a public key part pke.
L666: To achieve the ciphertext update mechanism of UE, a token ∆e+1 must
L667: include information about ske since an update algorithm essentially decrypts a
L668: ciphertext at epoch e and generates a ciphertext for epoch e + 1. The question
L669: is: “Do we really need ske+1 for updating a ciphertext from e to e + 1?”. The
L670: answer is no. The point is that we need only the public key part of an epoch key
L671: to generate a ciphertext in most existing ciphertext-independent UE schemes.
L672: Thus, we might be able to construct an update token by using only ske and pke+1.
L673: More speciﬁcally, we might be able to transform a ciphertext for epoch e by using
L674: 4Everspaugh et al. [EPRS17] presented a ciphertext-independent UE scheme from
L675: authenticated encryption (AE). However, they assume an AE scheme is secure against
L676: related key attacks. So far, it seems that we need the power of public key encryp-
L677: tion (such as DDH) to achieve related key secure AE [HLL16]. In addition, Ev-
L678: erspaugh et al. retracted the ciphertext-independent construction in their full version
L679: paper (https://eprint.iacr.org/2017/527/20180903:192110).
L680: 14
L681: encryption of ske under pke+1 and homomorphic properties. This is what we do
L682: in Sec. 4. This insight comes from a few constructions of uni-directional proxy
L683: re-encryption [Gen09, ABPW13, CCL+14, NX15].
L684: Based on the observations above, we can say the backward-leak uni-directional
L685: key updates setting is natural. If a token ∆e+1 is generated by using (ske, pke+1), it
L686: is likely we can infer ske from ∆e+1 and ske+1 (our backward-leak uni-directional
L687: scheme is an example). However, it might be diﬃcult to extract information
L688: about ske+1 from ske and ∆e+1 since only pke+1 is embedded in ∆e+1. In fact, it
L689: is diﬃcult in our backward-leak uni-directional scheme.
L690: In the forward-leak uni-directional key updates setting, we assume that it is
L691: easy to infer ske+1 from ∆e+1 and ske. In some sense, this says ske+1 is directly
L692: embedded in ∆e+1. We might be able to execute bi-directional key/ciphertext
L693: updates if a token enables us to update a ciphertext (in the forward direction).
L694: Here, “directly embedded” means that a secret key is not encrypted. In fact,
L695: in all existing UE schemes bi-directional (and forward-leak uni-directional) key
L696: updates, ske+1 is directly embedded in ∆e+1 [LT18, KLR19, BDGJ20, Jia20]. In
L697: addition, generating a token ∆e+1 from ske+1 and pke is unnatural since it is
L698: unlikely such ∆e+1 can update a ciphertext under pke.
L699: Note that the argument above does not consider obfuscation [BGI+12]. If we
L700: can somehow obfuscate secret keys in a token, it could be diﬃcult to infer secret
L701: keys in the token even if we use those secret keys to generate the token. This is
L702: what we do in Sec. 5 to achieve a no-directional key updates scheme.
L703: As we argue in Sec. 1.1, backward-leak uni-directional key updates are more
L704: suitable than forward-leak ones in practice. In fact, we prove that conﬁdentiality
L705: in the backward-leak uni-directional key updates setting is strictly stronger than
L706: that in the forward-leak uni-directional key updates setting.
