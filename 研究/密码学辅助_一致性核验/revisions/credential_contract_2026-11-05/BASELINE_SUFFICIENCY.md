# G0与G9的充分性、费用和反例

本文件区分已观测实例、纸面条件命题和生产实现。以下充分性属于既有中介、事务及有限处置原理的实例化，原创性主张为0。

## 1. G0的完整规格

G0在可信R上做直接检查，但仍需同时满足当前批准、材料来源、task/account/audience/caller绑定、精确请求和原子接纳。结果只在其接纳边界生效。对未知来源或恢复后当前性缺口保留UNKNOWN。

现有代码提供以下支撑与缺口。

| 入口 | 已有功能 | 所需保证的缺口 |
|---|---|---|
| Gate.call | 操作许可、预算、故障注入及请求记账 | dispatch在锁外，缺少task/epoch生产式原子接纳 |
| Resource | task到原生AT映射、use关闭、remote对照 | 同时要求Bearer，没有独立代理身份和任务句柄授权协议 |
| BoundedController | 有限W_r筛选、内存pending和异常UNKNOWN | 表模型适配器，实际凭据持有与崩溃恢复另需实现 |
| Witness | 签名/issuer/audience/sub、内省及资源结果核验 | 评分结论不能自动作为运行者决策输入 |
| ci01固定序列 | W01来源隔离、待决结果和已知子代收尾 | 生产当前批准、完整队列与持久中介闭包未验收 |

锁外I/O可以与先原子接纳、再登记在途的正确设计兼容。这里保留的缺口是完整请求/任务代次绑定、可靠pending及恢复终态协议，不能仅凭锁外dispatch断言发生了并发授权漏洞。

这些缺口使G0的生产充分性保持条件性。G0逻辑无需新增隐私原语，并不表示现有原型已经完整实现G0。

## 2. 条件合同类F_MED

在同一声明资源profile内，定义F_MED满足下列条件。

1. R及其适配器可信，A无法取得或重新取得所选授权的原生材料、管理凭据、会话或可用签名能力。全部相关入口可被穷尽登记。
2. 每个请求在真正派发前与当前批准、精确请求和材料来源绑定，退役后不会出现清单外A派发。
3. 退役前已派发的请求数量有限，pending来源清单完整，所有产生的新材料归入原代次。重试不会被无依据地当成同一次原生效果。
4. 当前批准与pending/来源记录持久且恢复后可获得可信最新状态。
5. 每个待决请求最终获得可寻址结果，或获得符合原生合同的终态/无效果及围栏事实。有限预算足以执行这些步骤。
6. 对每个A原生处置单位，已确认的原生动作使所选UserInfo/refresh路径拒绝，后续允许转移不会恢复该退役单位。
7. A处置与B支持不重叠。B的批准、期限及其他环境条件在声明区间保持有效。若保留目标包含端到端使用，还要求R服务可用且调度不会因A收尾使B失去该目标。
8. 任何声称已完成的记录都在全部相关义务结清、证据作用域匹配后产生。

其中第1—4项是部署与实现前提，第5—7项还含原生契约和活性前提。N01/W01没有证明整个F_MED符合性。

### 条件命题 G0加有限原生处置充分

在F_MED中，G0先退役A.g0并停止其新派发，收集完整pending的终态，对已有和新返回的A单位执行声明的原生处置，保持未知项为义务，最后核对所选接受路径。

证明按不变量展开。初始材料和请求具有完整来源。当前批准及真实派发边界使退役后没有新的清单外A请求。每个已发请求的结果继续留在A.g0，B新批准不改变它。有限且可解决的pending只增加有限个已归属处置项。按第6项逐个关闭这些单位后，所有声明范围内A的原生接受均被排除。第7项在声明的可用性等级内保留B，持久当前状态使恢复后不会重新启用旧批准。原生B仍有效与R故障期间端到端可用分别判断，后者需要额外实现前提。

因此L成立，在途闭合后U与所声明的N成立。完成策略的终止依第3、5项，未知结果无统一解决界时仅保留安全拒绝/UNKNOWN，不能从有限决策步数推出墙钟完成时间。

该命题的作用是列出G0何时足够。它没有把生产闭包当成已经观察到的事实。

## 3. G9的重新审计

C02证明应用client_id/secret在本次用户过滤查询中取得A1/B0原生句柄。查询本身由评分者执行，尚无利用它自动恢复或撤销的运行策略。

| 义务 | 当前事实 | 完整G9所需内容 |
|---|---|---|
| 查询授权 | Basic应用凭据成功、普通Bearer业务error | 方法明确获准使用管理接口及允许数据范围，同条件给候选和G |
| 查询过滤 | C02传owner、organization、pageSize=100、p=1、field=user及用户名 | 核验组织和精确用户，处理API实际匹配语义 |
| 分页 | 实测只有2条、一页 | 全页读取、稳定排序/快照与无缺页证明，失败保留UNKNOWN |
| 结果传输 | API返回原生accessToken/refreshToken，日志只存摘要 | 全部返回字节、内存和秘密保管计费，管理结果不能直接变成代理输出 |
| 任务与派生归属 | A/B标签来自冻结调用序列和受信来源 | 从账本将原生记录映射到授权根/代次，不能按同账户或时间近似替代 |
| 枚举期间新材料 | C01说明旧A能独立刷新 | 有效的发行截止/完整pending闭合，或继续UNKNOWN |
| 撤销竞争 | 旧父撤销不关闭已产生子代 | 记录所有可能后继及真实关闭边界，处理先读旧记录后签发等相容顺序 |
| 保留B | 有限独立grant实例支持 | 归属及处置范围独立，含B刷新/期限的时间要求 |
| 未知后继 | 存在能力与接口缺口 | 保留来源不明、分页不全、结果丢失、未决请求，完整收尾证据不足时停止宣称完成 |

### 查询语义的静态核查

controllers/token.go的GetTokens只有在pageSize与p同时存在时使用field/value及分页分支。任一缺失时走GetTokens(owner,organization)，该分支没有使用field/value。G9适配器必须校验自己实际调用的分支。

分页分支经GetSession使用LIKE '%value%'，属于子串匹配，默认created_time排序。C02的随机新用户名及返回行精确核对在实例中成立，不能推广为所有用户名上的服务端精确隔离。客户端后置核验可以防止误处置，已经取得其他账户秘密时还涉及查询授权边界。

GetTokenCount和取页是不同查询，页面间没有本次审查已确认的快照版本或原子截止句柄。默认排序也未给出唯一tie-breaker证明。不能凭第一页的数量元数据宣告并发期间的完整清单。

### 分页与竞争反例

纸面例取每页2条，初始按创建时间降序为[B_old,A_target,B_keep]。B刷新先插入B_new，列表变成[B_new,B_old,A_target,B_keep]，此时第一页返回[B_new,B_old]。随后刷新删除B_old，列表为[B_new,A_target,B_keep]。第二页仍合法，offset=2返回[B_keep]，A_target被跳过。前后总页数均为2，单靠页数一致也无法发现遗漏。该例没有新增A材料，B_keep持续保留。

此例适用于允许B合法刷新且以任务可用性为目标的合同，并假定查询可与刷新内部步骤交错。它与已读的先AddToken再DeleteToken顺序相容，实际数据库事务/调度尚未原生复现。如果合同冻结每个B原文或有已证明的全查询互斥/快照，需重新判断适用性。该反例只说明offset遍历缺少清单一致性前提，不否定具备这些前提的强G9。

收集完清单再处置可以排除自身变更造成的一类干扰，其他并发写入和未知来源继续需要处理。

另一纸面例在枚举后、处置前允许A刷新当前RT得到新子代，旧行可能被删除，撤销旧值返回200。C01/W01提供了该模式的原生步骤证据，任意交错的完整运行仍未穷尽。上述例反驳缺少快照/截止条件的一遍扫描，未证明所有同能力G9策略不可行。

## 4. G9条件充分性

定义F_ENUM为F_MED中可用枚举恢复句柄的子类，另要求查询授权成立，返回范围完整且一致，任务归属可靠，所有A创建前沿已关闭，枚举后的处置不会遗漏相关后继，保留B条件成立。

G9在完整清单上只选择确定归属A的原生单位，对不确定记录保留UNKNOWN。归属正确避免误撤B，完整清单及关闭创建前沿避免漏A，原生处置正确给出N。G0维持退役和入口约束，后续恢复仍需可信当前状态。

这是一项条件充分性论证。如果为了稳定枚举暂停B的刷新，需要证明B在该窗口仍满足原定可用性，计入等待与期限条件。当前C02只证成权限与句柄可见性，尚未证成F_ENUM的完整映射。非分页全量查询可作为条件对照，但其更广返回范围、秘密暴露、传输和批准成本必须符合相同合同。

## 5. 成本边界

设P为必要页数，N为实际返回记录数，M为确定归属A且需处置的不同原生撤销单位数，V为核验请求数，F为失败/恢复新增请求。一次稳定扫描并处置的外部请求账本至少为P+M+V+F，来源账本、当前状态与管理批准另外计入。材料字符串数与原生撤销单位数分别登记。

传输按全部字段与实际token字节计量，空间至少包括已读清单、映射及pending。若有重复扫描或不稳定分页，不能继续使用一次扫描的P。没有前沿或收敛保证时，固定重复次数没有推出完整性。

W01相对仅撤父材料增加1次已知子代revoke，支持该实例终点。C02仅测一页两个记录和两种凭据权限，不提供大规模分页、并发收尾或性能分离。三批199次HTTP及22次采样数据库查询、4次事后只读查询和44次签名验证属于完整历史取证成本。

## 6. 三种合同的充分范围

| 合同 | G0/G9结论 | 仍需补齐 |
|---|---|---|
| P-MED满足F_MED | G0加既有原生处置条件充分 | 实现与部署符合性、持久状态、所有材料通道 |
| P-MED且需要枚举并满足F_ENUM | G0+G9条件充分 | 查询范围、可靠映射、稳定清单与前沿 |
| P-EXPORT且A可继续派生 | G0只控制本地，G9不能凭一次列表保证完整关闭 | 接收端截止、完整来源及同条件成熟能力 |
| 真正跨信任私密输入 | 当前尚无真实需求实例 | 先冻结角色、允许泄漏和独立验证职责 |

一条流程覆盖只排除该实例中的独立机制必要性。当前缺口集中于实现前提、接收方能力和恢复信息，没有证据把它们升级为必须由新密码协议解决的问题。
