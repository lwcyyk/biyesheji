## 2. 只研究一个主要功能

主要对象为 `F_AUTH_CURRENT`：可信 R 在撤回、迟到结果与恢复下，维持本地当前授权状态。三层责任为：

1. **L1 当前状态连续性**：已经承诺的撤回、消耗、预算和批准更新在恢复后仍有正确效力。
2. **L2 来源接口**：请求、调用者、任务、账户、受众、操作摘要及批准代次绑定；在途结果保持原来源。
3. **L3 原生效果**：AS/RP 的派生截止、已发请求终结和最终资源拒绝。

本轮证明和覆盖主要针对 L1，组合时保留 L2。L3 依赖对应接收方接口、完整观察与截止契约。旧 Bearer 的旁路接受、RT 后继、共享根处置和账号重置分别计量。

### 状态与接口

状态为 `S=(approval, pending, consumed, budgets, provenance, version)`。批准实例使用唯一 `(task, account, grant_id, generation)`；重新批准生成新实例。`pending[rid]` 绑定原批准与规范化请求摘要，保留 `UNSENT / DISPATCHED_UNKNOWN / RESULT_KNOWN / DISPOSED` 等明确状态。这里定义纸面功能，现有代码的生产实现状态见第 6 节。

- `Grant(authenticated_user_request)`：验证用户身份、用途与重复请求标识，提交新批准。
- `Revoke(grant_id, generation)`：持久提交撤回。只有满足所选合同的提交条件才发成功 ACK。
- `Begin(rid, binding)`：在同一本地线性化点检查当前批准、绑定、预算与消费条件，提交 pending 后才允许外发。是否允许已接纳待发请求在撤回后发送，由 L2 发送围栏合同决定。
- `Receive(rid, result)`：核验来源和请求绑定。旧 A 的结果归属 A 的原代次；隔离、拒绝或处置均保留原记录。新 B 批准单独检查。
- `Crash / Restore(snapshot) / Recover(freshness_source)`：核验状态完整性与当前性，恢复已提交记录及未决义务。证据不足返回 UNKNOWN。
- `Admit(binding)`：只有已恢复的当前状态允许该请求时返回 ACCEPT；确定无资格返回 REJECT。

`UNKNOWN` 表示缺少当前状态、来源或外部结果证据；`ABORT` 表示此次恢复/协议没有完成。二者均保持相关义务。持久拒绝所有合法任务无法满足合法恢复要求。

撤回 ACK 承诺的是 L1 截止：此后线性化的本地接纳拒绝该旧批准。此前已经接纳的外部操作继续保留 pending；将其全部关闭需要 L3 证据。读到当前版本与随后原子接纳之间也需要串行化、有效租约/失效通知或权威端验证，单次新鲜读不能授权无限期使用缓存。

## 3. 统一安全游戏与条件合同

攻击者控制旧代理及普通存储，可复制、修改、重放和隐匿快照，调度网络、迟到结果、崩溃和恢复。R、认证用户根、选择的当前性锚点及其密钥在模型内可信；自适应腐化这些可信组件未纳入主模型。密钥回滚若影响防重放状态，必须受同一锚点保护。密钥泄露需独立重开模型。

攻击者可调用合法用户接口产生新批准和撤回，提交自己获准的请求，执行 `Snapshot / RestoreOld / DelayResult / Replay / Crash / Recover / AttemptAdmit`。合法用户批准由挑战者认证，攻击者无法借接口伪造用户意愿。多恢复者扩展另允许 `Fork`，同时要求权威串行化或共享锚点具备全局互斥/栅栏作用。

安全失败事件：

- 撤回 ACK 以后，旧批准的新本地接纳返回 ACCEPT；
- 旧 A 的结果被记为 B 的新批准来源，或同一请求改正文/改代次后被当作等价重试；
- 恢复导致已消费资格或预算被再次使用；
- 在要求单一当前状态的合同中，两个被接受的恢复分支产生互相冲突的当前资格。

安全要求对上述允许轨迹的失败概率为 `negl(λ)`。可用性另在明确的稳定窗口内要求：当前可信状态和必要普通数据可获得、调度公平、获准通信可达、所需硬件存活时，恢复合法 B。中断上界记 `L_B`，本轮数值未定。无限恶意阻断或全部数据删除时，保留 UNKNOWN/ABORT；安全本身无法恢复被删除的信息。

| 条件模型 | 当前性来源 | 破坏/恢复能力 | ACK 与可用性条件 |
|---|---|---|---|
| T：可信当前数据库 | 数据库及恢复流程本身抗回滚 | 应用进程崩溃；数据库可信当前性保留 | 事务持久后 ACK；恢复数据可取 |
| O：离线任意断电 | 本地不可回滚持久锚点 | ACK 后可立即丢失全部易失状态；普通盘可回滚 | ACK 前建立持久区别；最新数据可取时恢复合法状态 |
| C：可靠关机检查点 | 受保护易失状态＋关机前可信刷写 | 每次破坏性掉电前保证 checkpoint | 硬件、UPS、关机处理及恢复条件全部计费 |
| N：在线当前权威 | 可信权威/合格复制账本 | R 本地缓存可丢失；权威仍满足其故障假设 | 权威提交后 ACK；恢复等待认证新鲜答复；接纳与撤回协调 |
| F：仅分叉一致历史 | 客户端各自历史见证 | 服务可隔离客户端 | 单独只提供历史一致/分叉检测；严格全局当前性需要增强 |

这些为条件分支，共用功能与成本账本。用户尚未选定实际分支。任意完全丢失可信当前信息的故障，不能直接套用依赖存活副本的模型 N。

## 4. 成本向量

`n` 为批准实例数；`u` 为影响安全的逻辑状态更新数；`c` 为恢复次数；`m` 为需保留的未决请求数。`u` 包含需要防回滚的消费、预算、来源与 pending 更新。可丢缓存、无状态读和幂等重复查询可单独优化。`b` 为满足相同承诺合同的已提交组数；一次组提交可包含多个更新。独立顺序承诺的最坏输入可有 `b=u`，一般输入无需如此。

辅助参数：`λ` 安全参数；`ℓ` 平均业务记录字节；`N` 当前认证索引条目数；`d_h` 一次恢复的增量历史大小；`a` 可信远端节点数；`Δ` 撤回正常 ACK 时限；`τ` 一次成功提交耗时。原文的具体安全参数和旧硬件性能保持原值；论文的历史毫秒测量没有移作本项目实测。

## 5. 条件充分性的组合论证（H）

假定：可信状态后端提供符合所选故障模型的当前性；批准验证正确；本地接纳和撤回串行化；请求/来源绑定完整；必要 pending 在外发前提交；恢复读到最新提交状态，或明确返回 UNKNOWN；合法恢复的存储和调度前提成立。

将上述 F 的状态机运行在该后端上。归纳每个提交点：Grant 仅加入经过认证的新实例；Revoke 将目标实例置为撤回；Begin 只能依据当前有效实例记账；Receive 保留原请求绑定；Recover 只重建同一已提交前缀或保留未知。于是三个本地安全失败事件均被状态转移守卫排除。多恢复者还需同一后端线性化和消费点栅栏。合法 B 的恢复由后端可用性与应用调度共同保证，具体上界待合同实例化。

这是标准可信状态机和状态连续性的组合实例。其充分性适用于满足这些前提的合同类；当前项目部署符合性仍未验收。证明没有推出原生 AS/RP 全局关闭，也没有推出最优一般资源下界。
