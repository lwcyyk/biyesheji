**可以。建议把新增密码学工作收敛为一个明确的协议，而不是同时叠加零知识证明、门限加密、匿名凭据和区块链。**

本轮我建议设计：

> **CCT-AB：面向 AI 代理的封闭凭据转换与可撤销使用协议**  
> *Closed Credential Transition Protocol for AI Agents*
>
> 核心目标是：**在一个凭据执行组件被主动攻破的条件下，用户批准的认证仍可通过两个独立执行域联合完成；密码、Cookie、访问令牌及刷新产生的后继材料始终保持为受保护状态，同时把“认证证据”和“后续实际使用的材料”绑定到同一次真实认证转换。**

这里的“封闭”有精确定义：**凭据可以被使用，也可以产生新的凭据；这些转换不应将可复用的认证能力输出给 AI 或单个执行域。**

这是本轮提出的**新候选协议设计 v0.1**，不是已经证明安全或确认全球首次的协议。下面给出近邻约束、具体构造、拟证明性质、与 A＋B 的连接，以及能够否定创新主张的比较条件。

## 一、调研结论：创新应落在哪里

### 1.1 直接近邻已经覆盖了哪些内容

| 工作 | 已有贡献 | 本方案不能重复主张的内容 |
|---|---|---|
| **SUDP，核对到公开 v3** | 操作规范化、用户批准、一次性使用授权、托管方代用秘密；明确讨论可复用派生权能。 | “AI 不拿密码，只提出操作”“批准绑定请求”“一次性使用秘密”不是新思想。其 v3 将托管方使用过程中的完整运行时失陷列为协议层范围之外。 |
| **Oblivious TLS，CT-RSA 2021** | 将 TLS 1.3 端点置于 MPC，针对主动腐化参与方给出安全构造，并可连接未修改的 TLS 对端。 | “两个参与方不重构密码而联合运行 TLS”已有直接基础。 |
| **DECO，CCS 2020** | 证明 TLS 数据来源和相关命题，同时保护未披露数据。 | “为网站返回的数据生成隐私证明”不是新的研究空白。 |
| **Garble-Then-Prove，USENIX Security 2024** | 利用特定的非对称安全目标降低网页数据认证成本，并支持将认证数据转换为承诺。 | “认证数据转承诺”“延迟检查加速 TLS 证明”已有深入研究。 |
| **TLSNotary** | MPC-TLS、选择性披露、在线及延迟解密。 | “只展示响应中的一部分”不是新机制。 |
| **反应式安全计算** | 处理保留内部状态、持续接受输入并产生输出的安全计算。 | “让 MPC 有状态、跨多轮执行”本身不是创新。 |

以上判断分别依据 SUDP 正文、Oblivious TLS 原始论文、DECO 作者资料、Garble-Then-Prove 原文、TLSNotary 官方文档和反应式计算的原始理论资料。:chatgpt-content-reference{index="0"}

因此，上一轮提出的“用 MPC 保护整个认证过程”仍然太宽。进一步设计必须回答：

> **已有 MPC-TLS 能保护通信计算，为什么还需要你的协议？它新增了什么必须被定义和证明的关系？**

我建议把答案集中在：

**跨认证步骤持续成立的“同源证据—同一材料—当前使用资格”关系，以及一种避免认证材料先被解密导出、再重新封装的协议表示。**

### 1.2 一个对本方案非常重要的近邻差异

Garble-Then-Prove 的论文明确利用了证明者和验证者安全目标的不对称性：某些行为可以在事后被检查，部分秘密输入最终会向证明者公开。这适合其原来的网页数据认证任务。:chatgpt-content-reference{index="1"}

但你的增强目标要求：

**即使执行者是恶意的，也不能先取得认证材料，或者先生成未经批准的有效认证请求，再靠事后拒绝证明补救。**

因此：

> **“最终证明会失败”与“失败前没有释放额外认证能力”是两个不同目标。**

这是应当写进新协议定义的区别。不能直接把某种网页证明协议当作安全执行协议，也不能因此称原论文存在漏洞。

## 二、建议研究的精确问题

### 2.1 从单次秘密使用扩展到认证状态转换

现有设计中的一次操作，可以抽象为：

\[
\operatorname{Use}(credential, request)
\rightarrow result
\]

对于持续工作的 AI，这个表示不够完整。更合适的是：

\[
\operatorname{Transition}
(
\Sigma_t,\ Approval,\ Request
)
\rightarrow
(
\Sigma_{t+1},\ Evidence,\ BusinessOutput
)
\]

其中：

\[
\Sigma_t=
\{
\text{长期凭据、Cookie、访问令牌、刷新材料、必要通道状态}
\}
\]

一次登录可能产生 Cookie；一次刷新可能替换旧材料；一次查询可能同时返回身份信息和新的认证材料。

**拟研究的对象不是一个“加密密码容器”，而是一个持续处理认证状态、且输出受限制的密码协议。**

### 2.2 三个必须解决的最小反例

以下是本轮为新协议提出的研究反例，不是对既有产品的漏洞报告。

**反例一：保护了密码，却交出了会话。**

密码在 MPC 中完成认证，但 `Set-Cookie` 被明文返回给执行器。密码没有泄露，执行器仍然获得了可绕过后续批准的认证材料。

**反例二：证据正确，使用材料却被替换。**

系统取得了“工作账户认证成功”的真实证据，但后续使用的 Cookie 来自另一会话。单独验证证据和单独保护 Cookie，都不能证明二者属于同一条认证路径。

**反例三：迟到材料绕过停止。**

用户停止任务后，先前刷新操作的结果才到达。结果真实，但新令牌不能因此自动成为该任务的普通使用材料。

你的历史研究已经明确区分原范围关闭、本地继续路径和实际远端接受，也明确指出本地切换不能保证远端持续可用。新密码协议应继承这些边界，而不是用“密码学保护”覆盖它们。:chatgpt-content-reference{index="2"} :chatgpt-content-reference{index="3"}

## 三、CCT-AB 的定位和威胁模型

### 3.1 参与方

建议设置五类参与方：

| 参与方 | 职责 | 是否持有完整认证秘密 |
|---|---|---|
| 用户 \(U\) | 登记凭据、确认目标和批准 | 初始登记时可以知道 |
| 控制核心 \(Q\) | M03/M08/M10 的批准、检查、预算和版本职责 | 增强执行路径不需要持有运行中的完整材料 |
| 执行域 \(E_0\) | 持有一份秘密状态，参加联合认证 | 否 |
| 执行域 \(E_1\) | 持有另一份秘密状态，参加联合认证 | 否 |
| 原生服务 \(S\) | 正常认证和业务执行 | 按其原生认证方式接收必要材料 |

AI 位于不可信请求方一侧，可以提出业务操作，但不属于批准源或秘密恢复方。

### 3.2 首版攻击模型

建议先固定为：

\[
\mathcal A
\text{ 可控制 AI、网络调度及 }E_0,E_1\text{ 中至多一个}
\]

被控制的执行域可以任意偏离协议、保存全部自身内存、重放消息、替换输入、选择性中止，并与 AI 串谋。

同时保留以下前提：

控制核心及用户批准入口可信；两个执行域不能同时失陷；诚实执行域的软件和密钥存储没有被攻击者读取；外部服务在已审定的认证契约范围内运行。

**首版只研究静态腐化。**暂不承诺攻击者先控制一个域、再控制另一个域，也不承诺两域失陷后的主动恢复或完整后向安全。

这属于对原架构的显式增强。两份秘密份额若部署在一个可被同一宿主管理员任意读取的环境中，就不能宣称抵御该宿主管理员失陷。

### 3.3 必须说明的代价

两个执行域中任意一个拒绝参与，都可能导致任务无法完成。因此首版目标是：

> **恶意安全且允许中止，不承诺恶意参与方存在时仍保证完成。**

此外，原有简单 P 路线仍然保留。**P/I/G 表示账户使用和授权配置；是否采用双域密码执行，是另一维度。**P 可以由普通可信代理实现，也可以由 CCT-AB 的双域执行后端实现，不必为了使用密码学而强制创建 G。

## 四、核心机制：将凭据表示为“可验证的受保护状态”

协议采用标准密码原语，研究增量放在协议构造和安全关系上，不重新设计 AES、签名或哈希函数。

### 4.1 基础原语

建议首版使用以下抽象：

\[
\operatorname{Sig},\quad
\operatorname{Com},\quad
\operatorname{AEAD},\quad
\Pi_{\mathrm{2PC}}^{\mathrm{mal}},\quad
\Pi_{\mathrm{TLS}}
\]

分别表示不可伪造签名、隐藏且绑定的承诺、认证加密、主动安全两方计算以及受保护的 TLS 实现。

MPC 后端必须选择主动安全模式。MP-SPDZ 官方资料区分了被动、主动、诚实多数和不诚实多数等不同协议配置，不能只因为使用了某个 MPC 框架就默认具有所需保证。:chatgpt-content-reference{index="4"}

承诺可采用成熟构造。原型为便于进入电路，也可研究随机化哈希承诺：

\[
C_x =
H(
\textsf{domain}
\parallel
\operatorname{Encode}(meta)
\parallel
\rho
\parallel
\operatorname{Pad}(x)
)
\]

其中 \(\rho\) 为独立高熵随机数，和 \(x\) 一样被秘密共享。**这一实例的隐藏性需要明确采用相应随机预言机模型分析，不能只从哈希抗碰撞性推出。**

禁止公开裸的 \(H(password)\)、\(H(cookie)\)，以免引入猜测验证信号。

### 4.2 受保护凭据胶囊

每个逻辑凭据用一个胶囊表示：

\[
\mathsf{Cap}_j =
(
id_j,\ type_j,\ origin_j,\ binding_j,\ version_j,\ C_j,\ repr_j
)
\]

其中：

- `origin` 指向产生它的认证转换及父胶囊；
- `binding` 绑定服务、账户上下文和允许的材料用途；
- \(C_j\) 绑定隐藏内容或其受保护来源；
- `repr` 指定材料的内部表示；
- 实际使用仍须读取当前 `Approval`、`Binding` 和停止状态。

**胶囊不是可以直接交给网站的 bearer token，也不是独立原生授权证明。**知道胶囊 ID 不足以使用它。

### 4.3 同一次转换输出三类结果

一次成功接纳应输出：

\[
(
\mathsf{Evidence},
\{\mathsf{Cap}'_1,\ldots,\mathsf{Cap}'_k\},
[\mathsf{Data}]
)
\]

分别是受限事实、受保护后继材料、尚待释放的业务数据。

三者共同绑定：

\[
B_t =
H(
sid,\ operation,\ approvalVersion,\ inputCaps,\ transcriptRoot,
outputCaps,\ contractHash
)
\]

这里的 `transcriptRoot` 是固定认证记录的摘要，不能通过替换另一段响应或另一把 TLS 密钥重新解释。

**关键要求是同源、同一次计算、同一输入关系，不是简单地分别给三份 JSON 加签名。**

## 五、具体协议流程

下面给出可以进入详细协议规格的八个阶段。

### 阶段 0：凭据登记

用户可信入口将凭据 \(x\) 和承诺随机数 \(\rho\) 分成两份：

\[
x=x_0\oplus x_1,\qquad
\rho=\rho_0\oplus\rho_1
\]

两份通过各自认证的机密通道交给 \(E_0,E_1\)。控制核心保存胶囊元数据、承诺和登记批准，不需要取得两份完整开口。

每个执行域使用自己的存储密钥封装份额。可以由 M10 的同一运行库保存这些**分别加密的份额密文**，但两个解密密钥不能都交给控制核心或同一不可信执行域。

登记只证明输入来自获准登记过程，**不证明该密码已经被网站接受**。

### 阶段 1：从 A/B 输出生成使用票据

B 产生配置建议，A 提供所需的适用认证事实。M08 检查后，控制核心生成：

\[
\mathsf{Ticket}=
\operatorname{Sign}_{Q}
(
task,\ actor,\ account,\ inputCaps,\ action,
contractHash,\ approvalVersion,\ bindingEpoch,
budgetDomain,\ nonce
)
\]

用户批准的是任务及其允许范围；控制核心只能在这个范围内派生有限执行票据，不能代替用户新增批准。

票据绑定的是**固定动作模板和材料引用**，不是“允许执行任意 Python 函数”。

### 阶段 2：建立受保护的原生 TLS 通道

两执行域联合建立到固定服务的 TLS 通道，验证准确的服务身份，并保持应用流量密钥为秘密共享状态。

原生服务看到正常 TLS 客户端，不需要理解胶囊。但 TLS 兼容并不意味着已经支持任意网站的 HTTP 认证流程。Oblivious TLS 提供的是协议基础，具体认证适配仍须逐项实现和核对。:chatgpt-content-reference{index="5"}

得到实际通道标识后，再把它与本次操作绑定，避免将为一个服务准备的计算移用于另一个通道。

### 阶段 3：领取资格，然后生成限定请求

M10 原子检查并登记当前批准、预算、版本和唯一使用票据。

随后，2PC 内执行：

\[
[x]=\operatorname{OpenCommittedCapsule}(\mathsf{Cap})
\]

\[
[q]=\operatorname{Serialize}_{\Gamma}(action,args,[x])
\]

\[
c_q=\operatorname{TLS.Seal}([k_{\rm send}],[q],sid,seq)
\]

只有固定序列化器产生的请求能够被封装；秘密值从胶囊进入请求，不先进入普通 HTTP 客户端内存。

**所有必要的主动安全检查必须在有效请求密文被释放之前完成。**不能先让恶意执行域取得有效认证请求，最后再宣布其证明不合格。

一旦请求密文已经产生并被交给发送方，就属于可能在途的请求。用户随后停止任务，不能据此宣称该请求不再到达服务。

### 阶段 4：认证响应内的事实与后继材料联合处理

响应仍以密文进入联合计算：

\[
[m]
=
\operatorname{TLS.OpenAndVerify}
(
[k_{\rm recv}],c_r,sid,seq
)
\]

\[
(e,\{z'_j\},[d])
=
\operatorname{Parse}_{\Gamma}([m],inputCaps)
\]

解析器只支持已审定的有限格式。它把响应划分为：

**允许作为证据的事实、必须继续保护的认证材料、允许释放的业务数据。**

未知字段、重复字段、冲突的 Cookie 语义、不支持的编码或越界长度不能直接被当作普通业务文本放行。协议安全取决于这个分类契约；不存在自动理解所有响应语义的密码学捷径。

### 阶段 5：封装后继材料，形成联合转换回执

每个新材料直接成为新胶囊，不能经过“输出明文 token，再调用保存函数”的路径。

两方对本次共同输出形成回执：

\[
\mathsf{Receipt}_t=
(
B_t,\ e,\ outputCaps,\ outcomeClass
)
\]

两方各自认证同一回执，控制核心只接纳满足协议条件的结果。

这份回执的含义是：

> 至少一个诚实执行域参加的联合执行，按指定契约处理了这次认证转换。

**它不是原生网站对任意语义的数字签名，也不能把 `active:false` 扩大为整个授权家族已撤销。**

### 阶段 6：持久接纳与有限输出释放

后继材料先被可靠封装并登记为隔离或恢复用途。随后 M07/M10接纳证据、更新预算、义务和计划适用性。

业务数据保持受保护状态，直到通过当前输出资格检查后才释放给 AI。

若任务已停止，仍可接纳历史与恢复材料，但不能自动恢复普通使用。若一方中止导致必要份额或响应缺失，结果保持未决，不能通过重跑原生认证来伪造恢复。

### 阶段 7：后续使用

下一次操作必须引用实际胶囊：

\[
\mathsf{Ticket}_{t+1}
\longrightarrow
\mathsf{Cap}'_j
\longrightarrow
\text{受保护的下一请求}
\]

2PC 重新检查承诺、来源关系和当前票据，防止“工作账户证据＋私人会话材料”的拼接。

即便原子步骤都正确，也不能自动证明认证身份沿任意材料更新保持不变。比如登录返回 Cookie，后续 `/me` 返回主体信息，这个主体证据首先绑定到**实际用于 `/me` 的 Cookie**。若 `/me` 又替换 Cookie，新 Cookie 是否保持主体，需要服务契约或新的适用核验。

### 阶段 8：停止与恢复

停止任务 T1 后，控制核心不再签发该任务和账户代次的新使用票据；诚实执行域拒绝基于旧票据继续联合计算。

这加强的是受控使用路径的 L 保证。**R 仍需真实原生撤销能力；E 仍需实际效果边界。**OAuth 撤销是否影响其他材料，本来就与原生授权关系及部署行为有关。:chatgpt-content-reference{index="6"}

---

## 六、最值得作为专用机制研究的部分：受保护转录切片胶囊

如果协议只做到前面的流程，审稿人仍可能认为：

> 这是标准主动安全 MPC、可信账本和认证适配器的组合。

因此，我建议进一步提出并比较一个具体机制：

> **让部分后继凭据以“受保护 TLS 转录中的可验证切片”存在，不立即将其转换成独立凭据值。**

这是本方案区别于笼统“全部放进 MPC”的主要候选构造。

### 6.1 两种凭据表示

**物化表示：**

\[
\mathsf{Cap}^{\rm mat}
=
(
meta,\operatorname{Com}(x;\rho),[x],[\rho]
)
\]

保存独立的凭据秘密份额。

**转录切片表示：**

\[
\mathsf{Cap}^{\rm slice}
=
(
meta,\mathsf{ChannelKeyRef},
\mathsf{RecordRoot},
\mathsf{Selector},
\mathsf{ReceiptRef}
)
\]

其中 `Selector` 指向已经认证并解析过的响应中的确切字段、记录位置和必要解码规则。

例如，Cookie 值位于某个经过认证的 TLS 响应头中。胶囊可以引用这个字段，而不是把 Cookie 重构成明文再存储。

### 6.2 下一次使用如何取得材料

执行域在 2PC 内计算：

\[
[x]
=
\operatorname{DecodeSlice}
\left(
[k_{\rm recv}],
\mathsf{AuthenticatedRecords},
\mathsf{Selector}
\right)
\]

然后将 \([x]\) 直接送入下一请求的序列化器：

\[
[c_{\rm next}]
=
\operatorname{TLS.Seal}
\left(
[k'_{\rm send}],
\operatorname{Serialize}_{\Gamma}(\ldots,[x],\ldots)
\right)
\]

整个过程中，单个执行域都没有完整 \(x\)。

### 6.3 为什么切片不能由 AI 随意指定

持有旧通道密钥份额，原则上与该通道其他数据相关。因此必须同时绑定：

\[
(
\text{确切接收密钥承诺},
\text{确切密文记录},
\text{认证序号},
\text{字段选择器},
\text{解码规则},
\text{使用票据}
)
\]

不能暴露通用 `decrypt(offset,length)` 接口。

选择器只能由已审定解析器从真实响应产生，并进入联合回执。下一次使用时，2PC核对的必须是这个选择器，而不是执行器重新传入的偏移。

### 6.4 它带来的理论问题

需要证明两种表示具有一致的凭据语义：

\[
\operatorname{Materialize}
(\mathsf{Cap}^{\rm slice})
=
x
=
\operatorname{Open}
(\mathsf{Cap}^{\rm mat})
\]

并进一步证明，这种表示替换不会改变：

当前批准要求、账户绑定、认证前缀效果、停止范围、恢复行为，以及允许泄漏的信息。

这里的研究对象是**认证状态表示的密码学保持性**，而不是重新宣称发明秘密共享或选择性解密。

### 6.5 必须正面处理的代价

切片表示并不一定更快。

物化方案保存的秘密数据约与凭据总长度相关；切片方案可能要保留更大的原始密文和接收密钥份额，后续每次使用还可能增加局部解密成本。

因此只能提出：

> **在特定材料数量、使用次数、响应大小和审计保留条件下，切片表示可能降低材料转换与重复处理成本。**

不能预先宣布它具有渐近优势。TLSNotary 和 Garble-Then-Prove 已经研究转录、承诺转换与解密开销，正确对照必须充分利用这些成熟优化。:chatgpt-content-reference{index="7"}

还有一项重要代价：归档接收密钥份额会延长相关秘密状态的保留时间。首版不能因此宣称获得新的前向安全或抗移动腐化保证。

## 七、协议需要证明什么

建议把理论工作限定为四个核心性质和一个表示保持命题。

### 7.1 单执行域腐化下的持续秘密保密

目标是证明：

\[
\operatorname{View}_{\mathcal A}^{\Pi}
\approx_c
\operatorname{Sim}
(
\mathcal L_{\Gamma}
)
\]

\(\mathcal L_{\Gamma}\) 是预先声明的允许泄漏，包括服务标识、消息长度类别、部分时序、允许公开的成功或拒绝结果，以及用户批准的业务输出。

这个定义必须覆盖**多次自适应调用和后继材料**，不能只覆盖初次密码输入。

它也不能声称阻止用户明确允许的认证查询所带来的推断。比如允许一次候选认证，就可能有意披露“本次候选是否被接受”。

### 7.2 同源证据—同一材料绑定

拟定义：

\[
\operatorname{Accept}(e,\mathsf{Cap}')
\land
\operatorname{Use}(\mathsf{Cap}')
\]

必须对应某次真实联合转换中产生的**同一个隐藏材料**，而不是另一次认证的替代值。

攻击者获胜事件包括：证据来自工作账户，而胶囊实际对应私人材料；胶囊声明来自响应 A，实际从响应 B 提取；替换通道密钥后重新解释同一密文。

这一点不能只依赖“AEAD 验证成功”。AFT 2025 关于 TLS oracle 的研究专门分析了 AEAD 的上下文不可伪造性质，说明不同验证设置下必须区分密文认证与上下文绑定。:chatgpt-content-reference{index="8"}

### 7.3 认证转换不额外导出权能

对每次合法转换：

\[
\mathsf{ProtectedState}
\xrightarrow{\Gamma,\ Approval}
\mathsf{ProtectedState}'
+
\mathsf{PermittedOutput}
\]

要求所有被契约识别为可复用认证材料的输出继续进入受保护状态。

这里的“所有”只限于审定契约和支持的接口范围。若服务在某个普通字段中返回新的 API 密钥，而契约没有识别，协议不能自动理解其业务意义。这是契约完整性验证门，不是可以被证明忽略的细节。

### 7.4 停止与恢复不产生新的使用资格

设 \(t_{\rm stop}\) 为控制核心持久提交停止的排序点。对之后的新资格领取：

\[
t>t_{\rm stop}
\Rightarrow
\neg \operatorname{NewAuthorizedEmission}
(T1,account,epoch)
\]

需要明确排除停止前已经合法产生并可能在途的请求。

恢复可以接纳历史、恢复胶囊或执行另行批准的处置，但不能重置额度、自动重新激活普通使用，或者产生第二次未知业务提交。

这与历史方案对未知会话的约束一致：没有适用句柄、查询或终止机制时，不能凭恢复程序保证远端处置完成。:chatgpt-content-reference{index="9"}

### 7.5 物化与切片表示的保持性

这是建议集中证明的专用命题：

> 在通道密钥、原始密文、解析选择器和上下文均经过绑定，且材料只经获准转换使用的条件下，用受保护切片胶囊替代物化胶囊，不改变其可授权使用语义，也不增加声明之外的泄漏或撤回后使用能力。

证明需要处理跨记录字段、解码规则、重复字段、迟到激活和父胶囊版本变化，而不只是证明两个字节串相等。

### 7.6 安全论证的形式

建议先完成固定执行序列及静态腐化模型下的理想—现实证明，再考虑更强组合性。

目标证明结构可以是：

\[
\operatorname{Adv}^{\mathrm{CCT}}
\le
\epsilon_{\mathrm{2PC}}
+
\epsilon_{\mathrm{TLS}}
+
\epsilon_{\mathrm{Sig}}
+
\epsilon_{\mathrm{Com}}
\]

各项需按具体多会话实例定义，不能直接把这个式子当成已完成定理。

证明应依次替换底层安全计算、通道、签名和承诺，再对每次转换进行归纳，说明秘密与资格边界得到保持。原生契约正确、控制状态持久且不回退等前提仍须单列；它们不能靠密码学归约顺带证明。

## 八、与 A＋B 的直接连接

### 8.1 A：只提出必要的安全核验，不决定秘密如何导出

A 的动作契约需要补充：

\[
\Gamma =
(
\text{输入胶囊类型},
\text{原生请求},
\text{响应格式},
\text{证据规则},
\text{后继材料规则},
\text{允许输出}
)
\]

A 仍负责判断是否有必要调用 Q1 或 Q2、风险是否可接受、结果未知时有哪些后置义务。

CCT-AB保证：该核验不会因为某个执行域恶意而悄悄变成另一项认证操作，且新材料继续受保护。

**它不会帮助 A 获得接口没有暴露的事实。**尤其不能把 Keycloak 的 `active` 或 `client_id` 自动解释成独立撤销关系。

### 8.2 B：配置方式不变，执行保证增强

B 继续选择 P/I/G及其组合。

新增的是一个执行安全要求：

\[
SecurityProfile
\in
\{
\text{TrustedExecutor},
\text{OneDomainCorruptionTolerant}
\}
\]

后者要求选择 CCT-AB 实现。它不是第四种原生授权，也不能创造网站不支持的独立 grant。

必须禁止安全降级：若一个材料已经按增强配置承诺不向单执行域公开，就不能在 MPC 超时后自动转入明文代理路径。

### 8.3 共享材料下选择性停止

假设 T1 和 T2通过同一个原生 Cookie 工作。

CCT-AB可以使 T1 的新受控使用被拒绝，而 T2继续取得自己的当前票据。它不需要销毁共享 Cookie，也不会因此声称服务器能够选择性撤销 T1。

这与现有研究关于“本地任务、密码管理器批准、服务原生授权必须分开”的要求保持一致。:chatgpt-content-reference{index="10"}

## 九、两个完整示例

### 示例一：Q2隔离核验建立正确工作账户会话

初始密码以胶囊保存。A发现当前配置缺少 F2，用户允许一次候选认证，并明确接受其后置政策。

协议联合产生登录请求，服务返回 Cookie。Cookie 不被发送给 AI，而是形成待核对胶囊。

随后，联合执行器使用**该胶囊**请求 `/me`。若得到工作账户主体，回执记录“这个主体结论来自使用胶囊 C 的实际请求”。M07接纳，B可以在当前批准内选择其作为 P＋I 的材料。

若得到私人主体，业务内容不释放；若响应丢失，保持可能会话及义务；若 F3不支持严格处置，A必须在认证前拒绝，而不是等协议完成后再补解释。

### 示例二：刷新期间用户停止 T1

T1的一次刷新资格已提交，随后用户停止 T1。

服务返回新的访问令牌与刷新令牌。两域可以保护并登记它们，但新胶囊只进入历史或恢复用途。原先的使用票据不能自动批准后继普通请求。

若响应完全没有返回，不能假设没有后代材料，也不能重复刷新来“恢复原结果”。

若 T2拥有独立原生范围，其材料和批准不受 T1局部停止影响；若共用范围，则 B继续按原有规则诊断 R冲突。密码协议不会抹去原生控制粒度的限制。

## 十、哪些是候选创新，哪些必须承认是成熟技术

| 内容 | 应如何定位 |
|---|---|
| 秘密共享、主动安全2PC、TLS、签名、承诺、AEAD | 成熟密码学基础，不单独主张创新 |
| 用户批准、当前版本检查、预算及恢复账本 | 继承工程基础，不重新命名为密码协议创新 |
| 证据、后继材料和后续使用之间的同源绑定定义 | 候选安全模型贡献，需要直接近邻与分离实例 |
| 不导出后继材料的认证转换协议 | 候选协议贡献，需要具体构造和多轮安全论证 |
| 受保护转录切片胶囊及表示保持性 | 候选专用机制，是建议重点证明和比较的部分 |
| A契约、B配置与具体密码执行之间的保持关系 | 候选领域协议连接；不能只靠接口字段数量证明创新 |

**最严格的反对意见仍然是：一个正确的通用反应式 MPC，也能实现这些功能。**

因此，不能通过证明“通用 MPC 可以实现它”就宣布完成强密码学创新。你最终至少要取得以下一种实质性增量：

有说服力的新安全关系及必要分离；一个具有非平凡构造内容的专用实现；或者在同等安全模型、同等输出和故障语义下，相对正确通用实现的可重复成本优势。

若三者都没有，工作仍可能形成应用密码学系统论文，但不能继续以“全新密码学机制”作为主要贡献。

## 十一、原型与实验必须怎样设计

### 11.1 首版实现范围

建议保留原来的两个受控服务、两个代理和 A/B规模，不增加业务线。

密码学后端先支持固定 TLS 套件和有限认证模板；关闭首版不需要的会话恢复与0-RTT路径，避免引入额外状态。TLS 1.3本身对0-RTT具有不同的重放风险，不能用普通握手路径的分析直接覆盖它。:chatgpt-content-reference{index="11"}

完整原型至少包括：

| 工件 | 必须实际完成的内容 |
|---|---|
| **协议规格与安全游戏** | 输入输出、腐化能力、允许泄漏、停止排序点、中止和恢复语义 |
| **物化参考协议** | 真实主动安全2PC、真实TLS、真实Cookie或令牌；无明文替代核心 |
| **切片候选协议** | 通道根、选择器、来源绑定、跨请求使用和当前资格检查 |
| **A/B接入** | Q2核验、P充分路径、共享范围冲突、独立范围条件正例 |
| **攻击与故障测试** | 替换材料、伪造证据、旧票据、错账户、偏移篡改、响应丢失、迟到结果 |
| **证明与独立检查** | 理想功能、关键归约、表示保持性、有限状态检查及可复现反例 |

不能用可信模拟返回值代替真实 MPC，再报告协议性能。

### 11.2 必须设置的比较基线

**基线一：正确的单域可信代理。**  
用来衡量增强威胁模型的实际代价，不应在它原本不声称支持的腐化条件下把失败称为产品漏洞。

**基线二：操作绑定秘密托管方案。**  
与 SUDP相同或明确对齐的保证比较；原论文实现与自己编写的简化实现必须分开报告。

**基线三：完整通用主动安全 MPC＋TLS＋相同状态规则。**  
这是判断你是否只是封装通用技术的核心基线。

**基线四：已优化的物化方案。**  
允许其复用预处理、批处理认证、使用相同的固定解析器和持久状态。不能故意让对照反复解密或重复计算。

TLSNotary或Garble-Then-Prove只有在调整到同样的秘密输出与主动安全目标后，才能作为安全性等价对照；否则只能说明不同目标下的性能差异。:chatgpt-content-reference{index="12"}

### 11.3 测量项目

测量必须包含预处理、握手、请求生成、响应认证、解析、胶囊生成、后继使用、持久化、停止和恢复，另外记录通信量、轮数、内存和完整业务时间。

**不能预先声称切片方案只与秘密长度有关。**完整记录认证、格式定位以及实际需要公开的业务数据仍有成本。对于短 token 高频使用，物化表示可能更便宜；这一负结果必须保留。

原 W0不应被静默提高。新增密码执行成本应单列并计入相应端到端路径；若不能满足目标，就明确报告兼容范围和成本，而不是把密码计算移出统计口径。

## 十二、创新性与工作量的最终判断

我的判断是：

**这条路线具有足够明确的研究对象，也具有足够的实现、证明和实验工作量；它比在现有方案上单独增加签名、零知识证明或门限存储更接近密码学协议研究。**

但建议只认定以下定位：

> **以“认证后继材料持续保密”为安全目标，以“同源证据与实际材料绑定”为协议约束，以“受保护转录切片胶囊及其表示保持性”为专用机制，构造服务于 A＋B 的双域凭据使用协议。**

最值得争取的论文贡献是：

**第一，定义并分析跨多次认证转换的凭据封闭性及其与批准、停止和恢复的关系。**

**第二，给出物化参考构造与切片候选构造，证明同源绑定和表示保持性，明确其泄漏、腐化及中止边界。**

**第三，在真实认证路径和相同安全目标下，验证候选机制的成本收益、适用范围与失败条件。**

最终应采用清晰的否定标准：**如果专用构造与正确的通用MPC方案在定义、证明和完整成本上没有实质区别，就收缩“新密码机制”的主张；如果切片表示确实解决了同源连接、持久后继使用或成本上的非平凡问题，再把它提升为核心贡献。**

本轮已完成直接近邻核对和具体候选协议设计，**尚未完成完整安全证明、密码学原型运行或穷尽查新**。接下来最有价值的工作是固定 CCT-AB 的理想功能与“材料替换、事后检查来不及保护前缀效果”两个最小分离实例，再决定切片机制是否值得进入正式编码。
