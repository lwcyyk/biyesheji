# G4 VDNS、透明日志与检查点阶段实施记录

日期：2026-07-23  
规范基线：`spec-001-v2.0.0-g0.2`  
阶段目标：完成 VDNS L1～L5 验证、可验证 current-state 解析、RFC 9162 形状透明日志、周期检查点、公告适配器和异常监控。

阶段结论：**G4 的 10 项任务已形成可执行闭环。设备先验证根授权身份、能力和动态状态，再验证从本地可信检查点到候选树头的包含/一致性证据，最后由本地策略输出冻结的 Verdict。current version 只来自已验证的 StateDescriptor；云端对象顺序和所谓“最新版本”不参与选择。**

## 1. VDNS 五层验证

### 1.1 L1：身份与根链

L1 的输入由“不可信对象字节”和“接收方自有信任上下文”分开表示。验证顺序为：

```text
接收方 RootPublicKey / Namespace / Chain / RootKeyGeneration
  → 验证根签名 DeviceOperationCredential
  → 从已验证凭证取得设备 AuthPublicKey 和 SecretGeneration
  → 验证 OperationEvent 签名
  → 验证 CredentialStateDescriptor 签名
  → 绑定 Namespace、DeviceID、credential hash 和 updater
```

对象内携带的 KeyID、Namespace 或 key generation 不能自行成为信任根。错误根、错误 Namespace、错误 key generation、事件签名篡改和 descriptor 签名篡改均在暴露强类型状态前拒绝。

### 1.2 L2：能力与私有范围

L2 验证：

- `OperationType → RequiredCapability`；
- `CredentialScope` 的 Namespace/集合/OriginBinding/单凭据语义；
- `ValidFromSequence ≤ FinalSequence ≤ ValidUntilSequence`；
- 当前 issuance counter；
- 当前 status reference。

scope 成员仍只存在于根签名设备凭证和本地验证过程，不进入公开日志叶或检查点。已有 G1 的设备凭证授权逻辑继续保留；G4 额外导出只读 `Scope.Allows`，供分层验证器复用，未创建第二套授权语义。

### 1.3 L3：动态状态

L3 的当前值必须由接收方本地已接受状态提供，统一检查：

- `revoked_at_sequence` 的最终生效；
- 当前 secret generation；
- `device_counter = accepted_counter + 1`；
- `previous_event_hash`；
- descriptor 的 `LastOperationEvent` 和 `FinalSequence`；
- active version 单调且最多前进一版；
- 事件 CredentialID 与 descriptor CredentialID 一致；
- CREATE/UPDATE/ROTATE/MIGRATE 的 old/new version 与已接受版本一致；
- predecessor descriptor hash；
- ACTIVE、UPDATE_PENDING、SITE_CONFIRM_PENDING、SUSPENDED、REVOKED、CONFLICTED 的合法边。

因此，正确签名但已经撤销、旧代际、counter 跳跃、回滚版本或非法状态边仍会被拒绝。

### 1.4 L4：透明证明

L4 验证完整 ProofBundle：

```text
ProofBundle 签名与 Namespace
  → starting SignedCheckpoint 签名、digest 和 provider
  → candidate SignedTreeHead 签名、LogID、tree size、final sequence
  → 目标 StateDescriptor 的公开叶绑定
  → inclusion proof
  → starting checkpoint → candidate head consistency proof
  → 周期锚定要求
```

解析器还要求：

```text
SubjectDigest
= StateDescriptorDigest
= 当前 L1 已验证 descriptor digest
```

并要求公开叶的对象类型确为 `STATE_DESCRIPTOR`，防止有效日志证明被替换成无关对象证明。

### 1.5 L5：本地策略与 Verdict

代码实现协议注册表的 12 个冻结 Verdict：

```text
ACCEPT
DEGRADED_OFFLINE
DEGRADED_PENDING_LOG
REVIEW_REQUIRED
REJECT_IDENTITY
REJECT_CAPABILITY
REJECT_REVOKED
REJECT_CAUSAL
REJECT_PROOF
REJECT_ORIGIN
REJECT_POLICY
REJECT_OBJECT
```

低风险 `RESOLVE/AUTOFILL/SYNC_ACCEPT` 只有在存在已接受缓存且未超过 sequence-age 上限时才允许显式降级。CREATE、UPDATE、ROTATE、REVOKE、DEVICE_ENROLL 等写操作在 L4 不可用或待锚定时返回拒绝，不允许静默降级。

## 2. 可验证 current-state resolver

解析器按 L1→L5 顺序执行，并返回：

```text
State
Principal
Authorization
CurrentVersion
AuditProof
ProofDigest
Verdict
LayerResults[5]
```

`ResolveRequest` 没有 `CloudCurrentVersion` 字段。`CurrentVersion` 唯一取自通过 L1～L4 验证的 `CredentialStateDescriptor.ActiveVersion`。无效 ProofBundle 返回 `REJECT_PROOF`；网络不可用和证明密码学无效被明确区分。

该边界完成了 G3 留出的 trust seam：同步服务可以下载候选对象，但不能依据云端到达顺序决定 current。

## 3. 透明日志与规范对象

### 3.1 Merkle 哈希

实现严格使用基线公式：

```text
LeafHash(x)  = SHA256(0x00 || Domain(LOG-LEAF) || ExactCBOR(x))
NodeHash(l,r)= SHA256(0x01 || Domain(LOG-NODE) || l || r)
EmptyTreeHash= SHA256("")
```

树形和包含/一致性路径采用 RFC 9162 的 append-only Merkle 语义。测试穷举验证 257 叶内全部 `(oldSize,newSize)` 一致性组合，并对 proof hash 变异执行失败安全测试。

固定 1/2/3/7 叶根为：

| 叶数 | RootHash |
|---:|---|
| 1 | `8b49eb056f7433a93142de8f55a1c24148f0fd42b615bab8fc7bc6cbad45b9de` |
| 2 | `4e01f34af56596c9a83e76e72afcd93e013b8d40f4ffa1b8246da0d2a751f523` |
| 3 | `18bf1de9d5e169b9184b035366e964425c6d1e54ad852ba7bb7df50b02b8010e` |
| 7 | `969ae539683a860114143eb2e69bae685f1444e17d268163e585fc9af3f73e79` |

### 3.2 公开叶最小化

`LogLeaf` 只允许：

- Namespace commitment；
- 周期 subject pseudonym；
- object/operation type；
- object digest；
- final sequence；
- epoch。

类型中无法表达密码、Origin、用户名、账号关系、完整事件或稳定密码复用标签。

### 3.3 签名树头和 ProofBundle

`SignedTreeHead` 绑定 Namespace、LogID、tree size、root hash、final sequence、SuiteID 和统一 SigInput 的签名 key generation。

ProofBundle 明确携带：

- starting checkpoint object；
- candidate signed tree head；
- inclusion/consistency proof；
- root chain objects；
- device credential object；
- capability status proof；
- descriptor digest；
- local policy input hash。

验证器根据 L1 的接收方根公钥、Namespace、ChainID 和 root key generation 独立重建根信任投影，并要求其有序 chain digest 与 ProofBundle 一致；完整 DeviceOperationCredential 对象也必须与 L1 已验证对象的 hash 一致。仅在 bundle 中放入任意非空 root/device 字节不能通过。

SignedTreeHead、ProofBundle 和 Checkpoint 均有确定性 CBOR 往返、签名上下文负向测试和固定 digest KAT。

## 4. 周期检查点与公告

`CheckpointPayload` 是封闭白名单，不是可扩展 metadata map：

```text
NamespaceStateRoot
DeviceStateRoot
CredentialStateRoot
AuditLogRoot
RevocationRoot
CryptoPolicyHash
CheckpointHeight
FinalSequence
ProviderKind
optional VRFOutputHash
```

公告应用层拒绝“checkpoint 声明的 provider”和实际适配器类型不一致。

- `memoryanchor` 只能返回 `SIMULATED`；
- `anvilanchor` 只能返回 `ANVIL`；
- 两者均不能返回 `CONSENSUS`；
- Anvil 边界只接收签名检查点对象和 digest，不接收密码或密钥。

当前 Anvil 测试使用确定性 client fake 验证适配器合同和标签，不代表已完成真实链部署、确认深度或生产共识评估。

## 5. Monitor 与证据保留

Monitor 检测：

- 同一 tree size 不同 root：`SPLIT_VIEW`；
- tree size/final sequence 回退：`TREE_ROLLBACK`；
- 增长树无有效 consistency path：`BAD_CONSISTENCY`；
- 同一私有 subject commitment、同一版本双 descriptor：`DOUBLE_DESCRIPTOR`；
- 检查点高度回退或同高冲突：`ANCHOR_CONFLICT`。

合法追加且一致性证明有效时不产生 finding。证据只保存对象 digest、位置、可选 subject commitment 和规范证据 digest。SQLite repository 支持证据幂等保留，并拒绝 digest/内容不一致。

## 9. 明确边界与下一阶段

G4 完成的是密码管理主路径的可验证控制骨架，尚不代表生产部署：

- 透明树的纯应用实现和 v5 持久模型已完成，但真实多节点日志复制不在本阶段；
- Anvil 只完成 provider 合同和不可冒充标签，未形成真实链吞吐/重组实验；
- 用户界面、浏览器 Origin 门禁、secret handle API 和自动填充体验属于 G5；
- Epoch 隐私审计与 SCOPE-ZK 可选增强仍属于 G6；
- 跨进程部署、完整数据集和论文统计属于 G7。

下一阶段进入 **G5 API、浏览器扩展与日常密码管理体验**，把 G2/G3 的密码库和生命周期能力接到 G4 resolver，完成创建、解析、自动填充、改密、同步、设备和恢复的端到端日常主线。
