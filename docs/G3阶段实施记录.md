## 1. 生命周期与网站确认

### 1.1 双层状态机

凭据聚合状态机覆盖：

```text
NONEXISTENT
  → CREATE_PENDING
  → ACTIVE
  → UPDATE_PENDING
  → SITE_CONFIRM_PENDING
  → ACTIVE
  → SUSPENDED
  → REVOKED
```

发生并发 descriptor 时进入 `CONFLICTED`，当前值和竞争值全部保留，禁止云端顺序或最后写入自动覆盖。

内部版本状态机独立覆盖：

```text
PENDING_CANDIDATE
  → SITE_UPDATE_PENDING
  → FAILED_RETRYABLE | SITE_STATUS_UNKNOWN
  → SITE_CHANGED_LOCAL_COMMIT_PENDING
  → ACTIVE_LOCAL_PENDING_PROOF
  → ACTIVE
```

每个持久状态都映射确定性的重启动作。进程在网站请求发出后崩溃时先查询回执，不盲目重放改密请求；模糊结果保持 `SITE_STATUS_UNKNOWN` 并要求人工复核。

### 1.2 Mock Site 与确认门禁

Mock Site 覆盖：

- 成功；
- 明确拒绝；
- MFA 缺失/成功；
- 策略拒绝；
- 超时且状态未知；
- 网站已应用但响应丢失；
- 幂等重试和回执查询。

候选版本及其全部字段对象必须先处于 durable/COMMITTED 状态，才能进入网站调用。签名的 `APPLIED` 回执只推进到 `SITE_CONFIRM_PENDING`；激活还要求持久化、能力检查通过的 `UPDATE_CONFIRM` 操作事件。

证据策略固定为：

```text
AUTOFILL_OBSERVED / SUBMIT_OBSERVED / LOGIN_INFERRED
    → 不允许激活

USER_CONFIRMED / SITE_CONFIRMED
    → 可在签名确认事件存在时激活
```

SQLite `site_change_attempts` 保存 change ID、候选版本、公开请求摘要、回执、证据等级和确认事件。公开请求摘要不包含当前密码、新密码或其无 key 哈希，避免形成离线猜测 oracle。

## 2. 多设备同步与不可信云

### 2.1 SyncManifest v2

`SyncManifest` 签名绑定：

- NamespaceID 和发布设备；
- base/target checkpoint；
- highest device counter；
- 规范排序的对象集合 Merkle root；
- 对象数量和 created sequence；
- CP-2 统一 SigInput 的协议、套件、链、KeyID 和 key generation。

Manifest 具有固定 KAT、规范 CBOR 往返、重复对象拒绝和 fuzz 入口。

### 2.2 云端边界

内存云适配器只提供：

```text
PutObject
FetchObject
PublishManifest
PullManifests
```

不存在 `GetCurrentVersion` 或等价接口。故障注入可模拟对象缺失、字节篡改、隐藏后续清单和反向返回顺序，以证明云端顺序不是有效性信号。

### 2.3 接受算法

同步接受顺序为：

```text
接收方给定 expected checkpoint
  → 验证 Manifest 签名/设备信任接口
  → target checkpoint 必须等于接收方可信值
  → 下载 Manifest 中全部对象
  → 逐个校验 size + SHA-256
  → 解析 CredentialEnvelope
  → 验证完整 SignedStateDescriptor 对象
  → 校验 namespace/credential/version
  → 校验 envelope hash、descriptor hash、policy、predecessor
  → 校验每个字段密文和 wrapped-DEK 对象均已补齐
  → 一次调用原子 CandidateCommitter
```

任何对象缺失、篡改、字段遗漏、旧 checkpoint 或可信状态不一致都会在本地提交前失败，且不得回退到旧版本。

G3 通过 `ManifestTrustVerifier`、`DescriptorTrustVerifier` 和 `SnapshotTrustResolver` 保留强制信任接缝；G4 必须在这些接口接入 VDNS 五层验证，当前阶段不宣称已完成 L1～L5。

## 3. 冲突、设备与恢复

### 3.1 冲突保留

聚合模型至少保留当前 descriptor 和竞争 descriptor。SQLite `credential_conflicts_v2` 使用 `(namespace, credential, version, descriptor)` 作为主键；人工解决必须引用已持久化的 `RESOLVE` 事件，并在一个事务中把一个候选标记为 `SELECTED`、其余标记为 `REJECTED`。解决动作不绕过后续 accepted-state 验证。

### 3.2 设备加入

设备加入挑战绑定：

- NamespaceID；
- 新 DeviceID；
- Ed25519 认证公钥；
- X25519 HPKE 公钥；
- 请求的 capability bits；
- 私有 scope 的摘要；
- 过期 final sequence；
- 随机 ChallengeID 和 nonce。

六位短码用于两台设备的带外人工比对，数据库只保存短码承诺。批准动作要求已授权设备产生签名 `DEVICE_ENROLL` 事件，同时生成根签名设备操作凭证，并将 RootSecretBundle 通过接收方公钥绑定的 RFC 9180 HPKE 封装。

新设备打开 HPKE 后创建自己的 DeviceSecret 和 RootCapsule。挑战只能从 `ISSUED → APPROVED → CONSUMED` 推进一次；重复消费在调用激活端口前被拒绝。

### 3.3 撤销和新代际

代际 rollover 只选择状态为 `ACTIVE` 且不等于被撤销设备的接收者。每个剩余设备得到独立 HPKE SecretEnvelope；被撤销或 suspended 设备没有 g+1 envelope。

只有全部接收者对象建立完成且撤销 final sequence 被接受后，代际才能激活。已有设备授权器继续根据 receiver-owned final sequence、revoked-at sequence、issuance counter、status reference 和 current generation 拒绝旧凭证。

### 3.4 备份和恢复

备份快照绑定：

- RecoveryCapsule digest；
- 加密 manifest hash；
- RouteMap root；
- credential-state root；
- 完整对象集合 root；
- accepted checkpoint；
- secret generation 和 created sequence。

恢复必须按顺序完成：

```text
PREPARED
  → ROOT_RECOVERED
  → OBJECTS_VERIFIED
  → VDNS_VERIFIED
  → COMPLETED
```

对象集合缺失、恢复胶囊代际不一致、接收方检查点不一致或未通过正常 VDNS ProofBundle 验证时均不能完成。备份自身不能成为旧状态的信任根。

## 7. 明确未完成边界

G3 已完成生命周期、多设备和恢复的协议/应用安全骨架，但以下内容属于后续阶段：

- G4：VDNS L1～L5、ProofBundle、透明日志、Merkle inclusion/consistency、周期检查点和分叉检测；
- G5：浏览器扩展、桌面端和真实同步传输；
- G6：Epoch 隐私审计和关系事实；
- G7：可选 SCOPE-ZK 与最小影响修复。

当前 Mock Site、memory cloud 和 application trust seam 是可故障注入的研究实现。论文和界面不得把它们描述为生产网站集成、生产云服务或已经完成的链上共识验证。
