L0: What about Bob?
L1: The Inadequacy of CPA Security for
L2: Proxy Reencryption ⋆
L3: Aloni Cohen
L4: MIT, Cambridge MA, USA,
L5: aloni@mit.edu
L6: Abstract. In the simplest setting of proxy reencryption, there are three
L7: parties: Alice, Bob, and Polly (the proxy). Alice keeps some encrypted
L8: data that she can decrypt with a secret key known only to her. She wants
L9: to communicate the data to Bob, but not to Polly (nor anybody else).
L10: Using proxy reencryption, Alice can create a reencryption key that will
L11: enable Polly to reencrypt the data for Bob’s use, but which will not help
L12: Polly learn anything about the data.
L13: There are two well-studied notions of security for proxy reencryption
L14: schemes: security under chosen-plaintext attacks (CPA) and security un-
L15: der chosen-ciphertext attacks (CCA). Both deﬁnitions aim to formalize
L16: the security that Alice enjoys against both Polly and Bob.
L17: In this work, we demonstrate that CPA security guarantees much less
L18: security against Bob than was previously understood. In particular, CPA
L19: security does not prevent Bob from learning Alice’s secret key after re-
L20: ceiving a single honestly reencrypted ciphertext. As a result, CPA secu-
L21: rity provides scant guarantees in common applications.
L22: We propose security under honest reencryption attacks (HRA), a strength-
L23: ening of CPA security that better captures the goals of proxy reencryp-
L24: tion. In applications, HRA security provides much more robust security.
L25: We identify a property of proxy reencryption schemes that suﬃces to
L26: amplify CPA security to HRA security and show that two existing proxy
L27: reencryption schemes are in fact HRA secure.
L28: Keywords: proxy reencryption · deﬁnitions · public-key cryptography

L48: under Bob’s public key for his use, but that will not reveal the data to Polly.

L50: rectness) and that Polly cannot learn anything about Alice’s data (security). The
L51: most widely-studied model of security for proxy reencryption is called CPA se-
L52: curity, named after the corresponding notion from standard encryption on which
L53: it is based.
L54: But what about Bob? As already observed, if we do not require any secu-
L55: rity against Bob, proxy reencryption is trivial: Alice uses the Trivial Scheme,
L56: simply sending Bob her encrypted secret key. This is undesirable, unsatisfying,
L57: and insuﬃcient for a number of supposed applications of proxy reencryption
L58: (Section 2).

L60: when the public key encryption scheme used is circularly secure [6]! Bob com-
L61: pletely learns Alice’s secret key, and circular security is used only to prove se-
L62: curity against a malicious Polly. Furthermore, the CPA-security of any proxy
L63: reencryption scheme remains uncompromised if Polly attaches the reencryption
L64: key to every reencrypted ciphertext sent to Bob, even though this would enable
L65: Bob to decrypt messages encrypted under Alice’s public key (Section 3.1).
L66: These “constructions” of CPA-secure proxy reencryption—original to this
L67: work—demonstrate the inadequacy of CPA security for proxy reencryption. If
L68: they had been observed previously, perhaps CPA security would not have gained
L69: the traction that it has.
L70: Throughout this work, we use CPA (respectively, CCA and HRA) to refer
L71: to the security notion for proxy reencryption, and Enc-CPA (resp., Enc-CCA)
L72: to refer to the security notion for standard encryption. We restrict our attention
L73: to unidirectional proxy reencryption, where the reencryption key allows Alice’s
L74: ciphertexts to be reencrypted to Bob’s key, but not the reverse. In a bidirectional
L75: scheme, Bob—using his own secret key and Alice’s public key— is able compute
L76: the Alice-to-Bob reencryption key himself; thus a lack of security against Bob is
L77: inherent.
L78: 1.1
L79: CPA and CCA Security of Proxy Reencryption
L80: First considered by Blaze, Bleumer, and Strauss [5], proxy reencryption has
L81: received signiﬁcant and continuous attention in the last decade, including deﬁ-
L82: 2
L83: nitions [22, 4, 10, 28], number-theoretical constructions [3, 26, 12], lattice-based
L84: constructions [19, 2, 30, 17], implementations [25, 20, 31, 8], and early success
L85: in program obfuscation [21, 11].
L86: Adapting notions from standard encryption, this literature considers two
L87: main indistinguishability-based security notions for proxy reencryption: security
L88: under chosen plaintext attacks (CPA) [3] and chosen ciphertext attacks (CCA)
L89: [10]. While CCA security is considered the gold-standard, CPA security has
L90: received signiﬁcant attention [4, 3, 21], especially in latticed-based constructions
L91: [19, 2, 30, 31]. CPA security has been used as a testing ground for new techniques
L92: for proxy reencryption and in settings where eﬃciency concerns make the added
L93: security of CCA undesirable.
L94: We now brieﬂy describe the deﬁnitions of CPA and CCA security for proxy
L95: reencryption, with the goal of communicating the underlying intuition. For this
L96: informal description, we restrict our attention to the limited three party setting
L97: of Alice, Bob, and Polly and strip away many of the complexities of the full
L98: deﬁnition. For a full deﬁnitions of CPA and CCA security, see Deﬁnitions 3 and
L99: the full version of this article [13], respectively.
L100: Both notions are typically deﬁned using a security game between an adver-
L101: sary and a challenger in which the adversary’s task is to distinguish between
L102: encryptions of two messages. Both notions allow the adversary to corrupt either
L103: Bob (learning skbob) or Polly (learning the reencryption key rk). CCA and CPA
L104: security diﬀer in the additional power granted to the adversary.
L105: CCA security grants the adversary access to two oracles:
L106: – ODec: The decryption oracle takes as input a ciphertext along with the public
L107: key of either Alice or Bob, and outputs the decryption of the ciphertext using
L108: the corresponding secret key.
L109: – OReEnc: The reencryption oracle takes as input a ciphertext ctalice and outputs
L110: a reencrypted ciphertext ctbob.
L111: These oracles come with restrictions to prevent the adversary from simply reen-
L112: crypting or decrypting the challenge ciphertext, adapting replayable chosen-
L113: ciphertext security of standard encryption (Enc-CCA) in the natural way.
L114: CPA security of proxy reencryption, however, removes both oracles.1 Why?
L115: First, to adapt chosen-plaintext security from standard encryption (Enc-CPA)
L116: to proxy reencryption, we must of course do away with ODec. Secondly, it seems
L117: we must also remove OReEnc: otherwise, by corrupting Bob it seems that the ad-
L118: versary can use the combination of OReEnc and skbob to simulate ODec. Removing
L119: both decryption and reencryption oracles, according to [3], naturally extends the
L120: Enc-CPA security to proxy reencryption, yielding CPA security.
L121: As we observe in this work, a natural deﬁnition is not always a good deﬁni-
L122: tion. Not only is the above intuition for removing OReEnc false (see full version
L123: 1 This description is an oversimpliﬁcation. In the many party setting, the adversary
L124: has access to a reencryption oracle which will reencrypt ciphertexts between two
L125: uncorrupted parties or between two corrupted parties, but not from an honest party
L126: to a corrupted party.
L127: 3
L128: [13]), but CPA security as deﬁned above guarantees little against a honest-but-
L129: curious Bob, even under normal operation. The deﬁnition only requires that
L130: the adversary will not win the game as long as it never sees any reencrypted
L131: ciphertexts. It guarantees nothing if Bob sees even a single reencrypted cipher-
L132: text. This vulnerability is not purely theoretical: in the CPA secure scheme of
L133: [31], Bob can recover Alice’s secret key with signiﬁcant probability from a single
L134: reencrypted ciphertext (Theorem 4).
L135: This makes CPA security ill-suited for the most commonly cited applications
L136: of proxy reencryption, including forwarding of encrypted email and single-writer,
L137: many-reader encrypted storage (Section 2). CPA security is inadequate for proxy
L138: reencryption and must be replaced.
L139: 1.2
L140: Security Against Honest Reencryption Attacks
L141: What minimal guarantees should proxy reencryption provide? First, it should
L142: oﬀer security against a dishonest proxy Polly when Alice and Bob are honest and
L143: using the proxy reencryption as intended. Polly’s knowledge of a reencryption key
L144: from Alice to Bob (or vice versa) should not help her learn anything about the
L145: messages underlying ciphertexts encrypted under pkalice or pkbob. Such security
L146: against the corrupted proxy is guaranteed by CPA.
L147: Second, proxy reencryption should oﬀer security against a dishonest receiver
L148: Bob when Alice and Polly are honest and using the proxy reencryption as in-
L149: tended. Bob’s knowledge of honestly reencrypted ciphertexts (that were honestly
L150: generated to begin with) should not help him learn anything about the mes-
L151: sages underlying other ciphertexts encrypted under pkalice that have not been
L152: reencrypted. As we show in this work, such security against the corrupted re-
L153: ceiver is not guaranteed by CPA.
L154: Generalizing these dual guarantees to many possibly colluding parties, we
L155: want security as long as the adversary only sees honestly reencrypted ciphertexts.
L156: In Section 4, we formalize this notion as proxy reencryption security against hon-
L157: est reencryption attacks (HRA). Recall that CCA security provides the adversary
L158: with both ODec and OReEnc while CPA provides neither oracle. In contrast, HRA
L159: security provides the adversary with a restricted reencryption oracle which will
L160: only reencrypt honestly generated ciphertexts.
L161: By guaranteeing security of both kinds described above, HRA is a strength-
L162: ening of CPA security that better captures our intuitions for security of proxy
L163: reencryption. Furthermore, HRA guarantees more meaningful security in the
L164: most common applications of proxy reencryption (Section 4.1). HRA security is
L165: an appropriate goal when developing new techniques for proxy reencryption and
L166: in settings where full CCA security is undesirable or out of reach.
L167: Security of Existing Schemes. Can we construct a proxy reencryption scheme
L168: that is HRA secure? HRA security is a strict strengthening of CPA security,so it
L169: is not immediately clear that any existing constructions are HRA secure without
L170: redoing the proofs from scratch. Indeed, the CPA secure scheme of [31] is not
L171: HRA secure (Theorem 4).
L172: 4
L173: In Section 5, we identify a property—reencryption simulatablity—which is
L174: suﬃcient to boost CPA security to HRA security. Very roughly, reencryption
L175: simulatability means that reencrypted ciphertexts resulting from computing
L176: ReEnc(rkalice→bob, ctalice) can be simulated without knowledge of the secret key
L177: skalice (but with knowledge of the plaintext message m). Reencryption simulata-
L178: bility allows a reduction with access to the CPA oracles to eﬃciently implement
L179: the honest reencryption oracle, thereby reducing HRA security to CPA security.
L180: We the examine the simple construction of proxy reencryption from any
L181: fully-homomorphic encryption [19], and the pairing-based construction of [4].
L182: In the ﬁrst case, if the fully-homomorphic encryption secure is circuit private,
L183: then the resulting proxy reencryption scheme is reencryption simulatable. In
L184: the second case, rerandomizing reencrypted ciphertexts suﬃces for reencryption
L185: simulation.2

L187: Related Work
L188: The below mentioned works are just the most directly relevant. There is by
L189: now an extensive research literature on proxy reencryption, presenting a zoo of
L190: deﬁnitions. There have been three main approaches to deﬁning security: CPA,
L191: CCA, and (to a much lesser extent) obfuscation-based. The CPA notion, in one
L192: form or another, is by far the most well studied. In this work, we make the
L193: deliberate choice to address the core CPA deﬁnition, not to present an ultimate
L194: deﬁnition of security for proxy reencryption nor to address the vast array of
L195: diﬀerent criticisms or strengthenings of CPA security that have been or may be
L196: considered. We hope that doing so will make these ideas more understandable
L197: and adaptable.
L198: RIND-CPA Security In concurrent and independent work deﬁning and con-
L199: structing forward-secure proxy reencryption, Derler, Krenn, Lor¨unser, Ramacher,
L200: Slamanig, and Striecks identify the same problem with CPA security as discussed
L201: in this work [14, Deﬁnition 14]. As in our work, they address the problem with
L202: CPA security by deﬁning a new security notion—RIND-CPA security—which
L203: expands the power of the adversary. They additionally separate RIND-CPA and
L204: CPA security with a construction that is essentially our Concatenation Scheme.
L205: However, this is where the resemblance between [14] and our work ends. In
L206: the RIND-CPA game oﬀered by [14], the adversary gets access to an reencryption
L207: oracle that works on all inputs (not just honestly generated ones), but only before
L208: the challenge ciphertext is generated.3 In contrast, HRA allows reencryption
L209: both before and after the challenge, but only for honestly generated ciphertexts.
L210: RIND-IND is inadequate as a replacement for CPA security in the research
L211: literature: its usefulness in applications is unclear, and it appears too strong

L219: In the course of normal operation of a proxy reencryption in applications, an
L220: adversarial party will typically see many reencrypted ciphertexts. These cipher-
L221: texts may come at any time—both before and after other ciphertexts whose con-
L222: tents should remain secret. HRA is meaningful in many such applications—many
L223: more than CPA security. But because RIND-CPA restricts the reencryption or-
L224: acle to the period before the challenge ciphertext, its usefulness in applications
L225: is not clear.
L226: The challenge of proving CCA security for encryption (proxy or otherwise) is
L227: demonstrating that an adversary cannot use dishonestly generated, malformed
L228: ciphertexts to win in the security game. In this respect, RIND-CPA security
L229: is much more akin to CCA security than to CPA security. HRA, on the other
L230: hand, makes minimal assumptions about the distribution of plaintext messages
L231: by allowing the adversary to choose messages itself, just as in Enc-CPA for
L232: standard encryption.
L233: Appendix B discusses RIND-CPA security in more depth, expanding on the
L234: arguments above and proving that RIND-CPA and HRA security are incompa-
L235: rable.
L236: Subsequent Work Two subsequent works continue the study of HRA secure
L237: proxy reencryption. Fuchsbauer, Kamath, Klein, and Pietrzak study CPA and
L238: HRA secure proxy reencryption in an adaptive corruption model [18]. As in our
L239: work, they prove the HRA security of their construction by ﬁrst proving CPA
L240: security and then lifting it to full HRA security using a version of reencryption
L241: simulatability.
L242: More recently, Dottling and Nishimaki study the problem of converting ci-
L243: phertexts between diﬀerent public-key encryption schemes, a problem they call
L244: universal proxy reencryption [15]. They deﬁne security by extending HRA secu-
L245: rity to the universal setting. [15] extends Theorem 5 to show that a computa-
L246: tional version of reencryption simulatability suﬃces to lift CPA to HRA security.
L247: However, they prove HRA security directly rather, ﬁnding that proving compu-
L248: tational reencryption simulatability is not much more simple than proving HRA
L249: security itself.
L250: Other Related Work Our dual-guarantee conception of proxy reencryption
L251: security mirrors the security requirements of what Ivan and Dodis call CPA
L252: security [22]. Their notion diﬀers substantially from what is now referred to
L253: by that name. The [22] conception of CPA security is only deﬁned in a proof
L254: in the appendix of that work and seems to have been completely overlooked
L255: by the later works proposing the modern notion of CPA security (beginning
L256: with [4] and then in its present form in [3]). If, however, Ivan and Dodis had
L257: undertaken to revisit proxy reencryption after [3], they might have proposed a
L258: security deﬁnition similar to HRA.

L260: In [28], Nu˜nez, Agudo, and Lopez provide a parameterized family of CCA-
L261: type attack models for proxy reencryption. Their weakest model corresponds to
L262: CPA security and their strongest to full CCA security. That work is partially
L263: a response to a claimed construction of CCA-1 secure proxy reencryption in a
L264: security model that does not allow reencryption queries. [28] provide an attack
L265: on the construction in the presence of a reencryption oracle consisting of care-
L266: fully constructed, dishonestly generated queries which leak the reencryption key.
L267: They do not consider restricting the reencryption oracle in the security game to
L268: honestly generated ciphertexts. We discuss [28] further in the full version [13].

L270: Vaikuntanathan which studies proxy reencryption using an obfuscation-based
L271: deﬁnition that is incomparable to CPA security [21]. Their deﬁnition requires
L272: that the functionality of the obfuscated reencryption circuit be statistically close
L273: to that of the ideal reencryption functionality: namely, that ReEnc(rki→j, Enc(pki, m)) ≈s
L274: Enc(pkj, m). Thus the deﬁnition of [21] (and even the relaxed correctness found
L275: in [11]) imply reencryption simulatability deﬁned in Section 5.

L353: Security Against Chosen Plaintext Attacks
L354: In this section, we recall the deﬁnition of CPA security for proxy reencryption
L355: and illustrate its shortcomings. We begin with the deﬁnitions of syntax, correct-
L356: ness, and CPA security from [3, Deﬁnition 2.2] (with minor changes in notation
L357: and presentation, and the change noted in Remark 1 at the end of this subsec-
L358: tion). The syntax and correctness requirements are common to CPA, HRA, and
L359: CCA security.
L360: For the sake of concreteness, simplicity, and brevity, we restrict the discussion
L361: to unidirectional, single-hop schemes. In multi-hop schemes, reencryption keys
L362: rkA→B and rkB→C can be used to reencrypt a ciphertext ctA from pkA to pkC.
L363: In single-hop schemes, they cannot. Single-hop or multi-hop schemes each have
L364: their beneﬁts and drawbacks, and works typically focus on one or the other
L365: notion.6 To the best of our knowledge, our observations and results can all be
L366: adapted to the multi-hop setting.
L367: Deﬁnition 1 (Proxy Reencryption: Syntax [3]). A proxy reencryption scheme
L368: for a message space M is a tuple of algorithms PRE = (Setup, KeyGen, ReKeyGen,
L369: Enc, ReEnc, Dec):
L370: Setup(1λ) →pp. On input security parameter 1λ, the setup algorithm outputs
L371: the public parameters pp.
L372: KeyGen(pp) →(pk, sk). On input public parameters, the key generation algo-
L373: rithm outputs a public key pk and a secret key sk. For ease of notation, we
L374: assume that both pk and sk include pp and refrain from including pp as input
L375: to other algorithms.
L376: ReKeyGen(ski, pkj) →rki→j. On input a secret key ski and a public key pkj,
L377: where i ̸= j, the reencryption key generation algorithm outputs a reencryp-
L378: tion key rki→j.
L379: Enc(pki, m) →cti. On input a public key pki and a message m ∈M, the
L380: encryption algorithm outputs a ciphertext cti.
L381: ReEnc(rki→j, cti) →ctj. On input a reencryption key from i to j rki→j and
L382: a ciphertext cti, the reencryption algorithm ouputs a ciphertext ctj or the
L383: error symbol ⊥.

L385: (i.e., able to reencrypt at least once, but agnostic about whether reencrypting more
L386: than once is possible) or if it is also a security property (i.e., a ciphertext can be reen-
L387: crypted once, but never twice). This distinction manifests in the security deﬁnition.

L391: and 5 for simplicity of presentation only.

L457: Remark 1. Another deﬁnitional subtlety of proxy reencryption worth discussing
L458: aﬀects not just CPA security, but HRA and CCA security as well. Consider the
L459: speciﬁcation of OReKeyGen and OReEnc in Deﬁnition 3. As deﬁned, the reencryption
L460: keys rki→j are persistent: the same key is used each time a pair (i, j) is queried.
L461: This follows [3, Deﬁnition 2.5] and [2, 17], though we ﬁnd our formalization
L462: somewhat simpler.
L463: Contrast this with [3, Deﬁnition 2.2] in which reencryption keys are ephemeral:
L464: they are generated afresh each time either oracle is invoked on the same pair
L465: (i, j). [7, 30, 10] similarly use ephemeral keys in their deﬁnitions. In the re-
L466: maining papers we examined, it was less clear whether reencryption keys were
L467: ephemeral or persistent.
L468: Neither deﬁnition implies the other; any scheme secure with persistent keys
L469: can be modiﬁed into one that is insecure with ephemeral keys, and vice-versa.
L470: The deﬁnitions, however, are not in serious tension; any scheme secure with per-
L471: sistent keys and having deterministic ReKeyGen is also secure with ephemeral
L472: keys, and ReKeyGen can in general be derandomized using pseudorandom func-
L473: tions. Of course, one can easily deﬁne a hybrid notion stronger than both by
L474: allowing the adversary to specify for each query whether it wants to use reen-
L475: cryption keys that are new or old.
L476: We adopt the persistent formalization as it better captures ‘typical’ use.
L477: To the best of our knowledge, all claims in this work can be adapted to the
L478: ephemeral setting.

L559: Security Against Honest Reencryption Attacks
L560: We seek a deﬁnition of security which holds as long as the adversary only sees
L561: honestly reencrypted ciphertexts, unless the set of corrupt parties can trivially
L562: violate security (by some chain of reencryption keys from an uncorrupted public
L563: key to a corrupted public key).
L564: We term this notion security against honest reencryption attacks (HRA). To
L565: formalize it, we model the ability of an adversary to see honest reencryptions by
L566: granting it access to a modiﬁed reencryption oracle OReEnc. Instead of taking a
L567: ciphertext as input, the modiﬁed OReEnc takes as input a reference to a previously
L568: generated ciphertext (either as the output of OEnc or OReEnc itself).
L569: 13
L570: To implement such an oracle, we introduce to the security game a key-value
L571: store C as additional state: the values are ciphertexts ct which are keyed by a
L572: pair of integers (i, k), where i denotes the index of the key pair (pki, ski) under
L573: which ct was (re)encrypted, and k is a unique index assigned to ct.
L574: As described, this new OReEnc admits a trivial attack: simply reencrypt the
L575: challenge ciphertext to a corrupted key and decrypt. To address this issue, we
L576: adapt an idea from [10]’s deﬁnition of CCA security: we rule out the trivial attack
L577: by storing a set Deriv of ciphertexts derived from the challenge by reencrypting,
L578: and rejecting queries to OReEnc for ciphertexts in Deriv and a corrupted target
L579: key. We might have instead chosen to forbid any reencryptions of the challenge
L580: ciphertext, even between uncorrupted keys. Though this would have simpliﬁed
L581: the deﬁnition, it would have been unsatisfactory. For example, in the single-
L582: writer, many-reader encrypted storage application the contents of a message m
L583: that gets reencrypted from Alice to Charlie should be hidden from Bob.

L665: 4.1
L666: Suﬃciency of HRA Security for Applications
L667: Returning to the applications of proxy reencryption described in Section 2, we
L668: observe that HRA security provides substantially stronger security guarantees.
L669: Encrypted email forwarding Using proxy reencryption with HRA security,
L670: Alice can forward encrypted email to Bob for a short period of time (during a
L671: vacation, say) and be sure that Bob cannot read her email after she returns.
L672: Key escrow Similar to encrypted email forwarding, proxy reencryption with
L673: HRA can be used to enable law enforcement to read certain encrypted mes-
L674: sages without compromising the secrecy of documents outside the scope of
L675: a search warrant or subpoena, for example.
L676: Single-writer, many-reader encrypted storage Whereas proxy reencryp-
L677: tion with CPA security can only support all or nothing access (i.e., all readers
L678: may access all data), HRA security can support ﬁne grained access control
L679: (i.e., each reader may access only a speciﬁc subset of the data).
L680: There is no question that HRA does not provide as much security as CCA, and
L681: that CCA-secure proxy reencryption would yield more robust applications. HRA
L682: security, however, can provide meaningful guarantees in the above applications.
L683: Encrypted email forwarding If Alice is forwarding all emails to Bob, then
L684: Bob could certainly mount an attack outside the honest reencryption model.
L685: On the other hand, if Alice is forwarding only those emails from a third-party
L686: sender Charlie, then such an attack is impossible without the involvement
L687: of Charlie (supposing of course that the sender of an email can be authenti-
L688: cated).
L689: Key escrow The hypothetical legal regime that establishes the government’s
L690: power of exceptional access by way of key escrow could additionally pro-
L691: hibit the government from mounting chosen-ciphertext attacks. In the United
L692: States, a Constitutional argument could perhaps be made that law-enforcement
L693: use of chosen-ciphertext attacks must be limited.
L694: Single-writer, many-reader encrypted storage The only ciphertexts be-
L695: ing reencrypted are those uploaded by the single-writer to the proxy server
L696: (hence the name). It is by no means a stretch to require that the proxy server
L697: does not allow writes by unauthorized parties (i.e., the readers). If the honest
L698: writer only uploads honestly generated ciphertexts, HRA is appropriate.

L702: Can we construct HRA-secure proxy reencryption? The most natural place to

L704: We begin by demonstrating that the CPA secure scheme of [31] is not HRA

L715: Remark 3. It may seem that CCA security should imply HRA security, but
L716: unfortunately the situation is not so clear. Intuitively, CCA security allows
L717: the adversary to make relatively unrestricted queries to both OReEnc and ODec,
L718: whereas HRA restricts the adversary to making only honest reencryption queries
L719: to OReEnc.

L721: a naive attempt at a reduction. The CCA deﬁnition prevents reencryptions or de-
L722: cryptions of all ciphertexts that could in principle be derived from the challenge
L723: (including by rerandomization). On the other hand, the HRA security game re-
L724: stricts reencryption queries only when the ciphertext is actually a derivative of
L725: the challenge. The adversary may reencrypt other encryptions of the challenge
L726: messages, so long as those encryptions were honestly generated independently
L727: from the challenge ciphertext.
L728: We do not resolve the question of whether CCA security implies HRA se-
L729: curity. By Theorem 5, any CCA secure proxy reencryption scheme satisfying
L730: reencryption simulatability is also HRA secure. See the full version of this arti-
L731: cle [13] for further discussion.

L852: Fully Homomorphic Encryption and Proxy Reencryption
L853: There is an intimate connection between FHE and proxy reencryption: a suﬃ-
L854: ciently powerful somewhat homomorphic encryption scheme implies CPA secure
L855: proxy reencryption, which can be used to “bootstrap” the scheme to achieve
L856: fully homomorphic encryption [19]. For the relevant FHE deﬁnitions, see [19,
L857: Section 2].
L858: Let FHE = (SetupFHE, KeyGenFHE, EncFHE, DecFHE, EvalFHE) be an FHE scheme.
L859: Proxy reencryption can be constructed as follows (compare to the Trivial Scheme):
L860: KeyGenPRE, EncPRE and DecPRE are identical to their FHE counterparts.
L861: ReKeyGenPRE(ski, pkj) = EncFHE(pkj, ski)∥pkj. The reencryption key rki→j is
L862: an encryption under pkj of ski, along with the target public key pkj.
L863: ReEncPRE(rki→j, cti): Let cti→j ←EncFHE(pkj, cti). Homomorphically compute
L864: the FHE decryption function DecFHE(ski, cti) using the corresponding cipher-
L865: texts rki→j and cti→j (under pkj). Namely, ctj = EvalFHE(pkj, DecFHE, rki→j, cti→j).
L866: The correctness of the FHE implies the correctness of the resulting proxy reen-
L867: cryption:
L868: DecPRE(skj, ctj) = DecFHE(skj, ctj) = DecFHE(ski, cti) = DecPRE(ski, cti).
L869: Furthermore, the proxy reencryption scheme is CPA secure.
L870: To demonstrate that the construction might not be HRA secure, consider
L871: the following fully homomorphic encryption scheme FHE′ constructed from any
L872: existing scheme FHE. The only modiﬁcation made in FHE′ is to EvalFHE′:
L873: EvalFHE′(pkj, C, ct1, ct2) := EvalFHE(pkj, C, ct1, ct2)∥ct1.
L874: Note that FHE′ does not violate FHE compactness if ct1 (in the proxy reencryp-
L875: tion construction, rki→j) is always of some size bounded by a polynomial in the
L876: security parameter of the FHE scheme; this suﬃces for our purpose. Instanti-
L877: ating the proxy reencryption construction with FHE′ essentially results in the
L878: Concatenation Scheme, which is not HRA secure.
L879: 20
L880: Circuit Privacy. An FHE scheme is circuit private if ciphertexts resulting
L881: from FHE evaluations are statistically indistinguishable from fresh ciphertexts
L882: [19]. Namely, if for any circuit C and any ciphertexts ct1,. . . ,ctt:
L883: EncFHE(pk, C(ct1, . . . , ctt)) ≈s EvalFHE(pk, C, ct1, . . . , ctt).
L884: In [19], an FHE scheme without circuit privacy is modiﬁed to be circuit private
L885: by rerandomizing the ciphertexts resulting from EvalFHE.
L886: While our proxy reencryption construction above is not in general HRA se-
L887: cure, it is easy to see that if the underlying FHE is circuit private, then the
L888: proxy reencryption is reencryption simulatable (Deﬁnition 7). By Theorem 5,
L889: the resulting scheme is therefore HRA secure.

L1200: B.1
L1201: Informal comparison
L1202: RIND-CPA is less suitable than HRA as a replacement for CPA security of proxy
L1203: reencryption. First and most importantly, HRA better captures the intuitive
L1204: guarantees of Enc-CPA security for standard encryption. Second, access to an
L1205: unrestricted ReEnc oracle makes it a more useful as a testing ground for the
L1206: development of new techniques. Finally, two idiosyncrasies of the [14] formulation
L1207: of RIND-CPA security present additional issues.
L1208: Capturing Enc-CPA security. In Enc-CPA security for standard encryption, the
L1209: adversary is able to arbitrarily aﬀect the distribution of plaintext messages. One
L1210: way of viewing this aspect of the deﬁnition is that Enc-CPA requires security
L1211: while being agnostic as to the true distribution over messages (except that it is
L1212: eﬃciently sampleable). Other than choosing the distribution over messages, the
L1213: adversary is only allowed to see publicly-available information (i.e. public keys
L1214: and parameters) and honestly encrypted ciphertexts. Informally, the Enc-CPA
L1215: guarantee is that security should hold under normal operating conditions against
L1216: eavesdropping parties without making distributional assumptions on plaintext
L1217: messages. However, Enc-CPA makes no guarantees about dishonestly generated
L1218: or malformed ciphertexts.
L1219: HRA security captures this intuitive guarantee better than RIND-CPA. In
L1220: the course of normal operation of a proxy reencryption, an adversarial party
L1221: will see reencrypted ciphertexts. These ciphertexts may come at any time—
L1222: both before and after other ciphertexts whose contents should remain secret.
L1223: While HRA allows reencryption both before and after the challenge, RIND-CPA
L1224: restricts the reencryption oracle to the period before the challenge.
L1225: HRA makes minimal assumptions about the distribution of plaintext mes-
L1226: sages by allowing the adversary to choose messages itself, just as in Enc-CPA.
L1227: RIND-CPA goes further by making requirements in the face of malformed or
L1228: dishonestly generated ciphertexts.
L1229: A testing ground for new techniques. For classical encryption, Enc-CCA security
L1230: is strictly stronger than Enc-CPA security. In fact, there are many settings where
L1231: Enc-CPA security is demonstrably insuﬃcient. Why then does the cryptography
L1232: community continue to study it? There are many answers to this question, but
L1233: we mention only two. First, although insuﬃcient for some applications, Enc-CPA
L1234: is useful in others. Second, it is useful as an intermediate goal because it seems
L1235: to capture a sort of hard core of the general problem of encryption and spurs
L1236: the development of new techniques.
L1237: HRA security enjoys these same features; RIND-CPA does not. As for useful-
L1238: ness for applications, HRA is meaningful in many of the envisioned applications
L1239: of proxy reencryption—many more than CPA security. Because RIND-CPA re-
L1240: stricts the reencryption oracle to the period before the challenge ciphertext, its
L1241: usefulness in applications is less clear.
L1242: The challenge of constructing CCA secure proxy reencryption is the same as
L1243: the challenge of Enc-CCA secure encryption: namely, dealing with dishonestly
L1244: 27
L1245: generated, possibly malformed ciphertexts. RIND-CPA, by allowing malformed
L1246: ciphertexts, presents similar challenges as full CCA security.
L1247: As for the usefulness of HRA as an intermediate goal towards CCA secu-
L1248: rity, the historical development of proxy reencryption is proof itself. This sounds
L1249: paradoxical: how can this be true if the notion has only just been introduced
L1250: in this work? Many of cryptographers that were targeting CPA security de-
L1251: veloped schemes that achieve HRA security with only minimal modiﬁcation.
L1252: The techniques developed in these constructions were later adapted to achieve
L1253: CCA security. This suggests that cryptographers’ intuitions for the hard core of
L1254: reencryption were not ﬂawed, only the formalization of these intuitions as CPA
L1255: security. HRA security is a better formalization for these intuitions and thus an
L1256: appropriate intermediate goal for reencryption research.
L1257: Idiosyncrasies of the RIND-CPA deﬁnition. We mention two unusual proper-
L1258: ties of the [14] deﬁnition. Unlike the adversary’s access to a ReEnc oracle, these
L1259: properties are not inherent in the RIND-CPA concept. It would be easy to pro-
L1260: pose a modiﬁed RIND-CPA deﬁnition that did not have these properties (e.g.,
L1261: IND-CCA0,1 in [28]).
L1262: First, the deﬁnition only considers the two party setting. Much like the in-
L1263: formal description of proxy reencryption in Section 1, there is only a single
L1264: uncorrupted key and a single corrupted key. It is easy to show that security in
L1265: the two party setting does not imply security in a many party setting.
L1266: Second, not only are inputs to ReEnc allowed to be malformed, but the cor-
L1267: rupted public key pk∗can be malformed as well. The adversary outputs pk∗itself
L1268: and it needs not be honestly generated. This makes RIND-CPA security as de-
L1269: ﬁned in [14] formally incomparable to all other deﬁnitions of proxy reencryption
L1270: security we know of, including the IND-CCA0,1 of [28].
L1271: These drawbacks of the [14] deﬁnition do not aﬀect the proof of Theorem 7,
L1272: but neither does the proof depend on them.

L1311: CPA and HRA security would be easy if it were possible to use Enc oracle
L1312: to generate a fresh, honest encryption of the challenge plaintext. This fresh

L1314: key, revealing the challenge plaintext.

L1316: of the outer layer is equal to the ciphertext space of the inner layer. If the
L1317: challenge ciphertext comes from the inner layer, then it can be used as input to

L1319: the challenge plaintext—namely, an encryption of the challenge ciphertext. The

L1321: and decrypted. But it seems we are no better oﬀ; decrypting the outer ciphertext

L1323: party.
