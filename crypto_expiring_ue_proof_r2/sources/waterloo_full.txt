                                         Abstract

    Updatable public-key encryption (UPKE) serves as a key tool for ensuring compro-
mise resilience in dynamic group messaging systems such as MLS and TreeKEM. Prior
work has introduced a variety of security notions for UPKE, including chosen-randomness
and chosen-update security, chosen ciphertext attack (CCA) security, adaptive corruption
resilience, public verifiability, and adversarially generated forking update structures. How-
ever, these notions make the security definition complex, and there is very little work on
instantiating schemes that satisfy it.
    In this work, we develop generic transformations that enable a sequence of upgrades
from weaker to stronger UPKE notions, each introducing additional security properties.
These security properties include straightline and forking update structures, selective and
adaptive corruptions, public verifiability, chosen randomness and chosen-update security,
and CPA and CCA notions. We define intermediate security notions that serve as useful
stepping stones while adding the aforementioned properties. Some transformations rely
only on standard tools such as random oracles, while others additionally exploit natural
structural properties of schemes such as update uniformity and ciphertext updatability,
which we identify and formalize in this work. This modular structure allows one to isolate
and focus on specific combinations of properties of interest, facilitating easier security
analysis.

Introduction

Modern secure messaging applications have cryptographic needs beyond simple confiden-
tiality, integrity, and authentication. Secure messaging sessions are often long-lived, in-
creasing the likelihood that secret keys will be compromised. To protect against such
leaks, these applications often incorporate properties such as forward secrecy (FS) and
post-compromise security (PCS). Forward secrecy promises that even if the long-term se-
cret key leaks, past messages remain confidential. Similarly, post-compromise security
ensures that there is a mechanism to return to a secure state after a compromise, so that
future messages remain secure. These properties are most commonly achieved by frequently
updating the secret key material used to encrypt messages, and it is imperative that both
parties update to the same key, even if one of them is offline. The Messaging Layer Secu-
rity (MLS) [BBR+ 23] protocol is a standard for secure group messaging that incorporates
many security properties, including FS and PCS for groups. An important building block
for achieving these properties in secure group messaging is continuous group key agree-
ment (CGKA) [ACDT20, AAN+ 22, ACJM20] which helps the group agree on and update
secret key values. In MLS, the TreeKEM component uses updatable public-key encryption
schemes (UPKEs) to implement the CGKA process.
    UPKEs [JMM19, EJKM22, HLP22, AW25, DKW21, HPS23] allow one user to issue
updates to other users so they can roll their secret key material forward. More specifically,
UPKEs augment standard public key encryption (PKE) with two algorithms, UpdPk and
UpdSk, that facilitate key updates. These two algorithms enable any sender to initiate a
key update by updating the public key and generating an update token, which the receiver
uses to update their private key accordingly, achieving a form of forward secrecy. The
security definition for UPKEs builds on the IND-CPA game of standard PKEs and aims
to capture forward secrecy by giving the adversary access to two additional oracles: one

                                             1
for adversarial updates to the key and the other for a non-adversarial update followed by
a leak of the secret key material. We call the latter an honest-update-and-reveal query.
Chosen randomness security for UPKEs captures the notion of security when the adversary
is allowed to tell a party to update their secret key with a well-formed update token, then
reveal the secret key after an honest update; the adversary should not be able to learn any-
thing about messages encrypted under earlier keys. Chosen-update security strengthens
chosen-randomness security by capturing the notion that the adversary may submit mal-
formed update tokens, somewhat analogous to chosen-ciphertext attacks on PKEs, where
the adversary can submit malformed ciphertexts.
    MLS uses UPKEs in TreeKEM, and requires that they are secure against chosen-update
and chosen-ciphertext attacks. However, Alwen, Fuchsbauer, and Mularczyk [AFM24]
showed that there are scenarios in which an adversary can still attack UPKEs in TreeKEM
and proposed stronger security notions with additional properties for UPKEs. In TreeKEM,
if synchronization fails, the adversary can cause different users to update the same key ma-
terial in different ways. From the adversary’s perspective, the key may no longer be a
single chain of updates, but a tree of updates; forking security definitions for UPKEs allow
the adversary to construct such trees. Since TreeKEM is designed to be asynchronous, it
might be the case that some user updates the public key for a receiver while that receiver
is offline. In this case, other users would like to know whether the update token and the
new public key are a valid update, since an adversary could have instead sampled a fresh
public key and submitted a bogus token; this property is called public verifiability. At
the same time, with forking enabling a tree of keys, it does not make sense to restrict
the adversary to a single honest-update-and-reveal query; so the security definition can be
extended to allow arbitrary honest updates, as well as corruption of multiple nodes in the
tree, provided that such reveals do not make the game trivial to win.
    The UPKEs used in the current MLS standard do not include forking, public verifiabil-
ity, or corruption in their security definitions; likely because it is hard to construct efficient
schemes that satisfy such complex security requirements. To our knowledge, only two
schemes in the literature satisfy these security properties. When [AFM24] proposed these
properties, they instantiated them with a scheme based on the discrete-log assumption in
groups. Later, [AFMR25] modified the lattice-based UPKE of [HPS23] to add these prop-
erties, but it remains unclear how generalizable these modifications are. There is a need
for more constructions of strong UPKEs to understand the security and efficiency char-
acteristics of schemes instantiated under this definition, which will help choose a suitable
candidate to strengthen TreeKEM and prevent potential attacks.

1.1      Our Contributions
In this work, we provide generic transformations that lift UPKEs to these stronger se-
curity definitions. Starting with a straightline, chosen-randomness, CPA-secure UPKE,
we introduce security properties like chosen-updates, forking, public verifiability (PV),
CCA-security and corruptions one-by-one to come up with many intermediate security
definitions, and provide transforms for achieving these definitions. To facilitate these trans-
forms, we identify two useful properties for UPKEs: ciphertext updatability and update
uniformity, which, alongside the random oracle model, help us prove that our transforms
satisfy these security definitions. Our first transform uses Asano and Watanabe’s [AW25]
FO-like derandomization and re-encryption in the update function to lift a straightline
IND-CR-CPA-secure UPKE to a straightline IND-CU-CPA-secure one. Then, using ci-
phertext updatability, along with a straight-line simulation extractable NIZK-PoK, we can
lift it to an intermediate “half-forking” IND-CU-CPA UPKE with PV. The key idea of
the reduction for this transform is using ciphertext updatability to update the challenge
ciphertext encrypted under a given key to a key that the adversary expects. After that, we
lift the scheme to full forking security, while maintaining IND-CU-CPA and PV by using
update uniformity. Update uniformity implies that it is hard for an adversary to know if
a keypair resulted from a direct update on a parent node A or another node B elsewhere
in a given update tree. This property, along with the ZK property of the NIZK-PoK and
one-wayness of the UPKE allows our reduction to forge an honest update carried out by
the challenger. So if an adversary asks for an honest-update-and-reveal query on a node
A, we can ask the challenger for the same query on a different node B and pass the result
to the adversary as if it was performed on node A.
    Next we use a modified version of the Fujisaki–Okamoto (FO) transform [HHK17] com-
monly used in modern post-quantum KEMs like ML-KEM (Kyber) to add chosen cipher-
text security while maintaining forking, chosen-update security with PV. Before adding
selective corruption, we introduce another intermediate definition called reordered forking
IND-CU-CCA security with PV, which allows the adversary to ask for the honest-update-
and-reveal before asking for the challenge ciphertext; this intermediate step makes our final
transform much easier. We lift our UPKE to this definition using ciphertext updatability
to once again update the challenge ciphertext in the reduction. Finally, we add selective
corruptions to our security requirements. In this setting, the adversary must first commit
to the tree structure of the updates it intends to perform, along with the indices of the
nodes in the challenge set. The reduction can make use of this selective information (the
challenge set), along with update uniformity, to forge honest updates between nodes in-
side the challenge set to those outside it. This forgery is the same as the ones we used

   Here is a summary of all the terms discussed so far:

   • Straightline security: The security setting where the adversary is only allowed to
     update the latest node, resulting in a graph of updates that looks like a straight line
     chain.

   • Forking security: The security setting where the adversary is allowed to update
     any node that exists, resulting in a graph of updates that looks like a tree.

   • Chosen randomness security: The security setting where the adversary provides
     the randomness used to update a node honestly. This property is related to the
     security of the update mechanism.

   • Chosen update security: The security setting where the adversary may provide
     malformed update tokens to update a node. This property is related to the security
     of the update mechanism.

   • Public verifiability: The security property which allows other members of the
     group (non secret key holders) to verify that an update was generated properly.

                                                    4
   • Corruptions: The security property that allows the adversary to ask for the secret
     keys of arbitrary nodes, as long as they do not allow it to win trivially. It is a
     generalization of the honest-update-and-reveal query in the forking setting.

   • Selective corruptions: The security setting where the adversary has to commit
     some information about the nodes it is going to corrupt at the start of the game.

   • Adaptive corruptions: The security setting where the adversary can decide which
     nodes to corrupt on the fly without having committed to anything in the past.

   • Chosen plaintext security: The security setting where the adversary is given
     access to a challenge oracle but no decryption oracle for ciphertexts. This property
     is related to the security of the ciphertexts.

   • Chosen ciphertext security: The security setting where the adversary is given
     access to a decryption oracle alongside the challenge oracle. The adversary cannot
     ask for decryption of the challenge ciphertext under the corresponding challenge key
     to prevent trivial wins. This property is related to the security of the ciphertexts.


1.2      Organization
The remainder of this work is organized as follows. In Chapter 2, we describe our notation,
terminology, and review concepts that are useful to understand our work. Chapter 3
covers straightline security definitions and the transform that lifts a chosen-randomness-
secure UPKE to a chosen-update-secure one in the straightline setting. In Chapter 4, we
add forking security and public verifiability to our definitions and present transformations
achieving them. Chapter 5 upgrades chosen plaintext attack (CPA) security to chosen
ciphertext attack (CCA) security, and Chapter 6 covers transformations to add security
against corruptions. In Chapter 7 we discuss the utility of our transforms and how generally
applicable they are before finally closing with some limitations and discussion of future work
in Chapter 8.

Preliminaries

Notation. We use λ for the security parameter. For a distribution D, we write x ∈ D
(e.g., (pk0 , sk0 ) ∈ KGen(1λ )) to mean x is in the support of D, and use x ←$ D to mean x
is sampled from D. For a set S, x ←$ S means x is uniformly sampled from S.


Namespaces. Throughout the paper, we talk about many schemes with much over-
lapping syntax. We use namespaces with schemes and their functions, such as CR.Π or
CU.UpdPk, to disambiguate the scheme or function in question.


Stacks and Queues. In our reductions, we will need to make use of some basic data
structures. We define the syntax for those here.
    The first structure is called a stack. It is a last-in-first-out (LIFO) data structure,
meaning that the items added to the stack are removed in the reverse order of their in-
sertion. We write A ← Stack() to initialize a stack in the variable A. We add an item x
to the stack using A.push(x). Finally, A.pop() removes and returns the most recent item
added to the stack. We also use the functions A.is empty() and A.is not empty() to check
whether the stack is empty or contains items, respectively.
    Similar to a stack, the queue is a data structure. It is a first-in-first-out (FIFO) data
structure, meaning items are retrieved from the queue in the order they were added. We
write A ← Queue() to initialize a queue in the variable A. We can add an item x to the
queue using A.add(x). Finally, A.get() removes and returns the oldest item in the queue.
We also use the functions A.is empty() and A.is not empty() to check whether the queue
is empty or contains items, respectively.

2.1      Updatable PKEs
We review the syntax of updatable public-key encryption schemes (UPKEs).
Definition 1 (UPKE [DKW21, ABL25]). An updatable public key encryption (UPKE)
scheme with message space M, private key space SK, public key space PK, ciphertext space
C, update token space UP, encryption randomness space R1 , and update randomness space
R2 consists of five probabilistic polynomial time (PPT) algorithms:

   – (pk0 , sk0 ) ←$ KGen(1λ ): takes as input 1λ , and outputs an initial public-private key
     pair (pk0 , sk0 ) ∈ PK × SK.
   – c ← Enc(pki , m; r): takes as input a public key pki ∈ PK and a message m ∈ M,
     randomness r ∈ R1 and outputs a ciphertext c ∈ C.
   – m/⊥← Dec(ski , c): takes as input a secret key ski ∈ SK and a ciphertext c ∈ C, and
     outputs a message m ∈ M or ⊥ on failure.
   – (pki+1 , upi ) ← UpdPk(pki ; r): takes as input a public key pki ∈ PK, and randomness
     r ∈ R2 and outputs a new public key pki+1 ∈ PK and an update token upi ∈ UP.
   – ski+1 ← UpdSk(ski , pki , upi , pki+1 ): takes as input a secret key ski ∈ SK, a corre-
     sponding public key pki ∈ PK, an update token upi ∈ UP and the resultant public
     key pki+1 ∈ PK, and outputs a new secret key ski+1 ∈ SK.

For correctness we require that for all (pk0 , sk0 ) ∈ KGen(1λ ), m ∈ M, and i ∈ {0, 1, 2, . . . },
and (pkj+1 , upj ) ←$ UpdPk(pkj ), skj+1 ← UpdSk(skj , pkj , upj , pkj+1 ) for all 0 ≤ j ≤ i, we
have
                        Pr[Dec(ski , Enc(pki , m)) = m] ≥ 1 − negl(λ) ,
where the probability is taken over the randomness of Enc.

private output d called the shift value and there exist efficient deterministic algorithms
ShiftPK, ShiftSK such that for any (pk1 , sk1 ) ∈ Corr with

             (pk2 , up1 , d) ←$ UpdPk(pk1 ) and sk2 ← UpdSk(sk1 , pk1 , up1 , pk2 ) ,

we have

                      pk2 = ShiftPK(pk1 , d) and sk2 = ShiftSK(sk1 , d) .

    Since it is a private output, the shift value d is not part of the syntax, but it is always
visible to the entity running the function. We note that the above definition of shiftable
is trivially satisfied by any UPKE by setting the shift value to the random coins used in
UpdPk and including the public key in the secret key. However, later in Chapter 4, when
we want to prove that an adversarially provided key is the result of an update, the above
formulation is useful for moving all the extra steps outside the proof itself, making it more
efficient. Consider as an example a UPKE scheme where (pk1 , sk1 ) and (pk2 , sk2 ) have an
algebraic relation and the UpdPk algorithm first passes its random coins through a function
H to derive this relation, applies it to pk1 to get pk2 , and finally calls another function G
to generate the update token. One way to generate such a proof would be to prove each
step of this computation, including the functions H and G, which would be expensive. On
the other hand, there might exist efficient proofs of the algebraic relation connecting the
keypairs, which might be sufficient for the security requirements. In such cases, the latter
proof would be preferable for concrete efficiency, and formulating a UPKE as shiftable
allows us to talk about such scenarios generically.
   For the rest of the document, we will only work with shiftable UPKEs.

Straightline Security

In this chapter, we look at straightline security definitions, where the adversary is restricted
to only updating the latest node in the security games. We define indistinguishability un-

updates and CPA in Section 3.3. Finally, we show the transformation for lifting a straight-
line chosen randomness CPA-secure UPKE to a straightline chosen updates CPA-secure
UPKE and prove its security in Section 3.4.

3.4     Lifting Chosen Randomness To Chosen Update

We use the FO transform, via derandomization and re-encryption, to convert a
S-IND-CR-CPA UPKE scheme CR.Π = (CR.KGen, CR.Enc, CR.Dec, CR.UpdPk, CR.UpdSk)
into a S-IND-CU-CPA UPKE scheme CU.Π = (CU.KGen, CU.Enc, CU.Dec, CU.UpdPk,
CU.UpdSk); the main idea is to apply the FO transform to ensure wellformedness of the
update token.
   We set CU.KGen = CR.KGen, CU.Enc = CR.Enc, CU.Dec = CR.Dec and then define
CU.UpdPk and CU.UpdSk in Figure 3.4. In the construction, H and G are two independent
random oracles. Since the function CR.UpdPk is run inside the transform, the private
output shift value is preserved by the transform. This will be useful for the next transform.

IND-CU-CCA security. Our transform is a stripped-down version of the construction

   We first give a proof outline. The main idea is that we can determine whether an
update query was generated properly and the randomness used for it by observing the
random-oracle queries made by A. Since the transformation requires an RO call at each
step to derive the randomness, we should be able to see all parts of the update function
being carried out in the RO queries.
    For the games, we first start with the unmodified game G0 . In game G1 , we abort if
we find a honestly generated, but faulty update token. In game G2 , we then handle the
rejection of update queries without knowing the secret key, by observing the RO queries
made by the adversary. There is a negligible chance here that the adversary generated
a valid update token without making the corresponding RO queries. Next in game G3 ,
we generate the final update token by encrypting a random value r, and show that the
adversary cannot notice this difference if CR.Π is OW-CR-CPA secure. Finally, we show
that any adversary that beats G3 can be used to construct an adversary that beats the
IND-CR-CPA game of the underlying UPKE.
    This proof works for reducing straight-line IND-CU-CPA to straight-line IND-CR-CPA
as well as reducing forking IND-CU-CPA to forking IND-CR-CPA, with forking security
defined in Chapter 4. The reduction revolves around the ability to reject malformed update
tokens and to extract randomness from honestly generated tokens using random oracles.
This core ability does not depend on the games being straight-line or forking, so the proof
proceeds identically for both. For the sake of brevity, we only show the details of the
straight-line games below.

Chapter 4

Adding Forking And Public
Verifiability

In this chapter, we add forking security and public verifiability to our system of trans-
forms. We start by recalling the definitions of forking security and public verifiability (PV)
as introduced in [AFM24]. Then, in Section 4.1 we define our intermediate half-forking se-
curity notion and present our transform to achieve in Section 4.2. Similarly, in Section 4.3
we define the full forking security notion with public verifiability and show the transform
achieving it in Section 4.4.


Forking. MLS and TreeKEM enforce some level of synchronization to ensure message
ordering. This synchronization ensures that updates are ordered and received in a straight
line. However, we must consider an adversary that may control the network and reorder
messages differently for each participant in the chat. In such scenarios, while the up-
dates appear to be in a straight line from the users’ perspectives, there is actually forking
from the adversary’s perspective. Hence, security must hold even in the presence of fork-
ing/concurrent updates.
     Whereas the straight-line games involve a straight chain of updates, the forking game
allows the adversary to update any node i (not necessarily the latest one), thereby inducing
a tree structure with forks. The adversary may request the challenge ciphertext at a node
i∗ , issue further updates, and request key revelation after an honest update on another
arbitrarily chosen node.



                                             23
Public verifiability. Since the adversary may update keys for an offline receiver, we
want any party—not just the receiver—to be able to verify the validity of a newly formed
public key; otherwise, the adversary could trivially win by registering arbitrary keys. To
enable this, every update message, including adversarially issued ones, must include a
publicly verifiable proof attesting to the validity of the new public key. This allows any
party to verify the new public key independently of the secret-key holder. Note that the
goal here is to protect the confidentiality of messages encrypted under updated keys, but
we do not aim to provide any guarantees regarding the validity or correctness of the update
itself.
    To achieve public verifiability, we modify the UpdPk algorithm to output a proof at-
testing to the linkage between the old and new public keys. This proof is then checked
by a verification algorithm VerifyPk. Receivers must also verify this proof before updating
their secret keys. Formally, we add the following algorithms:

   • (pki+1 , upi , πi ) ←$ UpdPk(pki ): The public update algorithm takes in a public key pki
     and outputs the updated public key pki+1 , the update token upi , and a proof πi .

   • 0/1 ← VerifyPk(pki , pki+1 , πi ): The verify algorithm takes in the old public key pki ,
     the new public key pki+1 , and the proof πi , and outputs 0/1.

   With the correctness requirement that for any (pki+1 , upi , πi ) ←$ UpdPk(pki ),
VerifyPk(pki , pki+1 , πi ) should output 1.


Modelling security. With PV, we want to protect other members who do not have
the secret key (non-receivers) against maliciously generated public key updates. These
other members use the proofs to decide whether they can trust the updated key; if a
proof is valid, then the confidentiality of the messages encrypted under the key should be
maintained. To capture this idea, we extend the security game by introducing a new oracle
called VerifyO, which models the behavior of non-receivers in the presence of potentially
malicious updates.

   • VerifyO(i, pk′ , π ′ ): The oracle runs VerifyPk on (pki , pk′ , π ′ ). If the output is 0, it
     returns ⊥. If the output is 1, it creates a new child of node i and sets its public key
     as pk′ .

   Since the child is created using only the proof, not the update token, the challenger is
not expected to know the child’s secret key. Such nodes created by VerifyO are called half

                                               24
nodes, since they only have public keys. Other nodes created by the UpdO oracle that have
both public and secret keys are called full nodes. The adversary can ask for the challenge
ciphertext on these half nodes.
    Naturally, the adversary cannot ask for corrupt queries or honest-update-and-reveal
queries on half nodes. Hence, if an adversary ever creates a half node in a straight-line
game, it loses the ability to ask for a UpdHRev query and consequently gets less information
to win the game. Therefore, half nodes are useless in the straight-line security games, which
is why we add forking before or alongside adding public verifiability.


4.1      HF-IND-CU-CPA-PV: Half-Forking, Chosen Updates
As we have shown so far, public verifiability and forking are closely intertwined. Hence, in
our series of transforms, we choose to add PV first by introducing an intermediate notion
called half-forking, which we later upgrade to full forking security in subsequent transforms.

create forks using the VerifyO oracle. The result is that our update tree consists of a

contrast to the straight-line game. This game is shown in Figure 4.1. This game does
not correspond to any real-world adversary since half-forking is an arbitrary restriction on
forking, but it serves as a convenient intermediate notion to make our transforms and their
respective proofs easier.

4.4      Lifting Half-Forking to Forking Security
To enable our transform from half-forking to full-forking security, we introduce a new
property: update uniformity. At a high level, this captures the idea that the result of a
single update can be any key in the update closure. While there always exists a series of
shift values connecting a key to any other key in the closure, it is not necessarily true that
there is a single update randomness that does this. Update uniformity means that such a
randomness always exists, or at least that the adversary cannot detect when it does not
exist.
    If update uniformity holds (and the scheme is OW-CR-CPA-secure), we can use it
to forge the response to the “honest-update-and-reveal” query on a node by querying a
completely different node at the challenger. We do so by giving out the keypair obtained
from the same query on another node, forging the update token, and simulating the proof.
We will show that the adversary does not detect this forgery in our security proofs, but
first, we define update uniformity below.

Chosen Ciphertext Security

In this chapter we introduce security against chosen ciphertext attacks (CCA security).
As a part of the transform for achieving CCA security, we also convert our UPKE to an
updatable KEM (UKEM). We introduce the relevant definitions in Section 5.1 and then
present our transform along with its proof of security in Section 5.2. The transform we use
is an adaptation of the FO transform used by PKEs [HHK17] to the UPKE setting.


5.1     CCA-Secure UKEM
Our next transform lifts CPA security to chosen ciphertext attack (CCA) security. CCA
security is an important property for most PKE schemes, including UPKEs, because it
rules out a large class of attacks. At the same time, the KEM-DEM paradigm [CS03] has
proven to be a useful framework in the public key setting and there exist many efficient and
generic transforms that lift a CPA-secure PKE to a CCA-secure KEM [HHK17], which is
our approach as well. We provide the syntax for a UKEM with public verifiability, adapted
from [AFM24].

5.2      Lifting CPA UPKE To CCA UKEM
We can use a modification of [HHK17]’s modular FO transform to obtain a CCA-secure
UKEM. There are two potential issues to worry about when introducing CCA security:
the adversary using the decryption oracle on update tokens, and dealing with well formed
ciphertexts that are a result of shifting an existing ciphertext. Due to the domain separation
between the random oracles in our construction, querying the decryption oracle on update
tokens should almost always return ⊥, which takes care of the first issue. To deal the latter
issue, we include the public key in the oracle call used to derive the randomness of the
ciphertext. With this modification, even if a shifted ciphertext preserves the message and
the randomnes, it will not be considered a well formed ciphertext for the new public key.
The transform is shown in Figure 5.2.

Corruptions

The last property we add is security against corruptions, which is a generalization of the
UpdHRev query. Instead of a single honest-update-and-reveal query, we will allow the
adversary to make many independent honest update queries and many reveal (also called
corruption) queries. We need to have some restrictions on which nodes the adversary can
corrupt to avoid trivial wins. We will refer to the set of nodes that the adversary cannot
corrupt as the challenge set. The challenge set for a game with the challenge node i∗
consists of:

  1. All nodes i′ on the path from node 0 to node i∗ including both of them.

  2. All nodes i′ such that there exists i in the set with pki′ = pki .

  3. All descendants of the nodes in the set created from adversarial updates

    We include the nodes in point 1 because if the adversary learns any of the secret keys
on the path, it can use the update tokens it has seen throughout the game to update that
secret key to the challenge secret key. After including the nodes from point 1, we must
include nodes from point 2 since forking updates allow the adversary to re-use update
tokens and proofs to create nodes that are identical to nodes in the challenge set in all
aspects except their index at the challenger. The nodes from the point 3 in the above
description are included because generally, we can assume that if an update was generated
adversarially, then the adversary knows the shift value used to generate it. Knowing the
shift value could allow the adversary to roll back the update and learn the parent node’s
secret key.

tentially want to ask for the UpdHRev query before the challenge query, but the challenger
does not allow this. The interesting point here is that the challenge query needs no input
beyond specifying the node on which it is asked. So the main idea will be to immediately
ask for the challenge query and the UpdHRev query at the root node during initialization,
and then handle all queries made by the adversary ourselves. Then we can forge the up-
date for the UpdHRev query that the adversary asks for, and update the ciphertext to
the correct node when the adversary asks for the challenge query. One thing to note is
that when updating ciphertexts, we have no control over the randomness of the resulting
ciphertext, so we need to specify abort conditions to ensure the adversary does not realize
the ciphertext is malformed.
    For the games, we start with the unmodified game G0 . In game G1 , we abort if we
find a honestly generated, but faulty update token. In game G2 , we handle the rejection
of malformed update queries without the knowledge of the secret key, using the random
oracles. In game G3 , we abort if we find a honestly generated, but faulty ciphertext. In
G4 , we handle decapsulation queries without knowledge of the secret, again using random
oracles. In G5 , we begin forging the update in the UpdHRev query by replacing the proof
with one generated by the simulator. In G6 , we continue this forgery by replacing the
update token with a forged one. In G7 , we finish this forgery by replacing the correct

    The reduction works as follows: we use the challenger to handle queries on the nodes
inside the challenge set; we forge full honest updates connecting nodes inside the challenge
set to a node outside it; and we handle all queries on the nodes outside the challenge set
ourselves. These forged updates allow us to know the secret key for all nodes outside the
challenge set, which enables us to answer all update, decapsulate, and reveal queries on
these nodes. To implement this idea in the reduction, a simple check whether i is in the
challenge set suffices for most oracles. If i is in the challenge set, we call the corresponding
oracle at the challenger, and handle things ourselves otherwise.
   The honest update oracle, however, is not present at the challenger and needs more
care to be handled correctly. We handle each case in which the honest update oracle can


                                                      78
be called differently. For the full updates connecting a node inside the challenge set to one
outside it, we forge the update as in the previous games. We ask for a UpdHRev query on
the root node as soon as the game starts so that (pkf , skf ) exist for these forged updates.
For nodes that are completely inside the challenge set, we run an honest update and then
call either the challenger’s UpdO oracle (full update) or VerifyO oracle (half update). Lastly,
we handle all types of updates that occur outside the challenge set by manually running
the honest update.
   Since the nodes are created in a random order at the reduction, and only a few of those
nodes are recreated at the challenger, the indexing of the nodes at the challenger is different
from that at the reduction. To remedy this, we make use of the Id-M ap function, which
takes in the index at the reduction and outputs the corresponding index at the challenger.
By designing oracles in this way, B perfectly simulates A’s view from G3 . Hence, we have:

                         |Pr[G3 ] − 1/2| = AdvF-IND-CU-CCA-PV2
                                              B,CCA.Π          (λ).

    Combining all the bounds accumulated during the game hops yields the desired bound
in the theorem.

LWE-based. UPKEs based on LWE closely follow the structure of Regev’s LWE scheme
[Reg05], and we examine the UPKE of [HPS23]. The public key and encryption are similar
in structure to Regev’s scheme, and the updates are performed by adding a vector to the
secret key and increasing the noise in the public key. For a given key pair ((A, b), s) =
((A, As + e1 ), s) being updated using shift value d, the resultant keypair is ((A′ , b′ ), s′ ) =
((A, As + Ad + e1 + e2 ), s + d). Any ciphertext (c1 , c2 ) = (xA, xb + e3 + f · m) en-
crypted under the first keypair can be updated to be encrypted using the second keypair
as (c′1 , c′2 ) = (c1 , c2 + c1 d + e4 ). The updated ciphertexts are indistinguishable by the
hardness of LWE. Update uniformity follows from the fact that there always exists a shift
value d relating any two keypairs in the same update closure and the hardness of LWE.


LIP-based. The hardness of the lattice isomorphism problem (LIP) has also been used
to make UPKEs. In Hollow LWE [ABL25], the secret key is a vector sk = r and the public
key is pk = (A, rT A) for some tall matrix A. The ciphertexts are similar to Regev’s LWE
scheme as (c1 , c2 ) = (Ax + e, rT Ax + e + f · m) for some random vector x. The shift
values consist of a random orthogonal matrix O and a unimodular matrix U. Keys are
updated by setting sk′ = Or and pk′ = (OAU, rT AU). Using the shift value, we are able
to update any ciphertext (c1 , c2 ) encrypted under pk using randomness x to a ciphertext
encrypted under pk′ using randomness U−1 x by setting (c′1 , c′2 ) = (Oc1 , c2 ). The updated
ciphertexts are statistically indistinguishable from fresh encryptions under pk′ . Update
uniformity follows from the fact that there always exists a shift value (O, U) connecting
any two keys in the same update closure.
   As we have shown, our transformations are applicable to a wide range of UPKE
schemes.

Conclusions and Future Work

In this thesis, we have constructed generic transformations for UPKEs. These transfor-
mations lift any indistinguishability under chosen randomness and chosen plaintext attack
(IND-CR-CPA) secure UPKE with ciphertext updatability and update uniformity to a
UKEM that is secure under forking indistinguishability under chosen update, chosen cipher-
text attacks with public verifiability and selective corruptions (Sel-F-IND-CU-CCA-PV).
We hope these transformations make it easier to instantiate strongly secure UPKEs and
improve their security in secure messaging contexts.
   There are two few possible areas for future work:

   • QROM security: Our transformations were proven secure in the random oracle
     model (ROM). However, a quantum adversary might be able to query the random
     oracle in superposition, so there is a need for further analysis in the quantum ran-
     dom oracle model (QROM) to assess the security of our transforms against such
     adversaries.

   • Adaptive corruptions: Our transformations can only achieve security in the pres-
     ence of selective corruptions. Proving security in the presence of adaptive corruptions
     remains an open problem, and it is unclear if it requires further assumptions.

   • Further analysis of similar transforms: The transformations we present make
     no claims of being the most efficient or optimal. Further research could be conducted
     to construct transformations with stronger security guarantees or that require fewer
     assumptions.
