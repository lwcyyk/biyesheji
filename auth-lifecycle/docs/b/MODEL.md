# 统一配置模型和条件正确性

## 1. 有限域与可信输入

JSON schema 标识为 `auth-lifecycle-b/1`。`model.prepare` 拒绝额外字段、类型混淆、空目录、重复标识、未核实原生效果和重叠撤销域。最多 8 任务、16 授权、16 路径、16 环境、16 原生撤销域、16 场景，停止决策深度 H≤8。该上限是实现可接受域，**不是已经穷尽的模型空间**。

| 字段 | 含义 |
|---|---|
| `tasks[t]` | 绑定账户及任务要求的权限集合 |
| `credentials[g]` | 可通过已登记接口取得的授权实例、凭据类型、原生范围、issue 操作；token_labels 仅为合成标签 |
| `revocations[u]` | 原生撤销效果域 `affects`、证据引用、核实标记、`all_material`/`refresh_only`、撤销操作或不开放操作 |
| `environments[e]` | broker、isolated、direct；是否受控、create 和 stop 操作 |
| `paths[p]` | 指定任务/环境下的 AND 授权支持集合及 delegate 操作；任务的多条路径构成 OR |
| `approved` | 所有方法相同的已批准操作凭据名称集，不允许算法自行补批准 |
| `budgets` | 单次 setup+场景停止的总批准次数、总请求数、隔离环境数、G 上限 |
| `scenarios[s]` | 本地停止集合、远端停止集合、每个前缀必须保留的任务集合 |
| `horizon` | 单次停止计划最多执行的决策步数，不是墙钟时间，也不包括 setup 步数 |

每个 operation 明确 `interface, approval, approvals, requests`；无批准引用的操作不得自行消耗“新增批准”。批准的成员资格和计费是不同条件：先前获准的无新批准动作可以 `approvals=0`，但仍需批准名称存在。所有费用是非负整数，拒绝 Python bool 充当 0/1。

原生撤销效果域形成授权目录的分区：每个授权恰属一个效果域。两个别名 token 的字符串不同不会创建独立撤销单元；分区重叠或覆盖不全返回 UNKNOWN，不能默认独立。本版不表达嵌套、重叠的多级撤销动作；需要此类语义时必须扩展模型并重新验证，而不是拆成虚假独立域。

`verified=True` 与 `evidence` 是可信契约的输入条件，代码能核对声明的效果和分区一致性，**不能凭字符串鉴定外部证据真实性**。所有 fixture 的 `synthetic-fixture:*` 都是合成语义声明，未冒充真实 OAuth 核验结果。

## 2. 配置、委托和权限

令 C 为选择的路径集合，每个任务至少有一条路径。路径 p 的授权集合 R(p) 非空，其中每个授权的账户必须等于任务绑定账户，其范围并集必须覆盖该路径承担的任务权限。每条路径表示一个不可省略任一成员的 AND 支持；不能因为权限并集满足就把 AND 任意改成 OR。

配置取得的授权集合 A(C)=⋃R(p)，环境集合 E(C) 为选中路径的环境。所有取得的授权都来自同一输入目录；不能创建候选专享的 grant 或独立撤销接口。授权可以由多个任务、路径和环境共享。

setup 计划使用固定规范顺序：issue 已用授权 → create 已用环境 → delegate 每条已选路径。每条操作都核对批准并计费，检查器拒绝删除或替换 setup 操作。本版 setup 是可靠、确定、无额外副作用的契约操作，**目前只输出并检查计划，不向真实服务派发**。

三类环境：broker 可关闭自身的任务门控，isolated 可整体关闭该环境，direct 没有本地关闭动作。`controlled=False` 不产生本地停止动作。隔离环境不自动形成独立原生授权；把同一 root 的授权放入两个环境仍只属于一个撤销域。

路径目录必须覆盖所研究任务的全部已委托能力，包括缓存、拷贝、旁路和替代支持。这里不自动从 scope 字符串推断未登记的账户图边。不完整路径目录会产生错误的远端停止结论，这是外部抽象保持的关键未证明条件。

## 3. 运行状态与目标

独立解释器状态为 x=(L,E_open,D_open,q,a,r)：存活授权、开放环境、开放任务门控、已用请求、已用批准、剩余停止决策步。初态由 setup 唯一确定。

原生可用性：

`Native(t,x) ⇔ ∃p∈C_t : R(p)⊆L`。

本地可用性：

`Local(t,x) ⇔ ∃p∈C_t : R(p)⊆L ∧ env(p)∈E_open ∧ (env(p),t)∈D_open`。

关闭门控只改变 D_open；关闭环境只改变 E_open；撤销效果域 u 删除其中全部授权的存活性。`refresh_only` 的动作不能据此删除当前有效访问材料，因此此 profile 不生成能完成严格远端停止的该类撤销动作；本地门控仍可满足本地目标。没有提供 revoke 接口或者批准缺失时，不允许凭语义知识代替真实操作。

场景 s 的终态目标：本地停止任务均 ¬Local，远端停止任务均 ¬Native，保留任务均 Local。保留任务还必须在初态及**每个已执行动作前缀**可用。多条替代支持下，保留只需至少一条存活路径；停止必须切断全部相关路径。

所有操作须满足已批准、setup+stop 总预算不超限、r>0，每次实际停止动作使 r→r−1。r=0 只允许已经达到目标。操作不可逆且不新增路径、权限或批准，费用非负；重复已执行的操作没有新效果，删去重复不会使可行计划失效。该单调性支持候选缓存和反证中“每动作至多一次”的有限缩减。

停止场景是同一配置上**相互替代的未来请求**，每条计划从 setup 后的相同初态开始。不能把分别可行的两个场景计划按顺序拼接后声称仍保证保留任务。任意连续生命周期、途中发行/重绑、响应丢失及批准撤回均不属于此新 profile；原 v2.16 对这些现象的 L0 测试保持，但不能自动算作本 B 编译器已处理。

## 4. G 与固定目标

`G(C)=|{u : affects(u)∩A(C)≠∅}|`。

含义是由已核实原生契约确认的独立撤销效果域数量，不是 token 数，也不是隔离环境数。对 refresh-only 域计数只表示其原生撤销作用范围独立，**不表示其能满足现有材料失效目标**；能否交付目标由覆盖语义和计划检查另外决定。

目标唯一为最小 G。G 相同时取排序路径列表的字典序最小者；这只是可复现选择，不构成实用收益。批准、隔离、请求、scope excess、停止步数和 CPU 分列。本版不最小化停止请求或停止步数：DFS 可能给出合法但更长的计划，而 BFS 参考给出更短计划；二者 G 和配置相同不要求计划文本相同。失败惩罚 C_G 如需计算应为 `budgets.units+1`；本轮未做 H-B 均值或统计检验。

## 5. 条件性正确性命题与尚未证明部分

命题 S-B（有限契约内）：若输入通过语法检查，声明的效果、路径完整性和批准语义成立，独立检查器接纳 delivery，则 setup 满足批准与资源约束，每个登记场景的计划在 H 步内达到其停止目标并在全部前缀保留所要求任务。

论证思路：setup 检查建立 x0 与配置一致；对计划长度归纳，transition 对账户/范围之外的动态约束、批准、预算及状态效果逐一重算；每步 r 递减且检查保留谓词；最终分别检查 Local 和 Native 否定，并对全部替代路径量化。候选的“成功”字段不参与判定。此为代码相应的数学论证草图，**尚无机器核验实现正确性证明**。

命题 C-B（profile 内搜索完备）：所有合法配置均可写成每任务路径的非空子集积；新增路径不会消除既有 setup 违规，G 单调不减，故所用剪枝不删除更优解；所有有用停止动作不可逆且重复无益，深度至多 H 的不重复动作搜索覆盖可行计划。穷尽完成后可宣告当前 catalog 最优/不可行；限额中断不得宣告。仍需形式化机械证明，测试只覆盖已记录实例。

映射到真实认证系统至少还需证明：原生效果无遗漏、任务支持图完整、账户/接收方绑定、可靠执行与证据、批准存储真实性、费用保守性、并发/迟到请求的处置和终态反映。若未登记一条已泄漏 bearer 路径，Local 门控可能已关闭但 Native 仍真；若撤销只禁止刷新却被误标 all_material，参考和候选可同时产生错误结论。这些反例不由有限求解器自身修复。
