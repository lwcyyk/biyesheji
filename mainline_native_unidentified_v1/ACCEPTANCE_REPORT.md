# 无标识结果的授权枚举与阶段定案

2026-11-05，Asia/Shanghai。

最终裁决为 **专用组织的额外授权使登记的受限实例可关闭**。原共享组织中的精确账户级读取问题继续未解决。两条原生轨迹各采样一次，均为 PASS_CLOSED；安全失败、ABORTED、INCONCLUSIVE、未运行和重采均为 0。完整 operational inbox 与 identifier journal 关闭，A1 的新标识和材料由获准原生枚举首次恢复。

该结果属于成熟 G0/G9 在部署、授权及来源/效果前提下的覆盖，密码学辅助线保持 FROZEN。

## 无标识输入及读取范围

恢复后运行者保留 A0/B0、rid、attempt、批准、请求摘要、窗口和发送/效果上界。A1 在权威记录中为 DISPATCHED_UNKNOWN，lookup 返回 UNKNOWN，标识日志与完整收件箱均不存在。预查询投影没有 A1 的 AT/RT/jti 或原生记录名。

HTTP 响应证据改用普通 RSA-OAEP 封装随机 AES-GCM 密钥，单向封存给评分者。运行传输对象只加载审计公钥，对称审计密钥文件不存在。私钥位于 scorer_secret，运行者配置不加载该密钥。该隔离按可信代码/API 信息流核验，同 OS 用户恶意取证并未建立独立权限域。

本轮创建一个专用组织、一个专用应用和三个账户，其中干扰账户名称含第一个目标用户名。整个组织的 token 读取明确授权给可信 R。新增应用复用已有签名证书，未创建额外证书、provider 或 policy。原 l1-study/app-l1-0 仅读取参照。

原生查询采用 owner=admin、organization=专用组织、pageSize=100、p=1、空 field/value、name 升序，认证为新应用 Basic 凭据。先核对所有返回行的组织，再按账户和应用等值选择目标。宽于单账户的数据读取是本轮新增授权与部署成本。

第二次查询的组织记录总数仍为 5，但目标集合已由 A0/B0 变为 B0/A1。重复总数或页数没有被用于推断创建前沿关闭。

来源后验核对使用独立评分路径，确认原刷新使用 A0 的 RT，枚举选出的 AT 与该尝试的实际响应相同。该私有比对发生在运行决定之后，运行者的候选选择仅依赖获准查询和自身权威记录。

## 上界、完整性和信任前提

五项批准各预算 10，允许操作最多使用 50 个放行槽，每个创建发送最多产生一个原生记录。撤销和读取不新增记录，独立测量使用 RT 内省而不执行潜在创建的刷新。故整个专用范围的生命周期记录上界为 50，覆盖实际五次初始发行及两次未知刷新，并包含过期留存。

页容量 100 足够在一个 Find 读取快照中返回全部范围记录。GetTokenCount 和 Find 并非同一事务，返回页数只保存为观察。完整性只属于该读快照，不能单独证明观察后没有创建。发现可归属的唯一单位后，结合单发送/单效果上界才使剩余创建能力归零。

额外批准、多未知创建、传输重试、多效果、未登记写入者或不完整页都保留 UNKNOWN。R 窗口暂停目标账户新批准、发行和刷新，B 的已有资源使用继续。其他原生管理主体和恶意 OS 用户的排除属于受控夹具模型前提，源到二进制可复现构建仍未证明。

## 普通收据与独立检查

收据证据源为 AUTHORIZED_SCOPE_ENUMERATION，独立检查器另保留 M3 的 IDENTIFIER_POINT_READ 分支。枚举分支核对组织授权、返回范围、记录上界、页容量、单语句范围、已知单位差集、唯一候选、来源上下文、处置和 B 检查。

原始关闭收据位于 raw/batch01/M4-01/runner/closure_receipt.json 及 M4-02 对应路径；首次 UNKNOWN 位于 M4-02/runner/empty_receipt.json。原生集合正文为评分者封存密文，公开收据保存安全的组织/账户/应用/单位引用集合。

条件核验继续依赖可信 R/适配器的事实输入，独立轨迹评分另读权威、原生观察和日志。收据不充任恶意提供方证明，也不宣告任意 RP 外部效果终结。

## 成本与清理修复

| 类别 | 最终 HTTP | 上限 |
|---|---:|---:|

| 方法 | 28 | 60 |

原批次先记录 95 次 HTTP、39.672 秒，随后应用清理修复增加三次清理 HTTP，原轨迹没有重采。三次原生枚举都计入方法，全部返回材料及组织级曝光、配置、查询正文、加密封存与验证成本分别记录在 COST_AND_RESULTS.json。

最初 delete_application 未传 organization，原生返回成功状态但回读显示应用残留。源码 object/application.go 的 deleteApplication 同时按 PK 和 organization 过滤，导致该请求实际未删除对象。原始 SCOPE_CLEANUP.json 保留 application_absent=false。

修复后客户端要求删除携带原组织，清理函数以回读决定成功。缺失/错组织的合成回归 1/1 通过。使用剩余清理预算重新登录、删除本批应用并回读确认不存在，记录为 cleanup_repair_RESULT.json。组织和三个账户已确认删除；修复后应用也已确认不存在。

三个账户的清理后材料均在 UserInfo 路径拒绝。过期 token 行和证据密文按本批观测及留存政策分别登记，物理擦除和备份擦除没有在本轮验证。已有签名证书作为只读依赖保留。原生 AS 保持运行，所有本批临时服务退出。

## M2 / M3 / M4 的适用域

| 阶段 | 可用信息及权限 | 结论 |
|---|---|---|
| M2-03 | 响应及新标识丢失，原共享组织范围 | 保留 UNKNOWN，评分私有子代不回流 |
| M3 | 请求前启用标识日志，已有精确 get-token | 登记受限模型中条件性关闭，未追补 M2 历史 |
| M4 | 新标识完全缺失，专用组织整体授权与单页范围覆盖 | 通过枚举和来源排除完成受限关闭，付出额外部署、读取权限和成本 |

因此，原共享组织的账户级权限问题未解决；专用组织的额外授权使本轮实例可关闭。两者分别登记。本轮没有得到一般密码学增量或新提供方协议，辅助线继续 FROZEN。
