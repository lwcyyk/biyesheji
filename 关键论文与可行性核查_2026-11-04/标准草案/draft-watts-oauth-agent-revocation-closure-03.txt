      Revocation Closure and Authority Epochs for Agent Delegation
             draft-watts-oauth-agent-revocation-closure-03

Abstract

   Automated agents can exercise OAuth-derived authority through
   delegated credentials, child agents, asynchronous work, and
   operations spanning multiple administrative domains.  Invalidating an
   individual token does not necessarily establish that the authority
   represented by that token can no longer cause a new consequential
   operation.

   This document defines authority epochs, delegation-lineage
   requirements, admission fencing, and revocation-closure states for
   OAuth-based agent delegation.  It distinguishes token invalidation
   from authority closure and specifies that unresolved in-scope state
   produces UNKNOWN or PARTIAL rather than CLOSED.  The profile composes
   with OAuth Token Revocation, Token Exchange, Token Introspection,
   proof-of-possession mechanisms, Transaction Tokens, and workload-
   identity systems such as WIMSE.

1.  Introduction

   OAuth is a delegation framework.  In conventional deployments,
   invalidating an access token, refresh token, or authorization grant
   can be sufficient to prevent future use of that artifact.  Agentic
   and multi-workload systems add another layer: authority can be
   exchanged into new tokens, delegated to child agents, cached at
   intermediaries, attached to transaction context, or used to admit
   asynchronous work that executes after the initiating credential is
   invalidated.

   [RFC7009] defines OAuth 2.0 Token Revocation.  It allows a client to
   request invalidation of a token and, where applicable, related tokens
   or the underlying authorization grant.  This document addresses a
   different question: after invalidation begins, when may a deployment
   claim that the revoked authority can no longer cause a new
   consequential operation within a declared scope?

   The core distinction is:

         revocation request
                 !=
         token or grant invalidation
                 !=
         delegated-authority closure

   The model is intentionally fail-closed.  Unknown evidence is not
   successful closure.  The profile is scoped to prospective authority:
   it prevents new effects attributable to a revoked authority epoch.
   It does not reverse effects that were irreversibly committed before
   closure.

2.  Terminology

   Authority Epoch  An opaque identifier for a bounded lifetime of
      authority rooted in one authorization event or explicit
      reauthorization.  Derived authority remains associated with the
      originating epoch unless a new independent authorization event
      creates a new epoch.

   Authority Root  The authorization event, grant, or policy state from
      which authority in an epoch originates.

   Derived Authority  Authority obtained from, delegated by, exchanged
      from, cached from, or otherwise causally dependent on authority in
      an existing epoch.

   Consequential Sink  A protected resource, queue, executor, storage
      operation, external API, credential use, payment, actuator, or
      other operation whose admission can create an externally relevant
      effect.

   Pending Operation  An operation associated with an authority epoch
      that was admitted before invalidation but has not yet reached its
      declared irreversible commit point.

   Closure Barrier  An independently enforceable control point that
      prevents authority in an epoch from producing a new effect across
      a declared authority-to-sink path.

   Closure Receipt  An integrity-protected, non-bearer statement
      describing an authority epoch, declared scope, closure status,
      relevant evidence, and unresolved limitations.

   Authority Graph  A deployment model whose directed paths represent
      authority-bearing transitions from an authority root to
      consequential sinks within a declared scope.

   Declared Scope  The set of authority roots, descendants, enforcement
      points, pending operations, and consequential sinks covered by a
      closure determination.  A closure claim applies only to this
      scope.

   Normal-Path Witness  Evidence that, before closure enforcement, at
      least one modeled authority-root-to-sink path existed in ordinary
      operation.  This prevents a vacuous CLOSED result from an empty or
      disconnected model.

3.  Problem Statement and OAuth Boundary

   Token revocation and delegated-authority closure are related but
   distinct.  A successful response from the revocation endpoint
   specified by [RFC7009] is evidence that the authorization server
   accepted a revocation request.  It is not, by itself, evidence that
   every resource server, exchanged token, delegated agent, queue,
   cached decision, or asynchronous executor can no longer admit a new
   action derived from the revoked authority.

   [RFC8693] permits security-token exchange.  Token exchange can
   intentionally change token format, audience, issuer, or trust domain
   while preserving delegated authority.  For the purposes of closure,
   those changes MUST NOT be treated as automatically breaking authority
   lineage.

   [RFC7662] lets a protected resource query token state.  An inactive
   token is relevant to authorization invalidation, but an inactive-
   token result does not prove that work previously admitted elsewhere
   has been fenced or discharged.

   [RFC9449] sender-constrains tokens and mitigates replay.  Proof of
   possession does not, by itself, provide closure semantics for queued
   or derived authority.

4.  Relationship to Adjacent OAuth Agent Revocation Work

   [I-D.chen-oauth-agent-revocation] defines an agent-oriented explicit
   revocation extension with batch and cascade revocation, request and
   response structures, propagation behavior, and audit information.
   This document does not define a competing revocation endpoint.  It
   defines the post-propagation completion condition for a bounded
   authority epoch and declared enforcement scope.

   A deployment can therefore use an explicit or cascade revocation
   mechanism to initiate invalidation and use this profile to determine
   whether the resulting state is CLOSED, PARTIAL, FAILED, or UNKNOWN.
   A successful cascade request or acknowledgement is relevant evidence,
   but it is not by itself a CLOSED result when derived credentials,
   queued work, cached decisions, or downstream enforcement state remain
   unresolved.

5.  Authority Epochs

   An implementation of this profile MUST associate a revocation-closure
   determination with exactly one authority epoch.  The identifier is
   opaque to this specification.  It MAY be maintained as authorization-
   server state, carried in a protected transaction context, associated
   with token-exchange lineage, or represented by another integrity-
   protected mechanism.

   When authority from epoch E is used to derive another credential,
   delegate, transaction context, or queued operation, the derived
   object remains in the closure scope of E unless an independent
   authorization decision creates a new authority epoch E2.

   A closure receipt for E MUST NOT be accepted as evidence that E2 is
   closed.  A fresh authorization event MUST therefore create a
   distinguishable epoch or equivalent lineage boundary.

   Where an epoch identifier crosses a trust boundary, its integrity and
   issuer authenticity MUST be protected by the enclosing protocol.  An
   epoch identifier is not a bearer credential and MUST NOT itself grant
   access.

6.  Delegation Lineage

   A deployment claiming closure MUST maintain a deterministic method
   for associating in-scope derived authority with its originating
   epoch.  This method can use authorization-server records, token-
   exchange lineage, transaction identifiers, workload identities,
   delegated-agent identifiers, queue ownership, or equivalent protected
   state.

   When [RFC8693] is used, the resulting token remains attributable to
   the originating authority epoch unless the token exchange is
   accompanied by an independent authorization event that creates a new
   epoch.  A change of issuer, audience, subject representation, or
   token format alone does not create a new epoch.

   Deployments MUST NOT claim CLOSED if known derived authority cannot
   be attributed to either the revoked epoch or a separately authorized
   epoch.

7.  Revocation Closure State Machine

   Implementations exposing closure status SHOULD provide semantics
   equivalent to the following states:

   REQUESTED  A revocation request has been accepted.  No closure claim



Watts                      Expires 3 May 2027                   [Page 6]

Internet-Draft          Agent Revocation Closure            October 2026


      is made.

   PROPAGATING  One or more invalidation or fencing operations are in
      progress.

   CLOSED  All required closure barriers are enforced for the declared
      scope, no in-scope pending operation attributable to the epoch can
      create a new consequential effect, and no relevant state remains
      unknown.

   PARTIAL  Some authority paths are closed but one or more known in-
      scope paths or pending operations remain unresolved.

   FAILED  A required enforcement action failed, or a deployment-defined
      closure deadline expired without satisfying the CLOSED predicate.

   UNKNOWN  Available evidence is insufficient to determine closure.

         REQUESTED
             |
             v
         PROPAGATING
           / | | \
          /  | |  \
         v   v v   v
      PARTIAL UNKNOWN FAILED CLOSED

   PARTIAL, FAILED, and UNKNOWN MUST NOT be interpreted as CLOSED.  A
   relying component that requires closure before continuing a sensitive
   transition SHOULD fail closed when presented with any of those
   states.

8.  Admission and Queue Fencing

   After closure processing begins for epoch E, a participating
   enforcement point MUST prevent E from creating new in-scope
   authority-bearing descendants that bypass the declared closure
   barriers.

   Queues and delayed executors participating in this profile MUST
   retain enough protected context to determine the effective authority
   epoch of admitted work.  New work associated with a revoked epoch
   MUST NOT be admitted after the relevant admission barrier is active.

   Cancellation is not equivalent to fencing.  If a cancellation request
   can race with dequeue, retry, timer expiry, batch execution, or sink
   commit, the implementation MUST account for the commit-time behavior
   before reporting CLOSED.

9.  Outstanding Consequential Operations

   Pending operations that can create a new effect after a closure
   boundary remain in scope even if their original token has expired or
   been revoked.  Examples include delayed jobs, retries, scheduled
   tasks, previously admitted API calls, delegated child-agent actions,
   and asynchronous writes.

   A deployment MUST define the point at which an operation becomes
   irreversibly committed for the purposes of this profile.  Closure is
   prospective and does not reverse effects that crossed that commit
   point before closure.

   An implementation claiming CLOSED MUST establish one of the following
   for every in-scope pending operation attributable to the revoked
   epoch: the operation was canceled before commit; the sink fenced the
   operation; the operation completed before the closure boundary and is
   recorded as a pre-closure effect; or the operation was independently
   reauthorized under a new epoch.

10.  Closure Evaluation Algorithm

   Let E be the authority epoch under revocation, S the declared
   enforcement scope, Q the nonempty set of consequential sinks in S,
   and K the set of closure barriers.  Let Reachable(E,q,t) mean that
   authority from E can still cause admission of a new operation at sink
   q at time t.  Let Outstanding(E,S,t) be the set of admitted but not
   irreversibly committed operations attributable to E.  Let
   UnknownRelevant(E,S,t) be the set of in-scope authority or execution
   states whose closure status cannot be established.

   A CLOSED result at time t requires all of the following:

   1.  The authority-root set for E is nonempty.

   2.  Q is nonempty.

   3.  A Normal-Path Witness establishes that at least one authority-
       root-to-sink path existed before closure enforcement, preventing
       a vacuous closure claim.

   4.  Every declared authority-root-to-sink path crosses an enforced
       member of K, or the implementation establishes an equivalent
       sink-side denial condition.

   5.  For every q in Q, Reachable(E,q,t) is false for new admissions.

   6.  Outstanding(E,S,t) is empty.



Watts                      Expires 3 May 2027                   [Page 8]

Internet-Draft          Agent Revocation Closure            October 2026


   7.  UnknownRelevant(E,S,t) is empty.

   8.  The revoked epoch cannot create a new in-scope descendant that
       bypasses K.

   Formally, a necessary closure predicate is:

     CLOSED(E,S,t) only if

       CoverageKnown(E,S,t)
         AND for every q in Q: NOT Reachable(E,q,t)
         AND Outstanding(E,S,t) is empty
         AND UnknownRelevant(E,S,t) is empty
         AND NoNewBypassDescendant(E,S,t)

   If UnknownRelevant(E,S,t) is not empty, the status MUST NOT be
   CLOSED.

   The graph formulation is a model of the closure obligation.  It is
   not proof that an implementation has discovered every real-world
   dependency.  A deployment MUST bound its closure claim to the
   coverage it can establish.

11.  Closure Receipt

   This document defines receipt semantics but does not define a new
   wire encoding.  A future profile can encode a Closure Receipt using a
   signed JWT, COSE object, SCITT statement, protocol response, or
   another integrity-protected container.

   A receipt asserting CLOSED SHOULD contain or cryptographically bind
   at least the following information:

   *  the authority epoch;

   *  the declared enforcement scope and sink classes;

   *  the closure status;

   *  the request time and closure time or monotonic sequence
      information;

   *  a digest or identifier for the barrier/cut-set evaluation;

   *  an evidence digest or reference;

   *  any unresolved paths or excluded dependencies; and

   *  the authorized issuer of the receipt.

   A Closure Receipt MUST NOT contain bearer secrets or itself function

12.  Integration with Existing OAuth Mechanisms

12.1.  OAuth Token Revocation

   [RFC7009] can initiate token or grant invalidation.  An
   implementation of this profile MUST NOT report CLOSED solely because
   a token has been revoked, expired, invalidated, or rejected.  CLOSED
   requires evaluation of the in-scope derived authority and outstanding
   consequential operations identified by this profile.

12.2.  OAuth Token Exchange

   [RFC8693] can create a token representing delegated or exchanged
   authority.  Where that authority derives from a revoked epoch, the
   exchanged token remains in the closure scope unless independent
   reauthorization created a distinct epoch.

12.3.  OAuth Token Introspection

   [RFC7662] can inform a resource server that a token is inactive.
   Inactive-token status can contribute to closure evidence but does not
   establish that previously admitted work or independently cached
   authorization decisions are closed.

12.4.  Proof of Possession

   [RFC9449] can reduce replay risk by sender-constraining tokens.
   Sender constraint does not replace authority-epoch lineage or closure
   evaluation.

12.5.  Transaction Tokens

   [I-D.ietf-oauth-transaction-tokens] propagates user, workload, and
   authorization context through a call chain.  Where a deployment maps
   a transaction to an authority epoch, transaction-scoped enforcement
   points can participate in closure.  This profile does not modify the
   Transaction Token format.

12.6.  WIMSE and Agent Workload Identity

   [I-D.ietf-wimse-arch] and [I-D.ietf-wimse-aims] provide workload and
   agent identity architecture.  Identity establishes who or what is
   acting; OAuth determines delegated authority; this profile determines
   when withdrawal of that authority has reached a bounded closure
   condition.

13.  Resource Server Processing

   A resource server or consequential sink participating in this profile
   SHOULD enforce revocation as close as practical to the point where a
   new consequential operation is admitted.

   If the server has authoritative local knowledge that the effective
   authority epoch is revoked, it MUST deny new admission under that
   epoch.  If the server relies on introspection, token state,
   transaction context, or another upstream source, it MUST apply the
   freshness and failure policy established by the deployment.

   Where policy requires verified closure before a sensitive transition,
   an unavailable or indeterminate closure state MUST NOT be promoted to
   CLOSED.  The server SHOULD deny or defer the transition according to
   local policy.

14.  Multiple Administrative Domains

   Agent delegation can cross administrative domains.  A closure claim
   that spans multiple domains requires either coordinated enforcement
   evidence or an explicit statement that a dependency is outside the
   declared closure scope.






Watts                      Expires 3 May 2027                  [Page 11]

Internet-Draft          Agent Revocation Closure            October 2026


   If domain A cannot establish the state of a known downstream
   dependency in domain B, A MUST NOT claim global CLOSED for a scope
   that includes B.  It can report PARTIAL, UNKNOWN, or a narrower
   CLOSED result whose scope excludes B.

   This preserves the distinction between bounded evidence and global
   claims while allowing each administrative domain to retain its own
   enforcement mechanisms.

15.  Failure and Unknown-State Handling

   Implementations MUST preserve uncertainty.  Missing acknowledgements,
   unavailable queues, unresolved descendants, stale topology, or lost
   lineage MUST NOT be interpreted as successful closure.

   A known enforcement failure SHOULD produce FAILED.  A known remaining
   path SHOULD produce PARTIAL while closure work can continue.
   Insufficient evidence to classify a relevant path SHOULD produce
   UNKNOWN.  These distinctions allow relying parties to select policy
   without manufacturing certainty.

   Closure computation SHOULD be idempotent and monotonic with respect
   to evidence: losing evidence MUST NOT transform a previously
   unresolved state into CLOSED.

16.  Worked Example

   A user authorizes Agent A under authority epoch E7.  Agent A uses
   Token Exchange to obtain a token for Service B.  Service B creates a
   delayed job in Queue Q.  The job can later invoke Resource Server R.

   The user requests revocation of Agent A.  The authorization server
   revokes Agent A's access token using [RFC7009].  That transition
   alone is REQUESTED or PROPAGATING, not CLOSED.  The deployment must
   also prevent the exchanged token from admitting new work and prevent
   the queued job from committing a new effect at R.

   If the exchanged token is denied and Q confirms that the E7 job was
   canceled before its commit point, and no relevant state remains
   unknown, the deployment can report CLOSED for the declared scope.  If
   Q is unreachable or outside the enforcement boundary, the deployment
   reports UNKNOWN, PARTIAL, or a narrower scoped result rather than
   global CLOSED.

17.  Conformance and Falsification Cases

   The following constructed cases are intended to make the semantics
   independently testable.  They are not deployment-performance
   measurements.

   1.  RFC 7009 revocation succeeds, but an exchanged token derived from
       the same epoch still authorizes a new in-scope request.  CLOSED
       is false.

   2.  Root and derived tokens are invalid, but a queued operation
       attributable to the epoch commits after the claimed closure
       boundary.  CLOSED is false.

   3.  A known cross-domain descendant cannot be observed or fenced.
       The result is UNKNOWN or PARTIAL, not CLOSED.

   4.  A receipt for epoch E7 is replayed while the relying party
       evaluates independently authorized epoch E8.  The receipt is
       inapplicable.

   5.  All in-scope new-admission paths are fenced and all pending
       operations are discharged with no relevant unknown state.  CLOSED
       is permitted for that declared scope.

   6.  An effect committed before closure remains visible afterward.
       That fact alone does not falsify closure because closure is
       prospective.

   7.  An independently reauthorized operation commits under a new
       epoch.  Its effect does not reopen the old epoch.

   8.  An implementation advertises no root-to-sink path and therefore
       trivially reports no surviving path.  The claim is insufficient
       and MUST NOT be promoted to CLOSED.

   An independent observer can falsify a CLOSED result by demonstrating
   an in-scope post-closure consequential admission that derives from
   the closed epoch or by identifying relevant state that was known to
   be unresolved when CLOSED was asserted.

18.  Privacy Considerations

   Authority graphs, epoch identifiers, workload identities, queue
   relationships, and closure receipts can expose organizational
   structure and behavioral linkage.  Implementations SHOULD disclose
   only the minimum information required to evaluate a closure claim.




Watts                      Expires 3 May 2027                  [Page 13]

Internet-Draft          Agent Revocation Closure            October 2026


   Opaque epoch identifiers, scoped evidence references, hashed barrier
   descriptions, and selective disclosure can reduce unnecessary
   topology exposure.  An epoch identifier SHOULD NOT be reused as a
   durable correlation identifier across unrelated authorization
   contexts.

19.  Security Considerations

   A forged CLOSED result is security-critical because it can cause a
   relying party to act under the false assumption that revoked
   authority can no longer produce consequences.  Closure evidence
   crossing a trust boundary MUST therefore be integrity protected and
   authenticated.

   Receipts are vulnerable to replay and substitution if they are not
   bound to the authority epoch, declared scope, issuer, and freshness
   context.  A relying party MUST reject a receipt that is inapplicable
   to the epoch or scope being evaluated.

   Implementations MUST consider stale-token replay, epoch substitution,
   lineage laundering through Token Exchange, queue and commit-time
   races, cached authorization decisions, delayed acknowledgements,
   graph incompleteness, and denial-of-service amplification through
   large delegation trees.

   Proof-of-possession mechanisms such as [RFC9449] can reduce token
   replay but do not eliminate stale authorization or queued-work
   hazards.  Deployments SHOULD follow the OAuth security guidance in
   [RFC9700].

   Closure evidence can itself become sensitive.  Evidence stores SHOULD
   be access controlled and SHOULD provide tamper evidence appropriate
   to the deployment threat model.
