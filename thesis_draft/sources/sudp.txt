Abstract—Agentic systems now act with user secrets for
APIs, messaging platforms, and cloud services. Today’s agent
runtimes typically implementauthorization by exposure: enabling
action means placing a reusable secret, or a reusable artifact
derived from it, inside the runtime, so a transient prompt-
injection or tool-side compromise becomes durable account
compromise. Existing defenses cover adjacent pieces such as
secret storage, scoped delegation, sender-constrained tokens, and
runtime monitoring, but none states the combined requirement:
an untrusted autonomous requester should be able to cause a
user-authorized secret-backed operation without gaining reusable
authority over it. We formalize this as theAgent Secret Use(ASU)
problem and identify seven security properties any solution must
satisfy, spanning authorization integrity and secret confidentiality.
We propose theSecret-Use Delegation Protocol(SUDP), in which
a requester proposes a canonical operation, the user authorizes
it with a fresh authenticator-backed grant, and a custodian
redeems the grant to perform the bounded use; reusable authority
never crosses the requester boundary. We specialize SUDP for
LLM-driven agents, where it applies whenever a tool call would
exercise user-enrolled authority-bearing material. Under standard
cryptographic assumptions, SUDP satisfies six of the seven
properties; the seventh, runtime-memory confidentiality, is closed
by composition with a hardware-rooted runtime. A reference
implementation, available at https://github.com/xhyumiracle/sudp,
adds sub-millisecond protocol overhead per mediated call.
I. INTRODUCTION
A coding agent holding a GitHub token can be steered by
an injected README into pushing code to a public repository:
once a reusable secret is inside the agent runtime, indirect
prompt injection becomes durable account compromise [ 1, 2].
Tool-augmented language-model agents now routinely perform
such authority-bearing actions: they call model and platform
APIs [ 3–5], send messages, and authenticate to third-party
tools [ 6, 7], backed by API keys, OAuth tokens, or signing
keys held in environment variables, databases, or secret
managers [8, 9] and handed to the agent for ad-hoc use. Across
successive agent-safety benchmarks [ 10–13], agent runtimes
have continued to fall to prompt injection and tool misuse,
including on secret-adjacent tasks, despite improving base
models; under the bearer-secret pattern, every such failure
becomes durable authority compromise.
The question for agentic systems is:how can an agent be
authorized to cause a secret-backed operation without ever
gaining reusable authority over it?Today’s model bundles

II. RELATEDWORK
a) Agent systems and external capabilities.:AutoGPT
and AutoGen made long-horizon, tool-using agents a concrete
software pattern rather than only a prompting style [ 27, 28].
Recent products push the same pattern toward browser, desktop,
and multi-step task execution: Manus, OpenAI Operator, and
Anthropic’s computer-use interface [29–31].
b) Secret management, authorization, and delegation.:
Capability-based access control [14, 15], OAuth 2.0 bearers [16,
32], DPoP [ 18], OAuth Rich Authorization Requests [ 33],
GNAP [34], MCP authorization [ 35], and Macaroons [ 17] ad-
dress scoped delegation but pass possession-bearing or reusable
artifacts through the requester. WebAuthn [ 19] and its PRF
extension [20] provide phishing-resistant user authentication
and authenticator-bound key derivation, primitives that SUDP
builds on (§V). Secret managers and KMS services [ 8, 9]
provide mature storage, access control, and rotation, but
their privileged backend assumes the authorization decision is
upstream of the requester; SUDP complements them at the
authorization layer. A recent line of agentic delegation work
extends web-identity and provenance constructs to agent princi-
pals: Authenticated Delegation [36] binds agent credentials to a
verified human delegator; SAGA [ 37] gates inter-agent contact
through a user-registered provider that distributes one-time
access-control keys; Agentic JWT [ 38] binds each agent action
to verifiable user intent and, optionally, to a workflow step;
HDP [39] targets multi-hop human-delegation provenance; and
OIDC-A [40] extends OIDC with agent identity. Each touches
a different subset of the ASU axes; the per-axis comparison is
in §IV-B.
c) Runtime defenses, monitors, and benchmarks.:A
large body of work hardens the agent or contains the con-
sequences of misbehavior: instruction-data separation and
prompt-engineering defenses [ 41–43], capability-tracking in-
terpreters [44], per-tool policy engines [ 45–47], verify-before-
commit mitigations [ 48], guardrail stacks [ 49, 50], and execu-
tion sandboxes [ 51]. These approaches reason about what the
agent does or contain where it does it; SUDP constrains what
a secret can be used for and composes with them rather than
substituting. Recent adaptive evaluations show that stronger
attacks bypass published behavioral defenses [ 52], motivating
protocol-level guarantees beyond behavioral filtering, and
an empirical audit of 17,022 deployed LLM agent skills
finds exploitable and persistent credential leakage in 520 of
them [53]. Agent-safety benchmarks across model generations
report nontrivial failure rates: attack success under prompt
injection [10, 12, 54], unsafe tool use [ 13, 55, 56], and privacy
leakage across tool and inter-agent channels [ 57, 58]. Surveys
identify ad-hoc secret handling and least-privilege maintenance
over credentials as an open gap [ 59, 60]; lifecycle analyses
place capability enforcement at the execution stage [ 61, 62].

III. AGENTSECRETUSE
Agent Secret Use(ASU) arises when an autonomous re-
quester must cause a user-authorized operation without ever
gaining reusable authority over that operation.
A. The Problem
Agent Secret Use poses a conflict between three parties.
A user U holds authority at an external environment E,
exercised through authority-bearing material s (Definition 1)
that E accepts on U’s behalf for operations in a space
OE. An autonomous requester R, acting on U’s behalf, lies
outside U’s trust boundary: R must never gain reusable
authority (Definition 2) over those operations. The unmediated
native interface cannot satisfy both requirements (Figure 2);
Definition 3 states the resulting problem.
Definition 1 (Authority-bearing material).Material s is
authority-bearing at E if possession of s, or of material derived
from s that E accepts, enables operations at E under the
authority of the party that enrolleds.
Definition 2 (Reusable authority).Reusable authorityover
operations at E is the capability to cause more than one
invocation of operations at E, whether via direct possession
of authority-bearing material (Definition 1) or via any derived
artifactEaccepts.
Definition 3 (Agent Secret Use Problem).Agent Secret Use
is the problem of enabling an untrusted autonomous requester
R, acting on U’s behalf, to cause operations in OE to be
executed at E, without ever exposing R to reusable authority
(Definition 2) over whatUexplicitly authorizes.
B. Adversary Model
We parameterize the adversaryAby capability:
•A R: controlsR.
•A net: controls the network (observes, modifies, drops, re-
plays, and reorders any message).
•A state: reads at rest the persistent state of any component a
solution introduces to hold authority-bearing material.

C. Security Properties
We formalize the Agent Secret Use problem (Definition 3)
via seven security properties, grouped along the classical
confidentiality / integrity distinction [ 63, 64]. The fourcore
properties (A V , OB, UB, CRC) together preclude the two
adversarial wins of § III-B: A V , OB, and UB rule outmisuse;
CRC rules outextraction. We say a mechanismsolves the
ASU problemif it enforces these four core properties under the
baseline adversary (AR,A net). The threerobustness extensions
(CSB, CMC, RFS) target the stronger adversaries Astate and
Amem; they are not required for the baseline solution, and a
mechanism that holds secret material only within U satisfies
them trivially. For the protocol of §V, Appendix B restates these
properties as adversarial games and proves them by reduction.
a) Authorization integrity.:
• A V: Authorization Verifiability.Any successful execution in-
duced through the mechanism is covered by an authorization
event attributable to U under the mechanism’s stated identity
and trust assumptions. An authenticator-bound assertion U
produces for a specific operation provides stronger direct
evidence than an identity provider’s assertion aboutU.
• OB: Operation Binding.An authorization is bound to
a specific operation o; the mechanism does not induce
execution of any operation semantically distinct fromo.
• UB: Use Boundedness.Execution induced through the
mechanism cannot exceed the boundsUauthorized.
b) Secret confidentiality.:
• CRC: Confidentiality under Requester Compromise.
Compromise of the requester does not expose authority-
bearing material (Definition 1).
• CSB: Confidentiality under Storage Breach.Compromise
of the persistent state of a secret-holding component does
not expose the secret. Encryption whose unlock key resides
in the same compromised state does not satisfy CSB.
• CMC: Confidentiality under Runtime-Memory Com-
promise.Compromise of the runtime memory of a secret-
processing component does not expose the secret. Hardware-
rooted TEEs may satisfy CMC within their threat model [ 65];
software-only schemes relying on OS process isolation
generally do not.
• RFS: Rotation Forward Secrecy.Compromise of secret
material in one rotation epoch does not expose material in any
other epoch (forward and post-compromise secrecy [ 66, 67]).
Rotating only the wrapping key while reusing the same
authority-bearing secret is epoch-key isolation, not authority-
level forward secrecy.
Deployment concerns (client or authenticator compromise, logs
and telemetry, IPC, crash dumps, supply-chain code injection,
side channels, out-of-band copying) lie outside the seven
security axes.
IV. POSITIONING
A. Relation to Prior Paradigms
Agent Secret Use is a confused-deputy setting [ 68] with
an added confidentiality constraint: the deputy must not
gain reusable authority it could be induced to misuse. Prior
paradigms place the authority-holding boundary at different
points; ASU prescribes no location, only the negative condition
that R stay outside any boundary containing authority-bearing
material accepted atE.
a) Prior paradigms, by boundary placement.:
• Token-based authorization(OAuth 2.0 bearer [ 16, 32] and
sender-constrained [18] tokens) places the boundary at the
token itself: possession or proof-of-possession material is
passed to the requester, which remains trusted with reusable
authority.
•Authorization-server delegation(OAuth Rich Authorization
Requests [33], GNAP [ 34], MCP authorization [ 35]) places
the boundary at an authorization server, but the minted token
still lands at the requester.
• Centralized secret storage(Vault, KMS services [ 8, 9])
places the boundary at the storage system and addresses
access control and rotation, but the authorization decision
sits upstream of the requester rather than being bound to
specific operations.
• Hardware-rooted boundaries(HSMs, secure enclaves, TEE-
backed runtimes [ 65, 69]) place the boundary inside tamper-
resistant hardware that confines signing keys or code; this
addresses host-memory confidentiality but does not by itself
authorize specific agentic operations.
• Transaction authentication ceremonies(closest analogue),
exemplified by PSD2 dynamic linking, banking 2FA, Se-
cure Payment Confirmation [ 70], and WebAuthn UV [ 19]
ceremonies, place the boundary at a trusted user-facing
client cooperating with a relying party. This is the prior
paradigm closest to ASU’s operation-bound user approval,
but it assumes the user interacts directly with a trusted client
rather than through an autonomous agentic requester.
A separate body of concurrent work targets the same agentic
setting as SUDP:agentic delegation protocols(Authenticated
Delegation [36], SAGA [37], OIDC-A [40], HDP [39], Agentic
JWT [38]). These are not prior paradigms but contemporary
peers; we compare them per-axis in §IV-B.

V. SECRET-USEDELEGATIONPROTOCOL
SUDP is a protocol-level answer to capability-constrained
secret use. The unit of delegation is theuseof a secret for
one specific authorized operation o, not the secret itself: the
requester is delegated the right tocausean authorized use,
the custodian is delegated the right toperformthe use within
U’s signed bounds, and reusable authority never crosses the
requester boundary. This section fixes SUDP’s roles and trust
model (§V-A), then defines SUDP as an abstract protocol over
generic cryptographic interfaces (§ V-B–V-G) together with the
rotation discipline that delivers per-credential forward secrecy
(§V-H).
A. Roles and Trust Model
SUDP solves the Agent Secret Use problem (§ III-A) by
introducing one new protocol role: acustodian T that holds
authority-bearing material as sealed state Σ, issues freshness,
verifies U-rooted operation-bound grants, and performs the
authorized secret-backed action within the bounds U signed.
The custodian is a protocol role, not necessarily a deployment
component: realizations include a local proxy, a hosted proxy,
an OS-level credential mediator, an HSM- or TEE-backed
service, or, in cooperative settings, the environment itself. The
agentic specialization (how R is drawn around the LLM-context
exposure surface and how native calls are bound to canonical
operations) is deferred to §VI.
a)SUDPentities.:Three parties run the protocol:
•U : theauthorizer, governing whether a secret-backed opera-
tion may proceed.
•R : therequester, initiating an operation request, typically
an agent.
•T : thecustodian, holding the sealed state Σ, validating
authorization, redeeming operation-bound grants, and using
protected authority material to perform the secret-backed
operation; distinct fromU.
We sayauthorizerrather thanuserbecause the role is
functional, not human: U is typically a person signing on
a personal device, but may equally be an agent holding further-
rooted authority in a chained delegation. The environment
E is as in Agent Secret Use: the execution target, outside
the protocol, assumed only to accept its existing credential
interface.
b)SUDP-specific trust assumptions.:Beyond authorizer-
controlled authorization (§III-A), SUDP adds two assumptions.
Restricted trust in the custodian: T is trusted only to validate
authorization, redeem grants, and transiently use secret material
during valid consumption; R is never trusted with secret
access.Sealed persistent state: Σ alone does not suffice for

B. Key Hierarchy
SUDP uses the standard envelope-encryption pattern (Fig-
ure 3). The protected state M (the contents of Σ the protocol
secures) is sealed once under a state-encryption keyK;Kis
in turn wrapped separately under each authorizer credential’s
wrapping key Wc. This separation is deliberate: rotating K does
not require interacting with every credential (each Wc simply
rewraps the new K), and registering a new credential does
not require re-encrypting M (only a new [K] c is appended).
Formally,
C←Enc K(M), M←Dec K(C),
and for each enrolled credentialc,
[K] c ←Wrap Wc(K), K←Unwrap Wc([K] c).
The persistent cryptographic state consists of C and {[K] c};
{Wc} defines the recoverability structure of K. By construction,
the requester never receives K, any Wc, or any value from
which either can be efficiently derived.
C. Authorized Operation
Rather than authorizing decryption in the abstract, SUDP
authorizes a specific secret-backed operation together with its
redemption binding and validity conditions. A well-formed
authorization object encodes three aspects: (i)authorization
semantics: what is approved; (ii)redemption binding: who
may redeem and, if extracting, who receives; and (iii)validity
constraints: how long the authorization is valid and how it
resists replay and substitution. Each component corresponds to
a distinct security obligation: the semantics must be reviewable
at U, the binding must resist substitution, and the validity must
resist replay. Freshness is supplied by the Phase II freshness
token r (§V-F) rather than carried inside o; o commits to r
implicitly through the Phase II binding.
Definition 4 (Authorized operation).Anauthorized operation
is a canonical protocol tuple
o:= (act,bind,valid),
where act:= (type,target,scope) , bind:=
(redeemer,recipient) , and valid:= (expiry,multiplicity) .
Here type specifies the semantic class of the secret-backed
action (e.g., use, export, write, rotate, enroll, revoke); target
identifies the protected object; scope carries canonicalized
operation-specific constraints; redeemer identifies the party
entitled to redeem; recipient identifies the intended recipient
of any extracting delivery; expiry bounds the validity window;
and multiplicity∈Z + ∪ {∞} sets the grant’s execution
budget: T admits at most multiplicity Phase III executions
under the grant before expiry; 1 consumes the grant at first
redemption (high-authority transaction-style actions), and ∞
yields astanding grant( U-declared low-risk repeat patterns
such as inbox reads). Freshness for the Phase II verification
is enforced separately, via the single-use token r issued at
Phase II.1 and consumed at Phase II.3.
We reserve specific terms: agrant G is the protocol artifact
representing U’s authorization ofo; it commits to o and conveys
for redemption both the authorization signature and the acting
credential’s wrapping key (the full structure is in § V-F). The
wrapping key is secret: G is therefore not a public bearer
token, and the U→T leg carrying it requires end-to-end
confidentiality. Aredeemed grant ρ is G’s custodian-internal
post-validation form. SUDP binds G and ρ to the same β
commitment in Phase II so that the artifact T redeems matches
the oneUauthorized.
SUDP’s cryptographic binding attaches to the canonical
bytes of o. Two deployment obligations anchor those bytes at
the endpoints of the authorization; A V and OB hold when both
are met.
a) Render at U.: Render(o) is deterministic, complete,
and confined to U’s trusted client, so U approves exactly what
H(o)commits.
b) Execution at E.:The action performed at E is a
deterministic function of o, the material T unwraps, and any
auxiliary content that o commits by hash. No authority-relevant
input enters betweenU’s authorization and the action.

The Wrap interface binds wrapping context through the
derivation of W rather than through a separate parameter:

construction, and the interface accommodates both associated-

domain-separation labels.

an externally supplied challenge µ, and evaluates PRFc on
one or more caller-supplied salts ηi, returning the outputs
yi ←PRF c(ηi). The number of PRF evaluations admissible per
invocation is a parameter of Aut c’s interface; the rotation-class
operations of § V-G require at least two. The signing key and
the PRF key never leave the module. Enrollment releases public
material (cid c,pk c). Every info or ad argument carrying a
domain-separation label DS⋆ uses a stable, context-disjoint
string; labels are pairwise disjoint and no label is ever reused.
The protocol equations explicitly name DSbind and DSwrap;
concrete profiles may use additional disjoint labels for sealing,
delivery, and transport without affecting the abstract contract.
b) Canonical serialization.: H(o) presumes a determin-
istic encoding of the structured value o that is also identical
at U and T . A concrete profile must fix this serialization (for
instance, a canonical CBOR or RFC 8785 JCS encoding of
the (act,bind,valid) fields) and enforce it at both endpoints.
Ambiguity in the encoding can defeat operation binding without
violating collision resistance of H: two semantically distinct
descriptors may serialize to the same bytes (so that an adversary
substitutes o′ ̸=o with the same H-input), or the same
descriptor may serialize differently at U and T (so that U
authorizes an operation whose canonical form at T differs
from the one Render presented at authorization time). Both
failures collapse OB regardless of H’s strength. The specific
serialization is a profile parameter, not a protocol choice.
Pairwise communication runs over a pre-established au-
thenticated channel; transport is assumed, not re-specified.
Confidentiality is required on the U→T leg (which carries
W ⋆) and on the final response leg (which may carry the delivery
artifact π or a use-result ρout). This requirement is on the
logical U→T leg end-to-end and is not in general satisfied by
hop-by-hop transport security; a deployment with a plaintext-
inspecting intermediary between U and T must supply end-to-
end confidentiality at the application layer (§ VII-B). Integrity
is required on every leg. The T→U conveyance (Phase II.1)
carries only public material (o, r,{(cid c, ηc)}) and does not
require confidentiality; its only protection need is against denial-
of-service tampering, which is detected at redemption through
the signature onβ.

H. Rotation and Forward Secrecy
Rotation is aprotocol invariantof SUDP: every SUDP-
conformant deployment advances both the wrapping epoch

the underlying authority-bearing secret at E together with
revocation of the retired secret. The first part is enforced
by Phase III.3 below; the second part is mandated by the
protocol’s type=rotate operation class (Phase III.3, § V-G)
and its compliance requirement that authority-bearing secrets
never persist beyond their rotation epoch. This section specifies
the wrapping-side mechanism; the authority-side cadence is a
deployment policy parameter.

that retired authority-bearing secrets at E be revoked on
the deployment’s rotation cadence; without that revocation,
compromise of the current epoch confers the same authority as
compromise of any prior epoch and the wrapping-side forward
secrecy is meaningless againstE.

VI. SECRET-USEINTERFACES FORAGENTICSYSTEMS
Applying SUDP to an agent system requires identifying the
trust boundaries and mapping the protocol roles accordingly.
This section describes how SUDP is applied in an LLM-based
agent system; Figure 6 illustrates the interface.
A. The Agentic Requester Boundary
In an agentic system, the agent’s actions are driven by the
output of the LLM, which is in turn shaped by whatever enters
its context. Retrieved documents, tool outputs, and memory
reads can carry injected instructions, and the model may
hallucinate even on benign input; model output is thus untrusted,
as is any component acting on it. Therefore, the requester
boundary must enclose every component whose behavior model
output can steer, including the LLM runtime, the tool scheduler
and tool clients (MCP-style runtimes among them), and agent-
visible memory. The custodian T and the authenticator Aut c
must accordingly remain outside this boundary; hosting either
within model-influenced code would reinstate authorization by
exposure.
B. Where SUDP Applies in an Agentic System
A single criterion determines whether a call enters the SUDP
path: its execution must exercise authority-bearing material
(Definition 1) that U has enrolled at an external environment
E. Calls that exercise no enrolled authority, such as a public
web search or a local file read, pass through unmodified. The
criterion applies at both layers of an agent’s secret use.
a) Tool-call layer.:Tool calls reach external environments
such as code hosts and payment rails, and meet the criterion
whenever execution would present a credential enrolled by U,
for instance a mailbox token or a cloud key. These calls are
the motivating workload of the agentic specialization; § VI-C
describes their mediation.
b) LLM-API layer.:The agent authenticates to its model
provider with an API key. Once U enrolls that key, it routes
through SUDP like any other credential; since these calls are
frequent and uniform, the authorizer will typically cover them
with a standing grant of broad scope, which preserves the
confidentiality properties (CRC, CSB) and avoids a ceremony
per call.
c) Scope.:SUDP addresses authorization integrity and
secret confidentiality. Behavioral safety, the question of which
operations an agent chooses to propose, is a separate concern;
runtime monitors, policy DSLs, taint tracking, and sandboxes
constrain proposals and compose with SUDP (§IV). The
protocol likewise fixes the authorization mechanism while
leaving approval policy to the deployment. The authorizer
chooses the scope, validity window, and execution budget
of each grant, from single-use to standing (§ V-C), and A V ,
OB, and UB hold at every granularity. Per-request approval is
therefore the narrowest policy setting rather than a protocol
obligation.
C. From Native Calls to Canonical Operations
R needs no protocol integration. It issues the native call it
would issue without the protocol, with an opaquecredential
referencein place of the secret: the reference names an enrolled
credential but confers no authority, and can therefore reside
inside R. At the mediation boundary the call is canonicalized
into o (target credential, method, authority-relevant fields, body
digest) and rendered to U (§V-C); after the grant, T executes
the accepted call with the secret substituted for the reference.
Mediation is thus transparent to the agent: any tool capable of
issuing its native call participates unmodified. The completeness
condition (P1 in §VIII) fixes the canonicalization obligation:
every field that can affect the authority exercised at E must
be bound ino.
VII. STANDARDCONSTRUCTION
This section gives the standards-based cryptographic instan-
tiation of the protocol: each abstract interface of §V is fixed
to a standardized component. The construction introduces no
new cryptographic assumption.
A. Primitives
a) Authenticator Aut c.:The abstract protocol requires a
tamper-resistant module Aut c that (i) signs a challenge under
user verification and (ii) emits an authenticator-bound pseudo-
random value scoped per credential. We instantiate Aut c with
WebAuthn credentials using the PRF extension [19, 20].
The abstract σ←Sig sk c(β) interface is realized by a
WebAuthnassertionproduced with challenge =β , using
ES256/P-256 as the profile-selected COSE signing algorithm.
The corresponding Vrfy check covers the assertion signature to-
gether with the assertion’s rpId hash, origin, user-verification
flag, and credential-ID binding; a signature-verification success
without these structural checks does not satisfy the Sig interface
in this profile.

[PDF_PAGE 11]
The authenticator-bound pseudo-random value is real-

hmac-secret where available, with a per-credential salt;
credentials or assertions whose response does not contain
the PRF output are rejected by the profile. Two compliance
implications follow: (a) binding PRF output to a passkey means
deletion of the passkey implies loss of access to any data
encrypted under the derived key; (b) per-credential PRF salts
support domain separation across credentials.
b) Key derivation.:The abstract protocol requires a
KDF that supports extract-then-expand semantics and domain
separation. We instantiate KDF with HKDF-SHA-256 [ 21],
following NIST SP 800-56C key-derivation guidance [ 77].

D. Residual Limitations
Five residual limitations (L1–L5) are explicit in the design.
(L1) Runtime compromise during consumption.A fully com-
promised T runtime during legitimate consumption exfiltrates
plaintext by construction: III.0 materializes K and M inside
T ’s memory, and no protocol-level mechanism prevents code
executing inside T from reading them. Composition with
confidential-computing runtimes is the natural remediation;
zeroizing K, W ⋆, and derived plaintext immediately after use
narrows the window.
(L2) Authenticator compromise.A fully compromised au-
thenticator Aut c⋆ reduces Phase II.2 to adversary-controlled
authorization; authenticator security (A3) is an assumption, not
a protocol-level property.
(L3) Dormant-credential forward-secrecy gap.Lemma 1’s
forward secrecy is per-credential and activates only after a
credential rotates. A credential that is registered but never
participates in a state-update retains its initial salt indefinitely;
historical PRF capture remains useful against its wrapping entry
until the credential is exercised. This is intrinsic to any-of- N
authorization without a global ceremony; deployments should
drive scheduled rewraps for dormant credentials (§V-H).
(L4) Peer-map cross-credential exposure.Under the in-state
peer-map construction, Phase III.0 by any credential transiently
exposes the current {Wc}c∈Creds to T ; a captured Wc′ con-
tinues to unwrap subsequent rewraps until c′ itself rotates.
Deployments requiring stronger cross-credential isolation may
substitute the all-present alternative of §V-H.
(L5) Authorization is bounded by U’s judgment.SUDP
enforces the operations U signs; a dangerous but correctly
rendered descriptor approved by U is executed. The semantic
content of a conformant Release(o) is similarly a deployment-
policy concern outside protocol scope.
IX. CONCLUSION
Agents that act autonomously on a user’s behalf must be
able to use the user’s secrets without ever gaining reusable
authority over them. We formalize this as theAgent Secret Use
problem and decompose it into seven security properties (A V ,
OB, UB for authorization integrity; CRC, CSB, CMC, RFS
for secret confidentiality).
SUDP solves the problem by fusing authorization and access
in a single authenticator ceremony: the invocation that signs
the operation-bound grant is the same one that releases the key
material unwrapping the secret, so no execution path reaches the
secret without a reviewed operation. Six of the seven properties
hold natively under standard cryptographic assumptions; the
seventh, CMC, is closed by composition with a hardware-
rooted runtime. Instantiated with commodity passkeys and
standard primitives, the reference implementation adds sub-
millisecond overhead per mediated call. In an LLM-based
agent, the protocol mediates a call exactly when its execution
would exercise user-enrolled authority-bearing material; the
mediation is transparent to the agent.
Four directions remain open: formal verification under
active adversaries; empirical evaluation of approval cost under
realistic agent workloads; reconciling agent autonomy with
grant granularity, by data-driven grant bounds or composition
with policy systems; and authenticator primitives for non-
human principals, allowing chains whose authorizer is itself
an agent under further-rooted authority.

APPENDIXA
DESIGNRATIONALE
Several SUDP design decisions are consequential but other-
wise scattered across the construction. This section consolidates
the architectural-level choices to make their rationale visible
together; smaller decisions (domain-separation strings, concrete
primitive selections) are discussed inline at the point of
construction.
a) Per-grant U-signed authorization committed to H(o).:
The redeemed grant ρ is cryptographically bound to a specific
operation via H(o) at the authenticator, not to a stored consent
reused across token lifetimes. This lifts anti-replay and anti-
substitution from engineering discipline (TTLs, revocation lists,
nonce tracking in each tool) to protocol-level guarantees: any
captured artifact, within any time window, is redeemable only
against the operation it was signed for. SUDP carries the
execution budget in o.valid.multiplicity∈Z + ∪ {∞}, which
U signs as part of the grant.Single-usegrants ( multiplicity=1)
match transaction-confirmation ceremonies (PSD2 dynamic
linking, banking 2FA): consumed on first use, suited to high-
authority actions whose misuse already warrants per-action hu-
man oversight.TTL-bounded standinggrants ( multiplicity=∞,
bounded by expiry) match a multi-entry visa with a fixed
validity window: U explicitly opts into repeated use within a
U-declared rule, suited to low-risk repeat patterns (e.g., inbox
reads) where per-action confirmation is operationally untenable.
In both modes, the bounds are committed by U’s per-grant
signature, not delegated to an authorization server’s policy.
b) Authenticator-bound PRF for wrapping material.:
Wrapping keys are derived from authenticator-bound PRF
outputs ( yc =PRF c(ηc) inside Aut c) rather than from pass-
words, server-held master keys, or envelope-encryption KMS
services. The unlock material therefore lives exclusively in U’s
authenticator hardware: neither the server’s persistent state nor
its runtime memory can reconstruct a wrapping key without a
live U-verified invocation. This is what distinguishes SUDP’s
satisfaction of CSB from schemes whose “encrypted at rest”
claim collapses when an attacker captures the server together
with its unlock material (§IV). The cost is a WebAuthn PRF-
capable authenticator, or an equivalent authenticator-bound PRF,
as a deployment prerequisite. Ordinary passkey availability is
broad, but PRF support remains a profile requirement that
deployments must check.
c) Rewrap policy at rotation.:A SUDP profile inherits
the recoverability semantics of its authenticator family: if
all enrolled credentials are lost, M becomes unrecoverable
through SUDP. Deployments that need recovery must provision
it as an additional enrolled credential (a recovery passkey,
a second hardware authenticator, or an enterprise-controlled
escrow credential whose use is itself an SUDP-authorized
lifecycle operation), and never as a backend master-key bypass,
which would surrender CSB. Each enrolled credential therefore
holds its own wrapping key Wc, and every Phase III.3 state-
update by one credential must rewrap the new K ′ under all
peers (§ V-H). Three rewrap policies meet this requirement,
summarized in Table IV.In-state peer map(default) keeps
each rewrap single-invocation, at the cost of a transient {Wc}
exposure to T during III.0, a per-peer forward-secrecy gap until
that peer itself rotates, and the key-cycle assumption (A10) of
§VIII-A.All-present rotationremoves the exposure but forces
every credential online at each rewrap, which is ill-suited
to continuous agent workflows.Append-only chainsupports
offline catch-up at unbounded chain storage but is not forward-
secret: a captured Kj walks the chain forward. The default
favors single-invocation rewrap for agent workflows that rotate
on every write; deployments needing stronger cross-credential
isolation may substitute all-present, or adopt append-only as
an offline-catchup auxiliary with the FS caveat above.

lary {use,export,lifecycle} covers the canonical consumption

they meet these conditions and do not require modification of
Phases I or II. Extensions that weaken non-disclosure relative
to the canonical modes are admissible at the profile level only
as deliberate trade-offs and must be surfaced as such, both
at authorization time to U and in the profile’s stated security
claims.
g) Submission topologies.:The sealed grant may reach
T directly, over TLS 1.3 or the envelope above, or through
a relay that forwards the ciphertext. The natural relay in an
agentic deployment is R itself, which lets the agent retry, batch,
or schedule submission while observing nothing beyond the
HPKE ciphertext sealed to pkT . Both topologies carry the same
guarantees, since σ⋆ binds the operation independently of the
carrier and r is single-use. Direct submission keeps the session
under U’s control but requires T to be reachable at signing
time; relayed submission decouples signing from delivery at
the cost of routing throughR’s trust boundary.

F . Coverage and Scope
Three boundaries of the model remain informal, each named
where it is assumed. The equivalence ≡E and the injectivity
of canonical serialization are taken as given (A4, P1); the
environment E and the semantics of Release are abstract
parameters (P3), so what a conformant result form discloses is a
deployment question (L5); and the model covers one custodian
and one protected state, with multi-state deployments running
independent instances. Mechanized analysis of the games in a
tool such as Tamarin or ProVerif is left to future work (§VIII).
