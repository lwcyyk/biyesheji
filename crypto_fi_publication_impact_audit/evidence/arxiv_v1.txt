Abstract. In this paper we construct a new efﬁcient updatable encryption (UE) scheme based on
FrodoPKE learning with errors key encapsulation [1]. We analyse the security of the proposed
scheme in the backward-leak uni-directional setting within the rand-ind-eu-cpa model. Since the
underlying computationally hard problem here is LWE, the scheme is secure against both classical
and quantum attacks.
Keywords:
Updatable Encryption; Unidirectional Key Update; Lattices; LWE problem.
1.
Introduction
Updatable encryption (UE) allows a third party to periodically rotate encryption keys from one epoch
to another without the need to download, decrypt, re-encrypt and upload already encrypted data by
a client. Updating those outsourced ciphertexts is carried out via the use of so-called update tokens
which in turn are generated during key rotation and can be sent (publicly) to the third party.
In this paper we construct a new efﬁcient UE scheme and consider its security in rand-ind-eu-cpa
model. Since the underlying computationally hard problem here is LWE, the scheme is secure against
both classical and quantum attacks. In addition, we analyse the existing security requirement and
provide the new one that turns out to be strictly stronger than its more general counterpart.

The security notion(s) for UE is based on leakage sets given by [3], [2]. These sets are used to
track epochs in which the adversary corrupted a key, a token, or a version of challenge-ciphertext:
• K: set of epochs in which the adversary corrupted the epoch key through O.Corr;
• T : set of epochs in which the adversary corrupted the update token through O.Corr;
• C: set of epochs in which the adversary obtained a challenge-equal ciphertext through O.Chall
or O.UpdeC.
In addition, it is also the need to track ciphertexts and their updates that can be known to the
adversary:
• L: Set of non-challenge ciphertexts (qid, ct, e; m), where query identiﬁer qid is a counter incre-
mented by each invocation of O.Enc, ct is the given ciphertext, e is the epoch when the query is
asked, and m is the underlying plaintexts. The adversary learned these ciphertexts from O.Enc
or O.Upd.
• eL: Set of challenge-equal ciphertexts (ect, e), where ect is the given challenge-equal ciphertext,
and e is the epoch when the query is asked. The adversary learned these ciphertexts from
O.Chall or O.UpdeC
In [2] the sets L and eL, along with their extensions, are used only in the deterministic versions of
UE, and concerning the randomized UE there are deﬁned two plaintexts-based sets Q∗and eQ∗. This
distinction lets the author of [2] to obtain a one-to-one correspondence between ciphertexts and the
associated messages, independently of the case. However, although in this paper we construct and
consider a randomized UE scheme we show that such strict assumptions are not necessary and it is
sufﬁcient to only take advantage of the former group of these sets.
In addition, since the adversary is able to learn or infer information via its known tokens, there are

comprehensive introduction to this theory can be found in [8].
Any discrete additive subgroup L of Rm is called an m-dimensional lattice, i.e. L is a lattice iff
the following conditions hold:
1. 0 ∈L, and if v, w ∈L then −v, v + w ∈L;
2. there is ε > 0 such that for every v ∈L we have L ∩{w | ∥v −w∥< ε} = {v}.

Theorem 4.4. The advantage of any PPT adversary A in converting a ciphertext under a public key
pke+1 into a ciphertext under pke by using (ske, pke), pke+1 and ∆e+1 is negligible.
Proof:
Suppose, for contradiction, that A can convert a ciphertext under pke+1 into one under pke. Since
FrodoPKE is ind-cpa-secure, we construct a PPT adversary B that is able to break the security under
pke+1.
Algorithm B is given parameters and pke+1. B generates (ske, pke) ←UE.KG(parameters)
and ∆e+1 ←UE.TG(ske, pke+1) (see Remark 4.2), computes m0, m1 ∈M, of the same length,
and sends them to its challenger. The challenger computes ct∗←FrodoPKE.Enc(pk, mb), where
b $←{0, 1}, and sends ct∗to B. Next B run A on input ((ske, pke), ∆e+1, ct∗). A outputs a ciphertext
ct′ under pke. Eventually, B computes m′ ←FrodoPKE.Dec(ct′, ske), and if m′ = mb′ it outputs b′.
Obviously, b′ = b with overwhelming probability. This completes the proof.

5.
Implementations
This section provides a detailed analysis of the execution times for different parts of the updatable
encryption scheme based on FrodoPKE variants, including AES and SHAKE versions for various
security levels (i.e. NIST level 1, level 3, and level 5). The results include average times and standard
deviations for key generation, encryption, decryption, token generation, and update operations.
We made the implementation of an updatable encryption scheme based on FrodoPKE in Python pro-
gramming language utilizing NumPy library. As the core of our implementation, we used the ref-
erence one of FrodoPKE. It should be noticed that although Python is not be considered as a high-
performance language, the primary goal of this implementation is to compare the execution time of
the individual components of an updatable encryption scheme based on FrodoPKE. Despite Python’s
slower execution time, it still remains a popular choice for this tasks since its simplicity and the ac-
cess to a number of libraries. A library that can be indicated here is NumPy, which provides a lot of
powerful tools for numerical computations.
We conducted 100 series of tests in terms of the execution times, so as to analyze the relationships
between algorithm parts depending on algorithm variants and random messages. Out of the examined
factors, decryption times are consistently low and have minimal standard deviations. Due to multi-
plications of many large matrices, the most computationally complex part of the algorithm is token
generation and its computation time increases signiﬁcantly with the type of FrodoPKE. These results
highlight the trade-offs between security levels and performance, with higher security levels leading
to increased computation times, especially in token generation and overall execution time.
